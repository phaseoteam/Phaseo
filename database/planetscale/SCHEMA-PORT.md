# Schema port: Supabase to PlanetScale Postgres 17

This file covers how the Supabase schema becomes the PlanetScale migrations: what is removed or replaced, how to regenerate it, and what still needs a decision. The identity model and roles are defined in `README.md`.

## Files

| File | What | How it is made |
|---|---|---|
| `migrations/0000_platform.sql` | Schemas `extensions`, `auth`, `private`, `catalogue_private`; extensions; NOLOGIN roles `anon`, `authenticated`, `service_role`; `auth.uid()`, `auth.role()`, `auth.jwt()` | Hand-written, idempotent |
| `migrations/0001_auth.sql` | Better Auth tables, including `auth.users` | Owned by the auth worker, not this port |
| `migrations/0002_baseline.sql` | Every table, view, function, index, foreign key, trigger, policy and grant in `public`, `private` and `catalogue_private`, plus the signup trigger on `auth.users` | Generated by `scripts/build-baseline.mjs` |
| `migrations/0003_cron.sql` | The 8 active pg_cron jobs | Hand-written, idempotent |
| `scripts/build-baseline.mjs` | Generator for 0002 | |
| `scripts/verify-baseline.mjs` | Applies 0000 to 0002 to a throwaway local PostgreSQL 17 and checks the result | |

Apply in order on the direct connection (port 5432), each file with `psql --single-transaction -v ON_ERROR_STOP=1 -f <file>`. The files use no psql meta-commands, so any client that stops on the first error works.

## Regenerate and verify

The declarative schema in `supabase/schemas` is the source of truth. The migration history in `supabase/migrations` is not read. When main moves:

```sh
node database/planetscale/scripts/build-baseline.mjs           # rewrite 0002_baseline.sql
node database/planetscale/scripts/build-baseline.mjs --check   # exit 1 if 0002 is stale
node database/planetscale/scripts/build-baseline.mjs --report  # also list pg_strict hazards
node database/planetscale/scripts/verify-baseline.mjs          # apply and check locally
```

The generator stops on any statement shape it does not recognise, for example a new kind of `COMMENT ON` target or a signup-function body that no longer matches the pg_net transform. Extend the generator instead of editing 0002 by hand.

The verifier needs a local PostgreSQL 17. By default it runs one from `@embedded-postgres` on port 55433, installed outside the repo so the workspace is untouched:

```sh
mkdir E:/tmp/ps-schema-pg && cd E:/tmp/ps-schema-pg && npm init -y
npm install @embedded-postgres/windows-x64@17.6.0-beta.15 pg@8.13.1   # 17.6 = prod's version
```

Set `PS_SCHEMA_PG_DIR` to use another folder, or `PS_VERIFY_DATABASE_URL` to use an existing superuser connection, such as a Docker `postgres:17` container. The cluster is created once with ICU `en-US` collation, matching Supabase. Each run creates a fresh database and drops it at the end. Pass `--keep` to keep it.

### What the verifier checks

1. 0002 matches a fresh build, so it is not stale against `supabase/schemas`.
2. 0000 applies, and applies again (idempotency). Then 0001 applies, or, while 0001 does not exist yet, a clearly marked `auth.users` STUB with the README contract columns plus `deleted_at` and `is_anonymous`. Then 0002 applies in one transaction, stopping on the first error.
3. Names per schema match a count derived from `supabase/schemas` for tables, views, functions (counting overloads), policies, indexes, triggers and RLS-enabled tables. Indexes backing constraints and child indexes and triggers cloned onto partitions are left out of the comparison.
4. Foreign keys: the total matches the source, the 79 references to `auth.users` are all there, and every key is validated and resolves.
5. Every function in `public`, `private`, `catalogue_private` and `auth` is re-created with `check_function_bodies = on` inside a rolled-back transaction. This fully checks SQL functions. For plpgsql it checks syntax only.
6. `auth.users` has every column the schema reads through `auth.users <alias>.<column>`.
7. `auth.uid()`, `auth.role()` and `auth.jwt()` read `request.jwt.claims`, and the legacy `request.jwt.claim.sub` takes precedence, as on Supabase.
8. A rolled-back runtime smoke test: inserting into `auth.users` fires the signup trigger and creates `public.users`, and `SET LOCAL ROLE authenticated` and `anon` can query RLS-protected tables.
9. No function still calls pg_net, index_advisor or pg_cron.
10. 0003: if pg_cron is available, it is applied. The embedded build does not ship pg_cron, so locally 0003 is **not applied**. Instead, each job's command runs once in a rolled-back transaction, which proves that the functions the jobs call exist and run.

The verifier does not compare grants, column privileges or comments with the source. They are applied, so syntax errors and unknown roles would fail, but they are not diffed. It also runs as a superuser, so privilege limits on PlanetScale are not exercised; see "Open decisions".

Last run (2026-11-03, PostgreSQL 17.6 embedded, auth.users STUB): all checks passed. That covers 279 tables, 34 views, 597 functions, 370 policies, 617 indexes, 195 triggers, 278 RLS tables and 440 foreign keys (79 to `auth.users`), with 600 function bodies compiled. Notes from that run: hypopg is not in the embedded build, so 0000 skipped it with a warning, and pg_cron is not either, so 0003 was not applied.

## How 0002 is built

The declarative files are ordered file by file, not statement by statement. A table file holds its own triggers, policies and foreign keys, and those point at functions and tables that load later. The generator therefore reads the files in `.pgdelta-export.json` load order and regroups the statements into pg_dump-style phases. Within a phase, the original order is kept.

1. Schemas, schema privileges, and the cleared default privileges from `public/adp_wipes.sql`
2. Types
3. Functions whose signatures use no table or view row types, with `check_function_bodies = off` as in pg_dump
4. Tables and partitions, columns, defaults, checks, RLS switches, and table comments and grants
5. Views, sorted by their references to each other
6. The 26 functions whose signatures use table row types
7. Indexes
8. Foreign keys
9. Triggers
10. Policies
11. The event trigger and the remaining default privileges

Each group is introduced with a `-- source: supabase/schemas/<file>` comment, so any statement can be traced back to its source file.

| `auth/tables/users.sql` | Not copied as a table: 0001 owns `auth.users`. The file holds only the `on_auth_user_created_enqueue_welcome` trigger, which is kept in the trigger phase of 0002, after the table exists. | Better Auth owns the table. |
| `public.handle_auth_user_created()` | Kept, minus the pg_net block. See below. | pg_net is not available. |
| `CREATE SCHEMA "private"` / `"catalogue_private"` | `CREATE SCHEMA IF NOT EXISTS` | 0000 already creates them. |
| 566 `GRANT` and 565 `REVOKE` statements whose only grantee is `postgres`, plus `postgres` removed from 2 grantee lists (`get_artificial_analysis_coverage`, `publish_artificial_analysis_snapshot`) | Dropped | `postgres` is Supabase's object-owner role. Every one of these is a `REVOKE ALL ... FROM postgres; GRANT EXECUTE ... TO postgres` pair on a function, or the same on `SCHEMA public`. That pair leaves the owner with EXECUTE, which an owner has anyway. On PlanetScale the owner is whichever role runs the migrations. |
| `ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" ...` (11 statements) | `ALTER DEFAULT PRIVILEGES ...` (for the role that runs the migration) | Same reason. The 9 `adp_wipes.sql` revokes clear Supabase's platform defaults and are no-ops on PlanetScale. The 2 `REVOKE ALL ON FUNCTIONS FROM PUBLIC` statements still matter for future functions. |
| `CREATE EVENT TRIGGER ensure_rls` (calls `public.rls_auto_enable()`) | Wrapped in a `DO` block that skips it, with a warning, on `insufficient_privilege` | Event triggers need superuser. See "Open decisions". |
| `CREATE INDEX ... ON ONLY public.gateway_requests` / `gateway_upstream_requests` (29 + 5) | `ON` instead of `ON ONLY` | In the source, these indexes load before the partitions and then cascade to them. Here indexes come after the partitions, so `ON ONLY` would leave the partitions unindexed and the parent index invalid. |
| Inline foreign keys in `CREATE TABLE` (named table constraints, unnamed table constraints, and column-level `REFERENCES`) | Moved to `ALTER TABLE ... ADD ...` in the foreign-key phase | Tables reference tables that load later. PostgreSQL picks the same default names in both forms. |

Kept unchanged: all 370 RLS policies, the 48 `auth.uid()` calls and 1 `auth.role()` call (served by the 0000 compat functions), all grants to `anon`, `authenticated` and `service_role`, the `public` schema ACL including `pg_database_owner`, and the 79 foreign keys to `auth.users(id)`.

### Signup trigger: what moved and what stayed

`public.handle_auth_user_created()` runs `AFTER INSERT ON auth.users` (trigger `on_auth_user_created_enqueue_welcome`).

**Stays in the database (0002):**
- Upserts `public.users (user_id)` with `on conflict do nothing`. This step is mandatory: if it fails, the signup is aborted.
- `raise log` and `raise warning` lines tagged `[signup-trigger]`.
- `SECURITY DEFINER`, `search_path = public`, and the grants.

**Moves to Better Auth (`databaseHooks.user.create.after`):**
- The optional Discord notification. It read the webhook URL from the GUC `app.settings.discord_signup_webhook_url`, skipped when that was unset, and called `net.http_post` with JSON `{"content": "New AI Stats signup\n- user_id: `<id>`\n- email: `<email or unknown>`\n- created_at: `<created_at>`", "allowed_mentions": {"parse": []}}`. Failures were logged and never blocked a signup.
- The hook should keep the same rules: never block signup, and skip when no URL is configured. The message still says "AI Stats" (an old product name); whether to change it is up to the hook owner.

The function comment was updated to say that the notification moved. The unused variables (`v_webhook_url`, `v_request_id`, `v_created_at`) were removed.

### What 0001_auth.sql must provide

The baseline reads these `auth.users` columns: `id`, `email`, `raw_user_meta_data`, `created_at`, `last_sign_in_at`, `deleted_at` and `is_anonymous`. **`deleted_at` and `is_anonymous` are not in the README contract.** `public.enqueue_feedback_request_emails` and `public.queue_slack_agent_refusal_email` read them. Both are plpgsql, so a missing column only fails at runtime. Add both columns to 0001, or change those functions on main. The verifier checks this once 0001 exists.

## pg_strict hazards

`build-baseline.mjs --report` scans every function body for `UPDATE` or `DELETE` statements without a top-level `WHERE`, including dynamic SQL in string literals. It skips `ON CONFLICT DO UPDATE`, `FOR UPDATE` and trigger DDL text. One hit:

- `public.refresh_public_monitor_weekly_usage()` starts with `delete from public.public_monitor_weekly_usage;`. The active cron job `refresh-public-monitor-weekly-usage` runs it every 15 minutes, so with pg_strict on, the job would fail on every run.

No other function body, and none of the cron commands, trips pg_strict. `truncate` (used on `pg_temp` tables in `process_v2_analytics_outbox`) is not affected.

## Open decisions

1. **Role model on PlanetScale.** Decide which role runs the migrations and so owns every object, and which role the apps log in as. The app login role needs `GRANT anon, authenticated, service_role TO <role> WITH INHERIT FALSE, SET TRUE` for the compat client's `SET LOCAL ROLE`. 0000 has this line as a comment, because the role name comes from the dashboard. If the app logs in as a role that does not own the objects, it relies on the explicit grants to `service_role` and friends, exactly as on Supabase. The dropped grants to `postgres` change nothing as long as the migration role owns the objects.
2. **`service_role` and BYPASSRLS.** On Supabase, `service_role` bypasses RLS. Creating a BYPASSRLS role needs BYPASSRLS or superuser. If PlanetScale's role has neither, 0000 creates `service_role` without it and warns. Server-side code using `service_role` would then be subject to the RLS policies, and most tables have no `service_role` policy. Confirm on the real database, or have PlanetScale support grant it.
3. **Event trigger `ensure_rls`.** It needs superuser, so on PlanetScale it will most likely be skipped with a warning. Today it is only a safety net: every table in the source enables RLS explicitly, and `ensure_gateway_requests_partitions()` enables RLS and adds the deny policy on each new partition itself. Without the trigger, a future migration that forgets `ENABLE ROW LEVEL SECURITY` is not caught. A CI lint on new migrations could replace it.
4. **pg_strict and `refresh_public_monitor_weekly_usage()`.** Fix this on main in `supabase/schemas` (with a matching Supabase migration) and regenerate, rather than patching it in the generator. Options are `delete ... where true` (check that pg_strict accepts a constant predicate), a `truncate`, which takes an ACCESS EXCLUSIVE lock and blocks the public monitor page's readers until commit, or relaxing pg_strict for the role cron uses.
5. **`cleanup-dormant-enterprise-teams`.** Keep the job on the renamed no-op function (what 0003 does now), or drop it on both Supabase and PlanetScale.
6. **`deleted_at` and `is_anonymous` on `auth.users`.** Add them to 0001, or change the two functions that read them (see above).
7. **Public schema ACL.** 0002 runs `COMMENT ON SCHEMA public`, plus `REVOKE` and `GRANT ... ON SCHEMA public`, including to `pg_database_owner`. These need the migration role to own the database (through `pg_database_owner`) or the schema. Check this on the real database first. If it fails, those 11 statements (from `public/schema.sql`) can go: on PostgreSQL 15 and later the defaults are the same apart from the explicit grants to `anon`, `authenticated` and `service_role`.
8. **Collation.** Supabase uses ICU `en-US`. In August, PlanetScale's default turned out to be libc `en_US.UTF-8`, and `00_target_compatibility.sql` then patched the `ORDER BY` in `get_monitor_model_rows` and `get_monitor_history_page` with `COLLATE "en-US-x-icu"`. This port does not do that. Check `datcollate`/`datlocprovider` on the new database. If it is libc, either create the database with ICU or decide whether the text ordering of capped RPC result sets matters.
9. **gateway_requests partitions.** The declarative export has monthly partitions through `2026_10` plus `_default`. Prod has later ones made by the weekly job. Run `select public.ensure_gateway_requests_partitions(2);` after 0002 and before copying data. Otherwise new rows land in `_default`, and later creating that month's partition fails.
10. **pg_cron runtime.** Jobs run as the role that scheduled them, in the database named by `cron.database_name`. Run 0003 as the owner role in that database. Confirm that PlanetScale runs jobs through background workers or a trusted local connection.
11. **Diagnostics extensions.** Enable `hypopg` and `pg_stat_statements` in the dashboard if they are wanted, then re-run 0000.

## Prior art (August 2026, `ce24ea641b`)

The August attempt disabled RLS on every table (`00_target_compatibility.sql`, `0002_remove-legacy-rls.sql`) and dropped the Supabase request-context functions and the RPCs that used them (`0004_remove-supabase-context-functions.sql`). This port does the opposite: RLS, policies, `auth.uid()`, and the RPCs stay as they are, and the compat functions in 0000 provide the request context. Its `00_target_bootstrap.sql` used a one-column `auth.users (id)` anchor. Here, 0001 owns the real table.
