Usa esta página para entender qué significa un error de Phaseo y qué hacer a continuación.

Todas las respuestas de error usan el mismo formato JSON, para que tu aplicación pueda gestionar los fallos de manera coherente entre modelos y proveedores. El campo `error` es un objeto con `code`, `message` y `type`, la forma que leen los SDK compatibles con OpenAI, así que sus excepciones incluyen el mensaje del gateway.

## Ejemplo de respuesta de error

```json
{
  "error": {
    "code": "upstream_error",
    "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
    "type": "server_error",
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "attempt_count": 1,
  "failed_providers": ["google-ai-studio"],
  "failed_statuses": [403],
  "provider_failure_diagnostics": {
    "category": "provider_access_missing",
    "hint": "The provider account appears not to have access to this model or feature yet. Verify account entitlements and provider-side access.",
    "provider": "google-ai-studio"
  },
  "upstream_error": {
    "code": "PERMISSION_DENIED",
    "message": "The caller does not have permission.",
    "description": null,
    "param": null
  },
  "failure_sample": [
    {
      "provider": "google-ai-studio",
      "type": "upstream_non_2xx",
      "status": 403,
      "upstream_error_code": "PERMISSION_DENIED",
      "upstream_error_message": "The caller does not have permission.",
      "upstream_error_description": null,
      "upstream_error_param": null,
      "upstream_payload_preview": "{\"error\":{\"status\":\"PERMISSION_DENIED\"}}",
      "retryable": false
    }
  ]
}
```

## Campos que siempre recibirás

- `generation_id`: ID de solicitud estable que puedes compartir con soporte.
- `status_code`: coincide con el código de estado HTTP.
- `error`: un objeto que describe el fallo:
  - `error.code`: código de error legible por máquina, como `validation_error`.
  - `error.message`: explicación clara de lo que ocurrió.
  - `error.type`: el tipo de error (consulta la sección Tipos de error más abajo).
  - `error.param`: el parámetro de la solicitud que causó el error, cuando el gateway lo conoce; si no, `null`.
  - `error.metadata` (opcional): detalles estructurados como el proveedor que falló, el subtipo, los estados fallidos o `retry_after_seconds`. Los mismos valores también se devuelven en el nivel superior.
- `code`: el mismo código que `error.code`. Las respuestas anteriores devolvían este código como cadena en `error`; lee `code` si tu cliente esperaba ahí una cadena.
- `message`: el mismo texto que `error.message`.
- `error_type`: categoría general, normalmente `user` o `system`.
- `error_origin`: indica si el problema se debió principalmente al solicitante, a Phaseo o a un proveedor ascendente.
- `description`: explicación en lenguaje claro de lo ocurrido.
- `details` (opcional): detalles estructurados de validación cuando el error se debe a una solicitud no válida.

## Otros campos que pueden aparecer

Algunos errores incluyen más detalles para ayudarte a corregir el problema más rápido:

- `reason`: motivo más específico, como `all_candidates_failed` o `pricing_not_configured`.
- `provider_candidate_diagnostics` y `provider_enablement`: explican por qué no se pudo usar un modelo con el endpoint solicitado.
- `routing_diagnostics`: información adicional sobre cómo el enrutamiento o las comprobaciones de disponibilidad limitaron la solicitud.
- `provider_failure_diagnostics`: sugerencias sobre credenciales ausentes, falta de acceso, restricciones regionales, límites de tasa y otros fallos del proveedor.
- `upstream_error` y `failure_sample`: resumen aproximado del primer fallo del proveedor, si la solicitud llegó a un proveedor.
- `failed_providers`, `failed_statuses` y `attempt_count`: contexto adicional sobre reintentos y conmutación por error.

## Tipos de error

`error.type` sigue los [tipos de error documentados por OpenAI](https://platform.openai.com/docs/guides/error-codes) y se determina a partir del estado HTTP:

| Estado | `error.type` |
| --- | --- |
| `400`, `409`, `410`, `413`, `422` y otros 4xx | `invalid_request_error` |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `500`, `502` y otros 5xx | `server_error` |

Los errores de `/v1/messages` usan el mismo cuerpo, así que los SDK de Anthropic también encuentran `error.type` y `error.message`.

## Cómo interpretar las clases de estado

| Estado | Significado | Acción recomendada |
| --- | --- | --- |
| `400-499` | Problema con la solicitud, la autenticación o los permisos | Corrige la solicitud o las credenciales antes de reintentar. |
| `429` | Limitación de tasa del proveedor o de la ruta | Reintenta con espera progresiva y respeta `Retry-After`. |
| `500-599` | Fallo de Phaseo o de un proveedor ascendente | Reintenta con espera progresiva aleatoria y registra el ID de solicitud. |

## Códigos de error habituales

| `error.code` | Estado HTTP | `error.type` | Descripción |
| --- | --- | --- | --- |
| `unauthorised` | `401` | `authentication_error` | Falta la clave de API o no es válida. |
| `guardrail_blocked` | `403` | `permission_error` | Una guardrail o política de acceso del espacio de trabajo bloqueó la solicitud. |
| `not_found` | `404` | `not_found_error` | No se encontró el endpoint o el recurso. |
| `model_retired` | `410` | `invalid_request_error` | El modelo está retirado y ya no lo sirve ningún proveedor. Cambia a `replacement_model`. |
| `insufficient_funds` | `402` | `insufficient_quota` | El espacio de trabajo no tiene créditos suficientes para la solicitud. |
| `key_limit_exceeded` | `429` | `rate_limit_error` | La clave de API alcanzó uno de sus límites. |
| `phaseo_free_model_limit_exceeded` | `429` | `rate_limit_error` | Se agotó la cuota diaria compartida de modelos gratuitos de Phaseo (1.500 solicitudes por defecto). Respeta `Retry-After`, espera al reinicio a las 00:00 UTC o elige un modelo de pago. |
| `rate_limit_exceeded` | `429` | `rate_limit_error` | Se agotó una [política de límite de frecuencia](./limits.mdx) del espacio de trabajo. `policy_id` y `limit_scope` la identifican. Respeta `Retry-After` o pide a un administrador del espacio de trabajo que cambie la política. |
| `validation_error` | `400` | `invalid_request_error` | Los parámetros o el cuerpo de la solicitud no son válidos. `error.param` indica el primer campo no válido. |
| `upstream_error` | `429` | `rate_limit_error` | Todos los proveedores probados para la solicitud aplicaron un límite de frecuencia. Respeta `Retry-After`; las solicitudes BYOK también incluyen los encabezados `X-Phaseo-Upstream-RateLimit-*`. |
| `upstream_error` | `502` | `server_error` | El proveedor del modelo ascendente no respondió correctamente. |
| `upstream_stream_failure` | `502` | `server_error` | Una solicitud sin streaming cuyo proveedor falló después de empezar a generar. No se devuelve salida parcial y la solicitud no se cobra. |
| `gateway_error` | `500` | `server_error` | Se produjo un problema inesperado en Phaseo. |

## Cuando falla un proveedor

Si Phaseo llegó a un proveedor, pero la solicitud sigue fallando, es posible que veas:

- `provider_failure_diagnostics.category`
- `provider_failure_diagnostics.hint`
- `provider_failure_diagnostics.provider`

Las categorías actuales incluyen:

- `credentials_not_configured`
- `credentials_invalid_or_forbidden`
- `provider_access_missing`
- `region_or_project_restriction`
- `model_unavailable_for_endpoint`
- `rate_limited`
- `server_error`

Estos campos te ayudan a resolver el problema sin activar el modo de depuración completo.

## Cuando un modelo o endpoint no está disponible

En respuestas `unsupported_model_or_endpoint`, Phaseo puede incluir:

- `provider_candidate_diagnostics`
- `provider_enablement`
- `missing_pricing_providers`
- `routing_diagnostics`

Esto ayuda a distinguir entre:

- un modelo conocido que aún no está activo
- un modelo que no es compatible con el endpoint solicitado
- datos de precios ausentes
- restricciones de despliegue o disponibilidad interna

Campos habituales:

- `provider_candidate_diagnostics.totalProviders`: cantidad de proveedores conocidos para el modelo antes de filtrar por endpoint.
- `provider_candidate_diagnostics.supportsEndpointCount`: cantidad de esos proveedores compatibles con el endpoint solicitado.
- `provider_candidate_diagnostics.candidateCount`: cantidad de proveedores que quedaron después de las comprobaciones de adaptadores.
- `provider_candidate_diagnostics.droppedUnsupportedEndpoint`: proveedores descartados porque no admiten el endpoint.
- `provider_candidate_diagnostics.droppedMissingAdapter`: pares proveedor/endpoint descartados porque todavía no hay un adaptador de Gateway para ese endpoint.
- `provider_enablement.capability`: control de capacidad que se aplica, como `video_generation`.
- `provider_enablement.providersBefore` / `provider_enablement.providersAfter`: proveedores antes y después del filtrado por capacidad o habilitación.
- `provider_enablement.dropped[].reason`: motivos legibles por máquina, como `pricing_missing`.
- `routing_diagnostics.filterStages[].stage`: etapa de enrutamiento, por ejemplo, filtrado de capacidad, despliegue o estado de enrutamiento.
- `routing_diagnostics.filterStages[].beforeCount` / `routing_diagnostics.filterStages[].afterCount`: número de proveedores antes y después de cada etapa.
- `routing_diagnostics.filterStages[].droppedProviders[].reason`: motivos legibles por máquina, como restricciones de despliegue o enrutamiento.

### Ejemplo

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
    "message": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
    "type": "invalid_request_error",
    "param": null
  },
  "code": "unsupported_model_or_endpoint",
  "generation_id": "G-unsupported123",
  "status_code": 400,
  "description": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
  "provider_candidate_diagnostics": {
    "totalProviders": 3,
    "supportsEndpointCount": 2,
    "candidateCount": 1,
    "droppedUnsupportedEndpoint": ["provider-a"],
    "droppedMissingAdapter": [
      {
        "providerId": "provider-b",
        "endpoint": "responses"
      }
    ]
  },
  "provider_enablement": {
    "capability": "responses",
    "providersBefore": ["provider-b", "provider-c"],
    "providersAfter": ["provider-c"],
    "dropped": [
      {
        "providerId": "provider-b",
        "reason": "pricing_missing"
      }
    ]
  },
  "routing_diagnostics": {
    "filterStages": [
      {
        "stage": "provider_routing_status",
        "beforeCount": 1,
        "afterCount": 0,
        "droppedProviders": [
          {
            "providerId": "provider-c",
            "reason": "provider_status_not_ready"
          }
        ]
      }
    ]
  }
}
```

## Cuando se retira un modelo

Un modelo retirado se sigue sirviendo mientras algún proveedor lo sirva. Cuando ya no lo sirve ninguno, las solicitudes para ese modelo fallan con `410` y el error `model_retired`:

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

- `model`: el modelo que solicitaste.
- `retired_at`: cuándo se retiró el modelo, o `null` si no hay ninguna fecha registrada.
- `replacement_model`: el sustituto sugerido, o `null` si no hay ninguno.

Reintentar no sirve de nada. Actualiza el ID del modelo en tu solicitud. Para que estas solicitudes se sigan atendiendo mientras migras, añade el sustituto a la lista `models` de tu solicitud o activa el enrutamiento de modelos retirados para el espacio de trabajo. Consulta [Obsolescencia y retirada de modelos](../guides/model-retirement.mdx).

## Modo de depuración opcional

La mayoría de los esquemas de solicitud admiten un objeto `debug` para investigar problemas de forma controlada:

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

Campos disponibles:

- `enabled`
- `return_upstream_request`
- `return_upstream_response`
- `trace`
- `trace_level` (`summary` o `full`)

Usa el modo de depuración solo en desarrollo o en entornos estrictamente controlados.

## Estrategia de reintentos

- **Errores de la serie 400 salvo 429:** corrige la solicitud, las credenciales o la política de acceso antes de reintentar.
- **429:** usa espera progresiva exponencial y respeta el encabezado `Retry-After`.
- **Errores de la serie 500:** usa reintentos limitados solo cuando sea seguro repetir la operación. Un envío con resultado incierto puede haber creado ya un trabajo o generado un cargo; recupera un trabajo aceptado en lugar de enviarlo de nuevo.

Establece un límite de intentos y un plazo total, y añade variación aleatoria a los tiempos de espera. Consulta los [límites de solicitudes](./limits.mdx) para las cabeceras de respuesta y la gestión de reintentos.

## Notas específicas de streaming

- Si la solicitud falla antes de empezar el streaming, recibirás una respuesta de error JSON estándar.
- Si falla a mitad del flujo, el flujo termina con el evento de fallo del endpoint en lugar de un final normal: un frame `error` en Chat Completions, `response.failed` (o `error`) en Responses y un evento `error` en Messages. Trata el flujo parcial como incompleto y ofrece la opción de reintentar.
- El frame `error` de Chat Completions incluye el mismo objeto de error, con `error.type` determinado a partir del código:

  ```json
  {
    "object": "error",
    "message": "The upstream stream ended before the response completed.",
    "code": "upstream_stream_failure",
    "error": {
      "code": "upstream_stream_failure",
      "message": "The upstream stream ended before the response completed.",
      "type": "server_error",
      "param": null
    }
  }
  ```
- Una solicitud sin streaming cuyo proveedor falla a mitad devuelve `502` con `upstream_stream_failure`, no una respuesta parcial.
- Registra siempre `generation_id` y los metadatos del endpoint y del modelo.

## Consejos para resolver problemas

- Consulta la [página de estado de Gateway](https://status.phaseo.app) para ver incidentes en curso.
- Compara el cuerpo de tu solicitud con la documentación del endpoint.
- Comparte `generation_id` al contactar con soporte.

<Visibility for="agents">
Reglas de gestión de errores para agentes, resumen de esta página:

- Decide según `error.code` (también devuelto como `code` de nivel superior), `error.type` y `status_code`, no según el texto del mensaje. Registra `generation_id` en cada fallo.
- `400`, `401`, `403` y `404`: corrige primero la solicitud, la clave o el acceso. No repitas la misma solicitud sin cambios.
- `410` con `model_retired`: cambia a `replacement_model` cuando no sea `null`; si lo es, elige un modelo nuevo con `GET /v1/models`.
- `429`: si hay `Retry-After` (segundos o una fecha HTTP), espera ese tiempo antes de reintentar; si no, usa retroceso exponencial con variación aleatoria. Un error `key_limit_exceeded` sin `Retry-After` no se restablece solo, así que no lo reintentes.
- `500` a `599`: reintenta solo cuando repetir la llamada sea seguro, con un límite de intentos, un plazo total y retroceso exponencial con variación aleatoria. En trabajos asíncronos, consulta el trabajo aceptado en lugar de enviarlo de nuevo.
- Trata las cargas de depuración como información sensible y redáctalas antes de escribir registros persistentes.
- Para patrones probados de reintento y análisis de errores, instala la habilidad `phaseo-gateway`: `npx skills add https://phaseo.app/docs --skill phaseo-gateway`.
</Visibility>
