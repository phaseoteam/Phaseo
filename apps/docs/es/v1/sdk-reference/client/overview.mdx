## Qué envías y qué recibes

Los cuerpos de solicitud usan los nombres de campo JSON de la API en todos los SDK. [Uso](./usage) tiene un ejemplo por endpoint.

| Lenguaje | Cuerpo de la solicitud | Devuelve |
| --- | --- | --- |
| TypeScript | Objetos tipados generados a partir de la especificación OpenAPI | Objetos tipados |
| Python | Dicts; los tipos están en `phaseo.models` | Dicts `APIResponse` con `output_text`, `request_id` y `trace_url` |
| Go | `map[string]interface{}`, o los tipos `phaseo.ChatCompletionsRequest` y `phaseo.ResponsesRequest` (campos de struct en PascalCase como `Model`, `Messages`, `Input`) | JSON decodificado |
| C# | `Dictionary<string, object>` | `Dictionary<string, object>?` |
| PHP | Arrays | Arrays |
| Ruby | Hashes (argumentos con nombre) | Hashes |
| Java | Un `Map` o un `JsonNode` de Jackson; analiza antes las cadenas JSON | `JsonNode` |
| Rust | `&serde_json::Value` | `PhaseoResponse` con `status`, `body` y `request_id` |

Si falta la clave, falla al crear el cliente. Python lanza `ValueError`, `NewFromEnv()` de Go devuelve un error, C# y PHP lanzan `Missing API key. Pass apiKey or set PHASEO_API_KEY.`, Ruby lanza `ArgumentError: Missing API key. Pass api_key or set PHASEO_API_KEY.` y `Phaseo::from_env()` de Rust devuelve un `PhaseoError`.

Usa `AsyncPhaseo` con asyncio:

```python Python
import asyncio
from phaseo import AsyncPhaseo

async def main():
    async with AsyncPhaseo() as client:
        response = await client.responses.create({"model": "openai/gpt-6-astra", "input": "Hello"})
        print(response.output_text, response.request_id, response.trace_url)

asyncio.run(main())
```

Usa `async for event in client.responses.stream(request)` para recibir eventos de texto ya analizados. Cancelar la tarea de asyncio detiene la solicitud HTTP y cualquier sondeo. `AsyncPhaseo` tiene espacios de nombres de recursos para texto, imágenes, audio, tiempo real, música, vídeo, lotes, archivos, modelos, embeddings, OCR, rerank, parse, moderación, decisiones y extracciones; usa `await client.request(...)` para cualquier otra operación HTTP.

<span id="wait-for-music-video-or-batches"></span>
## Espera a la música, el vídeo o los lotes

Los helpers de espera están en TypeScript y Python. Los demás SDK devuelven el trabajo desde la llamada de creación; sondéalo con el método get o abre su [URL de WebSocket de trabajos](#find-the-method-for-each-endpoint).

<CodeGroup>

```typescript TypeScript
const music = await client.music.generateAndWait(
  { model: process.env.PHASEO_MUSIC_MODEL!, prompt: "Gentle instrumental piano" },
  { timeoutMs: 600_000, onPoll: (job) => console.log(job.id, job.status) },
);
```

```python Python
import os

music = client.music.generate_and_wait(
    {"model": os.environ["PHASEO_MUSIC_MODEL"], "prompt": "Gentle instrumental piano"},
    timeout=600,
    on_poll=lambda job: print(job["id"], job["status"]),
)
```

</CodeGroup>

Usa `videos.generateAndWait` / `videos.generate_and_wait` para vídeo y `batches.createAndWait` / `batches.create_and_wait` para lotes. Cada helper envía una sola vez. Si la primera respuesta ya está completa, la devuelve sin sondear; si no, sondea el mismo trabajo hasta que termina y devuelve la respuesta completa. Los trabajos fallidos, cancelados o caducados lanzan `JobFailedError`, cuyo `response` contiene los detalles. Un lote completado puede contener igualmente solicitudes individuales fallidas.

`wait(id, options)` en cada recurso retoma un trabajo existente y devuelve cualquier respuesta final, incluidos los fallos. En Python, la música también tiene `create(request)` y `retrieve(id)`.

| TypeScript | Python | Por defecto | Notas |
| --- | --- | --- | --- |
| `intervalMs` | `interval` | `5000` ms / `5` segundos | Mínimo `250` ms / `0.25` segundos. |
| `timeoutMs` | `timeout` | `1800000` ms / `1800` segundos (30 minutos) | Empieza cuando vuelve el envío; la solicitud de envío mantiene su propio tiempo de espera. |
| `signal` | `cancel_event` | ninguno | Deja de esperar. En Python, un `threading.Event`. |
| `onPoll` | `on_poll` | ninguno | Recibe la primera respuesta y cada sondeo. |

`JobTimeoutError` y `JobCancelledError` conservan el ID del trabajo y la última respuesta (`jobId`/`lastResponse` en TypeScript, `job_id`/`last_response` en Python), para que puedas retomarlo con `.wait(error.jobId)` o `.wait(error.job_id)`. Dejar de esperar no cancela el trabajo remoto. En TypeScript cancela el sondeo en curso; el cliente síncrono de Python comprueba la cancelación y el plazo entre solicitudes y callbacks, así que no puede interrumpir una llamada HTTP que ya está en marcha. Los fallos HTTP se lanzan tal cual, y los envíos nunca se reintentan. Estos helpers sondean desde tu proceso; no añaden ejecución en segundo plano al gateway.

### Conserva un handle entre procesos

`music.start`, `videos.start` y `batches.start` devuelven un handle con `result()`, `events()` y `cancel()`, además de `toJSON()` (TypeScript) o `to_dict()` (Python). Guarda el tipo y el ID que devuelve y reconstruye el handle más tarde con `resume(id)`. `result()` lanza una excepción ante fallos finales. Solo los trabajos de vídeo y de lotes admiten `cancel()`. En `AsyncPhaseo`, usa await con los métodos e itera los eventos con `async for`.

| Tarea | TypeScript | Python |
| --- | --- | --- |
| Transmitir el contenido de un vídeo | `videos.streamContent(id)`, escrito con `downloadTo(stream, writable)` | `videos.stream_content(id)`, escrito con el síncrono `download_to(chunks, binary_file)`, que no guarda toda la descarga en memoria |
| Transmitir los resultados de un lote | `batchResults(await client.batches.streamResults(id))` analiza el JSONL fila a fila; `matchBatchResult(row, inputsByCustomId)` empareja cada fila con su entrada y conserva los errores por fila | `batches.results(id)` |
| Preparar subidas | `toFile(bytes, filename, contentType)` | Pasa bytes, objetos `Path`, objetos de archivo o tuplas de archivo de HTTPX |

## Controles de solicitud y errores

Los reintentos son `0` por defecto en TypeScript, Python y Java, y solo se aplican a solicitudes `GET` y `HEAD`. Los envíos de pago, las escrituras y las solicitudes en streaming nunca se reintentan.

<CodeGroup>

```typescript TypeScript
const fast = client.withOptions({ timeoutMs: 30_000, signal, maxRetries: 2 });
```

```python Python
fast = client.with_options(timeout=30, max_retries=2)
```

```java Java
Phaseo client = new Phaseo(System.getenv("PHASEO_API_KEY"))
    .setTimeout(Duration.ofSeconds(30))
    .setMaxRetries(2);
```

</CodeGroup>

<Tabs>
<Tab title="TypeScript">

`withOptions(...)` devuelve un cliente nuevo con esos controles aplicados a cada llamada de recurso, de stream y de medios; el cliente original no cambia. Los reintentos respetan `Retry-After`. `timeoutMs` incluye la lectura del cuerpo de la respuesta.

`responseMetadata(result)` devuelve el ID de solicitud del gateway y la URL de la traza en el panel. Los errores HTTP son `PhaseoHttpError`, con el `status` HTTP, el `code` de error de la API, `requestId`, `traceUrl`, el retraso de reintento, el cuerpo y `headers`.

</Tab>
<Tab title="Python">

`with_options(...)` devuelve un cliente nuevo y también acepta `headers=...`; funciona tanto en `Phaseo` como en `AsyncPhaseo`. Los reintentos se hacen antes de leer la respuesta, hasta un máximo de `10`. Los tiempos de espera son tiempos de espera de HTTPX en segundos, así que limitan la inactividad de la red y no la duración total.

Las respuestas JSON son dicts `APIResponse` con `output_text`, `request_id` y `trace_url`. Los errores HTTP son `PhaseoHTTPError`, con `status`, `code`, `request_id`, `trace_url`, el retraso de reintento y el cuerpo.

Al actualizar desde una versión antigua, sustituye las capturas de `urllib.error.HTTPError` por `PhaseoHTTPError` (o `httpx.HTTPStatusError`), y las capturas de errores de conexión por `httpx.TransportError`.

</Tab>
<Tab title="Java">

Los errores HTTP son `Client.ApiException` (`app.phaseo.gen.Client`), con `getStatusCode()`, `getRequestId()`, `getResponseBody()` y los encabezados. `requestWithResponse(...)` devuelve los datos con su `requestId()`.

</Tab>
<Tab title="Rust">

Cada llamada devuelve `Result<PhaseoResponse, PhaseoError>`. `PhaseoError` implementa `std::error::Error` y `Display`; los fallos de transporte y de configuración no tienen `status`.

| Tipo | Campo | Significado |
| --- | --- | --- |
| `PhaseoResponse` | `status: u16` | Código de estado HTTP. |
| `PhaseoResponse` | `body: serde_json::Value` | Respuesta JSON analizada, o una cadena JSON cuando la respuesta no era JSON válido. |
| `PhaseoResponse` | `request_id: Option<String>` | El encabezado de respuesta `x-request-id`, si está presente. |
| `PhaseoError` | `message: String` | Mensaje de error de configuración, de transporte o del Gateway. |
| `PhaseoError` | `status: Option<u16>` | Estado HTTP del Gateway, cuando se recibió una respuesta. |
| `PhaseoError` | `body: Option<serde_json::Value>` | Cuerpo de error del Gateway analizado, si está disponible. |

</Tab>
</Tabs>

[Uso](./usage#handle-errors) muestra un manejador de errores completo en cada lenguaje.

## Llama a un endpoint sin wrapper

Cada SDK incluye también el cliente generado a partir de la especificación OpenAPI de Phaseo:

| Lenguaje | Cliente generado |
| --- | --- |
| TypeScript | `client.rawClient()`; las operaciones generadas se exportan como `operations`. |
| Python | `client.raw_client()`; las operaciones generadas están en `phaseo.ops`. |
| Go | `client.RawClient()`, desde `src/gen`. `client.Request(ctx, method, path, query, headers, body)` envía cualquier solicitud. |
| Java | `client.rawClient()`, con `requestLines` para streams y `requestBytes` para respuestas binarias. |
| Rust | `phaseo::gen` contiene el cliente, los modelos y las operaciones generados, reexportados como `phaseo::client`, `phaseo::models` y `phaseo::operations`. `phaseo::model_ids` tiene los ID de modelo generados. `client.post(path, body)` envía JSON a cualquier ruta bajo la URL base. Consulta [docs.rs](https://docs.rs/phaseo). |

Las operaciones generadas son de más bajo nivel que los métodos wrapper; usa el wrapper cuando exista.

## Analiza la salida y recopila streams

Estos helpers están en TypeScript y Python. `responses.parse(request, schema)` valida una respuesta JSON completa. En TypeScript, `schema` es un parser compatible con Zod; en Python, un modelo de Pydantic. Define también el formato de salida estructurada en la solicitud; el parser solo valida.

`collectStream(client.streamResponses(request))` (TypeScript), o `collect_stream` y `collect_async_stream` (Python), reúnen el texto y el uso transmitidos.

## Comprueba un modelo antes de llamarlo

`checkModelCapabilities` / `check_model_capabilities` (TypeScript y Python) comprueba las capacidades anunciadas y las restricciones escalares (`inputTypes`, `outputTypes`, `endpoints`, `parameters`, `parameterValues`, o los nombres en snake_case en Python) en una oferta de proveedor activa. Nunca cambia el modelo ni descarta parámetros, y no puede garantizar que un proveedor en directo acepte la solicitud. Los metadatos que faltan se tratan de forma distinta: TypeScript los indica como desconocidos y Python da la comprobación por fallida.

Para selectores de modelos y editores de parámetros, usa los metadatos de endpoints en directo:

<CodeGroup>

```typescript TypeScript
const support = await client.models.checkParameters(
  "anthropic/claude-haiku-4.5",
  { temperature: 0.7, top_p: 0.9 },
  { endpoint: "responses" },
);
```

```python Python
support = client.models.check_parameters(
    "anthropic/claude-haiku-4.5",
    {"temperature": 0.7, "top_p": 0.9},
    endpoint="responses",
)
```

</CodeGroup>

Cada parámetro vuelve como `supported`, `partial`, `unsupported` o `unknown`, con las rutas de proveedor que coinciden y los problemas de restricciones que puedes resaltar en línea. Estas comprobaciones son llamadas explícitas; no añaden una consulta a las solicitudes de generación. [Modelos](./models#check-one-model) indica el método en cada SDK.

## Prueba sin red

<Tabs>
<Tab title="TypeScript">

Importa `createMockTransport` y `jobFixtures` desde `@phaseo/sdk/testing` y pasa el `fetchImpl` del mock al cliente. Los fixtures son estrictos y ordenados: una llamada inesperada falla localmente y nunca llega a la red. Llama a `mock.assertDone()` para comprobar que se hicieron todas las solicitudes esperadas.

</Tab>
<Tab title="Python">

Pasa `phaseo.testing.MockTransport(fixtures)` a un `httpx.Client` o `httpx.AsyncClient` y entrégaselo al cliente de Phaseo como `http_client`. Una solicitud inesperada falla localmente; llama a `assert_done()` para comprobar que se usaron todos los fixtures. `phaseo.testing.job_fixtures(path, job_id)` construye los fixtures de envío y sondeo de un trabajo. Los fixtures no verifican el comportamiento de los proveedores en directo.

</Tab>
</Tabs>

## Exporta código desde una sala

Después de enviar una solicitud en una sala de Phaseo, **Obtener código** exporta su modelo y sus ajustes como TypeScript o Python, y **Ver solicitud** abre su traza en el panel cuando hay un ID de solicitud disponible. Ejecuta el código exportado en tu servidor con `PHASEO_API_KEY` definida.
