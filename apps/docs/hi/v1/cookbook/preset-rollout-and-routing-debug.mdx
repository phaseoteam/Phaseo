कई सेवाओं को एक प्रीसेट पर ले जाएँ ताकि वे एक ही प्रॉम्प्ट, मॉडल और प्रदाता नियम साझा करें, फिर अनुरोध लॉग से समझें कि हर अनुरोध कहाँ गया। अंत में आपके कॉलर `"model": "@release-summary"` और अपना इनपुट भेजेंगे, और आप नीति में बदलाव एक-एक कॉलर पर लागू कर सकेंगे।

अनुरोध ढाँचा प्रोडक्शन के लिए तैयार है। [प्रीसेट](../guides/presets) बताता है कि प्रीसेट की सेटिंग्स अनुरोध के साथ कैसे मिलती हैं; यह रेसिपी रोलआउट के बारे में है।

## किसी कॉलर को प्रीसेट पर ले जाएँ

<Steps>
<Step title="प्रीसेट बनाएँ">

**सेटिंग्स → प्रीसेट** में, सिस्टम प्रॉम्प्ट, मंज़ूर मॉडल, प्रदाता प्राथमिकताओं, और `temperature` जैसे डिफ़ॉल्ट पैरामीटर के साथ `release-summary` बनाएँ। या प्रबंधन कुंजी से:

```bash
curl https://api.phaseo.app/v1/presets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"@release-summary","config":{"model":"anthropic/claude-sonnet-5.5"}}'
```

</Step>
<Step title="इसे नाम से कॉल करें">

प्रीसेट को `model` के रूप में भेजें। कोई अलग `preset` फ़ील्ड नहीं है।

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@release-summary",
    "input": "Generate a release summary for the last 24 hours.",
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "@release-summary",
  input: "Generate a release summary for the last 24 hours.",
  meta: true,
});

console.log(response.model, response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "@release-summary",
        "input": "Generate a release summary for the last 24 hours.",
        "meta": True,
    }
)

print(response.get("model"), response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

प्रतिक्रिया में `model` वह मॉडल है जिसने जवाब दिया, और `meta.routing.selected_provider` प्रदाता है।

</Step>
<Step title="जाँचें कि प्रीसेट ने क्या लागू किया">

**सेटिंग्स → उपयोग → लॉग्स** में अनुरोध खोलें। यह दिखाता है कि कौन से प्रीसेट डिफ़ॉल्ट लागू हुए। प्रीसेट के मंज़ूर मॉडलों से बाहर का मॉडल दोबारा रूट होने के बजाय `validation_error` (कीवर्ड `preset_model_not_allowed`) के साथ विफल होता है।

</Step>
</Steps>

## रूटिंग फ़ैसला समझें

जब कोई अनुरोध आपकी उम्मीद के मुताबिक रूट नहीं हुआ, तो **सेटिंग्स → उपयोग → लॉग्स** में उस अनुरोध का **Routing observability** फैलाएँ। यह तीन सवालों के जवाब देता है:

| सवाल | कहाँ देखें |
| --- | --- |
| कोई प्रदाता क्यों छोड़ा गया? | रैंकिंग से पहले वजह के साथ बाहर किए गए प्रदाता, और अपने रोलआउट या रूटिंग स्टेटस की वजह से नीचे रैंक किए गए प्रदाता |
| अनुरोध क्यों ब्लॉक हुआ? | अनुरोध पर वर्कस्पेस-नीति या गार्डरेल के ब्लॉक |
| यह प्रदाता क्यों जीता? | हर रैंक किए गए प्रदाता का अंतिम स्कोर और उसके पीछे के कारक |

[रूटिंग फ़ैसला समझें](../guides/routing-and-fallbacks#explain-a-routing-decision) हर फ़ील्ड बताता है।

## नीति में बदलाव लागू करें

1. बदलाव को प्रीसेट के नए वर्ज़न के रूप में प्रकाशित करें, या बहुत अलग नीति के लिए नया स्लग बनाएँ।
2. कम जोखिम वाले एक कॉलर को उस पर ले जाएँ, उदाहरण के लिए उसे `@release-summary@v4` या किसी `canary` लेबल पर इंगित करके।
3. उसके अनुरोध विवरण और उपयोग के रुझानों की तुलना बाकी कॉलर से करें।
4. रूटिंग आपकी उम्मीद के मुताबिक होने पर बाकी कॉलर को भी ले जाएँ। वापस लौटने के लिए, लेबल को पिछले वर्ज़न पर इंगित करें।

[वर्ज़न और रोलबैक](../guides/presets#version-and-roll-back) वर्ज़न और लेबल के बारे में बताता है। अनुरोध-स्तर के उन ओवरराइड के लिए जिन्हें प्रीसेट में नहीं रहना चाहिए, [प्रदाता पिन करें या अनदेखा करें](./pin-or-ignore-providers-per-request) देखें।
