संदेश के टेक्स्ट के आधार पर नहीं, बल्कि `error.code` और HTTP स्थिति के आधार पर ब्रांच करें। हर एंडपॉइंट पर Phaseo की हर त्रुटि की JSON बॉडी एक जैसी होती है, और उसका `error` ऑब्जेक्ट (`code`, `message`, `type`, `param`) वही रूप है जिसे OpenAI-संगत SDK पढ़ते हैं, इसलिए उनके exceptions में Phaseo का संदेश आता है।

```json
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",

  "provider_failure_diagnostics": {
```

## हर त्रुटि के फ़ील्ड

| फ़ील्ड | सामग्री |
| --- | --- |
| `error.code` | मशीन द्वारा पढ़ा जा सकने वाला कोड, जैसे `validation_error`। [त्रुटि कोड](#error-codes) देखें। |
| `error.message` | सरल भाषा में स्पष्टीकरण। |
| `error.type` | त्रुटि वर्ग, HTTP स्थिति से तय। [त्रुटि प्रकार](#error-types) देखें। |
| `error.param` | त्रुटि पैदा करने वाला अनुरोध फ़ील्ड, जब Phaseo उसे जानता हो; वरना `null`। |
| `error.metadata` | वैकल्पिक। संरचित विवरण, जैसे `reason`, `failed_providers`, `failed_statuses` या `retry_after_seconds`। यही मान शीर्ष स्तर पर भी होते हैं। |
| `code` | `error.code` जैसा ही। पुरानी प्रतिक्रियाएं यह string `error` के रूप में लौटाती थीं; अगर आपका क्लाइंट वहां string की अपेक्षा करता है, तो `code` पढ़ें। |
| `message`, `description` | `error.message` वाला ही टेक्स्ट। |
| `generation_id` | लॉग करने और सपोर्ट के साथ साझा करने के लिए अनुरोध ID। |
| `status_code` | HTTP स्थिति। |
| `error_type` | `user` या `system`। |
| `error_origin` | समस्या कहां से आई: कॉलर (`user`), Phaseo (`gateway`) या कोई प्रदाता (`upstream`)। |
| `details` | वैकल्पिक। अनुरोध बॉडी अमान्य होने पर सत्यापन विवरण। |

कुछ त्रुटियां और संदर्भ जोड़ती हैं:

| फ़ील्ड | यह कब दिखता है |
| --- | --- |
| `reason` | एक खास उप-कारण, जैसे `all_candidates_failed` या `no_provider_pricing`। |
| `provider_failure_diagnostics` | किसी प्रदाता तक पहुंचा गया और वह विफल हुआ। [जब कोई प्रदाता विफल हो](#when-a-provider-fails) देखें। |
| `upstream_error`, `failure_sample` | पहली प्रदाता विफलता का यथासंभव सारांश। |
| `failed_providers`, `failed_statuses`, `attempt_count` | कौन-से प्रदाता आज़माए गए और उन्होंने क्या लौटाया। |
| `provider_candidate_diagnostics`, `provider_enablement`, `routing_diagnostics` | कोई प्रदाता इस एंडपॉइंट पर मॉडल नहीं दे सका। [जब कोई मॉडल या एंडपॉइंट उपलब्ध न हो](#when-a-model-or-endpoint-is-not-available) देखें। |

<span id="error-types"></span>
## त्रुटि प्रकार

`error.type` OpenAI के [दस्तावेज़ित त्रुटि प्रकारों](https://platform.openai.com/docs/guides/error-codes) का पालन करता है और HTTP स्थिति से तय होता है:

| स्थिति | `error.type` |
| --- | --- |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `408`, `500`, `502` और अन्य 5xx | `server_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `400`, `409`, `410`, `413`, `422` और अन्य 4xx | `invalid_request_error` |

`/v1/messages` पर त्रुटियां वही बॉडी इस्तेमाल करती हैं, इसलिए Anthropic SDK को भी `error.type` और `error.message` मिलते हैं।

<span id="error-codes"></span>
## त्रुटि कोड

| `error.code` | स्थिति | अर्थ | क्या करें |
| --- | --- | --- | --- |
| `validation_error` | `400` | कोई पैरामीटर या अनुरोध बॉडी अमान्य है। `error.param` पहले अमान्य फ़ील्ड का नाम बताता है। | अनुरोध ठीक करें। |
| `invalid_json` | `400` | बॉडी मान्य JSON नहीं है। | अनुरोध ठीक करें। |
| `model_required` | `400` | अनुरोध में `model` नहीं है। | `model` जोड़ें। |
| `unsupported_model_or_endpoint` | `400` | कोई प्रदाता इस एंडपॉइंट पर यह मॉडल नहीं दे सकता। | [नीचे](#when-a-model-or-endpoint-is-not-available) देखें। |
| `unsupported_modalities` | `400` | कोई रूट अनुरोध के इनपुट या आउटपुट प्रकार स्वीकार नहीं करता। | मॉडल या इनपुट बदलें। |
| `byok_credentials_required` | `400` | यह रूट सिर्फ़ आपकी अपनी प्रदाता कुंजी से चलता है। | एक योग्य [प्रदाता कुंजी](./endpoint/provider-credentials-create.mdx) जोड़ें। |
| `upstream_error` | `400`, `413` या `422` | हर प्रदाता ने अनुरोध को एक ही स्थिति के साथ अस्वीकार किया (कारण `upstream_rejected_request`)। | अनुरोध ठीक करें; दोबारा कोशिश करने से मदद नहीं मिलेगी। |
| `unauthorised` | `401` | कुंजी नहीं है या अमान्य है। `reason` बताता है क्यों। | `Authorization` हेडर जांचें। |
| `insufficient_funds` | `402` | वर्कस्पेस में पर्याप्त क्रेडिट नहीं हैं। | क्रेडिट जोड़ें। |
| `pricing_not_configured` | `402` | इस मॉडल के किसी प्रदाता की कीमत तय नहीं है (कारण `no_provider_pricing`)। | दूसरा मॉडल चुनें। |
| `guardrail_blocked` | `403` | किसी गार्डरेल या पहुंच नीति ने अनुरोध को रोक दिया। | अनुरोध या गार्डरेल बदलें। |
| `model_region_unavailable` | `403` | कोई प्रदाता आवश्यक क्षेत्र में, या कॉलर के स्थान से, मॉडल नहीं देता। | क्षेत्र की आवश्यकता ढीली करें या दूसरा मॉडल चुनें। |
| `not_found` | `404` | एंडपॉइंट या संसाधन मौजूद नहीं है। | पथ और ID जांचें। |
| `not_ready` | `409` | किसी जॉब के परिणाम अभी तैयार नहीं हैं। | जॉब की स्थिति पोल करें। |
| `model_retired` | `410` | मॉडल सेवानिवृत्त है और कोई प्रदाता उसे नहीं देता। | `replacement_model` पर जाएं। [नीचे](#when-a-model-is-retired) देखें। |
| `payload_too_large` | `413` | बॉडी उससे बड़ी है जितनी एंडपॉइंट स्वीकार करता है। `max_bytes` सीमा बताता है। | छोटी बॉडी भेजें या फ़ाइल अपलोड करें। |
| `key_limit_exceeded` | `429` | कोई कुंजी सीमा, बजट या प्रति-मिनट Gateway सीमा पूरी हो गई। | [अनुरोध सीमाएँ](./limits.mdx#key-limits-and-budgets) देखें। |
| `phaseo_free_model_limit_exceeded` | `429` | मुफ़्त मॉडलों का दैनिक कोटा (डिफ़ॉल्ट रूप से 1,500 अनुरोध) खत्म हो गया। | `Retry-After` का पालन करें, 00:00 UTC रीसेट का इंतज़ार करें, या सशुल्क मॉडल इस्तेमाल करें। |
| `rate_limit_exceeded` | `429` | वर्कस्पेस की कोई [रेट लिमिट नीति](./limits.mdx#rate-limit-policies) समाप्त हो गई। `policy_id` और `limit_scope` उसकी पहचान बताते हैं। | `Retry-After` का पालन करें, या किसी एडमिन से नीति बदलने को कहें। |
| `spend_rule_blocked` | `429` | ब्लॉक करने पर सेट किया गया कोई [खर्च नियम](../guides/spend-alerts.mdx) सक्रिय है। | `Retry-After` का पालन करें, या किसी मालिक या एडमिन से ब्लॉक हटाने को कहें। |
| `upstream_error` | `429` | आज़माए गए हर प्रदाता ने अनुरोध को रेट लिमिट किया। | `Retry-After` का पालन करें। BYOK अनुरोधों में `X-Phaseo-Upstream-RateLimit-*` हेडर भी होते हैं। |
| `provider_capacity_exhausted` | `429` | हर योग्य प्रदाता की क्षमता भरी हुई है (कारण `all_candidates_rate_limited`)। | मौजूद हो तो `Retry-After` का पालन करें, वरना बैकऑफ़ करें। |
| `gateway_error` | `500` | Phaseo के अंदर कुछ विफल हुआ। | बैकऑफ़ के साथ दोबारा कोशिश करें। |
| `not_implemented_yet` | `501` | यह ऑपरेशन अभी उपलब्ध नहीं है। | दोबारा कोशिश न करें। |
| `upstream_error` | `502` | प्रदाता सही प्रतिक्रिया देने में विफल रहा। | बैकऑफ़ के साथ दोबारा कोशिश करें। |
| `upstream_stream_failure` | `502` | बिना स्ट्रीमिंग वाला अनुरोध, जिसका प्रदाता जनरेट करना शुरू करने के बाद विफल हो गया। कोई आंशिक आउटपुट नहीं लौटाया जाता और अनुरोध का शुल्क नहीं लिया जाता। | दोबारा कोशिश करें। |
| `provider_payment_required` | `502` | प्रदाता के पास Phaseo के खाते पर ध्यान देने की ज़रूरत है। | बाद में दोबारा कोशिश करें या इसकी रिपोर्ट करें। |

## सही त्रुटियों पर दोबारा कोशिश करें

| स्थिति | दोबारा कोशिश करें? |
| --- | --- |
| `429` को छोड़कर `400`–`499` | नहीं। पहले अनुरोध, कुंजी या पहुंच ठीक करें। |
| `429` | हां। `Retry-After` (सेकंड या HTTP तारीख) का इंतज़ार करें, वरना jitter के साथ exponential backoff इस्तेमाल करें। `Retry-After` के बिना `key_limit_exceeded` त्रुटि अपने आप रीसेट नहीं होती, इसलिए उस पर दोबारा कोशिश न करें। |
| `500`–`599` | सिर्फ़ तब जब ऑपरेशन दोहराना सुरक्षित हो। अस्पष्ट सबमिशन ने पहले ही कोई जॉब या शुल्क बना दिया हो सकता है; उसे दोबारा सबमिट करने के बजाय स्वीकृत जॉब खोजें। |

प्रयासों की एक सीमा और एक कुल समय-सीमा तय करें। रेट लिमिट हेडर के लिए [अनुरोध सीमाएँ](./limits.mdx) देखें।

<span id="when-a-provider-fails"></span>
## जब कोई प्रदाता विफल हो

जब Phaseo किसी प्रदाता तक पहुंचा और अनुरोध फिर भी विफल हुआ, तो `provider_failure_diagnostics` में एक `category`, एक `hint` और `provider` होता है। श्रेणियां:

| `category` | अर्थ |
| --- | --- |
| `credentials_not_configured` | इस रूट के लिए कोई क्रेडेंशियल सेट नहीं है। |
| `credentials_invalid_or_forbidden` | क्रेडेंशियल अस्वीकार कर दिया गया। |
| `provider_access_missing` | प्रदाता खाते के पास मॉडल या फ़ीचर की पहुंच नहीं है। |
| `region_or_project_restriction` | प्रदाता ने क्षेत्र या प्रोजेक्ट के कारण मना किया। |
| `model_unavailable_for_endpoint` | प्रदाता इस एंडपॉइंट पर मॉडल उपलब्ध नहीं कराता। |
| `rate_limited` | प्रदाता ने अनुरोध को रेट लिमिट किया। |
| `server_error` | प्रदाता विफल हुआ या उसका समय समाप्त हो गया। |

<span id="when-a-model-or-endpoint-is-not-available"></span>
## जब कोई मॉडल या एंडपॉइंट उपलब्ध न हो

`unsupported_model_or_endpoint` त्रुटियों में `provider_candidate_diagnostics`, `provider_enablement`, `missing_pricing_providers` और `routing_diagnostics` हो सकते हैं। ये मिलकर बताते हैं कि मॉडल अभी सक्रिय नहीं है, मॉडल एंडपॉइंट का समर्थन नहीं करता, कीमत मौजूद नहीं है, या रोलआउट प्रतिबंध है।

| फ़ील्ड | अर्थ |
| --- | --- |
| `provider_candidate_diagnostics.totalProviders` | एंडपॉइंट फ़िल्टरिंग से पहले मॉडल के लिए ज्ञात प्रदाता। |
| `provider_candidate_diagnostics.supportsEndpointCount` | मांगे गए एंडपॉइंट का समर्थन करने वाले प्रदाता। |
| `provider_candidate_diagnostics.candidateCount` | एडेप्टर जांच के बाद बचे प्रदाता। |
| `provider_candidate_diagnostics.droppedUnsupportedEndpoint` | एंडपॉइंट का समर्थन न करने के कारण हटाए गए प्रदाता। |
| `provider_candidate_diagnostics.droppedMissingAdapter` | प्रदाता और एंडपॉइंट के जोड़े जिन्हें इसलिए हटाया गया क्योंकि Phaseo के पास अभी उस एंडपॉइंट का एडेप्टर नहीं है। |
| `provider_enablement.capability` | लागू की जा रही क्षमता, जैसे `video_generation`। |
| `provider_enablement.providersBefore`, `providersAfter` | क्षमता फ़िल्टरिंग से पहले और बाद के प्रदाता। |
| `provider_enablement.dropped[].reason` | किसी प्रदाता को क्यों हटाया गया, जैसे `pricing_missing`। |
| `routing_diagnostics.filterStages[].stage` | रूटिंग का एक चरण, जैसे क्षमता, रोलआउट या रूटिंग-स्थिति फ़िल्टरिंग। |
| `routing_diagnostics.filterStages[].beforeCount`, `afterCount` | उस चरण से पहले और बाद के प्रदाता। |
| `routing_diagnostics.filterStages[].droppedProviders[].reason` | उस चरण पर किसी प्रदाता को क्यों हटाया गया। |

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
```

<span id="when-a-model-is-retired"></span>
## जब कोई मॉडल सेवानिवृत्त हो

सेवानिवृत्त मॉडल तब तक दिया जाता है जब तक कोई प्रदाता उसे देता है। जब कोई नहीं देता, तो अनुरोध `410` और `model_retired` के साथ विफल होते हैं:

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

`model` वह मॉडल है जो आपने मांगा, `retired_at` वह समय है जब इसे सेवानिवृत्त किया गया (या `null`), और `replacement_model` सुझाया गया विकल्प है (या `null`)।

दोबारा कोशिश करने से मदद नहीं मिलती; मॉडल ID बदलें। माइग्रेशन के दौरान इन अनुरोधों को चालू रखने के लिए, विकल्प को अनुरोध की `models` सूची में जोड़ें या वर्कस्पेस के लिए सेवानिवृत्त मॉडल रूटिंग चालू करें। [मॉडल का पदावनयन और सेवानिवृत्ति](../guides/model-retirement.mdx) देखें।

## स्ट्रीम के दौरान त्रुटियां

अगर कोई अनुरोध स्ट्रीमिंग शुरू होने से पहले विफल होता है, तो आपको ऊपर वाली JSON त्रुटि बॉडी मिलती है। अगर वह स्ट्रीम के बीच में विफल होता है, तो स्ट्रीम सामान्य समाप्ति के बजाय एंडपॉइंट के विफलता इवेंट के साथ खत्म होती है:

| एंडपॉइंट | विफलता इवेंट |
| --- | --- |
| Chat Completions | एक `error` फ़्रेम |
| Responses | `response.failed` (या `error`) |
| Messages | एक `error` इवेंट |

आंशिक आउटपुट को अधूरा मानें और दोबारा कोशिश का विकल्प दें। Chat Completions के `error` फ़्रेम में वही त्रुटि ऑब्जेक्ट होता है, जिसमें `error.type` कोड से तय होता है:

```json
{
  "object": "error",
  "message": "The upstream stream ended before the response completed.",
  "code": "upstream_stream_failure",
  "error": {
    "code": "upstream_stream_failure",
    "message": "The upstream stream ended before the response completed.",
    "type": "server_error",
    "param": null
  }
}
```

बिना स्ट्रीमिंग वाला अनुरोध, जिसका प्रदाता बीच में विफल हो जाता है, आंशिक प्रतिक्रिया नहीं, बल्कि `upstream_stream_failure` के साथ `502` लौटाता है। [स्ट्रीमिंग](../guides/streaming.mdx) देखें।

<span id="debug-a-request"></span>
## किसी अनुरोध को डीबग करें

रूटिंग ट्रेस और अपस्ट्रीम पेलोड पाने के लिए एक `debug` ऑब्जेक्ट भेजें:

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

`trace_level` `summary` या `full` होता है। डीबग पेलोड में आपके अनुरोध की सामग्री हो सकती है, इसलिए इन्हें सिर्फ़ डेवलपमेंट या कड़े नियंत्रण वाले वातावरण में इस्तेमाल करें। [`debug`](./parameters.mdx#parameter-debug) देखें।

जब कोई अनुरोध विफल हो, तो घटनाओं के लिए [स्टेटस पेज](https://status.phaseo.app) देखें, अपने पेलोड की तुलना एंडपॉइंट के संदर्भ पेज से करें, और एंडपॉइंट और मॉडल के साथ `generation_id` लॉग करें। [सपोर्ट](https://phaseo.app/help) से संपर्क करते समय `generation_id` शामिल करें।

<Visibility for="agents">
एजेंट के लिए त्रुटि-संभाल नियम, इस पेज का सारांश:

- संदेश के टेक्स्ट पर नहीं, बल्कि `error.code` (जो शीर्ष-स्तर `code` के रूप में भी लौटता है), `error.type` और `status_code` पर ब्रांच करें। हर विफलता के साथ `generation_id` लॉग करें।
- `400`, `401`, `403` और `404`: पहले अनुरोध, कुंजी या पहुंच ठीक करें। वही अनुरोध बिना बदले दोबारा न भेजें।
- `model_retired` के साथ `410`: जब `replacement_model` `null` न हो, तो उस पर जाएं; वरना `GET /v1/models` से नया मॉडल चुनें।
- `429`: जब `Retry-After` मौजूद हो (सेकंड या HTTP तारीख), तो दोबारा कोशिश से पहले उतना इंतज़ार करें; वरना jitter वाला exponential backoff इस्तेमाल करें। `Retry-After` के बिना `key_limit_exceeded` त्रुटि अपने आप रीसेट नहीं होती, इसलिए उस पर दोबारा कोशिश न करें।
- `500` से `599`: सिर्फ़ तब दोबारा कोशिश करें जब कॉल दोहराना सुरक्षित हो, प्रयासों की सीमा, कुल समय-सीमा और jitter वाले exponential backoff के साथ। एसिंक जॉब के लिए, उसे दोबारा सबमिट करने के बजाय स्वीकृत जॉब खोजें।
- डीबग पेलोड को संवेदनशील मानें और स्थायी लॉग में लिखने से पहले उन्हें रिडैक्ट करें।
- परखे हुए retry और error-parsing पैटर्न के लिए `phaseo-gateway` skill इंस्टॉल करें: `npx skills add https://phaseo.app/docs --skill phaseo-gateway`।
</Visibility>
