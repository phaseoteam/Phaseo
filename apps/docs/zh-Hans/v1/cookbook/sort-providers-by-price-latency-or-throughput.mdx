在单个请求上设置 `provider.sort`，按 `price`、`latency` 或 `throughput` 对同一模型的提供商排序，而不是使用默认的均衡排序。完成后，你会得到用你所用语言编写的请求，并能在响应和日志中看到排序选中了哪个提供商。

这些请求结构可直接用于生产环境。[选择提供商的排序方式](../guides/routing-and-fallbacks#choose-how-providers-are-ranked)介绍了工作区默认设置、`routing.mode`，以及 `:cheap`、`:fast` 和 `:nitro` 模型后缀。

| `sort` | 适用于 |
| --- | --- |
| `price` | 批处理和后台任务，成本比尾部延迟更重要时 |
| `latency` | 聊天、copilot 和需要人工参与的工具 |
| `throughput` | 输出较长的大批量生成和数据回填 |

`meta: true` 会添加 `meta.routing.selected_provider`，即排序选中的提供商。

## 每种排序看重什么

排序改变的是提供商得分的权重；它不会去掉其他信号，因此不可靠的廉价提供商仍可能落选：

| 排序 | 价格 | 成功率 | 中位延迟 | 尾部延迟 | 吞吐量 |
| --- | --- | --- | --- | --- | --- |
| `price` | 0.40 | 0.25 | 0.15 | 0.10 | 0.05 |
| `latency` | 0 | 0.25 | 0.55 | 0.15 | 0.02 |
| `throughput` | 0 | 0.20 | 0.20 | 0.10 | 0.40 |

延迟和吞吐量来自 Phaseo 对每个提供商的最新测量。

## 在批准的范围内排序

当候选范围里只剩你能接受的提供商时，排序效果最好。添加 `only`，排序就会在该范围内进行：

```json
{
  "model": "anthropic/claude-sonnet-5.5",
  "input": "Summarize the incident in one sentence.",
  "provider": {
    "only": ["anthropic", "google-vertex"],
    "sort": "latency"
  }
}
```

[固定或忽略提供商](./pin-or-ignore-providers-per-request)介绍了 `only`、`order` 和 `ignore`。

## 检查排序结果

在**设置 → 用量 → 日志**中打开该请求，展开**路由可观测性**。其中列出了参与考虑的提供商、它们的排名，以及每个得分的因素和权重，你可以据此确认排序是否符合预期。要把同样的排序应用到多个调用方，请把它放进[预设](./preset-rollout-and-routing-debug)。
