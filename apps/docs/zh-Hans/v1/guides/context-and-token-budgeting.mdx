为每类请求设定输入目标和输出上限，然后用实际用量对照检查。你发送或接收的每个 token 都会增加延迟和成本，而输出上限过小会截断回答。

## 请求中哪些部分会被计入

| 部分 | 计为 | 需要留意 |
| --- | --- | --- |
| 系统和开发者指令 | 输入 | 每个请求都重复发送的冗长指令。请用[提示缓存](./prompt-caching.mdx)缓存它们。 |
| 用户输入 | 输入 | 不受限制的粘贴内容和上传文件。 |
| 检索到的上下文（文档、搜索结果、工具输出） | 输入 | 相关性低的段落，它们会增加 token 并稀释回答。 |
| 工具 schema 和函数定义 | 输入 | 已声明的工具无论模型是否调用，都会计入输入。 |
| 推理 | 输出 | 推理模型会在作答前消耗一部分输出上限。 |
| 回答 | 输出 | 会截断回答或结构化输出的上限。 |

## 推理用尽输出上限时

推理模型可能在给出回答之前就用尽整个输出上限。此时响应仍是 HTTP `200`，包含已生成的推理内容，不会虚构回答：

| 端点 | 你会得到 |
| --- | --- |
| Chat Completions | `reasoning_content`，以及 `finish_reason: "length"` |
| Responses | 推理输出项，以及 `status: "incomplete"` |

正常结束时仍为 `stop`（Chat Completions）或 `completed`（Responses）。如果经常遇到上述情况，请提高输出上限或降低推理强度。

## 为每条路由设定预算

1. 为每类请求（例如搜索回答或长篇草稿）设定最大输入大小。不要把同一个上限照搬到所有端点。
2. 为该类请求应当产生的最长回答预留输出空间。
3. 发送前裁剪或总结大段上下文，从最不可能有用的段落开始。
4. 检查输出是否被截断，例如 `finish_reason: "length"` 或不完整的 JSON；出现时，留出更多空间后重试。
5. 持续跟踪每个响应 `usage` 中的 token 数，并随着提示词的变化调整上限。

输出上限与采样如何相互作用，请参阅[推理参数](./inference-parameters.mdx)。
