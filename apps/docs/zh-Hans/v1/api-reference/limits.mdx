请求可能被所选提供商或适用的工作区或密钥策略限流。路由和回退可以减少提供商故障，但请求仍可能返回 `429`。

## 网关限制

每个工作区中的每位用户都有每分钟请求配额，按滚动一分钟计算。同一用户创建的 API 密钥共享此配额。OAuth 请求按已认证用户计数。没有所有者的密钥共享工作区配额。

配额取决于工作区的账户状况，并会随着工作区逐步稳定而自动提高：

| 工作区 | 每分钟请求数 |
| --- | --- |
| 新工作区 | 10 |
| 创建至少 7 天，或已完成付费充值 | 25 |
| 创建至少 30 天，且扣除退款后的付费充值至少 50 美元 | 60 |
| 按发票结算 | 120 |

工作区会获得其符合条件的最高配额。更改会在几分钟内生效。

免费模型路由还受**每个 UTC 日 1500 个请求**的配额限制，由同一用户和工作区的所有免费模型共享。付费模型请求不消耗此每日配额。已获准的免费请求即使随后发生提供商故障，也会计数；同一请求内的回退尝试只计一次。

这些限制在所有网关区域之间统一生效，并可针对特定用户和工作区提高。文件操作和作业状态轮询会消耗每分钟配额；管理端点不会。

网关配额耗尽时会返回 `429`，并通过 `Retry-After` 指定等待秒数。错误原因是 `customer_requests_per_minute` 或 `free_requests_per_day`。请等待指定时间后重试。配额检查暂时不可用时，网关会返回 `503` 并提供重试提示。

## 密钥限制和预算

达到 API 密钥的每日、每周或每月请求和支出上限，或工作区的[预算](./endpoint/budgets-list.mdx)时，会返回 `429` 和错误代码 `key_limit_exceeded`。响应正文中的 `reason`、`limit_window` 和 `reset_at` 字段说明触发的是哪个限制以及其周期何时重置。`Retry-After` 给出距离重置的秒数。如果限制不会自动重置（例如终身预算或被临时封禁的密钥），则不会返回该标头；此时请不要重试，而是提高工作区预算；如果是密钥上限，请提高该密钥的上限或改用其他密钥。

工作区所有者和管理员也可以在控制台的[设置 → 预算](https://phaseo.app/settings/budgets)中设置、更改和删除预算。该页面显示每项预算目前的支出、已用比例、本周期的预测以及重置时间。每日、每周和每月预算按 UTC 边界重置：午夜、周一 00:00 和每月 1 日。在 CLI 中使用 `phaseo budgets create|update|delete`。

部门预算通过 `/v1/department-budgets` API 管理。部门的支出计入的密钥和 OAuth 请求与下文的部门速率限制相同。部门用完每日、每周或每月预算后，计入该部门的 API 密钥请求会返回 `429`，错误代码为 `key_limit_exceeded`，原因为 `department_daily_cost_budget_reached`、`department_weekly_cost_budget_reached` 或 `department_monthly_cost_budget_reached`。响应正文中的 `department_id` 和 `department_name` 字段标明是哪个部门，`reset_at` 和 `Retry-After` 说明其预算何时重置。部门预算不会阻止批处理作业、实时会话和 OAuth 请求。如果预算检查短暂不可用，请求会被放行而不是被拒绝，因此部门可能会在短时间内超出预算。当预算用到约 80% 以及 100% 时，所有者和管理员会收到移动推送通知。这些提醒来自可能延迟最多一小时的用量数据，因此请求可能在 100% 提醒送达之前就被拒绝。

所有者和管理员也可以在[设置 → 预算](https://phaseo.app/settings/budgets)中管理部门预算，或使用 Terraform 提供程序的 `phaseo_department_budget` 资源。在 CLI 中使用 `phaseo department-budgets`。

[支出警报](../guides/spend-alerts.mdx)可以在达到这些限额之前发出警告。设置为拦截的支出规则会改为返回带有 `spend_rule_blocked` 错误代码的 `429`；它为尽力而为，在支出超过其限额几分钟后才开始，因此如需精确上限，请使用密钥限额和预算。

## 速率限制策略

工作区管理员可以通过 `/v1/rate-limits` 管理 API 创建命名的速率限制策略，并将其分配给 API 密钥、工作区成员、部门、防护规则，或作为每个最终用户的默认值。网关会按滚动的一分钟窗口分别执行策略的 `requests_per_minute` 和 `tokens_per_minute`：

- **密钥：**该密钥自己的配额。
- **成员：**由该成员的密钥和 OAuth 请求共享的一份配额。
- **部门：**计入该部门的所有请求共享的一份配额。关联到某个部门的密钥只计入该部门。其他密钥计入其创建者所属的所有部门，OAuth 请求计入其用户所属的所有部门。设置了部门覆盖的成员只计入覆盖指定的部门。若要让这些密钥和 OAuth 请求只计入此人的主要部门，请将工作区的部门归属设置为 primary：可在[设置 → 通知](https://phaseo.app/settings/notifications)中设置，也可在 `PATCH /v1/notifications/settings` 中使用 `spend.department_attribution`，或运行 `phaseo notifications settings update --department-attribution primary`。部门预算和支出规则使用同一设置。
- **防护规则：**防护规则覆盖的每个密钥（或 OAuth 用户）各有一份独立配额。
- **最终用户默认值：**每个最终用户各有一份独立配额，通过请求的 `user` 字段或 `X-Phaseo-User-Id` 请求头识别。没有最终用户 ID 的请求不受其限制。

所有者和管理员也可以在[设置 → 速率限制](https://phaseo.app/settings/rate-limits)中管理策略及其分配，或使用 Terraform 提供程序的 `phaseo_rate_limit_policy` 和 `phaseo_rate_limit_assignment` 资源。在 CLI 中使用 `phaseo rate-limits policies` 和 `phaseo rate-limits assignments`。

当多个策略同时适用时，每个策略都会计数，最先耗尽的策略会拒绝请求。策略限制在上述网关限制之外另行生效。策略变更约在一分钟内生效。在控制台或通过 SCIM 进行的部门成员变更最多可能需要约五分钟才能生效。

`tokens_per_minute` 会在每个请求完成后统计其输入和输出 token，包括消耗了 token 的流式请求和失败请求。某个额度在最近一分钟内的用量一旦达到上限，后续请求就会被拒绝，因此已在处理中的请求可能使用量超出上限。

被拒绝的请求返回 `429`，包含错误代码 `rate_limit_exceeded`、原因 `policy_requests_per_minute` 或 `policy_tokens_per_minute`、`policy_id` 和 `limit_scope`（`key`、`member`、`department`、`guardrail` 或 `end_user`），以及以秒为单位的 `Retry-After`。适用策略的请求的响应会包含最严格的请求数限制的 `x-ratelimit-limit-requests`、`x-ratelimit-remaining-requests` 和 `x-ratelimit-reset-requests`（例如 `60s`），以及最严格的 token 限制的 `x-ratelimit-limit-tokens`、`x-ratelimit-remaining-tokens` 和 `x-ratelimit-reset-tokens`。被拒绝的请求只包含导致拒绝的那个限制的响应头。计数在后台进行，因此 `remaining` 为近似值，且 token 响应头尚未包含当前请求本身的用量。同一请求内的提供商回退只计一次，响应缓存命中不计数。

`concurrent_requests` 限制可同时处理的请求数量。请求从被接受起占用一个名额，直到其响应完全发送完毕（流式响应则到整个流结束），同一请求内的提供商和模型回退共享这个名额。所有名额都被占用时，请求会被拒绝，原因为 `policy_concurrent_requests`，并附带 `Retry-After: 1`。检查并发限制需要等待策略的计数器，因此会给其覆盖的请求增加少量延迟。释放丢失的名额会在 15 分钟后自动释放。批处理和实时会话不受此限制，视频生成只在启动它的请求处理期间占用名额。

默认情况下，如果无法检查策略的限制，请求会被放行。设置 `fail_closed` 可使策略变为严格模式。严格策略的请求数和令牌限制会在请求发送前检查，而不是在后台进行，因此结果精确，但会增加延迟；如果两秒内无法完成检查，请求会被拒绝，原因为 `policy_unavailable`。因并发和 `policy_unavailable` 被拒绝的请求不带 `x-ratelimit-*` 响应头。

## 提供商限制

BYOK 请求使用你的提供商账户限制。托管请求使用提供商的共享容量；该容量并非单个工作区的专属配额。

当路由到的提供商提供 `Retry-After` 值时，Phaseo 会验证并转发该值。BYOK 响应还可能包含 `X-Phaseo-Upstream-RateLimit-*` 标头。这些配额标头描述的是提供商的共享容量，因此托管请求会省略这些标头。其他上游标头不会被转发。

## 处理被限流的请求

1. 检查[错误代码](./errors.mdx)，区分提供商的临时限流与需要更改配置的策略或预算限制。
2. 如果存在 `Retry-After`，请遵循其要求。该值可能是以秒为单位的延迟，也可能是 HTTP 日期；在安排重试前验证该值。
3. 否则，使用带随机抖动和最大延迟的指数退避。
4. 同时限制重试次数和总体截止时间。取消已放弃的任务，并在重试前释放每个失败响应的响应体。
5. 如果限流持续，请降低并发量。

不要自动重试结果不明确的任务提交，也不要重复执行已完成的工具操作。即使客户端未收到响应，请求也可能已到达提供商；重试可能导致重复处理和重复收费。对于已受理的视频或批处理任务，请使用其状态端点，而不要重新提交。

## 监控限流

按端点和模型跟踪 `429` 的发生率，并在请求日志中检查回退频率。将应用日志与[路由设置](../guides/routing-and-fallbacks.mdx)以及 BYOK 流量的提供商账户配额进行对比。

有关工作区的支出和访问控制，请参阅[预算](./endpoint/budgets-list.mdx)和[防护规则](./endpoint/guardrails.mdx)。

面向智能体的速率限制规则（本页摘要）：

- Gateway 配额会返回 `429`，原因为 `customer_requests_per_minute` 或 `free_requests_per_day`；请等待 `Retry-After` 指定的秒数。如果配额检查不可用，Gateway 会返回带有重试指引的 `503`。

- 已用完的部门预算会返回带有 `key_limit_exceeded`、原因 `department_<interval>_cost_budget_reached`、`department_id`、`department_name` 和 `reset_at` 的 `429`；请等待 `Retry-After` 指定的秒数或提高预算。部门预算不会阻止批处理、实时和 OAuth 请求。如果预算检查不可用，请求会被放行。
- 拦截型支出规则返回带 `spend_rule_blocked` 的 `429`；请等待 `Retry-After`，或请所有者或管理员解除拦截。`x-phaseo-spend-warning` 表示可能即将拦截。
- 工作区速率限制策略会返回带有 `rate_limit_exceeded`、`policy_id` 和 `limit_scope` 的 `429`。`x-ratelimit-remaining-requests` 是近似值。
- `Retry-After` 可以是秒数或 HTTP 日期；安排重试前先校验该值。不要重新提交结果不明确的视频或批处理任务，而应查询其状态。
