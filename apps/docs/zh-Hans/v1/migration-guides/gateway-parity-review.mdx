在规划网关切换前，请先完成这项检查。即使两个平台都接受兼容 OpenAI 的请求，某些行为仍可能发生变化。

## 1. 梳理集成边界

记录当前网关出现的所有位置：

- 基础 URL 和 API 密钥环境变量
- SDK 初始化和自定义请求头
- 模型 ID 和回退模型
- 提供商顺序、允许列表和隐私要求
- 流式传输、工具调用和结构化输出代码
- 批处理任务、文件、Webhook 和异步状态轮询
- 请求归因以及用户或会话元数据

将此清单与发布计划放在一起，方便评审人员确认迁移后没有遗留隐藏的第二套配置路径。

## 2. 为每项能力分类

为每种生产环境行为指定一个状态：

| 状态 | 含义 |
| --- | --- |
| 保持不变 | 已验证使用相同的请求字段和响应行为。 |
| 已映射 | Phaseo 通过不同的字段或配置提供相同结果。 |
| 需适配 | 兼容层会转换请求或响应。 |
| 不支持 | 工作负载必须移除这项依赖，或继续使用当前路径。 |
| 未验证 | 可能已有支持，但仍缺少接近生产环境的证据。 |

使用[迁移功能检查清单](./feature-parity-matrix.mdx)覆盖核心请求、路由、归因、异步任务和运维。

## 3. 验证代表性流量

根据真实工作负载模式构建一个小型测试集，不要复制敏感的生产数据。

测试以下内容：

1. 对每个正在使用的端点发送一个普通请求。
2. 使用与生产相同的客户端路径测试流式传输。
3. 使用符合实际情况的 Schema 测试工具调用和结构化输出。
4. 测试每项提供商或隐私约束。
5. 测试无效密钥、无效模型、速率限制和提供商不可用错误。
6. 让批处理或异步任务运行到成功、失败和取消等终止状态。

比较输出质量、延迟、令牌用量、所选提供商和最终费用。记录每个结果的请求 ID，以便在 Gateway 用量页面中检查。

## 4. 保留归因和可观测性

如果应用归因请求头用于标识发起调用的应用，请予以保留。Phaseo 支持稳定的应用 ID、名称、URL 和类别；迁移时删除这些信息会增加比较费用和用量的难度。

支持的请求头和类别值见[应用归因](../guides/app-attribution.mdx)。

## 5. 采用可回退的方式发布

先从开发和内部流量开始。测试集通过后，再切换一小部分生产流量。结果稳定前，将回退操作限制为更改端点和凭据配置。

不要在首次切换时同时进行无关的提示词、模型或路由优化。确认网关边界后，再进行这些更改。
