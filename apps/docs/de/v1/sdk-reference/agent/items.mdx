Unterscheide nach dem Typ jedes gestreamten Events oder Items, um Text, Reasoning, Tool-Aufrufe und Fortschritt beim Eintreffen darzustellen, und baue später dieselbe Timeline aus dem gespeicherten Laufergebnis wieder auf. TypeScript liefert eine typisierte Item-Union; die anderen Sprachen liefern die rohen Events als Maps, Dicts oder Hashes.

## Eine gestreamte Timeline darstellen

<CodeGroup>

```typescript TypeScript
const stream = agent.stream({ input, client });

for await (const item of stream.getItemsStream()) {
  switch (item.type) {
    case "message":
      renderAssistantMessage(item.content);
      break;
    case "reasoning":
      renderReasoning(item.text);
      break;
    case "tool_call":
      renderToolCall(item.toolCallId, item.name, item.input);
      break;
    case "tool_result":
      renderToolResult(item.toolCallId, item.output);
      break;
    case "error":
      renderError(item.message);
      break;
    case "output":
      renderFinalOutput(item.value);
      break;
  }
}
```

## Item-Typen in TypeScript

`AgentItem<TOutput>` ist eine Discriminated Union, und TypeScript grenzt jedes Item anhand seines `type` ein:

| `type` | Wichtige Felder | Steht für |
| --- | --- | --- |
| `message` | `role` (immer `assistant`), `content` | Assistententext |
| `reasoning` | `text` | Vom Modell geliefertes Reasoning |
| `tool_call` | `toolCallId`, `name`, `input` | Einen vorgeschlagenen Tool-Aufruf |
| `tool_result` | `toolCallId`, `name`, `output` | Einen abgeschlossenen Tool-Aufruf |
| `error` | `message`, optional Tool-Details | Einen Anbieter- oder Tool-Fehler |
| `output` | `value` | Die geparste endgültige Ausgabe des Agenten |

Items, die aus Anbieterausgaben gebaut werden, behalten außerdem die ursprüngliche Nutzlast in `rawProviderItem`, für das seltene Feld, das die portablen Typen nicht enthalten. Baue Produktlogik auf den portablen Feldern auf, weil sich `rawProviderItem` je nach Anbieter unterscheidet.

## Event-Typen in den anderen Sprachen

Go, C#, PHP, Ruby und Java liefern dieselben Event-Typen. `item_stream()` in Python liefert Anbieter- und Laufzeit-Items als Dicts mit einem Schlüssel `type`.

| Event-Typ | Felder |
| --- | --- |
| `response.output_text.delta` | `delta` (String) |
| `response.reasoning.delta` | `delta` (String) |
| `response.item` | `item` (das Ausgabe-Item des Anbieters, untypisiert) |
| `tool.started`, `tool.completed`, `tool.failed`, `tool.preliminary_result` | `tool_call_id`, `tool_name`, dazu `output`, `error` oder `result` |

Wo die Felder liegen, unterscheidet sich je nach Sprache:

| Sprache | Form des Events |
| --- | --- |
| Python | Dicts; lies `item.get("type")` |
| Go | `AgentEvent` mit `Type` und einer `Details map[string]any` |
| C# | `AgentEvent` mit `Type` und einem `Details`-Dictionary mit `object?`-Werten |
| PHP | Flache Arrays. Lifecycle-Events enthalten `type`, `run_id`, `agent_id`, `timestamp` und `status`; Modell-Events enthalten `type` und die obigen Felder auf oberster Ebene. |
| Ruby | Flache Hashes mit Symbol-Schlüsseln (`:type`, `:delta` usw.), aufgebaut wie die Arrays in PHP |
| Java | `AgentEvent` mit `type()` und einer `details()`-Map mit `Object`-Werten |

Keine davon ist eine typisierte Union. Validiere daher die Felder, die deine Oberfläche nutzt, kapsle anbieterspezifisches Parsen hinter einem Adapter und behalte einen Fallback für unbekannte Typen. In Go, C# und Java tragen Modell-Stream-Events die Lauf-ID `"stream"`; die echte Lauf-ID bekommst du aus Lifecycle-Events. Die vollständige Liste der Lifecycle-Events steht unter [Lifecycle-Hooks](./lifecycle-hooks).

## Eine Timeline nach dem Lauf wieder aufbauen

Der Event-Verlauf bleibt nach dem Ende des Laufs lesbar, sodass ein Consumer darstellen kann, während ein anderer Events speichert, ohne zweite Modellanfrage. Für eine dauerhafte Timeline speicherst du das abgeschlossene Laufergebnis:

<Tabs>
<Tab title="TypeScript">

Das abgeschlossene Ergebnis enthält in `items` dieselben geordneten Items wie der Stream:

```typescript
const completed = await stream.getResult();

for (const item of completed.items) {
  saveTimelineItem(completed.run.id, item);
}
```

</Tab>
<Tab title="Python">

| Feld | Inhalt |
| --- | --- |
| `run` | Dauerhafter Status: `id`, `status`, `input`, `context`, `pause`, `stop_reason`, `error`, `usage` und `next_turn_params` |
| `steps` | Ein `AgentStepRecord` pro Modell-Turn, mit `request_id`, `native_response_id`, `provider`, `model`, `model_attempts`, `usage`, `finish_reason`, `warnings` und `tool_calls` |
| `messages` | Die gesamte Unterhaltung einschließlich der Tool-Ergebnisse |
| `output` | Die endgültige Ausgabe nach `parse_output` und `output_schema` |
| `usage` | Summen in einer `AgentUsageSummary`: Eingabe-, Ausgabe-, gecachte und Gesamt-Tokens sowie Kosten |

</Tab>
<Tab title="Go">

`result.Messages` enthält jede Modell- und Tool-Nachricht, und `result.Steps` enthält die Tool-Aufrufe, Request-ID, Anbieter, Modell und Nutzung jedes Turns.

</Tab>
