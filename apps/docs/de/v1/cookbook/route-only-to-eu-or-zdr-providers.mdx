Füge dem `provider`-Objekt einer Anfrage Anforderungen an Datenresidenz und <Tooltip tip="Zero Data Retention: Der Anbieter speichert weder Prompts noch Ausgaben.">ZDR</Tooltip> hinzu, und Phaseo entfernt jedes Anbieterangebot, das sie nicht erfüllt, bevor es die übrigen ordnet. Am Ende läuft ein Workflow nur auf EU- oder ZDR-fähigen Anbietern, ohne dass du die Richtlinie für den ganzen Workspace änderst.

Die Anfrage ist produktionsreif. Erfüllt kein Anbieter des Modells alle Anforderungen, schlägt die Anfrage fehl, bevor ein Anbieter aufgerufen wird. Prüfe deshalb zuerst die Verfügbarkeit.

| Feld | Behält nur Anbieter, die |
| --- | --- |
| `required_execution_region: "eu"` | Das Modell in der EU ausführen |
| `required_data_region: "eu"` | Prompt- und Antwortdaten in der EU verarbeiten |
| `require_zero_data_retention: true` | Die Anforderungen an Zero Data Retention erfüllen |

## Eine eingeschränkte Anfrage senden

<Steps>
<Step title="Prüfen, ob ein Anbieter infrage kommt">

Auf der Seite des Modells zeigen die Anbieterkarten regionale Angebote wie **OpenAI EU** oder **Google Vertex EU**, die ZDR-Unterstützung sowie die Hinweise und Quellen zur Datenrichtlinie jedes Anbieters. Für die EU kannst du auch auflisten, was das EU-Gateway bedient:

```bash
curl https://eu.api.phaseo.app/v1/models \
  -H "Authorization: Bearer $PHASEO_API_KEY"
```

</Step>
<Step title="Nur die nötigen Anforderungen hinzufügen">

Jede Anforderung verkleinert die Auswahl, sodass die Anfrage zu einem teureren regionalen Angebot geroutet werden kann oder gar kein Anbieter übrig bleibt. Sende nur, was deine Richtlinie verlangt:

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-5.6-luna",
    "input": "Summarize the ticket in one line.",
    "provider": {
      "required_execution_region": "eu",
      "required_data_region": "eu"
    },
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "openai/gpt-5.6-luna",
  input: "Summarize the ticket in one line.",
  provider: {
    required_execution_region: "eu",
    required_data_region: "eu",
  },
  meta: true,
});

console.log(response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "openai/gpt-5.6-luna",
        "input": "Summarize the ticket in one line.",
        "provider": {
            "required_execution_region": "eu",
            "required_data_region": "eu",
        },
        "meta": True,
    }
)

print(response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

Um zusätzlich ZDR zu verlangen, füge `"require_zero_data_retention": true` hinzu. Mit allen drei braucht ein Modell mindestens einen EU-Anbieter, der auch ZDR erfüllt.

</Step>
<Step title="Prüfen, wo sie lief">

`meta.routing.selected_provider` nennt den Anbieter, der sie bedient hat, zum Beispiel `openai-eu`. Die Anfrage unter **Einstellungen → Nutzung → Protokolle** hält die geforderten Regionen und den gewählten Anbieter fest.

</Step>
</Steps>

## Anfragefelder, EU-Gateway oder Workspace-Einstellungen wählen

| Verwenden | Wann |
| --- | --- |
| Diese Anfragefelder auf `api.phaseo.app` | Die Regel gilt für einen Workflow, einen Kunden oder eine Anfrage. Alle Endpunkte und Funktionen bleiben verfügbar. |
| [`eu.api.phaseo.app`](../guides/regional-routing) | Jede Textanfrage eines Dienstes muss in der EU bleiben. Der Hostname erzwingt die Region und lehnt außerdem Medieneingaben, Phaseo-Server-Tools und vom Anbieter gehostete Tools ab. Wird dort `required_execution_region` oder `required_data_region` für eine andere Region gesendet, kommt `400 validation_error` mit dem Grund `deployment_region_conflict` zurück. |
| **Einstellungen → Datenschutz** | Die Regel gilt für jede Anfrage im Workspace. |

Regionales Routing schränkt ein, welche Anbieter den Modellaufruf verarbeiten. Es ist noch keine durchgängige Garantie für Datenresidenz; [Was außerhalb der Region bleibt](../guides/regional-routing#what-stays-outside-the-region) listet die gemeinsam genutzten Systeme auf. Um Anbieter ohne Residenzregel einzuschränken, siehe [Anbieter festlegen oder ignorieren](./pin-or-ignore-providers-per-request).
