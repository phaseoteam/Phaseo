Prüfe die [Statusseite](https://status.phaseo.app) und `GET /v1/health`, um zu sehen, ob Phaseo fehlerfrei läuft, `GET /v1/models`, um zu sehen, ob ein Modell gerade routbar ist, und deinen eigenen Testlauf, um zu sehen, ob eine Route dein Zuverlässigkeitsziel erfüllt.

## Aktuellen Servicestatus prüfen

1. Öffne die [Phaseo-Statusseite](https://status.phaseo.app) für aktuelle Vorfälle und den Vorfallverlauf.
2. Rufe `GET /v1/health` für eine minimale Gateway-Statusprüfung auf.
3. Wenn eine einzelne Anfrage fehlgeschlagen ist, bewahre ihre Request-ID auf und prüfe ihren Aktivitäts- oder Generierungsdatensatz, bevor du annimmst, dass der ganze Dienst ausgefallen ist.

```bash
curl https://api.phaseo.app/v1/health
```

```json
{
  "status": "ok"
}
```

<Note>
Die öffentliche Statusseite meldet den Servicestatus. Phaseo sichert derzeit keine vertragliche öffentliche Verfügbarkeits-SLA zu.
</Note>

## Prüfen, ob ein Modell routbar ist

Der Phaseo-Katalog listet mehr Modelle, als das Gateway routen kann: Ein Katalogeintrag bedeutet, dass Phaseo das Modell erfasst, nicht dass eine öffentliche Route existiert. `GET /v1/models` gibt standardmäßig nur aktuell routbare Modelle zurück:

```bash
curl https://api.phaseo.app/v1/models \
  -H "Authorization: Bearer $PHASEO_API_KEY"
```

Füge `availability=all` hinzu, um auch demnächst verfügbare und inaktive Zuordnungen zu sehen. Sende Produktions-Traffic nur an eine Anbieterzeile, wenn ihr `availability_status` `active` und `is_active_gateway` `true` ist. Unter [Anbieter- und Phaseo-Status](../guides/provider-statuses.mdx) erfährst du, was die Statussymbole auf Modellseiten bedeuten.

| Status | Bedeutung |
| --- | --- |
| `active` | Mindestens eine öffentliche Gateway-Route ist jetzt verfügbar. |
| `coming_soon` | Phaseo erfasst eine geplante oder Vorschau-Route, sie ist aber nicht öffentlich routbar. |
| `inactive` | Eine bekannte Route ist deaktiviert, nicht verfügbar, abgelaufen oder aus anderen Gründen nicht routbar. |
| `not_listed` | Für das Modell ist derzeit keine Gateway-Anbieterzuordnung aufgeführt. |

`active` garantiert weder Betriebszeit noch Zugang in jeder Region noch dieselben Geschäftsbedingungen für jeden Workspace.

## Leistungsmetriken interpretieren

Die Leistungsdaten von Phaseo fassen echte Anfragen zusammen, die über das Gateway geroutet wurden; sie sind kein kontrollierter Labor-Benchmark.

| Metrik | Definition |
| --- | --- |
| Gateway-TTFT | Vom Start der Gateway-Anfrage bis zur ersten generierten Ausgabe mit Inhalt. |
| Anbieter-TTFT | Von der Weiterleitung an den Anbieter bis zur ersten generierten Ausgabe mit Inhalt. |
| Anbieterdauer | Von der Weiterleitung an den Anbieter bis zur abschließenden Antwort. |
| Gateway-E2E | Vom Start der Gateway-Anfrage bis zum Abschluss. |
| Phaseo-Overhead | Die nicht negative Differenz zwischen Gateway-E2E und Anbieterdauer. |
| Effektiver Durchsatz | Alle Ausgabetokens geteilt durch die gesamte Anbieterdauer. |
| Ausgabegeschwindigkeit | Ausgabetokens nach dem ersten geteilt durch die Anbieterzeit nach TTFT. |

TTFT und Ausgabegeschwindigkeit erfordern eine Streaming-Antwort mit einer ersten Ausgabe, die Inhalt enthält. Eine Anfrage ohne Streaming trägt trotzdem zu Dauer und effektivem Durchsatz bei, aber nicht zu TTFT.

Lies jede Metrik zusammen mit ihrem Zeitfenster, ihrer Route, Region, ihrem Streaming-Modus und Perzentil. Anbieterauslastung, Prompt-Länge, Ausgabelänge, Wiederholungen und Netzwerkbedingungen verändern das Ergebnis.

Die vollständigen Definitionen findest du unter [Preise und Leistung](../exploring/pricing-performance) und [Wie Phaseo Latenz und Durchsatz misst](https://phaseo.app/how-phaseo-measures-latency-throughput).

## Mit deiner Arbeitslast validieren

Öffentliche Metriken zeigen die Richtung; sie beweisen nicht, dass eine Route dein Produktionsziel erfüllt. Führe vor einem Rollout einen kleinen, reproduzierbaren Test durch:

1. Entferne sensible Produktionsdaten und behalte eine repräsentative Prompt-Mischung bei.
2. Halte Modell-ID, Endpunkt, Anbietereinschränkungen, Region, Streaming-Modus und Parallelität fest.
3. Führe genügend Wiederholungen aus, um Verteilungen statt einer einzelnen Anfrage zu vergleichen.
4. Erfasse Erfolgsrate, Gateway-TTFT, Anbieterdauer, Gateway-E2E, Ausgabetokens und Endkosten.
5. Teste ungültige Schlüssel, ungültige Modelle, Ratenlimits und Fehler durch nicht verfügbare Anbieter.
6. Speichere Request-IDs und das genaue Zeitfenster, damit eine andere Person das Ergebnis reproduzieren kann.

Veröffentliche keinen Kundennamen, kein Zitat, kein Arbeitslastergebnis und keinen Zuverlässigkeitsprozentsatz ohne Erlaubnis und eine dokumentierte Methode.

## Fehlgeschlagene Anfrage untersuchen

1. Prüfe den [Servicestatus](https://status.phaseo.app).
2. Prüfe, ob das Modell weiterhin in der Standardantwort von [`GET /v1/models`](../api-reference/endpoint/models) erscheint, und prüfe seine [Endpunkte](../api-reference/endpoint/model-endpoints).
3. Schlage HTTP-Status und Fehlercode unter [Fehler und Debugging](../api-reference/errors) nach.
4. Wiederhole vorübergehende `429`- und `5xx`-Antworten mit begrenztem exponentiellem Backoff; siehe [Ratenlimits](../api-reference/limits.mdx).
5. Bewahre die Request-ID auf, wenn du den [Support](https://phaseo.app/help) kontaktierst.

Damit Anfragen weiter funktionieren, wenn ein Anbieter ausfällt, richte [Routing und Fallbacks](../guides/routing-and-fallbacks) ein.
