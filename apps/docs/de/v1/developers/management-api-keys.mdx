Erstelle einen Management-Schlüssel, um die Verwaltungs-APIs von Phaseo von deinen eigenen Servern aus aufzurufen: Guthaben, Aktivität, Workspaces, Schlüssel, Voreinstellungen, Einstellungen und Guardrails. Management-Schlüssel können keine Inferenzanfragen senden.

```bash
phaseo management-keys create --name <name> --template read-only --json
```

Oder erstelle einen im Dashboard unter **Einstellungen → Verwaltungsschlüssel**. Das Geheimnis wird nur einmal angezeigt, also speichere es in deinem Geheimnismanager. Sende es nur aus serverseitigem Code, an dieselbe Basis-URL wie das Gateway (`https://api.phaseo.app/v1`):

```http
Authorization: Bearer phaseo_v1_mk_<kid>_<secret>
```

## Management-Schlüssel, API-Schlüssel und OAuth-Tokens

| Zugangsdaten | Format | Verwendung | Begrenzt durch |
| --- | --- | --- | --- |
| Gateway-API-Schlüssel | `phaseo_v1_sk_<kid>_<secret>` | Modell- und Generierungsanfragen | Routing-Richtlinie, Budgets, Limits und zugewiesene Guardrails |
| Management-API-Schlüssel | `phaseo_v1_mk_<kid>_<secret>` | Verwaltungsanfragen | Seine Funktionen und deine Workspace-Rolle |
| OAuth-Zugriffstoken | | Verwaltung im Namen eines Nutzers | Die genehmigten OAuth-Bereiche und die Workspace-Rolle des Nutzers |

Management-Routen akzeptieren nur Management-Schlüssel (oder OAuth-Tokens); ein Gateway-API-Schlüssel kann sie nicht aufrufen.

[Guardrails](../cookbook/guardrails-for-api-keys.mdx) sind eine eigene Kontrolle: Sie gelten für Gateway-API-Schlüssel und steuern den Inferenz-Traffic, etwa Routing-Beschränkungen, Budgets, den Umgang mit Prompt-Injection und Regeln für vertrauliche Informationen. Die Funktionen eines Management-Schlüssels legen fest, welche Verwaltungs-APIs er aufrufen darf.

## Zugriffsstufe auswählen

Jede Vorlage wird beim Erstellen des Schlüssels in eine explizite Liste von Funktionen aufgelöst. Phaseo speichert nie einen Platzhalter wie `all`, daher erhält ein Schlüssel nie eine später hinzugefügte Berechtigung.

| Vorlage | `--template` | Gewährt |
| --- | --- | --- |
| **Read** | `read-only` | Jede aktuelle `*:read`-Funktion |
| **Write** | `read-write` | Jede aktuelle `*:read`- und `*:write`-Funktion, kein Löschen |
| **All** | `full-control` | Jede aktuelle Lese-, Schreib- und Löschfunktion |

Keine Vorlage enthält `billing:write`, womit Guthabenaufladungen gestartet werden; fordere es ausdrücklich mit `--scopes` an. Verwende **All** nur für vertrauenswürdige Verwaltungsautomatisierung.

Für eine kleinere Berechtigung übergibst du die benötigten Funktionen mit `--scopes scope_a,scope_b`:

| Bereich | Lesen | Schreiben | Löschen |
| --- | --- | --- | --- |
| Identität und Katalog | `me:read`, `models:read`, `providers:read`, `pricing:read` | | |
| Nutzung und Beobachtbarkeit | `credits:read`, `activity:read`, `analytics:read`, `generations:read`, `feedback:read` | `feedback:write` | |
| Abrechnung | | `billing:write` (nur auf Anforderung) | |
| Workspaces | `workspaces:read` | `workspaces:write` | `workspaces:delete` |
| Gateway-API-Schlüssel | `keys:read` | `keys:write` | `keys:delete` |
| Management-API-Schlüssel | `management_keys:read` | `management_keys:write` | `management_keys:delete` |
| Voreinstellungen | `presets:read` | `presets:write` | `presets:delete` |
| Einstellungen | `settings:read` | `settings:write` | |
| Anbieter-Zugangsdaten | `provider_credentials:read` | `provider_credentials:write` | `provider_credentials:delete` |
| Private Modelle | `private_models:read` | `private_models:write` | `private_models:delete` |
| Guardrails | `guardrails:read` | `guardrails:write` | `guardrails:delete` |
| Budgets | `budgets:read` | `budgets:write` | `budgets:delete` |
| Ratenlimits | `rate_limits:read` | `rate_limits:write` | `rate_limits:delete` |
| Klassifikatoren | `classifiers:read` | `classifiers:write` | `classifiers:delete` |
| Ausgabenregeln | `spend_rules:read` | `spend_rules:write` | `spend_rules:delete` |
| OAuth-Clients | `oauth_clients:read` | `oauth_clients:write` | `oauth_clients:delete` |

## Funktionen setzen Workspace-Rollen nicht außer Kraft

Phaseo prüft bei jedem Aufruf zwei Dinge: dass der Schlüssel die Funktion hat und dass der Schlüssel oder OAuth-Nutzer zum Workspace gehört und die Rolle besitzt, die die Aktion erfordert. `keys:write` erlaubt zum Beispiel die Schlüsselverwaltung, aber die Rollenprüfung entscheidet weiterhin, ob der Aufrufer in diesem Workspace Schlüssel verwalten darf. Ein Schlüssel kann eine Funktion nicht nutzen, um einen anderen Workspace zu erreichen oder Eigentümer- und Administratorprüfungen zu umgehen.

## Schlüssel sicher aufbewahren

- Halte Management-Schlüssel aus Browsern, Desktop-Protokollen, der Versionsverwaltung und Chats heraus.
- Verwende einen Schlüssel pro Integration, mit der engsten Vorlage, die funktioniert.
- Lege ein Ablaufdatum fest, wenn die Integration keinen unbegrenzten Zugriff braucht.
- Pausiere oder lösche ungenutzte Schlüssel sofort.
- Rotiere einen offengelegten Schlüssel, bevor du weiter untersuchst.
