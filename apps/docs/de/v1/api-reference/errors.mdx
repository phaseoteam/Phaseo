Verzweige anhand von `error.code` und dem HTTP-Status, nicht anhand des Meldungstexts. Jeder Phaseo-Fehler hat auf jedem Endpunkt denselben JSON-Body, und sein `error`-Objekt (`code`, `message`, `type`, `param`) hat die Form, die OpenAI-kompatible SDKs lesen. Ihre Ausnahmen enthalten daher die Meldung von Phaseo.

```json
{
  "error": {
    "code": "upstream_error",
    "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
    "type": "server_error",
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "attempt_count": 1,
  "failed_providers": ["google-ai-studio"],
  "failed_statuses": [403],
  "provider_failure_diagnostics": {
    "category": "provider_access_missing",
    "hint": "The provider account appears not to have access to this model or feature yet. Verify account entitlements and provider-side access.",
    "provider": "google-ai-studio"
  },
  "upstream_error": {
    "code": "PERMISSION_DENIED",
    "message": "The caller does not have permission.",
    "description": null,
    "param": null
  },
  "failure_sample": [
    {
      "provider": "google-ai-studio",
      "type": "upstream_non_2xx",
      "status": 403,
      "upstream_error_code": "PERMISSION_DENIED",
      "upstream_error_message": "The caller does not have permission.",
      "upstream_error_description": null,
      "upstream_error_param": null,
      "upstream_payload_preview": "{\"error\":{\"status\":\"PERMISSION_DENIED\"}}",
      "retryable": false
    }
  ]
}
```

## Felder in jedem Fehler

| Feld | Inhalt |
| --- | --- |
| `error.code` | Maschinenlesbarer Code, zum Beispiel `validation_error`. Siehe [Fehlercodes](#error-codes). |
| `error.message` | Verständliche Erklärung. |
| `error.type` | Fehlerklasse, abgeleitet vom HTTP-Status. Siehe [Fehlertypen](#error-types). |
| `error.param` | Das Anfragefeld, das den Fehler verursacht hat, sofern Phaseo es kennt, sonst `null`. |
| `error.metadata` | Optional. Strukturierte Details wie `reason`, `failed_providers`, `failed_statuses` oder `retry_after_seconds`. Dieselben Werte stehen auch auf oberster Ebene. |
| `code` | Wie `error.code`. Ältere Antworten lieferten diesen String als `error`; lies `code`, wenn dein Client dort einen String erwartet. |
| `message`, `description` | Derselbe Text wie `error.message`. |
| `generation_id` | Anfrage-ID, die du protokollierst und an den Support weitergibst. |
| `status_code` | Der HTTP-Status. |
| `error_type` | `user` oder `system`. |
| `error_origin` | Woher das Problem kommt: vom Aufrufer (`user`), von Phaseo (`gateway`) oder von einem Anbieter (`upstream`). |
| `details` | Optional. Validierungsdetails, wenn der Anfrage-Body ungültig ist. |

Manche Fehler enthalten zusätzlichen Kontext:

| Feld | Wann es erscheint |
| --- | --- |
| `reason` | Ein genauerer Grund, zum Beispiel `all_candidates_failed` oder `no_provider_pricing`. |
| `provider_failure_diagnostics` | Ein Anbieter wurde erreicht und ist fehlgeschlagen. Siehe [Wenn ein Anbieter ausfällt](#when-a-provider-fails). |
| `upstream_error`, `failure_sample` | Eine nach bestem Bemühen erstellte Zusammenfassung des ersten Anbieterfehlers. |
| `failed_providers`, `failed_statuses`, `attempt_count` | Welche Anbieter versucht wurden und was sie zurückgegeben haben. |
| `provider_candidate_diagnostics`, `provider_enablement`, `routing_diagnostics` | Kein Anbieter konnte das Modell auf diesem Endpunkt bedienen. Siehe [Wenn ein Modell oder Endpunkt nicht verfügbar ist](#when-a-model-or-endpoint-is-not-available). |

<span id="error-types"></span>
## Fehlertypen

`error.type` folgt den [dokumentierten Fehlertypen](https://platform.openai.com/docs/guides/error-codes) von OpenAI und wird aus dem HTTP-Status abgeleitet:

| Status | `error.type` |
| --- | --- |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `408`, `500`, `502` und andere 5xx | `server_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `400`, `409`, `410`, `413`, `422` und andere 4xx | `invalid_request_error` |

Fehler auf `/v1/messages` verwenden denselben Body, sodass auch Anthropic-SDKs `error.type` und `error.message` finden.

<span id="error-codes"></span>
## Fehlercodes

| `error.code` | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `validation_error` | `400` | Ein Parameter oder der Anfrage-Body ist ungültig. `error.param` nennt das erste ungültige Feld. | Korrigiere die Anfrage. |
| `invalid_json` | `400` | Der Body ist kein gültiges JSON. | Korrigiere die Anfrage. |
| `model_required` | `400` | Die Anfrage enthält kein `model`. | Füge `model` hinzu. |
| `unsupported_model_or_endpoint` | `400` | Kein Anbieter kann dieses Modell auf diesem Endpunkt bedienen. | Siehe [unten](#when-a-model-or-endpoint-is-not-available). |
| `unsupported_modalities` | `400` | Keine Route akzeptiert die Eingabe- oder Ausgabetypen der Anfrage. | Wechsle das Modell oder ändere die Eingaben. |
| `byok_credentials_required` | `400` | Die Route läuft nur mit deinem eigenen Anbieterschlüssel. | Füge einen geeigneten [Anbieterschlüssel](./endpoint/provider-credentials-create.mdx) hinzu. |
| `upstream_error` | `400`, `413` oder `422` | Jeder Anbieter hat die Anfrage mit demselben Status abgelehnt (Grund `upstream_rejected_request`). | Korrigiere die Anfrage; ein erneuter Versuch hilft nicht. |
| `unauthorised` | `401` | Der Schlüssel fehlt oder ist ungültig. `reason` nennt den Grund. | Prüfe den `Authorization`-Header. |
| `insufficient_funds` | `402` | Der Workspace hat nicht genug Guthaben. | Lade Guthaben auf. |
| `pricing_not_configured` | `402` | Kein Anbieter für dieses Modell hat Preise hinterlegt (Grund `no_provider_pricing`). | Wähle ein anderes Modell. |
| `guardrail_blocked` | `403` | Eine Guardrail oder Zugriffsrichtlinie hat die Anfrage blockiert. | Ändere die Anfrage oder die Guardrail. |
| `model_region_unavailable` | `403` | Kein Anbieter stellt das Modell in der geforderten Region oder vom Standort des Aufrufers aus bereit. | Lockere die Regionsvorgabe oder wähle ein anderes Modell. |
| `not_found` | `404` | Der Endpunkt oder die Ressource existiert nicht. | Prüfe Pfad und ID. |
| `not_ready` | `409` | Die Ergebnisse eines Jobs sind noch nicht fertig. | Frage den Status des Jobs ab. |
| `model_retired` | `410` | Das Modell wurde eingestellt und kein Anbieter stellt es mehr bereit. | Wechsle zu `replacement_model`. Siehe [unten](#when-a-model-is-retired). |
| `payload_too_large` | `413` | Der Body ist größer, als der Endpunkt akzeptiert. `max_bytes` nennt das Limit. | Sende einen kleineren Body oder lade eine Datei hoch. |
| `key_limit_exceeded` | `429` | Ein Schlüssellimit, ein Budget oder das Gateway-Limit pro Minute wurde erreicht. | Siehe [Ratenlimits](./limits.mdx#key-limits-and-budgets). |
| `phaseo_free_model_limit_exceeded` | `429` | Das tägliche Kontingent für kostenlose Modelle (standardmäßig 1.500 Anfragen) ist aufgebraucht. | Beachte `Retry-After`, warte auf den Reset um 00:00 UTC oder nutze ein kostenpflichtiges Modell. |
| `rate_limit_exceeded` | `429` | Eine [Ratenlimit-Richtlinie](./limits.mdx#rate-limit-policies) des Workspace ist ausgeschöpft. `policy_id` und `limit_scope` identifizieren sie. | Beachte `Retry-After` oder bitte einen Admin, die Richtlinie zu ändern. |
| `spend_rule_blocked` | `429` | Eine [Ausgabenregel](../guides/spend-alerts.mdx) mit Blockierung ist aktiv. | Beachte `Retry-After` oder bitte einen Owner oder Admin, die Blockierung aufzuheben. |
| `upstream_error` | `429` | Jeder versuchte Anbieter hat die Anfrage gedrosselt. | Beachte `Retry-After`. BYOK-Anfragen enthalten zusätzlich `X-Phaseo-Upstream-RateLimit-*`-Header. |
| `provider_capacity_exhausted` | `429` | Jeder geeignete Anbieter ist ausgelastet (Grund `all_candidates_rate_limited`). | Beachte `Retry-After`, falls vorhanden, sonst warte mit Backoff. |
| `gateway_error` | `500` | In Phaseo ist etwas fehlgeschlagen. | Versuche es mit Backoff erneut. |
| `not_implemented_yet` | `501` | Der Vorgang ist noch nicht verfügbar. | Nicht erneut versuchen. |
| `upstream_error` | `502` | Der Anbieter hat nicht korrekt geantwortet. | Versuche es mit Backoff erneut. |
| `upstream_stream_failure` | `502` | Eine Anfrage ohne Streaming, deren Anbieter nach Beginn der Generierung ausgefallen ist. Es wird keine Teilausgabe zurückgegeben und die Anfrage wird nicht berechnet. | Versuche es erneut. |
| `provider_payment_required` | `502` | Das Konto von Phaseo beim Anbieter erfordert Aufmerksamkeit. | Versuche es später erneut oder melde es. |

## Die richtigen Fehler wiederholen

| Status | Erneut versuchen? |
| --- | --- |
| `400`–`499` außer `429` | Nein. Korrigiere zuerst die Anfrage, den Schlüssel oder den Zugriff. |
| `429` | Ja. Warte die in `Retry-After` angegebene Zeit ab (Sekunden oder ein HTTP-Datum), sonst nutze exponentielles Backoff mit Jitter. Ein `key_limit_exceeded`-Fehler ohne `Retry-After` setzt sich nicht von selbst zurück, also versuche ihn nicht erneut. |
| `500`–`599` | Nur wenn eine Wiederholung des Vorgangs sicher ist. Eine unklare Übermittlung hat möglicherweise schon einen Job oder eine Abbuchung erzeugt; schlage einen angenommenen Job nach, statt ihn erneut zu senden. |

Lege ein Versuchslimit und eine Gesamtfrist fest. Die Ratenlimit-Header findest du unter [Ratenlimits](./limits.mdx).

<span id="when-a-provider-fails"></span>
## Wenn ein Anbieter ausfällt

Wenn Phaseo einen Anbieter erreicht hat und die Anfrage trotzdem fehlgeschlagen ist, enthält `provider_failure_diagnostics` eine `category`, einen `hint` und den `provider`. Kategorien:

| `category` | Bedeutung |
| --- | --- |
| `credentials_not_configured` | Für diese Route sind keine Zugangsdaten eingerichtet. |
| `credentials_invalid_or_forbidden` | Die Zugangsdaten wurden abgelehnt. |
| `provider_access_missing` | Das Anbieterkonto hat keinen Zugriff auf das Modell oder die Funktion. |
| `region_or_project_restriction` | Der Anbieter hat wegen der Region oder des Projekts abgelehnt. |
| `model_unavailable_for_endpoint` | Der Anbieter stellt das Modell auf diesem Endpunkt nicht bereit. |
| `rate_limited` | Der Anbieter hat die Anfrage gedrosselt. |
| `server_error` | Der Anbieter ist ausgefallen oder hat das Zeitlimit überschritten. |

<span id="when-a-model-or-endpoint-is-not-available"></span>
## Wenn ein Modell oder Endpunkt nicht verfügbar ist

`unsupported_model_or_endpoint`-Fehler können `provider_candidate_diagnostics`, `provider_enablement`, `missing_pricing_providers` und `routing_diagnostics` enthalten. Zusammen unterscheiden sie ein Modell, das noch nicht aktiv ist, ein Modell, das den Endpunkt nicht unterstützt, fehlende Preise und Rollout-Einschränkungen.

| Feld | Bedeutung |
| --- | --- |
| `provider_candidate_diagnostics.totalProviders` | Für das Modell bekannte Anbieter vor der Endpunktfilterung. |
| `provider_candidate_diagnostics.supportsEndpointCount` | Anbieter, die den angefragten Endpunkt unterstützen. |
| `provider_candidate_diagnostics.candidateCount` | Anbieter, die nach den Adapterprüfungen übrig bleiben. |
| `provider_candidate_diagnostics.droppedUnsupportedEndpoint` | Anbieter, die verworfen wurden, weil sie den Endpunkt nicht unterstützen. |
| `provider_candidate_diagnostics.droppedMissingAdapter` | Paare aus Anbieter und Endpunkt, die verworfen wurden, weil Phaseo für diesen Endpunkt noch keinen Adapter hat. |
| `provider_enablement.capability` | Die durchgesetzte Fähigkeit, zum Beispiel `video_generation`. |
| `provider_enablement.providersBefore`, `providersAfter` | Anbieter vor und nach der Filterung nach Fähigkeit. |
| `provider_enablement.dropped[].reason` | Warum ein Anbieter verworfen wurde, zum Beispiel `pricing_missing`. |
| `routing_diagnostics.filterStages[].stage` | Eine Routing-Stufe, zum Beispiel die Filterung nach Fähigkeit, Rollout oder Routing-Status. |
| `routing_diagnostics.filterStages[].beforeCount`, `afterCount` | Anbieter vor und nach dieser Stufe. |
| `routing_diagnostics.filterStages[].droppedProviders[].reason` | Warum ein Anbieter in dieser Stufe verworfen wurde. |

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
    "message": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
    "type": "invalid_request_error",
    "param": null
  },
  "code": "unsupported_model_or_endpoint",
  "generation_id": "G-unsupported123",
  "status_code": 400,
  "description": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
  "provider_candidate_diagnostics": {
    "totalProviders": 3,
    "supportsEndpointCount": 2,
    "candidateCount": 1,
    "droppedUnsupportedEndpoint": ["provider-a"],
    "droppedMissingAdapter": [
      {
        "providerId": "provider-b",
        "endpoint": "responses"
      }
    ]
  },
  "provider_enablement": {
    "capability": "responses",
    "providersBefore": ["provider-b", "provider-c"],
    "providersAfter": ["provider-c"],
    "dropped": [
      {
        "providerId": "provider-b",
        "reason": "pricing_missing"
      }
    ]
  },
  "routing_diagnostics": {
    "filterStages": [
      {
        "stage": "provider_routing_status",
        "beforeCount": 1,
        "afterCount": 0,
        "droppedProviders": [
          {
            "providerId": "provider-c",
            "reason": "provider_status_not_ready"
          }
        ]
      }
    ]
  }
}
```

<span id="when-a-model-is-retired"></span>
## Wenn ein Modell eingestellt wird

Ein eingestelltes Modell wird weiter bedient, solange irgendein Anbieter es bereitstellt. Sobald keiner es mehr tut, schlagen Anfragen mit `410` und `model_retired` fehl:

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

`model` ist das angefragte Modell, `retired_at` der Zeitpunkt der Einstellung (oder `null`) und `replacement_model` der vorgeschlagene Ersatz (oder `null`).

Ein erneuter Versuch hilft nicht; ändere die Modell-ID. Damit diese Anfragen während der Migration weiter funktionieren, füge den Ersatz zur `models`-Liste der Anfrage hinzu oder aktiviere das Routing eingestellter Modelle für den Workspace. Siehe [Einstellung und Außerbetriebnahme von Modellen](../guides/model-retirement.mdx).

## Fehler während eines Streams

Schlägt eine Anfrage fehl, bevor das Streaming beginnt, erhältst du den oben gezeigten JSON-Fehler-Body. Schlägt sie mitten im Stream fehl, endet der Stream statt mit einem normalen Abschluss mit dem Fehlerereignis des Endpunkts:

| Endpunkt | Fehlerereignis |
| --- | --- |
| Chat Completions | Ein `error`-Frame |
| Responses | `response.failed` (oder `error`) |
| Messages | Ein `error`-Ereignis |

Behandle die Teilausgabe als unvollständig und biete einen erneuten Versuch an. Der `error`-Frame von Chat Completions enthält dasselbe Fehlerobjekt, wobei `error.type` aus dem Code abgeleitet wird:

```json
{
  "object": "error",
  "message": "The upstream stream ended before the response completed.",
  "code": "upstream_stream_failure",
  "error": {
    "code": "upstream_stream_failure",
    "message": "The upstream stream ended before the response completed.",
    "type": "server_error",
    "param": null
  }
}
```

Eine Anfrage ohne Streaming, deren Anbieter mittendrin ausfällt, gibt `502` mit `upstream_stream_failure` zurück, keine Teilantwort. Siehe [Streaming](../guides/streaming.mdx).

<span id="debug-a-request"></span>
## Eine Anfrage debuggen

Sende ein `debug`-Objekt, um Routing-Traces und die Upstream-Payloads zu erhalten:

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

`trace_level` ist `summary` oder `full`. Debug-Payloads können den Inhalt deiner Anfrage enthalten, nutze sie daher nur in der Entwicklung oder in streng kontrollierten Umgebungen. Siehe [`debug`](./parameters.mdx#parameter-debug).

Wenn eine Anfrage fehlschlägt, prüfe die [Statusseite](https://status.phaseo.app) auf Störungen, vergleiche deine Payload mit der Referenzseite des Endpunkts und protokolliere `generation_id` zusammen mit Endpunkt und Modell. Gib `generation_id` an, wenn du dich an den [Support](https://phaseo.app/help) wendest.

<Visibility for="agents">
Regeln zur Fehlerbehandlung für Agents, als Zusammenfassung dieser Seite:

- Verzweige anhand von `error.code` (auch als `code` auf oberster Ebene zurückgegeben), `error.type` und `status_code`, nicht anhand des Meldungstexts. Protokolliere `generation_id` bei jedem Fehler.
- `400`, `401`, `403` und `404`: Korrigiere zuerst die Anfrage, den Schlüssel oder den Zugriff. Wiederhole dieselbe Anfrage nicht unverändert.
- `410` mit `model_retired`: Wechsle zu `replacement_model`, wenn es nicht `null` ist; andernfalls wähle ein neues Modell aus `GET /v1/models`.
- `429`: Wenn `Retry-After` vorhanden ist (Sekunden oder ein HTTP-Datum), warte so lange, bevor du es erneut versuchst; sonst nutze exponentielles Backoff mit Jitter. Ein `key_limit_exceeded`-Fehler ohne `Retry-After` setzt sich nicht von selbst zurück, also versuche ihn nicht erneut.
- `500` bis `599`: Versuche es nur erneut, wenn eine Wiederholung des Aufrufs sicher ist, mit einem Versuchslimit, einer Gesamtfrist und exponentiellem Backoff mit Jitter. Schlage bei asynchronen Jobs den angenommenen Job nach, statt ihn erneut zu senden.
- Behandle Debug-Payloads als sensibel und schwärze sie, bevor du sie in dauerhafte Logs schreibst.
- Für getestete Muster zum Wiederholen und Auswerten von Fehlern installiere den Skill `phaseo-gateway`: `npx skills add https://phaseo.app/docs --skill phaseo-gateway`.
</Visibility>
