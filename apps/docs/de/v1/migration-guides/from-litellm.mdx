Richte die Clients, die deinen LiteLLM-Proxy aufrufen, mit einem Phaseo-Schlüssel auf `https://api.phaseo.app/v1` aus und ordne dann jeden `model_name`-Alias und jede Proxy-Einstellung bewusst zu. Wenn du LiteLLM behalten und Phaseo stattdessen als dessen Upstream nutzen willst, siehe [LiteLLM-Integration](../guides/integrations/litellm).

| Einstellung | LiteLLM-Proxy | Phaseo |
| --- | --- | --- |
| Basis-URL | Dein Proxy, oft `http://localhost:4000` | `https://api.phaseo.app/v1` |
| API-Schlüssel | `LITELLM_MASTER_KEY` oder ein virtueller Schlüssel | `PHASEO_API_KEY` |
| Modell | `model_name`-Alias aus `config.yaml` | Phaseo-Modell-ID, ein Preset (`"model": "@slug"`) oder eine Zuordnungsfunktion |
| Routing und Standards | `router_settings`, `litellm_settings` | [Presets](../guides/presets) und [Routing und Fallbacks](../guides/routing-and-fallbacks) |

## Client umstellen

<CodeGroup>
```typescript TypeScript
import OpenAI from "openai";

// Vorher:
// new OpenAI({ apiKey: process.env.LITELLM_API_KEY, baseURL: process.env.LITELLM_BASE_URL });
const client = new OpenAI({
  apiKey: process.env.PHASEO_API_KEY,
  baseURL: "https://api.phaseo.app/v1",
});

const response = await client.chat.completions.create({
  model: "openai/gpt-6-astra",
  messages: [{ role: "user", content: "Reply with: migration ready" }],
});
```

```python Python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["PHASEO_API_KEY"],
    base_url="https://api.phaseo.app/v1",
)
```

```bash cURL
curl https://api.phaseo.app/v1/chat/completions \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-6-astra",
    "messages": [{"role": "user", "content": "Reply with: migration ready"}]
  }'
```
</CodeGroup>

Jeder Alias braucht eine explizite Zuordnung zu einer ID aus `GET /v1/models?format=openai`. Wenn Aufrufer interne Aliase verwenden, übersetze sie in einer einzigen Funktion an der Client-Grenze, statt jede Anfrage zu bearbeiten.

## Proxy-Konfiguration zuordnen

Erfasse Callbacks, Budgets und Wiederholungen, bevor du den Proxy entfernst: Diese hören stillschweigend auf, sobald er wegfällt.

| LiteLLM | Bei Phaseo |
| --- | --- |
| `fallbacks` | `models`-Array oder Fallbacks dynamischer Routen, versucht bei `429`, `500`, `502`, `503` und `504`, nie bei Anfragefehlern. |
| `context_window_fallbacks`, `content_policy_fallbacks` | Keine Entsprechung: Phaseo greift bei `400` nie auf einen Fallback zurück. Behandle diese Fälle in der App. |
| `routing_strategy` | Routing-Modus des Workspace oder `provider.sort` (`price`, `latency`, `throughput`). |
| Anbieterwahl pro Deployment | `provider.order`, `provider.only`, `provider.ignore` oder eine [anbieterqualifizierte ID](../guides/provider-qualified-models) wie `provider:org/model`, die nicht auf andere Anbieter ausweicht. |
| Selbst gehostete Deployments (vLLM und Ähnliches) | [Private Modelle](../guides/private-models), die einen öffentlichen HTTPS-Endpunkt `/chat/completions` im OpenAI-Format mit Bearer-Authentifizierung brauchen. |
| Antwort-Cache (`litellm_settings.cache`) | Kein Antwort-Cache. Cache bei Bedarf in der App; [Prompt-Caching](../guides/prompt-caching) senkt trotzdem die Eingabekosten. |
| Virtuelle Schlüssel (`max_budget`, `rpm_limit`, `tpm_limit`, `max_parallel_requests`, `models`) | API-Schlüssel mit Ausgabenlimits und erlaubten Modellen, Budgets sowie Ratenlimit-Richtlinien für Anfragen pro Minute, Tokens pro Minute und gleichzeitige Anfragen. Siehe [Limits](../api-reference/limits). |
| Team-Budgets, `metadata.tags` | Abteilungsbudgets und `X-Phaseo-Metadata`-[Labels](../guides/request-labels). Endbenutzer-Budgets lassen sich nur auf eine Ratenlimit-Richtlinie pro Endbenutzer abbilden; eine Ausgabengrenze pro Endbenutzer gibt es nicht. |
| `guardrails` (Presidio, Lakera und Ähnliches) | Schlüssel-Guardrails prüfen Anfragen auf Prompt-Injection und personenbezogene Daten. Antworten werden nicht geprüft. |
| Callbacks (`success_callback`, Langfuse, Datadog, OpenTelemetry) | [Observability-Ziele](../guides/integrations/observability) oder clientseitiges Tracing. Body-`metadata` wird als `phaseo.metadata.<key>` exportiert. |
| Anbieter-API-Schlüssel in der Konfiguration | BYOK (`phaseo byok create --provider <id> --name <name> --key-stdin` oder `POST /v1/byok`) oder Phaseo-Guthaben. Setze `byok_fallback_enabled` mit `phaseo settings update`, um auf Guthaben auszuweichen. |

Ein Proxy leitet den Traffic eines ganzen Teams über den Schlüssel einer einzelnen Person und teilt sich daher deren Kontingent an Anfragen pro Minute, das bei einem neuen Workspace 10 beträgt. Prüfe die [Gateway-Limits](../api-reference/limits#gateway-limits) und vereinbare vor der Umstellung ein höheres Limit.

## Testen und umstellen

Teste Streaming, Tools, strukturierte Ausgaben, Wiederholungen, die Zuordnung von Fehlern und jede Callback-basierte Telemetrie, die der Proxy übernommen hat. Vergleiche Latenz, Ausgabe, Tokennutzung und Kosten, bevor du Traffic schrittweise verschiebst. Vor der Umstellung:

- jede LiteLLM-URL, jeder Schlüssel und jede `LITELLM_*`-Variable ist erfasst;
- jeder Produktions-Alias hat eine explizite Phaseo-Zuordnung;
- gemeinsame Standards liegen in Presets oder in einer Grenzfunktion;
- benötigte Callbacks und Telemetrie haben einen Ersatz;
- du hast entschieden, ob LiteLLM, Phaseo oder beide maßgeblich für die Ausgaben sind;
- das Zurückrollen ist weiterhin nur eine Änderung von Basis-URL und Schlüssel.
