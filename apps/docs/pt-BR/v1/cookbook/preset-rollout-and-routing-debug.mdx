Migre vários serviços para uma única predefinição para que compartilhem um prompt, um modelo e regras de provedor, e depois use os registros de solicitações para explicar para onde cada solicitação foi. No fim, os seus chamadores enviam `"model": "@release-summary"` e a entrada, e você consegue implantar uma mudança de política um chamador por vez.

O formato da solicitação está pronto para produção. [Predefinições](../guides/presets) explica como as configurações de uma predefinição se combinam com a solicitação; esta receita trata da implantação.

## Migre um chamador para uma predefinição

<Steps>
<Step title="Crie a predefinição">

Em **Configurações → Predefinições**, crie `release-summary` com um prompt de sistema, os modelos aprovados, as preferências de provedor e parâmetros padrão como `temperature`. Ou pela CLI:

```bash
phaseo presets create --name @release-summary --model anthropic/claude-sonnet-5.5
```

</Step>
<Step title="Chame pelo nome">

Envie a predefinição como `model`. Não existe um campo `preset` separado.

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@release-summary",
    "input": "Generate a release summary for the last 24 hours.",
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "@release-summary",
  input: "Generate a release summary for the last 24 hours.",
  meta: true,
});

console.log(response.model, response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "@release-summary",
        "input": "Generate a release summary for the last 24 hours.",
        "meta": True,
    }
)

print(response.get("model"), response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

`model` na resposta é o modelo que respondeu, e `meta.routing.selected_provider` é o provedor.

</Step>
<Step title="Confira o que a predefinição aplicou">

Abra a solicitação em **Configurações → Uso → Registros**. Ali aparecem os padrões da predefinição que foram aplicados. Um modelo fora dos modelos permitidos da predefinição falha com `validation_error` (palavra-chave `preset_model_not_allowed`) em vez de ser roteado para outro.

</Step>
</Steps>

## Explique uma decisão de roteamento

Quando uma solicitação não foi roteada como você esperava, expanda **Observabilidade do roteamento** na solicitação em **Configurações → Uso → Registros**. Ela responde a três perguntas:

| Pergunta | Onde olhar |
| --- | --- |
| Por que um provedor foi pulado? | Os provedores excluídos antes da classificação, com o motivo, e os provedores rebaixados pelo status de implantação ou de roteamento |
| Por que a solicitação foi bloqueada? | Os bloqueios por política do espaço de trabalho ou por guardrail na solicitação |
| Por que este provedor venceu? | A pontuação final de cada provedor classificado e os fatores por trás dela |

[Explique uma decisão de roteamento](../guides/routing-and-fallbacks#explain-a-routing-decision) descreve cada campo.

## Implante uma mudança de política

1. Publique a mudança como uma nova versão da predefinição ou crie um novo slug para uma política muito diferente.
2. Migre um chamador de baixo risco para ela, por exemplo apontando-o para `@release-summary@v4` ou para um rótulo `canary`.
3. Compare os detalhes das solicitações e as tendências de uso dele com os dos outros chamadores.
4. Migre os demais chamadores quando o roteamento corresponder ao que você espera. Para reverter, aponte o rótulo para a versão anterior.

[Versione e reverta](../guides/presets#version-and-roll-back) explica as versões e os rótulos. Para substituições no nível da solicitação que não devem ficar em uma predefinição, veja [Fixe ou ignore provedores](./pin-or-ignore-providers-per-request).
