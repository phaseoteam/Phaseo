Uma requisição pode ser limitada pelo provedor selecionado ou por uma política aplicável ao espaço de trabalho ou à chave. O roteamento e as alternativas podem reduzir falhas do provedor, mas uma requisição ainda pode retornar `429`.

## Limites do gateway

Cada usuário em cada espaço de trabalho tem uma cota de requisições por minuto, medida em uma janela móvel de um minuto. As chaves de API criadas pelo mesmo usuário compartilham essa cota. Requisições OAuth usam o usuário autenticado. Chaves sem proprietário compartilham uma cota do espaço de trabalho.

A cota depende da situação da conta do espaço de trabalho e aumenta automaticamente à medida que o espaço de trabalho se consolida:

| Espaço de trabalho | Requisições por minuto |
| --- | --- |
| Espaço de trabalho novo | 10 |
| Pelo menos 7 dias de existência ou com uma recarga paga | 25 |
| Pelo menos 30 dias de existência e pelo menos US$ 50 em recargas pagas, descontados os reembolsos | 60 |
| Cobrança por fatura | 120 |

Um espaço de trabalho recebe a maior cota para a qual se qualifica. As alterações entram em vigor em poucos minutos.

As rotas de modelos gratuitos também têm uma cota de **1500 requisições por dia UTC**, compartilhada entre todos os modelos gratuitos do mesmo usuário e espaço de trabalho. Requisições a modelos pagos não consomem essa cota diária. Uma requisição gratuita admitida conta mesmo se o provedor falhar depois; fallbacks dentro dessa requisição contam uma única vez.

Esses limites valem para todas as regiões do gateway e podem ser aumentados para um usuário e espaço de trabalho específicos. Operações com arquivos e consultas de status de tarefas consomem a cota por minuto; endpoints de administração não.

Quando uma cota do gateway se esgota, a resposta é `429` com `Retry-After` em segundos. O motivo do erro é `customer_requests_per_minute` ou `free_requests_per_day`. Aguarde esse intervalo antes de tentar novamente. Se a verificação de cotas estiver temporariamente indisponível, o gateway retorna `503` com orientação para uma nova tentativa.

## Limites de chaves e orçamentos

Ao atingir os limites diários, semanais ou mensais de requisições e gastos de uma chave de API, ou os [orçamentos](./endpoint/budgets-list.mdx) do espaço de trabalho, a resposta é `429` com o código de erro `key_limit_exceeded`. Os campos `reason`, `limit_window` e `reset_at` do corpo identificam o limite e quando seu período é redefinido. `Retry-After` informa os segundos até essa redefinição. Ele é omitido quando o limite não é redefinido sozinho, como um orçamento vitalício ou uma chave bloqueada temporariamente; nesse caso, em vez de tentar novamente, aumente o orçamento do espaço de trabalho ou, se for um limite de chave, aumente o limite da chave ou use outra chave.

## Políticas de limite de taxa

Os administradores do espaço de trabalho podem criar políticas de limite de taxa nomeadas pela API de gerenciamento `/v1/rate-limits` e atribuí-las a chaves de API, membros do espaço de trabalho, proteções ou como padrão para cada usuário final. O gateway aplica o `requests_per_minute` de uma política, medido em um minuto móvel:

- **Chave:** a cota própria da chave.
- **Membro:** uma cota compartilhada pelas chaves e pelas solicitações OAuth do membro.
- **Proteção:** uma cota separada para cada chave (ou usuário OAuth) coberta pela proteção.
- **Padrão por usuário final:** uma cota separada para cada usuário final, identificado pelo campo `user` da solicitação ou pelo cabeçalho `X-Phaseo-User-Id`. Solicitações sem ID de usuário final não são limitadas por ela.

Quando várias políticas se aplicam, cada uma é contada e a primeira esgotada rejeita a solicitação. Os limites das políticas se somam aos limites do gateway acima. `tokens_per_minute`, `concurrent_requests` e atribuições a departamentos ainda não são aplicados. As alterações nas políticas entram em vigor em cerca de um minuto.

Uma solicitação rejeitada retorna `429` com o código de erro `rate_limit_exceeded`, o motivo `policy_requests_per_minute`, o `policy_id` e o `limit_scope` (`key`, `member`, `guardrail` ou `end_user`), além de `Retry-After` em segundos. As respostas a solicitações às quais uma política se aplica incluem `x-ratelimit-limit-requests`, `x-ratelimit-remaining-requests` e `x-ratelimit-reset-requests` (por exemplo, `60s`) da política mais restritiva. A contagem é feita em segundo plano, então `remaining` é aproximado. Fallbacks de provedor dentro de uma solicitação contam uma vez, e acertos do cache de respostas não são contados.

## Limites do provedor

Requisições BYOK usam os limites da sua conta no provedor. Requisições gerenciadas usam capacidade compartilhada do provedor; essa capacidade não é uma cota individual do espaço de trabalho.

O Phaseo encaminha um valor validado de `Retry-After` quando o provedor para o qual a requisição foi roteada o fornece. Respostas BYOK também podem incluir cabeçalhos `X-Phaseo-Upstream-RateLimit-*`. Esses cabeçalhos de cota são omitidos em requisições gerenciadas porque descrevem capacidade compartilhada do provedor. Outros cabeçalhos de origem não são encaminhados.

## Gerenciar uma requisição limitada

1. Inspecione o [código de erro](./errors.mdx) para distinguir uma restrição temporária do provedor de uma restrição de política ou orçamento que exija alterações de configuração.
2. Respeite `Retry-After` quando estiver presente. Pode ser um intervalo em segundos ou uma data HTTP; valide o valor antes de agendar uma nova tentativa.
3. Caso contrário, use espera exponencial com variação aleatória e um intervalo máximo.
4. Limite as novas tentativas tanto pela quantidade quanto por um prazo total. Cancele o trabalho abandonado e libere o corpo de cada resposta com falha antes de tentar novamente.
5. Reduza a concorrência se a restrição persistir.

Não repita automaticamente o envio de um trabalho com resultado incerto nem ações de ferramentas já concluídas. Uma requisição pode ter chegado ao provedor mesmo que o cliente tenha perdido a resposta; novas tentativas podem duplicar trabalho e cobranças. Para um trabalho de vídeo ou em lote aceito, use seu endpoint de status em vez de enviá-lo novamente.

## Monitorar restrições de taxa

Acompanhe a frequência de `429` por endpoint e modelo e inspecione a frequência das alternativas nos logs de requisições. Compare os logs da sua aplicação com as [configurações de roteamento](../guides/routing-and-fallbacks.mdx) e as cotas da conta no provedor para tráfego BYOK.

Consulte os [orçamentos](./endpoint/budgets-list.mdx) e as [proteções](./endpoint/guardrails.mdx) para os controles de gastos e acesso do espaço de trabalho.
