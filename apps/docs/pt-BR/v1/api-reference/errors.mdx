Use esta página para entender o que um erro da Phaseo significa e o que fazer em seguida.

Toda resposta de erro segue o mesmo formato JSON, para que seu aplicativo trate falhas de maneira consistente entre modelos e provedores. O campo `error` é um objeto com `code`, `message` e `type`, o formato que os SDKs compatíveis com a OpenAI leem, então as exceções deles trazem a mensagem do gateway.

## Exemplo de resposta de erro

```json
{
  "error": {
    "code": "upstream_error",
    "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
    "type": "server_error",
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "attempt_count": 1,
  "failed_providers": ["google-ai-studio"],
  "failed_statuses": [403],
  "provider_failure_diagnostics": {
    "category": "provider_access_missing",
    "hint": "The provider account appears not to have access to this model or feature yet. Verify account entitlements and provider-side access.",
    "provider": "google-ai-studio"
  },
  "upstream_error": {
    "code": "PERMISSION_DENIED",
    "message": "The caller does not have permission.",
    "description": null,
    "param": null
  },
  "failure_sample": [
    {
      "provider": "google-ai-studio",
      "type": "upstream_non_2xx",
      "status": 403,
      "upstream_error_code": "PERMISSION_DENIED",
      "upstream_error_message": "The caller does not have permission.",
      "upstream_error_description": null,
      "upstream_error_param": null,
      "upstream_payload_preview": "{\"error\":{\"status\":\"PERMISSION_DENIED\"}}",
      "retryable": false
    }
  ]
}
```

## Campos que você sempre receberá

- `generation_id`: ID estável da solicitação que você pode compartilhar com o suporte.
- `status_code`: corresponde ao código de status HTTP.
- `error`: um objeto que descreve a falha:
  - `error.code`: código de erro legível por máquina, como `validation_error`.
  - `error.message`: explicação clara do que aconteceu.
  - `error.type`: o tipo de erro (veja a seção Tipos de erro abaixo).
  - `error.param`: o parâmetro da solicitação que causou o erro, quando o gateway o conhece; caso contrário, `null`.
  - `error.metadata` (opcional): detalhes estruturados como o provedor que falhou, o motivo específico, os status com falha ou `retry_after_seconds`. Os mesmos valores também são retornados no nível superior.
- `code`: o mesmo código de `error.code`. Respostas anteriores retornavam esse código como string em `error`; leia `code` se o seu cliente esperava uma string ali.
- `message`: o mesmo texto de `error.message`.
- `error_type`: classe geral, normalmente `user` ou `system`.
- `error_origin`: indica se o problema foi causado principalmente pelo solicitante, pela Phaseo ou por um provedor upstream.
- `description`: explicação simples do que aconteceu.
- `details` (opcional): detalhes estruturados de validação quando o erro está na validação da solicitação.

## Outros campos que podem aparecer

Alguns erros trazem mais detalhes para ajudar a corrigir o problema rapidamente:

- `reason`: motivo mais específico, como `all_candidates_failed` ou `pricing_not_configured`.
- `provider_candidate_diagnostics` e `provider_enablement`: explicam por que um modelo não pôde ser usado com o endpoint solicitado.
- `routing_diagnostics`: detalhes adicionais sobre como o roteamento ou as verificações de disponibilidade restringiram as opções.
- `provider_failure_diagnostics`: dicas sobre credenciais ausentes, falta de acesso, restrições regionais, limites de taxa e falhas semelhantes do provedor.
- `upstream_error` e `failure_sample`: resumo aproximado da primeira falha do provedor, se a solicitação chegou até ele.
- `failed_providers`, `failed_statuses` e `attempt_count`: contexto adicional de novas tentativas e failover.

## Tipos de erro

`error.type` segue os [tipos de erro documentados pela OpenAI](https://platform.openai.com/docs/guides/error-codes) e é definido pelo status HTTP:

| Status | `error.type` |
| --- | --- |
| `400`, `409`, `410`, `413`, `422` e outros 4xx | `invalid_request_error` |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `500`, `502` e outros 5xx | `server_error` |

Erros em `/v1/messages` usam o mesmo corpo, então os SDKs da Anthropic também encontram `error.type` e `error.message`.

## Interprete as classes de status

| Status | Significado | Ação recomendada |
| --- | --- | --- |
| `400-499` | Problema na solicitação, autenticação ou permissão | Corrija a solicitação ou as credenciais antes de tentar novamente. |
| `429` | Limitação de taxa do provedor ou da rota | Tente novamente com espera progressiva e respeite `Retry-After`. |
| `500-599` | Falha da Phaseo ou do provedor upstream | Tente novamente com espera progressiva e aleatória e registre o ID da solicitação. |

## Códigos de erro comuns

| `error.code` | Status HTTP | `error.type` | Descrição |
| --- | --- | --- | --- |
| `unauthorised` | `401` | `authentication_error` | A chave de API está ausente ou é inválida. |
| `guardrail_blocked` | `403` | `permission_error` | Uma guardrail ou política de acesso do workspace bloqueou a solicitação. |
| `not_found` | `404` | `not_found_error` | O endpoint ou recurso não foi encontrado. |
| `model_retired` | `410` | `invalid_request_error` | O modelo foi aposentado e nenhum provedor o atende mais. Mude para `replacement_model`. |
| `insufficient_funds` | `402` | `insufficient_quota` | O workspace não tem créditos suficientes para a solicitação. |
| `key_limit_exceeded` | `429` | `rate_limit_error` | A chave de API atingiu um de seus limites. |
| `phaseo_free_model_limit_exceeded` | `429` | `rate_limit_error` | A cota diária compartilhada dos modelos gratuitos do Phaseo foi esgotada (1.500 solicitações por padrão). Respeite `Retry-After`, aguarde a redefinição às 00:00 UTC ou escolha um modelo pago. |
| `rate_limit_exceeded` | `429` | `rate_limit_error` | Uma [política de limite de taxa](./limits.mdx) do espaço de trabalho se esgotou. `policy_id` e `limit_scope` a identificam. Respeite `Retry-After` ou peça a um administrador do espaço de trabalho para alterar a política. |
| `validation_error` | `400` | `invalid_request_error` | Parâmetros ou corpo da solicitação inválidos. `error.param` indica o primeiro campo inválido. |
| `upstream_error` | `429` | `rate_limit_error` | Todos os provedores tentados para a solicitação aplicaram limite de taxa. Respeite `Retry-After`; solicitações BYOK também trazem os cabeçalhos `X-Phaseo-Upstream-RateLimit-*`. |
| `upstream_error` | `502` | `server_error` | O provedor upstream do modelo não respondeu corretamente. |
| `upstream_stream_failure` | `502` | `server_error` | Uma solicitação sem streaming cujo provedor falhou depois de começar a gerar. Nenhuma saída parcial é retornada e a solicitação não é cobrada. |
| `gateway_error` | `500` | `server_error` | Ocorreu um problema inesperado na Phaseo. |

## Quando um provedor falha

Se a Phaseo chegou a um provedor, mas a solicitação ainda falhou, você poderá ver:

- `provider_failure_diagnostics.category`
- `provider_failure_diagnostics.hint`
- `provider_failure_diagnostics.provider`

As categorias atuais incluem:

- `credentials_not_configured`
- `credentials_invalid_or_forbidden`
- `provider_access_missing`
- `region_or_project_restriction`
- `model_unavailable_for_endpoint`
- `rate_limited`
- `server_error`

Esses campos ajudam a resolver o problema sem ativar o modo de depuração completo.

## Quando um modelo ou endpoint não está disponível

Para respostas `unsupported_model_or_endpoint`, a Phaseo pode incluir:

- `provider_candidate_diagnostics`
- `provider_enablement`
- `missing_pricing_providers`
- `routing_diagnostics`

Essas informações ajudam a distinguir entre:

- um modelo conhecido que ainda não está ativo
- um modelo incompatível com o endpoint solicitado
- dados de preço ausentes
- restrições de rollout ou disponibilidade interna

Campos comuns:

- `provider_candidate_diagnostics.totalProviders`: número de provedores conhecidos para o modelo antes do filtro por endpoint.
- `provider_candidate_diagnostics.supportsEndpointCount`: número desses provedores compatíveis com o endpoint solicitado.
- `provider_candidate_diagnostics.candidateCount`: número de provedores restantes após as verificações de adaptador.
- `provider_candidate_diagnostics.droppedUnsupportedEndpoint`: provedores removidos por não oferecerem suporte ao endpoint.
- `provider_candidate_diagnostics.droppedMissingAdapter`: pares provedor/endpoint removidos porque ainda não existe um adaptador do Gateway para esse endpoint.
- `provider_enablement.capability`: recurso sob verificação, como `video_generation`.
- `provider_enablement.providersBefore` / `provider_enablement.providersAfter`: provedores antes e depois dos filtros de capacidade ou habilitação.
- `provider_enablement.dropped[].reason`: motivos legíveis por máquina, como `pricing_missing`.
- `routing_diagnostics.filterStages[].stage`: etapa de roteamento, por exemplo filtro de capacidade, rollout ou estado de roteamento.
- `routing_diagnostics.filterStages[].beforeCount` / `routing_diagnostics.filterStages[].afterCount`: quantidade de provedores antes e depois de cada etapa.
- `routing_diagnostics.filterStages[].droppedProviders[].reason`: motivos legíveis por máquina, como restrições de rollout ou roteamento.

### Exemplo

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
    "message": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
    "type": "invalid_request_error",
    "param": null
  },
  "code": "unsupported_model_or_endpoint",
  "generation_id": "G-unsupported123",
  "status_code": 400,
  "description": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
  "provider_candidate_diagnostics": {
    "totalProviders": 3,
    "supportsEndpointCount": 2,
    "candidateCount": 1,
    "droppedUnsupportedEndpoint": ["provider-a"],
    "droppedMissingAdapter": [
      {
        "providerId": "provider-b",
        "endpoint": "responses"
      }
    ]
  },
  "provider_enablement": {
    "capability": "responses",
    "providersBefore": ["provider-b", "provider-c"],
    "providersAfter": ["provider-c"],
    "dropped": [
      {
        "providerId": "provider-b",
        "reason": "pricing_missing"
      }
    ]
  },
  "routing_diagnostics": {
    "filterStages": [
      {
        "stage": "provider_routing_status",
        "beforeCount": 1,
        "afterCount": 0,
        "droppedProviders": [
          {
            "providerId": "provider-c",
            "reason": "provider_status_not_ready"
          }
        ]
      }
    ]
  }
}
```

## Quando um modelo é aposentado

Um modelo aposentado continua sendo atendido enquanto algum provedor o atender. Quando nenhum provedor o atende mais, as solicitações para ele falham com `410` e o erro `model_retired`:

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

- `model`: o modelo que você solicitou.
- `retired_at`: quando o modelo foi aposentado, ou `null` se nenhuma data estiver registrada.
- `replacement_model`: o substituto sugerido, ou `null` se não houver nenhum.

Tentar novamente não resolve. Atualize o ID do modelo na sua solicitação. Para continuar atendendo a essas solicitações durante a migração, adicione o substituto à lista `models` da solicitação ou ative o roteamento de modelos aposentados no espaço de trabalho. Consulte [Descontinuação e aposentadoria de modelos](../guides/model-retirement.mdx).

## Modo de depuração opcional

A maioria dos esquemas de solicitação aceita um objeto `debug` para investigação controlada:

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

Campos disponíveis:

- `enabled`
- `return_upstream_request`
- `return_upstream_response`
- `trace`
- `trace_level` (`summary` ou `full`)

Use o modo de depuração somente em desenvolvimento ou em ambientes rigorosamente controlados.

## Estratégia de novas tentativas

- **Erros da série 400, exceto 429:** corrija a requisição, as credenciais ou a política de acesso antes de tentar novamente.
- **429:** implemente espera exponencial e respeite o cabeçalho `Retry-After`.
- **Erros da série 500:** use tentativas limitadas apenas quando for seguro repetir a operação. Um envio com resultado incerto pode já ter criado um trabalho ou gerado uma cobrança; consulte um trabalho aceito em vez de enviá-lo novamente.

Defina um limite de tentativas e um prazo total e adicione variação aleatória aos intervalos de espera. Consulte os [limites de requisições](./limits.mdx) para os cabeçalhos de resposta e o tratamento de novas tentativas.

## Observações específicas sobre streaming

- Se a solicitação falhar antes do início do streaming, você receberá um payload JSON de erro padrão.
- Se falhar no meio do fluxo, o fluxo termina com o evento de falha do endpoint em vez de um encerramento normal: um frame `error` no Chat Completions, `response.failed` (ou `error`) no Responses e um evento `error` no Messages. Considere o trecho parcial incompleto e ofereça a opção de tentar novamente.
- O frame `error` do Chat Completions traz o mesmo objeto de erro, com `error.type` definido pelo código:

  ```json
  {
    "object": "error",
    "message": "The upstream stream ended before the response completed.",
    "code": "upstream_stream_failure",
    "error": {
      "code": "upstream_stream_failure",
      "message": "The upstream stream ended before the response completed.",
      "type": "server_error",
      "param": null
    }
  }
  ```
- Uma solicitação sem streaming cujo provedor falha no meio retorna `502` com `upstream_stream_failure`, não uma resposta parcial.
- Sempre registre `generation_id` e os metadados do endpoint/modelo.

## Dicas para solucionar problemas

- Consulte a [página de status do Gateway](https://status.phaseo.app) para verificar incidentes em andamento.
- Compare o payload da solicitação com a documentação do endpoint.
- Informe `generation_id` ao entrar em contato com o suporte.

<Visibility for="agents">
Regras de tratamento de erros para agentes, resumindo esta página:

- Decida com base em `error.code` (também retornado como `code` no nível superior), `error.type` e `status_code`, não no texto da mensagem. Registre `generation_id` em toda falha.
- `400`, `401`, `403` e `404`: corrija primeiro a solicitação, a chave ou o acesso. Não repita a mesma solicitação sem alterações.
- `410` com `model_retired`: mude para `replacement_model` quando ele não for `null`; caso contrário, escolha um novo modelo com `GET /v1/models`.
- `429`: quando houver `Retry-After` (segundos ou uma data HTTP), aguarde esse tempo antes de tentar de novo; caso contrário, use backoff exponencial com jitter. Um erro `key_limit_exceeded` sem `Retry-After` não é redefinido sozinho, então não tente de novo.
- `500` a `599`: tente de novo somente quando repetir a chamada for seguro, com limite de tentativas, prazo total e backoff exponencial com jitter. Em tarefas assíncronas, consulte a tarefa aceita em vez de enviá-la novamente.
- Trate payloads de depuração como sensíveis e oculte-os antes de gravar logs persistentes.
- Para padrões testados de nova tentativa e análise de erros, instale a skill `phaseo-gateway`: `npx skills add https://phaseo.app/docs --skill phaseo-gateway`.
</Visibility>
