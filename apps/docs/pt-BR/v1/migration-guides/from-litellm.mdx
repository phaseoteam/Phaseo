Aponte os clientes que chamam o seu proxy LiteLLM para `https://api.phaseo.app/v1` com uma chave do Phaseo e, em seguida, mapeie cada alias `model_name` e cada configuração do proxy de forma explícita. Para manter o LiteLLM e usar o Phaseo como upstream dele, veja [Integração com o LiteLLM](../guides/integrations/litellm).

| Configuração | Proxy LiteLLM | Phaseo |
| --- | --- | --- |
| URL base | O seu proxy, geralmente `http://localhost:4000` | `https://api.phaseo.app/v1` |
| Chave de API | `LITELLM_MASTER_KEY` ou uma chave virtual | `PHASEO_API_KEY` |
| Modelo | Alias `model_name` do `config.yaml` | ID de modelo do Phaseo, uma predefinição (`"model": "@slug"`) ou uma única função de mapeamento |
| Roteamento e padrões | `router_settings`, `litellm_settings` | [Predefinições](../guides/presets) e [Roteamento e fallbacks](../guides/routing-and-fallbacks) |

## Troque o cliente

<CodeGroup>
```typescript TypeScript
import OpenAI from "openai";

// Antes:
// new OpenAI({ apiKey: process.env.LITELLM_API_KEY, baseURL: process.env.LITELLM_BASE_URL });
const client = new OpenAI({
  apiKey: process.env.PHASEO_API_KEY,
  baseURL: "https://api.phaseo.app/v1",
});

const response = await client.chat.completions.create({
  model: "openai/gpt-6-astra",
  messages: [{ role: "user", content: "Reply with: migration ready" }],
});
```

```python Python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["PHASEO_API_KEY"],
    base_url="https://api.phaseo.app/v1",
)
```

```bash cURL
curl https://api.phaseo.app/v1/chat/completions \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-6-astra",
    "messages": [{"role": "user", "content": "Reply with: migration ready"}]
  }'
```
</CodeGroup>

Cada alias precisa de um mapeamento explícito para um ID em `GET /v1/models?format=openai`. Se os chamadores usam aliases internos, traduza-os em uma única função na fronteira do cliente em vez de editar cada solicitação.

## Mapeie a configuração do proxy

Faça um inventário de callbacks, orçamentos e novas tentativas antes de remover o proxy: eles param silenciosamente quando ele sai de cena.

| LiteLLM | No Phaseo |
| --- | --- |
| `fallbacks` | Array `models` ou fallbacks de rotas dinâmicas, tentados em `429`, `500`, `502`, `503` e `504`, nunca em erros da solicitação. |
| `context_window_fallbacks`, `content_policy_fallbacks` | Sem equivalente: o Phaseo nunca faz fallback em um `400`. Trate esses casos no app. |
| `routing_strategy` | Modo de roteamento do espaço de trabalho ou `provider.sort` (`price`, `latency`, `throughput`). |
| Escolha de provedor por implantação | `provider.order`, `provider.only`, `provider.ignore` ou um [ID qualificado por provedor](../guides/provider-qualified-models), como `provider:org/model`, que não faz fallback entre provedores. |
| Implantações auto-hospedadas (vLLM e similares) | [Modelos privados](../guides/private-models), que precisam de um endpoint `/chat/completions` público em HTTPS, compatível com OpenAI e com autenticação bearer. |
| Cache de respostas (`litellm_settings.cache`) | Sem cache de respostas. Faça cache no app se precisar; o [cache de prompts](../guides/prompt-caching) ainda reduz o custo de entrada. |
| Chaves virtuais (`max_budget`, `rpm_limit`, `tpm_limit`, `max_parallel_requests`, `models`) | Chaves de API com limites de gasto e modelos permitidos, orçamentos e políticas de limite de taxa para solicitações por minuto, tokens por minuto e solicitações simultâneas. Veja [Limites](../api-reference/limits). |
| Orçamentos de equipe, `metadata.tags` | Orçamentos de departamento e [rótulos](../guides/request-labels) `X-Phaseo-Metadata`. Orçamentos por usuário final só se mapeiam para uma política de limite de taxa por usuário final; não existe teto de gasto por usuário final. |
| `guardrails` (Presidio, Lakera e similares) | Os guardrails de chave verificam as solicitações em busca de injeção de prompt e PII. As respostas não são verificadas. |
| Callbacks (`success_callback`, Langfuse, Datadog, OpenTelemetry) | [Destinos de observabilidade](../guides/integrations/observability) ou tracing no cliente. O `metadata` do corpo é exportado como `phaseo.metadata.<key>`. |
| Chaves de API de provedores na configuração | BYOK (`phaseo byok create --provider <id> --name <name> --key-stdin` ou `POST /v1/byok`) ou créditos do Phaseo. Defina `byok_fallback_enabled` com `phaseo settings update` para fazer fallback para os créditos. |

Um proxy envia todo o tráfego de uma equipe pela chave de um único dono, então compartilha a cota de solicitações por minuto desse usuário, que é 10 para um espaço de trabalho novo. Consulte [Limites do Gateway](../api-reference/limits#gateway-limits) e providencie um limite maior antes da virada.

## Teste e faça o rollout

Teste streaming, ferramentas, saídas estruturadas, novas tentativas, mapeamento de erros e qualquer telemetria baseada em callbacks que o proxy fazia. Compare latência, saída, uso de tokens e custo antes de mover o tráfego aos poucos. Antes da virada, confirme que:

- toda URL, chave e variável `LITELLM_*` do LiteLLM foi identificada;
- cada alias de produção tem um mapeamento explícito no Phaseo;
- os padrões compartilhados ficam em predefinições ou em uma única função de fronteira;
- os callbacks e a telemetria necessários têm um substituto;
- você decidiu se o LiteLLM, o Phaseo ou os dois são a fonte oficial de gastos;
- o rollback ainda é só uma troca de URL base e chave.
