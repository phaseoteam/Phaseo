ストリーミングされる各イベントやアイテムの type で分岐し、テキスト、推論、ツール呼び出し、進捗を届いた順に表示します。後で、保存した実行結果から同じタイムラインを組み立て直せます。TypeScript は型付きのアイテムのユニオンを返し、その他の言語は生のイベントをマップ、dict、ハッシュとして返します。

## ストリーミングしたタイムラインを表示する

for await (const item of stream.getItemsStream()) {
  switch (item.type) {

Rust にはストリーミングがありません。下のように、完了した実行からタイムラインを組み立ててください。

## TypeScript のアイテムの型

`AgentItem<TOutput>` は判別可能なユニオンで、TypeScript は各アイテムを `type` から型を絞り込みます。

| `type` | 主なフィールド | 表すもの |
| --- | --- | --- |
| `message` | `role`（常に `assistant`）、`content` | アシスタントのテキスト |
| `reasoning` | `text` | モデルが提供した推論 |
| `tool_call` | `toolCallId`、`name`、`input` | 提案されたツール呼び出し |
| `tool_result` | `toolCallId`、`name`、`output` | 完了したツール呼び出し |
| `error` | `message`、任意のツール詳細 | プロバイダーまたはツールのエラー |
| `output` | `value` | パース済みのエージェントの最終出力 |

プロバイダーの出力から作られたアイテムは、移植可能な型に含まれないまれなフィールドのために、元のペイロードを `rawProviderItem` にも保持します。`rawProviderItem` はプロバイダーによって異なるため、製品のロジックは移植可能なフィールドの上に組み立ててください。

## その他の言語のイベントの種類

Go、C#、PHP、Ruby、Java は同じ種類のイベントを返します。Python の `item_stream()` は、プロバイダーとランタイムのアイテムを `type` キーを持つ dict として返します。

| イベントの種類 | フィールド |
| --- | --- |
| `response.output_text.delta` | `delta`（文字列） |
| `response.reasoning.delta` | `delta`（文字列） |
| `response.item` | `item`（プロバイダーの出力アイテム。型なし） |
| `tool.started`、`tool.completed`、`tool.failed`、`tool.preliminary_result` | `tool_call_id`、`tool_name`、さらに `output`、`error`、`result` のいずれか |

フィールドの置き場所は言語によって異なります。

| 言語 | イベントの形 |
| --- | --- |
| Python | dict。`item.get("type")` を読む |
| Go | `Type` と `Details map[string]any` を持つ `AgentEvent` |
| C# | `Type` と、`object?` 値の `Details` ディクショナリを持つ `AgentEvent` |
| PHP | フラットな配列。ライフサイクルイベントは `type`、`run_id`、`agent_id`、`timestamp`、`status` を持ち、モデルのイベントは `type` と上記のフィールドを最上位に持ちます。 |
| Ruby | シンボルキー（`:type`、`:delta` など）を持つフラットなハッシュ。構成は PHP の配列と同じです |
| Java | `type()` と、`Object` 値の `details()` マップを持つ `AgentEvent` |

どれも型付きのユニオンではないため、UI が使うフィールドは検証し、プロバイダー固有のパースは1つのアダプターの裏にまとめ、不明な種類へのフォールバックを残してください。Go、C#、Java では、モデルのストリームイベントの実行 ID は `"stream"` です。実際の実行 ID にはライフサイクルイベントを使います。ライフサイクルイベントの全一覧は[ライフサイクルフック](./lifecycle-hooks)にあります。

## 実行後にタイムラインを組み立て直す

イベントの履歴は実行が終わった後も読めるため、2回目のモデルリクエストなしで、1つのコンシューマーが表示し、別のコンシューマーがイベントを永続化できます。永続的なタイムラインには、完了した実行結果を保存してください。

<Tabs>
<Tab title="TypeScript">

完了した結果の `items` には、ストリームと同じ順序のアイテムが入っています。

```typescript
const completed = await stream.getResult();

for (const item of completed.items) {
  saveTimelineItem(completed.run.id, item);
}
```

</Tab>
<Tab title="Python">

| フィールド | 内容 |
| --- | --- |
| `run` | 永続的な状態：`id`、`status`、`input`、`context`、`pause`、`stop_reason`、`error`、`usage`、`next_turn_params` |
| `steps` | モデルターンごとに1つの `AgentStepRecord`。`request_id`、`native_response_id`、`provider`、`model`、`model_attempts`、`usage`、`finish_reason`、`warnings`、`tool_calls` を持ちます |
| `messages` | ツールの結果を含む会話全体 |
| `output` | `parse_output` と `output_schema` を通した後の最終出力 |
| `usage` | `AgentUsageSummary` の合計：入力、出力、キャッシュ、合計のトークン数と、コスト |

</Tab>
<Tab title="Go">

`result.Messages` にはすべてのモデルとツールのメッセージが、`result.Steps` には各ターンのツール呼び出し、リクエスト ID、プロバイダー、モデル、使用量が入っています。

</Tab>
<Tab title="C#">

`result.Messages` にはすべてのモデルとツールのメッセージが、`result.Steps` には各ターンのツール呼び出し、リクエスト ID、プロバイダー、モデル、終了理由、警告、使用量が入っています。

</Tab>
<Tab title="PHP">

`$result->messages` にはすべてのモデルとツールのメッセージが、`$result->steps` には各ターンのツール呼び出し、リクエスト ID、プロバイダー、モデル、終了理由、警告、使用量が入っています。

</Tab>
<Tab title="Ruby">

`result.messages` にはすべてのモデルとツールのメッセージが、`result.steps` には各ターンのツール呼び出し、リクエスト ID、プロバイダー、モデル、終了理由、警告、使用量が入っています。

</Tab>
<Tab title="Java">

`fullStream()` は、実行が終わるとイベントの完全な履歴を返します。`messages()` にはすべてのモデルとツールのメッセージが、`steps()` には各ターンのツール呼び出し、リクエスト ID、プロバイダー、モデル、終了理由、警告、使用量が入っています。

</Tab>
<Tab title="Rust">

`RunResult` には、`run`（ステータス、ID、実際に使われたモデル、ステップ上限、コンテキスト、一時停止の状態）、`steps`（各モデルターンのリクエスト ID、プロバイダー、モデル、終了理由、ツール呼び出し、使用量）、`messages`（モデルとツールのメッセージの完全な履歴）、`output`、`usage` があります。

</Tab>
</Tabs>
