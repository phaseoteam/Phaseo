icon: "list"

モデル、サービスティア、料金、制限をカタログフィードとして公開すると、Phaseo は各変更をオファーに取り込みます。承認済みのプロバイダーは、フィードまたはプロバイダー設定から既存の公開正規モデルのオファーを更新できます。新しい正規モデルには承認が必要です。各カタログは完全なスナップショットです。オファーを削除すると、フィードで管理されているそのオファーは終了し、料金履歴は残ります。

## 形式を選ぶ

| バージョン | 宣言 | 追加される内容 | スキーマ |
| --- | --- | --- | --- |
| V1 | `schema_version` なし、または `"1.0"` | `{"data": [...]}` 内の Standard ティアのオファー | [V1](https://phaseo.app/api/internal/provider-catalog/schema) |
| V1.1 | `"schema_version": "1.1"` | 各モデル内の `service_tiers` | [V1.1](https://phaseo.app/api/internal/provider-catalog/schema?version=1.1) |
| V1.2 | `"schema_version": "1.2"` | ティアごとの `data_policy` と任意の `declarations`。[データポリシーを宣言する](#declare-data-policies)を参照 | [V1.2](https://phaseo.app/api/internal/provider-catalog/schema?version=1.2) |

3 つのバージョンすべてに対応しており、既存の V1 フィードはそのまま動作し続けます。インポーターはバージョンを URL ではなく常にドキュメントから読み取るため、`?format=phaseo-v1.1` のようなクエリパラメーターは自分のエンドポイント向けの慣習にすぎません。対応していないバージョンは拒否されます。

## データポリシーを宣言する

V1.2 では、各サービスティアに機能ごとの学習と保持の宣言が加わります。V1.2 はいつでも公開できます。Phaseo はインポート時に宣言を検証しますが、Phaseo がポリシーの情報源を承認するまで、宣言は何の保証も与えません。

V1.2 では、モデルの識別情報、型付きの入出力の制限、パラメーターの説明、範囲を限定した料金と容量、割引、デプロイの詳細について、モデルレベルまたはティアレベルの任意の `declarations` も受け付けます。これらは検証され、レビューのために保持されます。パラメーターを自動で有効にしたり、課金される料金、容量の制御、データ所在地の保証を変えたりすることはありません。検証のフィードバックには保存された宣言が示されます。実際の料金と機能は、引き続き既存のフィールドで公開してください。

`schema_version` を `"1.2"` に設定し、該当する各ティアに `data_policy` オブジェクトを追加します。

```json
{
  "capabilities": [{
    "id": "text.generate",
    "training_policy": "no_train",
    "retention_mode": "none",
    "retention_days": 0,
    "zero_data_retention": true,
    "zdr_eligibility": "eligible",
    "requirements": { "contract_mode": "none", "account_settings": [] },
    "privacy_policy_url": "https://provider.example/privacy",
    "terms_of_service_url": "https://provider.example/terms"
  }]
}
```

この例はティアの `data_policy` の値で、フィード全体ではありません。機能 ID は正規のものです。モデルが `responses` や `chat.completions` を宣言している場合でも `text.generate` を使ってください。

宣言は、上流の処理チェーン全体でのプロンプトと出力の両方を対象とします。課金メタデータは対象外です。学習の値は `unknown`、`may_train`、`no_train`、`opt_out_available`、`enterprise_no_train` です。保持モードは `unknown`、`none`、`transient`、`fixed`、`until_deleted` です。none にはゼロ日、transient と fixed には正の最大期間、unknown と until-deleted には null を使います。

必要な契約は `contract_mode` で宣言します。値は `none`、`customer_agreement`、`enterprise_agreement` です。必要なアカウント設定は、`id`、`description`、HTTPS の `documentation_url` を持つオブジェクトとして `account_settings` 配列に入れます。条件付きのプログラムは `zdr_eligibility: "conditional"` を使い、有効な true の保証を宣言することはできません。Phaseo が条件の充足を検証できるまでは、情報としてのみ扱われます。

Phaseo はポリシーの情報源を独自に承認します。フィードが宣言を検証済みとすることはできません。このリリースで有効な ZDR が与えられるのは、バッチ以外のオファーでの無条件のテキスト生成で、学習なし、コンテンツの保持なしの場合だけです。モデルを自分でホストしているだけでは ZDR の宣言にはなりません。

オファーがフィードで管理されるポリシーを採用した後に、false を設定する、null を送る、宣言を省略する、またはフィードのバージョンを下げると、その保証は取り消されます。Phaseo による手動の上書きは別に管理されます。肯定的な宣言は、カタログの検証が 24 時間成功しないと失効します。承認の取り消しには、プロバイダーからの新しい取得は必要ありません。

## 正規化されたティアを公開する

| ティア | 意味 |
| --- | --- |
| `standard` | 通常の同期実行。すべてのモデルで必須です。 |
| `fast` | より高速な、または優先のオファー。HighSpeed のようなプロバイダー側の名前は上流モデル ID に残します。 |
| `ultrafast` | 対応している場合の、別の、さらに高速なオファー。 |
| `flex` | 柔軟で優先度の低い同期オファー。 |
| `batch` | Batch API による非同期実行。バッチ機能が必要です。 |

プロバイダー独自のティア名を正規化された ID として使わないでください。`priority` は呼び出し元向けの Fast のエイリアスとして引き続き使えますが、カタログでは `fast` を公開します。

Fast、Ultrafast、Flex の選択は、テキスト生成のリクエストで使えます。Batch は別の Batch API で実行され、プロバイダーの Batch 連携がインストールされている必要があります。ティアを公開してもその連携はインストールされません。アップロードしたプロバイダー独自形式のファイルには、宣言した Batch のモデル ID を使うか、Phaseo が変換できるようにリクエストをインラインで送信してください。

サービスティアには同じ正規モデル ID を使います。異なるモデルには別々の正規 ID が必要です。ティアはモデルの機能、制限、リリーススケジュールを引き継ぎます。各ティアは、それぞれの上流モデル ID、提供状況、実際の料金を宣言します。

```json
{
  "schema_version": "1.1",
  "data": [{
    "id": "your-provider/example-model",
    "name": "Example model",
    "capabilities": ["chat.completions"],
    "service_tiers": [{
      "service_tier": "standard",
      "provider_model_slug": "example-model",
      "availability": "ready",
      "pricing": [{
        "meter_key": "input_text_tokens",
        "modality": "text",
        "direction": "input",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 100000000,
        "display_label": "Input",
        "display_unit": "1M tokens"
      }, {
        "meter_key": "output_text_tokens",
        "modality": "text",
        "direction": "output",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 200000000,
        "display_label": "Output",
        "display_unit": "1M tokens"
      }]
    }]
  }]
}
```

Fast を追加するには、`"service_tier": "fast"`、その実際の料金、そのオファー用の別の上流モデル ID を持つティアオブジェクトをもう 1 つ追加します。プロバイダーがネイティブのパラメーターでレーンを選ぶ場合は、同じ上流モデル ID を使い、`"upstream_service_tier": "priority"` または `"fast"` を宣言します。モデル ID でレーンが選ばれる場合は、このフィールドを省略してください。Standard は `default` または `standard` を受け付け、Flex と Ultrafast はそれぞれ対応する値を受け付けます。別のモデル ID もネイティブのセレクターもない Standard 以外の同期ティアは、Phaseo が拒否します。

すべてのティアには、出力や課金するキャッシュ、メディアのメーターを含め、明示的な料金が必要です。ゼロの料金は有効です。負の料金、不明なメーター、重複したティア、条件付きの料金は拒否されます。`price_nanos` はプロモーション適用後の実際の料金です。料金が変わったら新しいスナップショットを公開してください。Phaseo は以前の実際の料金を保持します。

## レート制限を宣言する

プラットフォームが Phaseo のアカウントに適用するリクエストとトークンの制限は、任意のトップレベルの `rate_limits` 配列で宣言します。V1 と V1.1 のドキュメントで同じように機能します。すべてのモデルにわたる制限なら `model` を省略し、そうでなければ同じドキュメント内のいずれかのモデルまたはティアの上流 `provider_model_slug` を設定します。

```json
{
  "schema_version": "1.1",
  "data": [{ "id": "your-provider/example-model", "...": "..." }],
  "rate_limits": [
    { "requests_per_minute": 600, "tokens_per_minute": 2000000 },
    { "model": "example-model", "requests_per_day": 100000, "tokens_per_day": 500000000 }
  ]
}
```

各エントリは `requests_per_minute`、`requests_per_day`、`tokens_per_minute`、`tokens_per_day` を受け付けます。各値は正の整数か `null` で、各エントリには少なくとも 1 つの値が必要です。Phaseo は各制限を、自社からあなたへのすべてのトラフィックについて全体で数えます。モデルの制限は、すべてのモデルにわたる制限に加えて適用されます。

制限がリクエストをブロックすることはありません。オファーのトラフィックが制限に近づくと、Phaseo はそのオファーに送る割合を徐々に減らします。制限に達すると、制限がリセットされるまで Phaseo はそのオファーを他のプロバイダーより下位にランク付けします。低すぎる値は自分のトラフィックの割合を減らすだけです。そのため、プロバイダーの申請が承認されていれば、制限はレビューなしで、通常 1 分以内に適用されます。

配列がある場合、変更されたフィードのインポートが成功するたびに、宣言済みの制限が置き換えられます。空の配列を送ると制限は削除されます。プロバイダー設定で管理している制限を維持するには、`rate_limits` を省略してください。ドキュメントにないモデルを指定したエントリ、範囲の重複、正の整数でない値がある場合、Phaseo はスナップショット全体を拒否し、現在のカタログと制限を維持します。拒否は **修正が必要** として表示されます。

制限は **プロバイダー設定 → 自分のモデル → レート制限** でも編集できます。その編集はカタログの変更とは別に保存されます。カタログエディターは `rate_limits` を受け付けません。

## 更新して確認する

ポーリングと署名付きのカタログ変更 Webhook は、同じオンボーディングと更新のフローで3 つのバージョンすべてを受け付けます。プロバイダー設定では、上流 ID、提供状況、料金を編集する前にティアを選択してください。ティアをもう 1 つ追加すると、保存されたカタログは V1.1 に変わります。

カタログによって推論アダプターや認証情報が追加されることはありません。ルーティングを有効にする前に、プロバイダーとその公表している機能が連携されている必要があります。Batch の料金があっても、同期のチャットエンドポイントで Batch が使えるようにはなりません。

利用できない正規モデルや不明な公開者の対応付けは **修正が必要** として表示されますが、有効なモデルのインポートは妨げられません。モデルごとの理由はプロバイダーダッシュボードで確認してください。

API で提供されるカタログでは、ダッシュボードでの編集は永続的な上書きになります。インポートは上書きのないフィールドを更新します。上書きを削除してそのフィールドを再びフィードに従わせるには、**フィード値を使用** を選択します。ダッシュボードには最新のフィードの値、実際の値、編集者、日時が表示され、カタログのアクティビティには編集と元に戻した操作が記録されます。手動で追加したモデルはローカルのオファーのままです。フィードからモデルを削除すると、一部のフィールドが編集されていても、そのフィードのオファーは終了します。既存の手動のみのカタログも引き続きサポートされます。
