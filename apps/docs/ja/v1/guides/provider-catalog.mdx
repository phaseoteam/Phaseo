承認済みプロバイダーは、カタログフィードまたはプロバイダー設定から、公開済みの既存の正規モデルに対するオファーを更新できます。新しい正規モデルには承認が必要です。各カタログは完全なスナップショットです。オファーを削除すると、フィードで管理されているそのオファーは廃止され、料金履歴は保持されます。

## 形式の選択

既存の V1 フィードは変更なしでそのまま利用できます。バージョン指定のない `{"data": [...]}` ドキュメント、または `"schema_version": "1.0"` を宣言したドキュメントは、既存の Standard 階層の形式を使用します。

V1.1 は `"schema_version": "1.1"` を宣言し、各モデルの中で `service_tiers` を公開します。インポーターはドキュメントの内容から形式を判断します。`?format=phaseo-v1.1` などの URL クエリパラメーターは、エンドポイント側で任意に使える慣例にすぎず、Phaseo が URL からバージョンを推測することはありません。

[V1 スキーマ](https://phaseo.app/api/internal/provider-catalog/schema) または [V1.1 スキーマ](https://phaseo.app/api/internal/provider-catalog/schema?version=1.1) をダウンロードしてください。サポートされていないバージョンは明示的に拒否されます。

### V1.2 データポリシー（プレビュー）

V1.2 では、各サービス階層に、機能ごとのトレーニングと保持に関する宣言を追加できます。これらのフィールドを公開する前に、Phaseo と有効化を調整してください。古いインポーターはこれらを拒否します。V1 と V1.1 のフィードは引き続きサポートされます。

V1.2 では、モデルまたは階層ごとに任意の `declarations` も指定できます。モデルの識別情報、型付き入出力制限、パラメータの説明、適用範囲ごとの料金と処理能力、割引、デプロイの詳細を記述できます。これらは検証後、レビュー用に保存されます。パラメータの有効化、請求料金、処理能力制限の適用、データ所在地の保証を自動的に変更するものではありません。検証結果には保存された宣言が示されます。実際に適用する料金と機能は、引き続き既存のフィールドで公開してください。

`schema_version` を `"1.2"` に設定し、対象の各階層に `data_policy` オブジェクトを追加します。

```json
{
  "capabilities": [{
    "id": "text.generate",
    "training_policy": "no_train",
    "retention_mode": "none",
    "retention_days": 0,
    "zero_data_retention": true,
    "zdr_eligibility": "eligible",
    "requirements": { "contract_mode": "none", "account_settings": [] },
    "privacy_policy_url": "https://provider.example/privacy",
    "terms_of_service_url": "https://provider.example/terms"
  }]
}
```

この例は階層の `data_policy` の値であり、完全なフィードではありません。機能 ID は正規 ID です。モデルが `responses` や `chat.completions` を宣言していても、`text.generate` を使用してください。

宣言は、上流の処理チェーン全体にわたるプロンプトと出力の両方を対象とします。請求メタデータは対象外です。トレーニングの値は `unknown`、`may_train`、`no_train`、`opt_out_available`、`enterprise_no_train` です。保持モードは `unknown`、`none`、`transient`、`fixed`、`until_deleted` です。none には 0 日、transient/fixed には正の最大保持期間、unknown/until-deleted には null を指定します。

必要な契約は `contract_mode` で宣言します。値は `none`、`customer_agreement`、`enterprise_agreement` です。必要なアカウント設定は、`id`、`description`、HTTPS の `documentation_url` を持つオブジェクトとして `account_settings` 配列に指定します。条件付きプログラムでは `zdr_eligibility: "conditional"` を使用し、有効な保証として true を宣言することはできません。Phaseo が条件の充足を検証できるまでは、参考情報として扱われます。

Phaseo はポリシーの情報源を独立して承認します。フィードから宣言を検証済みにすることはできません。このリリースでは、トレーニングもコンテンツ保持も行わない、非バッチの無条件テキスト生成にのみ有効な ZDR を認めます。モデルを自社でホストしているだけでは、ZDR の宣言にはなりません。

フィード管理のポリシーを採用した後は、false の設定、null の送信、宣言の省略、フィードバージョンの引き下げによって保証が撤回されます。Phaseo の手動オーバーライドは別途管理されます。カタログの検証に 24 時間成功しなかった場合、肯定的な宣言は失効します。承認の取り消しにプロバイダーからの再取得は必要ありません。

## 正規化された階層の公開

| 階層 | 意味 |
| --- | --- |
| `standard` | 通常の同期実行です。すべてのモデルで必須です。 |
| `fast` | より高速な、または優先度の高いオファーです。HighSpeed などのプロバイダー独自の名称は、上流モデル ID の中に残します。 |
| `ultrafast` | 対応している場合に提供される、さらに高速な別のオファーです。 |
| `flex` | 柔軟で優先度の低い同期オファーです。 |
| `batch` | Batch API による非同期実行です。Batch 機能が必要です。 |

プロバイダー固有の階層名を正規化 ID として使用しないでください。`priority` は呼び出し側が Fast を指定するためのエイリアスとして引き続きサポートされますが、カタログでは `fast` を公開します。

Fast、Ultrafast、Flex の選択はテキスト生成リクエストで利用できます。Batch は別の Batch API を通じて実行され、プロバイダーの Batch 連携がインストールされている必要があります。階層を公開しても、その連携はインストールされません。プロバイダーネイティブ形式のファイルをアップロードする場合は、宣言された Batch モデル ID を使用するか、Phaseo が変換できるようにリクエストをインラインで送信してください。

同じモデルのサービス階層には、同じ正規モデル ID を使用します。異なるモデルには、それぞれ別の正規 ID が必要です。階層は、モデルの機能、制限、リリーススケジュールを継承します。各階層では、独自の上流モデル ID、利用可否、実効料金を宣言します。

```json
{
  "schema_version": "1.1",
  "data": [{
    "id": "your-provider/example-model",
    "name": "Example model",
    "capabilities": ["chat.completions"],
    "service_tiers": [{
      "service_tier": "standard",
      "provider_model_slug": "example-model",
      "availability": "ready",
      "pricing": [{
        "meter_key": "input_text_tokens",
        "modality": "text",
        "direction": "input",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 100000000,
        "display_label": "Input",
        "display_unit": "1M tokens"
      }, {
        "meter_key": "output_text_tokens",
        "modality": "text",
        "direction": "output",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 200000000,
        "display_label": "Output",
        "display_unit": "1M tokens"
      }]
    }]
  }]
}
```

Fast を追加するには、`"service_tier": "fast"`、その実効料金、そのオファー専用の別の上流モデル ID を含む階層オブジェクトをもう 1 つ追加します。プロバイダーがモデル ID ではなくネイティブパラメーターで処理レーンを選択する場合は、同じ上流モデル ID を使用し、`"upstream_service_tier": "priority"` または `"fast"` を宣言します。モデル ID でレーンが選択される場合は、このフィールドを省略してください。Standard は `default` または `standard` を受け付け、Flex と Ultrafast はそれぞれ対応する値を受け付けます。別のモデル ID もネイティブのセレクターもない Standard 以外の同期階層は、Phaseo によって拒否されます。

各階層には、出力や課金対象のキャッシュ／メディアのメーターを含め、明示的な料金が必要です。ゼロの料金は有効ですが、負の料金、不明なメーター、重複した階層、条件付き料金は拒否されます。`price_nanos` は引き続き、割引適用後の実効料金を表します。料金が変わったときは新しいスナップショットを公開してください。Phaseo は以前の実効料金を保持します。

## レート制限の宣言

プラットフォームが Phaseo のアカウントに適用するリクエスト数とトークン数の上限は、任意の最上位配列 `rate_limits` で宣言します。V1 と V1.1 のどちらのドキュメントでも同じように機能します。すべてのモデルにまたがる制限では `model` を省略し、特定のモデルに対する制限では、同じドキュメント内にあるモデルまたは階層の上流 `provider_model_slug` を指定します。

```json
{
  "schema_version": "1.1",
  "data": [{ "id": "your-provider/example-model", "...": "..." }],
  "rate_limits": [
    { "requests_per_minute": 600, "tokens_per_minute": 2000000 },
    { "model": "example-model", "requests_per_day": 100000, "tokens_per_day": 500000000 }
  ]
}
```

各エントリは `requests_per_minute`、`requests_per_day`、`tokens_per_minute`、`tokens_per_day` を受け付けます。各値は正の整数または `null` で、各エントリには少なくとも 1 つの値が必要です。Phaseo は各制限を、プロバイダーへ送るすべてのトラフィック全体でグローバルにカウントします。モデルの制限は、すべてのモデルにまたがる制限に加えて適用されます。

制限によってリクエストがブロックされることはありません。オファーのトラフィックが上限に近づくと、Phaseo はそのオファーに送るトラフィックの割合を徐々に減らします。上限に達すると、制限がリセットされるまでオファーを他のプロバイダーより後に並べます。値が低すぎても、減るのは自分のトラフィックの割合だけです。そのため、プロバイダー申請が承認されていれば、制限は審査なしで適用され、通常は 1 分以内に反映されます。

配列がある場合、変更されたフィードの取り込みが成功するたびに、宣言済みの制限が置き換えられます。空の配列を指定すると制限は削除されます。プロバイダー設定で管理している制限を維持するには、`rate_limits` を省略します。ドキュメントにないモデルを指定したエントリ、スコープの重複、正の整数ではない値のいずれかがある場合、Phaseo はスナップショット全体を拒否し、現在のカタログと制限を維持します。拒否された場合は **修正が必要** と表示されます。

制限は **プロバイダー設定 → あなたのモデル → レート制限** でも編集できます。これらの編集はカタログの変更とは別に保存されます。カタログエディターは `rate_limits` を受け付けません。

## 更新と確認

ポーリングと署名付きのカタログ変更 Webhook は、同じオンボーディングと更新のフローで両方のバージョンを受け付けます。プロバイダー設定では、上流 ID、利用可否、料金を編集する前に階層を選択してください。階層を追加すると、保存されたカタログは V1.1 に変わります。

カタログによって推論アダプターや認証情報が追加されることはありません。ルーティングを有効にする前に、プロバイダーと、そのプロバイダーが提示する機能を統合しておく必要があります。Batch の料金を公開しても、同期のチャットエンドポイントで Batch が利用できるようにはなりません。

利用できない正規モデルや不明な公開元の対応付けは **修正が必要** と表示されますが、有効なモデルの取り込みは妨げられません。モデルごとの理由はプロバイダーダッシュボードで確認してください。

API でフィードされるカタログでは、ダッシュボードでの編集は永続的なオーバーライドになります。取り込みでは、オーバーライドのない項目が更新されます。オーバーライドを解除してその項目を再びフィードに追従させるには、**フィード値を使用** を選択します。ダッシュボードには最新のフィード値、適用中の値、編集者、日時が表示され、カタログのアクティビティには編集と取り消しが記録されます。手動で追加したモデルはローカルのオファーとして残ります。フィードからモデルを削除すると、一部の項目が編集されていても、そのフィードのオファーは廃止されます。既存の手動専用カタログも引き続きサポートされます。
