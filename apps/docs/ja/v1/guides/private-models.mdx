専用デプロイやセルフホストのデプロイをワークスペースに追加すると、チームは `acme/legal-assistant` のようなモデル ID を使って通常の Phaseo API から呼び出せます。参照や呼び出しができるのは自分のワークスペースだけで、公開モデル ID が使える場所ならどこでも使えます。

主な接続元は、Baseten、Modal、RunPod、Fireworks、Together の専用デプロイや、vLLM などの OpenAI 互換サーバーを実行しているサーバーです。

## 始める前に

デプロイは次を備えている必要があります。

- 公開 HTTPS のベース URL
- OpenAI 互換の `/chat/completions` エンドポイント
- Bearer トークン認証
- そのエンドポイントが受け付ける上流のモデル ID またはデプロイ ID

`/responses` への対応は任意です。デプロイがそのエンドポイントを明示的に実装していない限り、無効のままにしてください。

<Warning>
プライベートモデルは、プロバイダー独自のプロトコルや独自の認証方式には対応しません。そうしたデプロイの前に OpenAI 互換レイヤーを置くか、Phaseo が対応しているプロバイダー連携を使ってください。
</Warning>

## デプロイを接続する

<Steps>
<Step title="プライベートモデルを開く">

**ダッシュボード → 設定 → ワークスペース → プライベートモデル** を開き、**モデルを追加** を選択します。ワークスペースのオーナーまたは管理者である必要があります。CLI からは、同じフィールドを指定して `phaseo private-models create` を実行し、認証情報は `--credential-stdin` で渡します。

</Step>

<Step title="モデルに名前を付ける">

既存のカタログモデルを選んでそのプロバイダー一覧にこのデプロイを追加するか、`legal-assistant` のような短いモデルスラッグを入力します。その一意のスラッグを持つカタログモデルがない場合、Phaseo は信頼済みのワークスペース名前空間とスラッグを組み合わせます。

```text
acme/legal-assistant
```

ワークスペースの名前空間は選択も置き換えもできません。カタログの ID を正確に指定した場合は、そのモデルの公開 ID を変えずにそのモデルに追加されます。

</Step>

<Step title="エンドポイントを設定する">

推論パスの手前までのベース URL を入力します。たとえば次のように指定します。

```text
https://model.example.com/v1
```

`/chat/completions` や `/responses` は含めないでください。上流のモデル ID またはデプロイ ID は別の欄に正確に入力します。Phaseo はリクエストを転送するときにこの ID に置き換えます。

</Step>

<Step title="認証情報を保存する">

デプロイの API キーを入力します。Phaseo は認証情報を暗号化し、保存後は二度と返しません。後からモデルの設定ページで置き換えられます。

</Step>

<Step title="モデルを呼び出す">

生成されたモデル ID を、通常の Chat Completions エンドポイントで使います。

```bash cURL
curl https://api.phaseo.app/v1/chat/completions \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "acme/legal-assistant",
    "messages": [{"role": "user", "content": "Summarize this contract."}]
  }'
```

呼び出しに使う API キーは、プライベートモデルと同じワークスペースに属している必要があります。

</Step>
</Steps>

## ルーティングの仕組み

単独のワークスペースモデルは、設定したエンドポイントにのみルーティングされます。カタログモデルに追加したエンドポイントは、ルーティングポリシーに従ってそのモデルのプロバイダー一覧に加わります。

| ダッシュボード | API の `routing_policy` | 効果 |
| --- | --- | --- |
| **優先**（既定） | `preferred` | モデルの公開プロバイダーより先に自分のデプロイが試されます。 |
| **通常のプール** | `balanced` | 自分のデプロイが公開プロバイダーと並んでランク付けされます。 |
| **フォールバックのみ** | `fallback` | 公開プロバイダーの後にのみ自分のデプロイが試されます。 |

Phaseo は保存された認証情報を Bearer トークンとして送り、設定された上流モデル ID に置き換えます。

プライベートモデルが公開プロバイダールートになることはなく、他のワークスペースからは見えません。有効なプライベートモデルは認証済みのモデルカタログに含まれ、**非公開** フィルターの下に表示されます。

<Note>
プライベートデプロイを追加、変更、または有効にした後は、ルーティングをテストするまで最大 1 分待ってください。それまでは一部のリクエストが、モデルの公開プロバイダーなど以前の設定を使う場合があります。すでに処理中のリクエストは別のルートに回されません。
</Note>

## プロバイダー別の例

| デプロイ | 入力する内容 |
| --- | --- |
| Baseten の専用エンドポイント | OpenAI 互換のベース URL、デプロイのモデル ID、API キー |
| Modal の Web エンドポイント | OpenAI Chat Completions の仕様を実装した公開 HTTPS エンドポイント |
| RunPod のサーバーレスエンドポイント | OpenAI 互換のプロキシ URL と Bearer 認証情報 |
| Fireworks または Together の専用デプロイ | 専用の OpenAI 互換 URL とプロバイダーのモデル ID |
| vLLM | `/v1` で終わる公開 URL と、vLLM が提供するモデル名 |

プロバイダーの製品や URL の形式は変わることがあります。ベース URL、モデル ID、認証方式、対応エンドポイントは、プロバイダーの最新のデプロイドキュメントで確認してください。

## API でプライベートモデルを管理する

サーバー側の管理には、必要に応じて `private_models:read`、`private_models:write`、`private_models:delete` を持つ管理キーで [Private Models API](../api-reference/endpoint/private-models-list) を使えます。

作成と更新のリクエストは `model_reference` を受け付けます。カタログモデルの正確な ID か短いスラッグのどちらかです。`model_id` は Phaseo が導出し、クライアントが直接送ることはできません。既存の Phaseo プロバイダーには `host_provider_id` を、それ以外の運営者には `custom_provider_name` と任意の `custom_provider_url` を使います。

## トラブルシューティング

- **プロバイダーから 404 が返る:** ベース URL が推論パスの手前で終わっているか確認してください。
- **不明なモデル:** プロバイダーの上流デプロイ ID を **上流モデルID** にコピーします。そこに Phaseo のワークスペースモデル ID を使わないでください。
- **上流リクエストが認証されない:** 保存した認証情報を置き換え、プロバイダーが Bearer 認証を受け付けることを確認してください。
- **Chat は動くが Responses が失敗する:** プロバイダーが `/responses` をネイティブに実装していない限り、**Responses API** を無効にしてください。
- **モデルがカタログに表示されない:** モデルが有効になっていること、呼び出し元が同じワークスペースで認証されていることを確認してください。
