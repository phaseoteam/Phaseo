Phaseo が正常かどうかは[ステータスページ](https://status.phaseo.app)と `GET /v1/health` で、モデルを今ルーティングできるかどうかは `GET /v1/models` で、ルートが信頼性目標を満たすかどうかは自分で行うテストで確認します。

## 現在のサービス状態を確認する

1. [Phaseo のステータスページ](https://status.phaseo.app)を開き、現在のインシデントと過去のインシデント履歴を確認します。
2. `GET /v1/health` を呼び出して、Gateway の最小限のヘルスチェックを行います。
3. 1 件のリクエストが失敗した場合は、サービス全体が停止していると判断する前に、そのリクエスト ID を控え、アクティビティまたは生成レコードを確認します。

```bash
curl https://api.phaseo.app/v1/health
```

```json
{
  "status": "ok"
}
```

<Note>
公開ステータスページはサービスの状態を報告するものです。Phaseo は現在、契約上の公開稼働率 SLA を掲げていません。
</Note>

## モデルがルーティング可能か確認する

Phaseo のカタログには、Gateway がルーティングできる数より多くのモデルが掲載されています。カタログに載っているのは Phaseo がそのモデルを追跡しているという意味であり、公開ルートが存在するという意味ではありません。`GET /v1/models` は既定で、現在ルーティング可能なモデルのみを返します。

```bash
curl https://api.phaseo.app/v1/models \
  -H "Authorization: Bearer $PHASEO_API_KEY"
```

近日公開や非アクティブのマッピングも表示するには `availability=all` を追加します。本番トラフィックは、`availability_status` が `active` で、`is_active_gateway` が `true` のプロバイダー行にのみ送ってください。モデルページのステータスアイコンの意味は[プロバイダーと Phaseo のステータス](../guides/provider-statuses.mdx)を参照してください。

| 状態 | 意味 |
| --- | --- |
| `active` | 少なくとも 1 つの公開 Gateway ルートが現在利用可能です。 |
| `coming_soon` | Phaseo は計画中またはプレビューのルートを追跡していますが、公開ルーティングはできません。 |
| `inactive` | 既知のルートが無効、利用不可、期限切れ、またはその他の理由でルーティングできません。 |
| `not_listed` | このモデルには現在、Gateway のプロバイダーマッピングが掲載されていません。 |

`active` は、稼働率、すべてのリージョンでのアクセス、すべてのワークスペースで同じ商用条件を保証するものではありません。

## パフォーマンス指標を読み取る

Phaseo のパフォーマンスデータは、Gateway を経由した実際のリクエストを集計したもので、管理された環境でのベンチマークではありません。

| 指標 | 定義 |
| --- | --- |
| Gateway TTFT | Gateway でのリクエスト開始から、内容を含む最初の生成出力まで。 |
| Provider TTFT | プロバイダーへの送信から、内容を含む最初の生成出力まで。 |
| Provider duration | プロバイダーへの送信から、最終レスポンスまで。 |
| Gateway E2E | Gateway でのリクエスト開始から完了まで。 |
| Phaseo overhead | Gateway E2E と Provider duration の差（負にならない値）。 |
| Effective throughput | すべての出力トークンを、プロバイダーでの処理時間全体で割った値。 |
| Output speed | 最初のトークン以降の出力トークンを、TTFT 以降のプロバイダー時間で割った値。 |

TTFT と Output speed には、内容を含む最初の出力があるストリーミングレスポンスが必要です。ストリーミングしないリクエストも処理時間と Effective throughput には反映されますが、TTFT には反映されません。

どの指標も、期間、ルート、リージョン、ストリーミングモード、パーセンタイルとあわせて読んでください。プロバイダーの負荷、プロンプトの長さ、出力の長さ、リトライ、ネットワーク状況はすべて結果に影響します。

完全な定義は、[料金とパフォーマンス](../exploring/pricing-performance)と [Phaseo がレイテンシーとスループットを測定する方法](https://phaseo.app/how-phaseo-measures-latency-throughput)を参照してください。

## 自分のワークロードで検証する

公開指標は傾向を示すものであり、ルートが本番の目標を満たすことを証明するものではありません。展開する前に、小規模で再現可能なテストを実行してください。

1. 機密性の高い本番データを取り除き、代表的なプロンプトの構成を維持します。
2. モデル ID、エンドポイント、プロバイダーの制約、リージョン、ストリーミングモード、同時実行数を記録します。
3. 1 件のリクエストではなく分布を比較できるだけの回数を繰り返します。
4. 成功率、Gateway TTFT、Provider duration、Gateway E2E、出力トークン、最終コストを記録します。
5. 無効なキー、無効なモデル、レート制限、プロバイダー利用不可による失敗をテストします。
6. 別のエンジニアが結果を再現できるよう、リクエスト ID と正確な期間を保存します。

許可と文書化された手法なしに、顧客名、引用、ワークロードの結果、信頼性の割合を公開しないでください。

## 失敗したリクエストを切り分ける

1. [サービスのステータス](https://status.phaseo.app)を確認します。
2. モデルが既定の [`GET /v1/models`](../api-reference/endpoint/models) レスポンスに引き続き含まれていることを確認し、その[エンドポイント](../api-reference/endpoint/model-endpoints)を確認します。
3. [エラーとデバッグ](../api-reference/errors)で HTTP ステータスとエラーコードを調べます。
4. 一時的な `429` と `5xx` レスポンスは、上限付きの指数バックオフでリトライします。[レート制限](../api-reference/limits.mdx)を参照してください。
5. [サポート](https://phaseo.app/help)に問い合わせる際は、リクエスト ID を控えておきます。

1 つのプロバイダーが失敗してもリクエストが動作し続けるようにするには、[ルーティングとフォールバック](../guides/routing-and-fallbacks)を設定してください。
