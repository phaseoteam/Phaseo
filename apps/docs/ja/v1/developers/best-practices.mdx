Gateway の呼び出しはバックエンドの 1 つのサービスの背後に置き、キーはクライアントやログに含めず、安全に再試行できるものだけを再試行し、モデルごとにレイテンシ、コスト、エラーを監視します。以下の各セクションから、詳しいページにリンクしています。

## 連携の構成を決める

- **Gateway の呼び出しを 1 つのサービスまたは SDK クライアントにまとめる。** モデルやプロバイダーを変更するときに、変更箇所が 1 か所で済みます。[Gateway との連携](./integrating-with-the-gateway.mdx)を参照してください。
- **チャット UI にはレスポンスをストリーミングする。** ユーザーはトークンが届くたびに確認できます。[ストリーミング](../guides/streaming.mdx)を参照してください。
- **急ぎでない処理はキューに入れる。** バックグラウンドでの生成や評価などをキューに入れて、トラフィックの急増を平準化します。[Batch API](../guides/async-video-and-batch.mdx) は大きなジョブを非同期で実行します。

## キーを秘密に保つ

- 本番環境では、API キーを `.env` ファイルではなくシークレットマネージャー（AWS Secrets Manager、Doppler、1Password）に保存します。
- Gateway はバックエンドから呼び出し、自分のクライアントアプリはバックエンドに対して認証させて、クライアントが Gateway のキーを持たないようにします。
- ログに記録するのはキーのプレフィックス（`phaseo_v1_sk_<kid>` など）だけにし、シークレットは決して記録しません。

[認証](./authentication.mdx)を参照してください。

## 安全に再試行する

- `429` と `5xx` のレスポンスは、ジッター付きの指数バックオフで再試行します。
- レート制限されたリクエストは、[`Retry-After`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Retry-After) の時間だけ待ってから再試行します。
- 各リクエストをどのプロバイダーが処理したかをリクエストのログで確認し、トラフィックが別のプロバイダーにフェイルオーバーしたときに気付けるようにします。

[エラーとデバッグ](../api-reference/errors.mdx)と[レート制限](../api-reference/limits.mdx)を参照してください。

## 適切な指標を監視する

| 指標 | 対処 |
| --- | --- |
| レイテンシ | p95 と p99 を追跡して、性能の低下を捉えます。 |
| トークン使用量 | コストを、それが支えるビジネス指標と比較します。 |
| エラー率 | 失敗率が 1% を超えた状態が続いたらアラートを出します。 |
| プロバイダーの構成比 | トラフィックが想定どおりにプロバイダー間で分散しているか確認します。 |

[リクエストログと可観測性](../guides/integrations/observability.mdx)を参照してください。プロンプトのテンプレート、パラメーター、出力の扱いは、チームがレビューできる場所に文書化しておきます。[プリセット](../guides/presets.mdx)を使うと、共有のプロンプトと既定値を 1 か所にまとめられます。
