本番ワークロードに Gateway を導入するには、まず確かな基盤を整えます。次の推奨事項に従って、耐障害性、セキュリティ、保守性を高めましょう。

---

## アーキテクチャ

-   **プロバイダーのロジックを分離する。** Gateway の呼び出しを専用サービスまたは SDK でラップし、変更の影響範囲を限定します。
-   **可能な限りレスポンスをストリーミングする。** 生成されたトークンをすぐに UI へ送信し、アシスタントのレイテンシを下げます。
-   **重要度の低いジョブをまとめる。** バックグラウンドの生成や評価をキューに入れて、トラフィックの急増を抑えます。

---

## セキュリティ

-   本番環境では `.env` ファイルではなく、シークレットマネージャー（AWS Secrets Manager、Doppler、1Password）に API キーを保存します。
-   独自 API でリクエスト署名を有効にし、クライアントアプリケーションから Gateway キーが漏れないようにします。
-   認証情報の漏えいを避けるため、キーは末尾を省略して記録します（例：`sk_prod_abcd...`）。

---

## 信頼性

-   再試行可能なすべてのエラー（HTTP 429 または 5xx）に対し、ジッターを加えた指数バックオフを実装します。
-   レート制限されたリクエストを再試行する前に、[`Retry-After`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Retry-After) ヘッダーに従います。
-   プロバイダーのメタデータを監視し、別のプロバイダーへの自動切り替えを検出します。

---

## 可観測性

| シグナル        | 推奨する対応                                                |
| ------------- | ----------------------------------------------------------------- |
| レイテンシ       | p95 と p99 の時間を追跡して、性能低下を早期に検出します。             |
| トークン使用量   | コストをビジネス指標と照らし合わせ、投資対効果を評価します。            |
| エラー率   | 失敗が一定期間 1% を超えたらアラートを出します。             |
| プロバイダー構成  | トラフィックが想定どおり各プロバイダーに分散されていることを確認します。         |

---

## コラボレーション

-   プロンプトのテンプレート、入力パラメーター、出力の処理方法を社内 Wiki に記録します。
-   ベンチマークの変化とプロダクトへの影響が分かるダッシュボードを共有します。
-   プロダクト、リサーチ、サポートの各チームで定期的にレビューし、動作の一貫性を保ちます。
