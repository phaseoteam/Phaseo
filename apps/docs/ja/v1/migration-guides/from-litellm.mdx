LiteLLM プロキシを呼び出しているクライアントの接続先を Phaseo キーとともに `https://api.phaseo.app/v1` に向け、各 `model_name` エイリアスと各プロキシ設定を一つずつ意図的に対応付けます。LiteLLM を残したまま Phaseo をその上流として使う場合は、[LiteLLM 連携](../guides/integrations/litellm)を参照してください。

| 設定 | LiteLLM プロキシ | Phaseo |
| --- | --- | --- |
| ベース URL | 自分のプロキシ。多くの場合 `http://localhost:4000` | `https://api.phaseo.app/v1` |
| API キー | `LITELLM_MASTER_KEY` または仮想キー | `PHASEO_API_KEY` |
| モデル | `config.yaml` の `model_name` エイリアス | Phaseo のモデル ID、プリセット(`"model": "@slug"`)、または 1 つの対応付け関数 |
| ルーティングと既定値 | `router_settings`、`litellm_settings` | [プリセット](../guides/presets)と[ルーティングとフォールバック](../guides/routing-and-fallbacks) |

## クライアントを切り替える

<CodeGroup>
```typescript TypeScript
import OpenAI from "openai";

// Before:
// new OpenAI({ apiKey: process.env.LITELLM_API_KEY, baseURL: process.env.LITELLM_BASE_URL });
const client = new OpenAI({
  apiKey: process.env.PHASEO_API_KEY,
  baseURL: "https://api.phaseo.app/v1",
});

const response = await client.chat.completions.create({
  model: "openai/gpt-6-astra",
  messages: [{ role: "user", content: "Reply with: migration ready" }],
});
```

```python Python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["PHASEO_API_KEY"],
    base_url="https://api.phaseo.app/v1",
)
```

```bash cURL
curl https://api.phaseo.app/v1/chat/completions \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-6-astra",
    "messages": [{"role": "user", "content": "Reply with: migration ready"}]
  }'
```
</CodeGroup>

すべてのエイリアスに、`GET /v1/models?format=openai` の ID への明示的な対応付けが必要です。呼び出し元が社内用のエイリアスを使っている場合は、すべてのリクエストを編集するのではなく、クライアントの境界にある 1 つの関数で変換してください。

## プロキシの設定を対応付ける

プロキシを外す前に、コールバック、予算、リトライを棚卸ししてください。プロキシがなくなると、これらは何の通知もなく止まります。

| LiteLLM | Phaseo での扱い |
| --- | --- |
| `fallbacks` | `models` 配列または動的ルートのフォールバック。`429`、`500`、`502`、`503`、`504` で試され、リクエストエラーでは試されません。 |
| `context_window_fallbacks`、`content_policy_fallbacks` | 代替はありません。Phaseo は `400` でフォールバックしないため、アプリで処理してください。 |
| `routing_strategy` | ワークスペースのルーティングモード、または `provider.sort`(`price`、`latency`、`throughput`)。 |
| デプロイごとのプロバイダー選択 | `provider.order`、`provider.only`、`provider.ignore`、または `provider:org/model` のような[プロバイダー指定 ID](../guides/provider-qualified-models)。後者はプロバイダー間でフォールバックしません。 |
| セルフホストのデプロイ(vLLM など) | [プライベートモデル](../guides/private-models)。Bearer 認証付きの、公開された HTTPS の OpenAI 互換 `/chat/completions` エンドポイントが必要です。 |
| レスポンスキャッシュ(`litellm_settings.cache`) | レスポンスキャッシュはありません。必要ならアプリでキャッシュしてください。[プロンプトキャッシュ](../guides/prompt-caching)では引き続き入力コストを削減できます。 |
| 仮想キー(`max_budget`、`rpm_limit`、`tpm_limit`、`max_parallel_requests`、`models`) | 支出上限と許可モデルを設定した API キー、予算、そして 1 分あたりのリクエスト数・1 分あたりのトークン数・同時リクエスト数のレート制限ポリシー。[制限](../api-reference/limits)を参照してください。 |
| チームの予算、`metadata.tags` | 部門の予算と `X-Phaseo-Metadata` の[ラベル](../guides/request-labels)。エンドユーザーの予算はエンドユーザー向けのレート制限ポリシーにしか対応付けられず、エンドユーザーの支出上限はありません。 |
| `guardrails`(Presidio、Lakera など) | キーのガードレールが、リクエストのプロンプトインジェクションと個人情報をスキャンします。レスポンスはスキャンされません。 |
| コールバック(`success_callback`、Langfuse、Datadog、OpenTelemetry) | [オブザーバビリティの送信先](../guides/integrations/observability)またはクライアント側のトレーシング。ボディの `metadata` は `phaseo.metadata.<key>` としてエクスポートされます。 |
| 設定内のプロバイダー API キー | BYOK(`phaseo byok create --provider <id> --name <name> --key-stdin` または `POST /v1/byok`)、または Phaseo のクレジット。クレジットにフォールバックするには、`phaseo settings update` で `byok_fallback_enabled` を設定します。 |

プロキシはチーム全体のトラフィックを 1 人のキー所有者経由で送るため、そのユーザーの 1 分あたりのリクエスト数の上限を共有します。新しいワークスペースではこの上限は 10 です。切り替え前に [Gateway の制限](../api-reference/limits#gateway-limits)を確認し、より高い上限を手配してください。

## テストして展開する

ストリーミング、ツール、構造化出力、リトライ、エラーの対応付け、そしてプロキシが処理していたコールバック経由のテレメトリをテストします。レイテンシー、出力、トークン使用量、コストを比較してから、段階的にトラフィックを移します。切り替え前に、次を確認してください。

- LiteLLM の URL、キー、`LITELLM_*` 変数をすべて特定した
- 本番のすべてのエイリアスに Phaseo への明示的な対応付けがある
- 共有の既定値がプリセットまたは 1 つの境界関数にまとまっている
- 必要なコールバックとテレメトリに代わるものがある
- 支出の記録を LiteLLM、Phaseo、またはその両方のどれにするか決めた
- 切り戻しが引き続きベース URL とキーの変更だけで済む
