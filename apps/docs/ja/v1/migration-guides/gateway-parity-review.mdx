ゲートウェイの切り替えを計画する前に、このレビューを使ってください。両方のプラットフォームがOpenAI互換のリクエストを受け付ける場合でも、変わる可能性がある動作を確認します。

## 1. 統合箇所を洗い出す

現在のゲートウェイが使われている箇所をすべて記録します。

- ベースURLとAPIキーの環境変数
- SDKの初期化とカスタムヘッダー
- モデルIDとフォールバックモデル
- プロバイダーの優先順、許可リスト、プライバシー要件
- ストリーミング、ツール呼び出し、構造化出力のコード
- バッチジョブ、ファイル、Webhook、非同期のステータス確認
- リクエストの帰属情報とユーザーまたはセッションのメタデータ

移行後に隠れた別の設定経路が残っていないことをレビュー担当者が確認できるよう、この一覧をロールアウト計画と一緒に保管してください。

## 2. 各機能を分類する

本番環境で使う動作ごとに、ステータスを割り当てます。

| ステータス | 意味 |
| --- | --- |
| 変更なし | 同じリクエストフィールドとレスポンス動作を確認済みです。 |
| マッピング済み | Phaseoでは別のフィールドまたは設定を使って同じ結果を実現できます。 |
| 変換が必要 | 互換レイヤーでリクエストまたはレスポンスを変換します。 |
| 非対応 | その依存関係を取り除くか、現在の経路を使い続ける必要があります。 |
| 未検証 | サポートされている可能性はありますが、本番に近い条件での確認が不足しています。 |

主要なリクエスト、ルーティング、帰属情報、非同期処理、運用を確認するには、[移行機能チェックリスト](./feature-parity-matrix.mdx)を使ってください。

## 3. 代表的なトラフィックを検証する

機密性の高い本番データをコピーせず、実際のワークロードのパターンから小さなテストセットを作成します。

次をテストします。

1. 使用中の各エンドポイントに対する通常のリクエスト。
2. 本番と同じクライアント経路でのストリーミング。
3. 現実的なスキーマを使ったツール呼び出しと構造化出力。
4. 各プロバイダーまたはプライバシーの制約。
5. 無効なキーやモデル、レート制限、プロバイダーが利用できない場合のエラー。
6. バッチまたは非同期ジョブの成功、失敗、キャンセルまでの状態遷移。

出力品質、レイテンシ、トークン使用量、選択されたプロバイダー、最終コストを比較します。Gatewayの使用状況から確認できるよう、結果ごとにリクエストIDを記録してください。

## 4. 帰属情報と可観測性を維持する

呼び出し元のアプリを示すアプリ帰属ヘッダーは保持してください。Phaseoでは安定したアプリID、名前、URL、カテゴリを利用できます。移行時に削除すると、コストや使用状況を比較しにくくなります。

対応するヘッダーとカテゴリの値については、[アプリの帰属情報](../guides/app-attribution.mdx)を参照してください。

## 5. 元に戻せる形で段階的に切り替える

開発環境と社内トラフィックから始めます。テストセットに合格してから、本番トラフィックの一部だけを移行します。結果が安定するまでは、ロールバックをエンドポイントと認証情報の設定変更に限定してください。

初回の切り替えと、プロンプト、モデル、ルーティングに関する無関係な最適化を同時に行わないでください。ゲートウェイの境界を検証した後に変更します。
