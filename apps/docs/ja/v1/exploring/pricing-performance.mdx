各プロバイダーでのモデルのコストと、そのプロバイダーが Gateway トラフィックをどれだけ速く処理してきたかを比較し、本番トラフィックを移す前に、候補を自分のプロンプトで確認します。

## ワークロードに重要な指標を選ぶ

| ワークロード | 最初に見る指標 | 理由 |
| --- | --- | --- |
| チャット、コパイロット、音声 | Gateway TTFT | ユーザーは、有用な出力がどれだけ早く始まるかに気づきます。 |
| 長い回答とコード生成 | Output speed | 長いレスポンスでは、持続的な生成速度が大部分を占めます。 |
| ツールと構造化ワークフロー | Gateway E2E | ルーティング、リトライ、オーケストレーションが結果全体に影響します。 |
| バッチやオフライン処理 | コストと Effective throughput | 全体のスループットと支出のほうが重要な場合は、開始が遅くても許容できることがあります。 |

あらゆるワークロードで最適なモデルであることを、1 つのスコアで証明することはできません。

## 料金を比較する

プロバイダーの料金表は、トークンあたり、100 万トークンあたり、画像あたり、秒あたり、分あたり、リクエストあたりなど、異なる単位を使います。Phaseo は各料金を元の単位のまま保持し、比較可能なテキストの料金は、カタログ表示と料金計算ツール向けに 100 万トークンあたりに換算します。

テキストモデルでは、入力、キャッシュされた入力、キャッシュ書き込み、推論、出力の課金項目がある場合、それぞれを個別に比較してください。メディアモデルは独自の課金単位を保ちます。秒あたりの動画料金は、他の秒あたりの料金とだけ比較してください。

<Note>
カタログの料金はリクエストの見積もりであり、あらゆるペイロードに対する見積書ではありません。プロバイダーのティア、リージョン別の提供内容、バッチ料金、キャッシュの動作、リクエスト固有の課金項目によって最終的な金額は変わります。
</Note>

代表的なペイロードで[料金計算ツール](https://phaseo.app/tools/pricing-calculator)を使い、テストリクエストの後に Gateway の使用量で実際の請求額を確認してください。

## パフォーマンス指標を理解する

Phaseo は、Gateway を経由したリクエストの運用上のタイミングを記録します。

| 指標 | 定義 |
| --- | --- |
| **Gateway TTFT** | Gateway でのリクエスト開始から、内容を含む最初の生成出力まで。 |
| **Provider TTFT** | 選択したプロバイダーへの送信から、内容を含む最初の生成出力まで。 |
| **Provider duration** | 選択したプロバイダーへの送信から、最終レスポンスまで。 |
| **Gateway E2E** | Gateway でのリクエスト開始から完了まで。 |
| **Phaseo overhead** | `max(0, Gateway E2E - provider duration)`。 |
| **Effective throughput** | すべての出力トークンを、プロバイダーでの処理時間全体で割った値。 |
| **Output speed** | 最初の出力以降の出力トークン（それより前に行われた非表示の推論を除く）を、TTFT 以降のプロバイダー時間で割った値。回答全体が 1 回のネットワーク読み取りで届いた場合は表示されません。 |
| **TPOT / ITL** | 最初の出力以降の、リクエスト単位でのトークンあたりの平均時間。 |

TTFT、Output speed、TPOT、ITL には、内容を含む最初の出力があるストリーミングレスポンスが必要です。メタデータのみのストリームフレームは含まれません。ストリーミングしないレスポンスも、TTFT を作り出すことなく、Provider duration、Gateway E2E、Effective throughput には反映されます。

Phaseo overhead は、選択したプロバイダー呼び出しの外側にかかる時間で、Gateway の処理、ルーティング、リトライ、ネットワークの影響を含みます。リクエストごとに変わるため、固定値ではなく、定めた期間での分布として読んでください。

## 運用データを正しく読む

パフォーマンスページは、実際の Gateway トラフィックを集計したものです。管理されたベンチマークの実行ではなく観測値であり、モデルそのものではなく、ある期間におけるルートを表します。過去のレイテンシーや稼働率は、将来の結果を保証するものではありません。

結果は次の要因で変動します。

- プロバイダーとルートの選択
- Cloudflare の実行場所とネットワーク経路
- プロバイダーでのキューイングやリージョンの負荷
- プロンプトと出力の長さ
- ストリーミングか非ストリーミングか
- リトライ、キャンセル、ツール呼び出し
- 選択した期間中のモデルやプロバイダーの更新

公開グラフでは、P50、P90、P95、P99 などのパーセンタイルを表示できます。レイテンシーは低いほど良く、スループットは高いほど良いため、スループットの低いパーセンタイルは遅い側の裾を表します。

結果には、選択した期間、ルート、リージョン、サンプルのフィルター、パーセンタイルを必ず併記してください。期間の異なる 2 つのスクリーンショットを、同じ調査であるかのように比較しないでください。

## 再現可能なワークロード調査を行う

公開テレメトリーで候補を絞り込み、最終候補を自分のプロンプト構成で検証します。

1. 既定の `GET /v1/models` レスポンスから、ルーティング可能なモデルを 2〜3 個選びます。
2. 短い、典型的な、長いリクエストを代表する、機密情報を取り除いたプロンプトセットを作成します。
3. エンドポイント、リージョン、ストリーミングモード、プロバイダーの制約、同時実行数を固定します。
4. 1 つのサンプルに頼らず、各プロンプトでリクエストを繰り返し実行します。
5. リクエスト ID、選択されたプロバイダー、成功またはエラー、出力トークン、Gateway TTFT、Provider duration、Gateway E2E、Phaseo overhead、コストを記録します。
6. 分布と失敗の傾向を比較し、生の結果をテスト構成とともに保存します。

結果のスキーマの例:

```json
{
  "study_id": "support-summary-v1",
  "model": "<verified-model-id>",
  "endpoint": "responses",
  "stream": true,
  "region": "<execution-region>",
  "request_id": "req_...",
  "gateway_ttft_ms": 0,
  "provider_duration_ms": 0,
  "gateway_e2e_ms": 0,
  "phaseo_overhead_ms": 0,
  "output_tokens": 0,
  "cost_usd": 0,
  "status": "completed"
}
```

ゼロの値はプレースホルダーです。測定値を公開する場合は、ワークロードの定義、サンプル数、期間、データを開示する許可をそろえてください。

カタログに掲載されていても、モデルがルーティング可能とは限らないため、既定の `GET /v1/models` レスポンスから始めてください。ベンチマークのスコアは、自分のプロンプト構成での品質を保証しません。スコアの出典が Gateway のテレメトリーとは別にどう扱われるかは、[ベンチマークの方法論](../research/benchmark-methodology)を参照してください。1 つのモデルのすべてのプロバイダールート、機能、料金を確認するには、[モデルエンドポイント API](../api-reference/endpoint/model-endpoints) または[比較](https://phaseo.app/compare)を使います。インシデントや障害の切り分けについては、[信頼性とステータス](../developers/reliability-and-status)を参照してください。
