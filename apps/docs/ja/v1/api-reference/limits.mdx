Gateway は現在、プラットフォーム独自のリクエスト上限を別途適用していません。スロットリングの大半は上流プロバイダーによるものです。

## 制限の仕組み

- 選択したモデルのプロバイダーがリクエスト頻度を制限する場合があります。
- BYOK トラフィックには、プロバイダーアカウントに設定された制限が適用されます。
- Gateway のルーティングとフォールバックで失敗を減らせますが、`429` が返る場合もあります。

## `429` 応答への対処

- `Retry-After` がある場合は、その値に従ってください。
- ジッターを加えた指数バックオフを使用してください。
- 最大再試行回数を設定し、上限に達したときは適切に失敗させてください。

ルーティング先のプロバイダーが値を返す場合、Phaseo は検証済みの `Retry-After` 値を転送します。BYOK リクエストでは、`X-Phaseo-Upstream-RateLimit-*` ヘッダーにプロバイダーのクォータ情報が含まれる場合もあります。管理対象プロバイダーへのリクエストでは、これらのクォータヘッダーは意図的に省略されます。共有 Phaseo 容量を示すもので、個々の顧客の割り当て量ではないためです。その他の上流ヘッダーは転送されません。

```ts
async function retryWithBackoff(run: () => Promise<Response>, maxRetries = 4) {
  for (let attempt = 0; attempt <= maxRetries; attempt += 1) {
    const response = await run();
    if (response.status !== 429) return response;

    const retryAfterHeader = response.headers.get("retry-after");
    const retryAfterMs = retryAfterHeader
      ? Number(retryAfterHeader) * 1000
      : Math.min(1000 * 2 ** attempt, 8000);

    await new Promise((resolve) => setTimeout(resolve, retryAfterMs));
  }

  throw new Error("Rate limit retries exhausted");
}
```

## モニタリング

- エンドポイントとモデルごとに `429` の発生率を追跡します。
- フォールバックの頻度を確認し、プロバイダーへの負荷を把握します。
- インシデントの調査では、ダッシュボードのメトリクスとアプリのログを併用します。

<Visibility for="agents">
エージェントとして再試行を実装する場合:

- 安全な再試行ループとタイムアウト制御には、リポジトリのスキルを使用してください。
- 再試行設定（回数、初期待機時間、最大待機時間）を一元管理してください。
- 明示的なプロダクト承認なしに、非冪等なリクエストを再試行しないでください。
</Visibility>
