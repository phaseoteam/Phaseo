選択したプロバイダー、または適用されるワークスペースやキーのポリシーによって、リクエストが制限される場合があります。ルーティングとフォールバックによりプロバイダーの障害を減らせますが、リクエストが `429` を返す可能性は残ります。

## ゲートウェイの制限

各ワークスペースの各ユーザーには、直近1分間で計測される1分あたりのリクエスト利用枠があります。同じユーザーが作成した API キーはこの利用枠を共有します。OAuth リクエストは認証済みユーザーに基づいて計数されます。所有者のないキーはワークスペース単位の利用枠を共有します。

利用枠はワークスペースのアカウント状況によって決まり、ワークスペースの利用実績が積み重なるにつれて自動的に引き上げられます。

| ワークスペース | 1分あたりのリクエスト数 |
| --- | --- |
| 新しいワークスペース | 10 |
| 作成から7日以上、または有料チャージ済み | 25 |
| 作成から30日以上かつ返金を差し引いた有料チャージ額が50ドル以上 | 60 |
| 請求書払い | 120 |

ワークスペースには、条件を満たす中で最も高い利用枠が適用されます。変更は数分以内に反映されます。

無料モデルのルートには、同じユーザーとワークスペースのすべての無料モデルで共有する**UTC の1日あたり1500リクエスト**の利用枠もあります。有料モデルのリクエストはこの日次枠を消費しません。受け付けられた無料リクエストは、その後プロバイダーが失敗しても計数されます。同じリクエスト内のフォールバックは1回として数えます。

これらの制限はすべてのゲートウェイリージョンに共通して適用され、特定のユーザーとワークスペースに対して引き上げることができます。ファイル操作とジョブのステータス確認は分単位の利用枠を消費しますが、管理エンドポイントは消費しません。

ゲートウェイの利用枠を超えると、秒数を示す `Retry-After` とともに `429` が返されます。エラーの理由は `customer_requests_per_minute` または `free_requests_per_day` です。その時間を待ってから再試行してください。利用枠の確認が一時的に利用できない場合、ゲートウェイは再試行の案内とともに `503` を返します。

## キーの制限と予算

API キーの日次・週次・月次のリクエスト数や支出の上限、またはワークスペースの[予算](./endpoint/budgets-list.mdx)に達すると、エラーコード `key_limit_exceeded` とともに `429` が返されます。レスポンス本文の `reason`、`limit_window`、`reset_at` フィールドで、どの制限に達したか、その期間がいつリセットされるかを確認できます。`Retry-After` はリセットまでの秒数を示します。生涯予算や一時的にブロックされたキーなど、制限が自動的にリセットされない場合は省略されます。その場合は再試行せず、ワークスペースの予算を引き上げてください。キーの上限の場合は、キーの上限を引き上げるか別のキーを使用してください。

ワークスペースのオーナーと管理者は、ダッシュボードの[設定 → 予算](https://phaseo.app/settings/budgets)でも予算を設定、変更、削除できます。このページには、各予算のこれまでの支出、使用率、期間の予測、リセット日時が表示されます。日次・週次・月次の予算は UTC の区切り（深夜 0 時、月曜 00:00、毎月 1 日）でリセットされます。CLI からは `phaseo budgets create|update|delete` を使います。

部門予算は `/v1/department-budgets` API で管理します。部門の支出には、後述の部門レート制限と同じキーと OAuth リクエストが計上されます。部門が日次、週次、または月次の予算を使い切ると、その部門に計上される API キーのリクエストは、エラーコード `key_limit_exceeded` と理由 `department_daily_cost_budget_reached`、`department_weekly_cost_budget_reached`、または `department_monthly_cost_budget_reached` を含む `429` を返します。レスポンス本文の `department_id` と `department_name` フィールドで部門がわかり、`reset_at` と `Retry-After` で予算がいつリセットされるかがわかります。バッチジョブ、リアルタイムセッション、OAuth リクエストは部門予算でブロックされません。予算の約 80% と 100% に達すると、オーナーと管理者にモバイルのプッシュ通知が届きます。これらのアラートは最大 1 時間遅れることがある使用量データに基づくため、100% のアラートが届く前にリクエストが拒否されることがあります。

オーナーと管理者は、部門予算を[設定 → 予算](https://phaseo.app/settings/budgets)で管理することも、Terraform プロバイダーの `phaseo_department_budget` リソースで管理することもできます。CLI からは `phaseo department-budgets` を使います。

## レート制限ポリシー

ワークスペース管理者は `/v1/rate-limits` 管理 API で名前付きのレート制限ポリシーを作成し、API キー、ワークスペースメンバー、部門、ガードレール、またはエンドユーザーごとの既定値として割り当てられます。ゲートウェイは、ポリシーの `requests_per_minute` と `tokens_per_minute` を、それぞれ直近 1 分間のローリングウィンドウで適用します。

- **キー:** キー専用の割り当て。
- **メンバー:** メンバーのキーと OAuth リクエストで共有する 1 つの割り当て。
- **部門:** 部門に計上されるすべてのリクエストで共有する 1 つの割り当て。部門に紐付けられたキーは、その部門にのみ計上されます。それ以外のキーは作成者が所属するすべての部門に、OAuth リクエストはそのユーザーが所属するすべての部門に計上されます。部門の上書きが設定されたメンバーは、上書き先の部門にのみ計上されます。
- **ガードレール:** ガードレールが対象とするキー（または OAuth ユーザー）ごとの個別の割り当て。
- **エンドユーザーごとの既定値:** リクエストの `user` フィールドまたは `X-Phaseo-User-Id` ヘッダーで識別されるエンドユーザーごとの個別の割り当て。エンドユーザー ID のないリクエストには適用されません。

オーナーと管理者は、ポリシーとその割り当てを[設定 → レート制限](https://phaseo.app/settings/rate-limits)で管理することも、Terraform プロバイダーの `phaseo_rate_limit_policy` と `phaseo_rate_limit_assignment` リソースで管理することもできます。CLI からは `phaseo rate-limits policies` と `phaseo rate-limits assignments` を使います。

複数のポリシーが適用される場合は、それぞれがカウントされ、最初に上限に達したポリシーがリクエストを拒否します。ポリシーの制限は、上記のゲートウェイ制限に加えて適用されます。ポリシーの変更は約 1 分以内に反映されます。ダッシュボードまたは SCIM で行った部門メンバーシップの変更は、反映まで最大 5 分ほどかかることがあります。

`tokens_per_minute` は、各リクエストの入力トークンと出力トークンをリクエストの完了時にカウントします。トークンを消費したストリーミングリクエストや失敗したリクエストも含まれます。直近 1 分間の使用量が上限に達した割り当てでは、リクエストが拒否されます。そのため、すでに処理中のリクエストによって使用量が上限を超えることがあります。

拒否されたリクエストは `429` を返し、エラーコード `rate_limit_exceeded`、理由 `policy_requests_per_minute` または `policy_tokens_per_minute`、`policy_id`、`limit_scope`（`key`、`member`、`department`、`guardrail`、`end_user` のいずれか）、および秒単位の `Retry-After` を含みます。ポリシーが適用されたリクエストのレスポンスには、最も厳しいリクエスト数の制限について `x-ratelimit-limit-requests`、`x-ratelimit-remaining-requests`、`x-ratelimit-reset-requests`（例: `60s`）が、最も厳しいトークン数の制限について `x-ratelimit-limit-tokens`、`x-ratelimit-remaining-tokens`、`x-ratelimit-reset-tokens` が含まれます。拒否されたリクエストには、拒否の原因となった制限のヘッダーのみが含まれます。カウントはバックグラウンドで行われるため、`remaining` は概算です。また、トークンのヘッダーには現在のリクエスト自身の使用量はまだ含まれません。1 つのリクエスト内のプロバイダーフォールバックは 1 回としてカウントされ、レスポンスキャッシュのヒットはカウントされません。

`concurrent_requests` は、同時に処理中にできるリクエストの数を制限します。リクエストは受け付けられてからレスポンスがすべて送信されるまで（ストリーミングレスポンスの場合は最後まで）スロットを 1 つ使い、同じリクエスト内のプロバイダーやモデルのフォールバックはそのスロットを共有します。すべてのスロットが使用中の場合、リクエストは理由 `policy_concurrent_requests` と `Retry-After: 1` で拒否されます。同時実行数の確認はポリシーのカウンターの応答を待つため、対象のリクエストにわずかなレイテンシーが加わります。解放が失われたスロットは 15 分後に自動的に解放されます。バッチとリアルタイムセッションは対象外で、動画生成がスロットを使うのは生成を開始するリクエストの処理中だけです。

既定では、ポリシーの制限を確認できない場合、リクエストは許可されます。`fail_closed` を設定すると厳格なポリシーになります。厳格なポリシーのリクエスト数とトークンの制限は、バックグラウンドではなくリクエストの送信前に確認されるため正確になりますが、レイテンシーが加わります。2 秒以内に確認できない場合、リクエストは理由 `policy_unavailable` で拒否されます。同時実行数と `policy_unavailable` による拒否には `x-ratelimit-*` ヘッダーは含まれません。

## プロバイダーの制限

BYOK リクエストには、ご自身のプロバイダーアカウントの制限が適用されます。管理対象のリクエストは共有のプロバイダー容量を使用します。この容量は、個々のワークスペースに割り当てられた利用枠ではありません。

ルーティング先のプロバイダーが `Retry-After` を返した場合、Phaseo は検証済みの値を転送します。BYOK のレスポンスには `X-Phaseo-Upstream-RateLimit-*` ヘッダーが含まれることもあります。これらのクォータヘッダーは共有のプロバイダー容量を示すため、管理対象のリクエストでは省略されます。その他の上流ヘッダーは転送されません。

## 制限されたリクエストへの対応

1. [エラーコード](./errors.mdx)を確認し、プロバイダーによる一時的な制限と、設定変更が必要なポリシーや予算の制約を区別してください。
2. `Retry-After` がある場合は従ってください。値は秒数による待機時間、または HTTP 日付です。再試行をスケジュールする前に値を検証してください。
3. それ以外の場合は、ランダムな揺らぎと最大待機時間を設定した指数バックオフを使用してください。
4. 再試行は、試行回数と全体の期限の両方で制限してください。不要になった処理をキャンセルし、再試行する前に失敗した各レスポンスのボディを解放してください。
5. 制限が続く場合は同時実行数を減らしてください。

結果が不明なジョブの送信を自動的に再試行したり、完了済みのツール操作を繰り返したりしないでください。クライアントがレスポンスを失っても、リクエストはプロバイダーに届いている可能性があります。再試行により処理や料金が重複するおそれがあります。受け付け済みの動画ジョブやバッチジョブは、再送信せずにステータスエンドポイントを使用してください。

## スロットリングの監視

エンドポイントとモデル別に `429` の発生率を追跡し、リクエストログでフォールバックの頻度を確認してください。アプリケーションのログを[ルーティング設定](../guides/routing-and-fallbacks.mdx)、および BYOK トラフィックに対するプロバイダーアカウントのクォータと照合してください。

ワークスペースの支出とアクセスの制御については、[予算](./endpoint/budgets-list.mdx)と[ガードレール](./endpoint/guardrails.mdx)を参照してください。

エージェント向けのレート制限ルール（このページの要約）:

- Gateway のクォータは理由 `customer_requests_per_minute` または `free_requests_per_day` とともに `429` を返します。`Retry-After` の秒数だけ待ちます。クォータの適用が利用できない場合、Gateway は再試行の案内とともに `503` を返します。

- ワークスペースのレート制限ポリシーは `rate_limit_exceeded`、`policy_id`、`limit_scope` を含む `429` を返します。`x-ratelimit-remaining-requests` は概算値です。
- `Retry-After` は秒数または HTTP 日付です。再試行を予定する前に値を検証します。結果が不明な動画ジョブやバッチジョブは再送信せず、ステータスを確認します。
