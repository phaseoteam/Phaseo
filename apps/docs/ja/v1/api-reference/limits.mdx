`429` のエラーコードと `reason` を読めば、どの制限でリクエストが止められたかがわかります。そのうえで `Retry-After` の分だけ待つか、制限を変更してください。ルーティングとフォールバックはプロバイダーの障害を減らしますが、プロバイダー、またはワークスペースやキーのポリシーによってリクエストがスロットリングされることは引き続きあります。

| 制限 | エラーコード | `reason` | 自動でリセットされるか |
| --- | --- | --- | --- |
| [1 分あたりのリクエスト数](#gateway-limits) | `key_limit_exceeded` | `customer_requests_per_minute` | はい。`Retry-After` は秒数 |
| [1 日あたりの無料モデルのリクエスト数](#gateway-limits) | `phaseo_free_model_limit_exceeded` | `free_requests_per_day` | はい。00:00 UTC |
| [キーの上限またはワークスペースの予算](#key-limits-and-budgets) | `key_limit_exceeded` | 到達した制限。`limit_window` と `reset_at` も付きます | `Retry-After` がある場合のみ |
| [部門の予算](#department-budgets) | `key_limit_exceeded` | `department_daily_cost_budget_reached`（または `weekly`、`monthly`） | はい。`reset_at` の時点 |
| [ブロックに設定された支出ルール](#key-limits-and-budgets) | `spend_rule_blocked` | | ブロックに `reset_at` がある場合はその時点、またはオーナーか管理者が解除したとき |
| [レート制限ポリシー](#rate-limit-policies) | `rate_limit_exceeded` | `policy_requests_per_minute`、`policy_tokens_per_minute`、`policy_concurrent_requests`、または `policy_unavailable` | はい。`Retry-After` は秒数 |
| [プロバイダー](#provider-limits) | `upstream_error` または `provider_capacity_exhausted` | | プロバイダーの `Retry-After` に従います |

これらはすべて `429` を返します。Gateway のクォータ適用が一時的に利用できない場合は、代わりに再試行の案内付きで `503` を返します。

<span id="gateway-limits"></span>
## Gateway の制限

各ワークスペースの各ユーザーには、直近 1 分間で計測される 1 分あたりのリクエスト利用枠があります。同じユーザーが作成した API キーはこの利用枠を共有します。OAuth リクエストはサインインしているユーザーの利用枠で計数され、所有者のないキーはワークスペース単位の利用枠を 1 つ共有します。

利用枠は、ワークスペースの実績が積み重なるにつれて自動的に引き上げられます。ワークスペースには条件を満たす最も高い行が適用され、変更は数分以内に反映されます。

| ワークスペース | 1 分あたりのリクエスト数 |
| --- | --- |
| 新しいワークスペース | 10 |
| 作成から 7 日以上、または有料チャージ済み | 25 |
| 作成から 30 日以上、かつ返金を差し引いた有料チャージ額が $50 以上 | 60 |
| 請求書払い | 120 |

無料モデルには、デフォルトで **UTC の 1 日あたり 1,500 リクエスト**の利用枠もあります。この利用枠はすべての無料モデルと、同じユーザーがリクエストを送信するすべてのワークスペースで共有されます。有料モデルのリクエストはこの利用枠を消費しません。受け付けられた無料リクエストは、その後プロバイダーが失敗しても計数され、1 つのリクエスト内のプロバイダーフォールバックは 1 回として計数されます。

どちらの制限も Gateway のリージョンをまたいで適用され、特定のユーザーとワークスペースについて引き上げることができます。ファイル操作とジョブステータスのポーリングは 1 分あたりの利用枠を使いますが、管理エンドポイントは使いません。

拒否されたリクエストは、秒数の `Retry-After` 付きで `429` を返します。その時間だけ待ってから再試行してください。

<span id="key-limits-and-budgets"></span>
## キーの上限と予算

API キーの日次、週次、月次のリクエスト数と支出の上限、およびワークスペースの[予算](./endpoint/budgets-list.mdx)に達すると、`429` と `key_limit_exceeded` が返されます。本文の `reason`、`limit_window`、`reset_at` で、どの制限に達したか、その期間がいつリセットされるかがわかり、`Retry-After` にはそれまでの秒数が入ります。

生涯予算やソフトブロックされたキーのように、制限が自動でリセットされない場合は `Retry-After` がありません。再試行せず、ワークスペースの予算を引き上げるか、キーの上限を引き上げるか、別のキーを使ってください。

ワークスペースのオーナーと管理者は、`phaseo budgets create|update|delete` または [設定 → 予算](https://phaseo.app/settings/budgets) で予算を管理します。この画面には、各予算のこれまでの支出、使用率、期間の予測、リセット日時が表示されます。日次、週次、月次の予算は UTC の区切り（午前 0 時、月曜日の 00:00、毎月 1 日）でリセットされます。

[支出アラート](../guides/spend-alerts.mdx)を使うと、これらの制限に達する前に警告を受け取れます。ブロックに設定された支出ルールは、`429` と `spend_rule_blocked` を返します。これはベストエフォートで、支出が上限を超えてから数分後に始まるため、正確な上限にはキーの上限と予算を使ってください。`x-phaseo-spend-warning` ヘッダーは、この後ブロックされる可能性があることを示します。

<span id="department-budgets"></span>
### 部門の予算

オーナーと管理者は、`phaseo department-budgets`、`/v1/department-budgets` API、[設定 → 予算](https://phaseo.app/settings/budgets)、または Terraform プロバイダーの `phaseo_department_budget` リソースで部門の予算を管理します。部門の支出は、[部門のレート制限](#rate-limit-policies)と同じキーと OAuth リクエストを計数します。

部門が日次、週次、または月次の予算を使い切ると、その部門に計数される API キーのリクエストは、`429`、`key_limit_exceeded`、理由 `department_daily_cost_budget_reached`、`department_weekly_cost_budget_reached`、または `department_monthly_cost_budget_reached` を返します。本文の `department_id` と `department_name` で部門を特定でき、`reset_at` と `Retry-After` で予算がいつリセットされるかがわかります。

- バッチジョブ、リアルタイムセッション、OAuth リクエストは、部門の予算でブロックされません。
- 予算の確認が一時的に利用できない場合、リクエストは許可されるため、部門が短時間だけ予算を超えて支出することがあります。
- オーナーと管理者には、予算の約 80% の時点と 100% の時点でモバイルのプッシュ通知が届きます。これらのアラートは最大 1 時間遅れることがある使用量データに基づくため、100% のアラートが届く前にリクエストが拒否されることがあります。

<span id="rate-limit-policies"></span>
## レート制限ポリシー

ワークスペースの管理者は、`requests_per_minute`、`tokens_per_minute`、`concurrent_requests` を設定する名前付きポリシーを作成し、キー、メンバー、部門、エンドユーザーに割り当てることができます。管理には、`phaseo rate-limits policies` と `phaseo rate-limits assignments`、`/v1/rate-limits` API、[設定 → レート制限](https://phaseo.app/settings/rate-limits)、または Terraform プロバイダーの `phaseo_rate_limit_policy` と `phaseo_rate_limit_assignment` リソースを使います。

| 割り当て先 | 1 つの利用枠を共有するもの |
| --- | --- |
| キー（`key`） | そのキーのリクエスト。 |
| メンバー（`member`） | そのメンバーのキーと OAuth リクエスト。 |
| 部門（`department`） | その部門に計数されるすべて（下記を参照）。 |
| エンドユーザーのデフォルト（`end_user`） | 各エンドユーザーが独自の利用枠を持ちます。エンドユーザーはリクエストの `user` フィールドまたは `X-Phaseo-User-Id` ヘッダーで識別されます。エンドユーザー ID のないリクエストは制限されません。 |

**部門に計数されるもの。** 部門に紐付けられたキーは、その部門にのみ計数されます。それ以外のキーは作成者が所属するすべての部門に計数され、OAuth リクエストはそのユーザーのすべての部門に計数されます。部門のオーバーライドが設定されたメンバーは、オーバーライド先の部門にのみ計数されます。これらのキーと OAuth リクエストをその人の主部門にのみ計数するには、[設定 → 通知](https://phaseo.app/settings/notifications)、`PATCH /v1/notifications/settings` の `spend.department_attribution`、または `phaseo notifications settings update --department-attribution primary` で部門の帰属を primary に設定します。部門の予算と支出ルールも同じ設定を使います。

複数のポリシーが適用される場合は、それぞれが計数され、最初に上限に達したものがリクエストを拒否します。ポリシーは [Gateway の制限](#gateway-limits)に加えて適用されます。ポリシーの変更は約 1 分以内に反映されます。ダッシュボードまたは SCIM による部門メンバーシップの変更は、反映まで最大約 5 分かかることがあります。

### 1 分あたりのリクエスト数とトークン数

どちらも直近 1 分間で計測されます。`tokens_per_minute` は、各リクエストの入力トークンと出力トークンを完了時に計数します。トークンを使用したストリーミングリクエストや失敗したリクエストも含まれます。直近 1 分間の使用量が上限に達した時点でリクエストは拒否されるため、すでに処理中のリクエストによって使用量が上限を超えることがあります。1 つのリクエスト内のプロバイダーフォールバックは 1 回として計数され、レスポンスキャッシュのヒットは計数されません。

拒否されたリクエストは、`429`、`rate_limit_exceeded`、理由 `policy_requests_per_minute` または `policy_tokens_per_minute`、`policy_id`、`limit_scope`（`key`、`member`、`department`、`workspace`、`end_user`）、秒数の `Retry-After` を返します。

ポリシーの対象となるリクエストのレスポンスには、最も厳しい制限のヘッダーが付きます。

| ヘッダー | 例 |
| --- | --- |
| `x-ratelimit-limit-requests`、`x-ratelimit-remaining-requests` | `60`、`42` |
| `x-ratelimit-reset-requests` | `60s` |
| `x-ratelimit-limit-tokens`、`x-ratelimit-remaining-tokens`、`x-ratelimit-reset-tokens` | トークン上限について同様 |

拒否されたリクエストには、拒否した制限のヘッダーのみが付きます。計数はバックグラウンドで行われるため `remaining` は概算で、トークンのヘッダーには現在のリクエスト自体の使用量はまだ含まれません。

### 同時リクエスト数

`concurrent_requests` は、同時に処理できるリクエスト数の上限です。リクエストは受け付けられた時点から、レスポンスがすべて送信されるまで（ストリーミングレスポンスの場合はその全体）1 つの枠を占有します。リクエスト内のプロバイダーとモデルのフォールバックはその枠を共有します。すべての枠が使用中の場合、リクエストは理由 `policy_concurrent_requests` と `Retry-After: 1` で拒否されます。

同時実行数の制限を確認する際はポリシーのカウンターを待つため、わずかにレイテンシーが増えます。解放が失われた枠は 15 分後に自動で解放されます。バッチとリアルタイムセッションは制限されず、動画生成は、それを開始するリクエストが処理中の間だけ枠を占有します。

### 厳格なポリシー

デフォルトでは、ポリシーはフェイルオープンです。制限を確認できない場合、リクエストは許可されます。厳格にするには `fail_closed` を設定します。厳格なポリシーは、リクエスト数とトークン数の制限をバックグラウンドではなくリクエスト送信前に確認します。これにより正確になりますが、レイテンシーが増えます。2 秒以内に確認できない場合、リクエストは理由 `policy_unavailable` で拒否されます。

同時実行数による拒否と `policy_unavailable` による拒否には、`x-ratelimit-*` ヘッダーは付きません。

<span id="provider-limits"></span>
## プロバイダーの制限

BYOK リクエストには、ご自身のプロバイダーアカウントの制限が適用されます。マネージドリクエストは共有のプロバイダー容量を使い、これはワークスペースに割り当てられた利用枠ではありません。

プロバイダーが `Retry-After` を送信した場合、Phaseo は検証したうえで転送します。BYOK のレスポンスには `X-Phaseo-Upstream-RateLimit-*` ヘッダーが含まれることもあります。マネージドリクエストでは共有容量を表すため省略されます。その他の上流のヘッダーは転送されません。プロバイダーの `429` コードについては[エラーコード](./errors.mdx#error-codes)を参照してください。

## スロットリングされたリクエストに対処する

1. [エラーコード](./errors.mdx)を読み、一時的なスロットリングなのか、設定変更が必要な上限、予算、ポリシーなのかを判断します。
2. `Retry-After` がある場合は従います。秒数または HTTP 日付のどちらかなので、再試行をスケジュールする前に検証してください。
3. ない場合は、ジッター付きで最大遅延を設けた指数バックオフを使います。
4. 試行回数と全体の期限で再試行を制限します。再試行の前に、放棄した処理をキャンセルし、失敗した各レスポンスの本文を解放します。
5. スロットリングが続く場合は、同時実行数を減らします。

結果が不明なジョブの送信を自動で再試行したり、完了したツール操作を再実行したりしないでください。クライアントがレスポンスを受け取れなくても、リクエストはプロバイダーに届いている可能性があるため、再試行すると処理と課金が重複することがあります。受け付けられた動画ジョブやバッチジョブは、再送信せずにステータスエンドポイントを使ってください。

スロットリングを監視するには、エンドポイントとモデルごとの `429` の割合を追跡し、リクエストログでフォールバックの頻度を確認します。これらを[ルーティング設定](../guides/routing-and-fallbacks.mdx)と、BYOK トラフィックの場合はプロバイダーアカウントのクォータと比較してください。[ガードレール](./endpoint/guardrails.mdx)では、どのキーがどのモデルとプロバイダーを使えるかを制御します。

<Visibility for="agents">
このページをまとめた、エージェント向けのレート制限ルール:

- Gateway のクォータは、理由 `customer_requests_per_minute`（コード `key_limit_exceeded`）または `free_requests_per_day`（コード `phaseo_free_model_limit_exceeded`）で `429` を返します。`Retry-After` の秒数だけ待ちます。クォータの適用が利用できない場合、Gateway は再試行の案内付きで `503` を返します。
- キーの上限と予算は、`key_limit_exceeded` と `reset_at` 付きで `429` を返します。`Retry-After` がない場合、制限は自動でリセットされません。再試行せず、上限を引き上げるか別のキーを使います。
- 使い切った部門の予算は、`key_limit_exceeded`、理由 `department_<interval>_cost_budget_reached`、`department_id`、`department_name`、`reset_at` 付きで `429` を返します。`Retry-After` の秒数だけ待つか、予算を引き上げます。バッチ、リアルタイム、OAuth のリクエストは部門の予算でブロックされません。予算の確認が利用できない場合、リクエストは許可されます。
- ブロックする支出ルールは、`spend_rule_blocked` 付きで `429` を返します。`Retry-After` を待つか、オーナーまたは管理者にブロックの解除を依頼します。`x-phaseo-spend-warning` は、この後ブロックされる可能性があることを示します。
- ワークスペースのレート制限ポリシーは、`rate_limit_exceeded`、`policy_id`、`limit_scope` 付きで `429` を返します。`x-ratelimit-remaining-requests` は概算です。
- `Retry-After` は秒数または HTTP 日付のどちらかです。再試行をスケジュールする前に検証します。結果が不明な動画ジョブやバッチジョブは再送信せず、ステータスを確認します。
</Visibility>
