選択したプロバイダー、または適用されるワークスペースやキーのポリシーによって、リクエストが制限される場合があります。ルーティングとフォールバックによりプロバイダーの障害を減らせますが、リクエストが `429` を返す可能性は残ります。

## ゲートウェイの制限

デフォルトの利用枠は、各ワークスペースの各ユーザーにつき**直近1分間で25リクエスト**です。同じユーザーが作成した API キーはこの利用枠を共有します。OAuth リクエストは認証済みユーザーに基づいて計数されます。所有者のないキーはワークスペース単位の利用枠を共有します。

無料モデルのルートには、同じユーザーとワークスペースのすべての無料モデルで共有する**UTC の1日あたり1500リクエスト**の利用枠もあります。有料モデルのリクエストはこの日次枠を消費しません。受け付けられた無料リクエストは、その後プロバイダーが失敗しても計数されます。同じリクエスト内のフォールバックは1回として数えます。

これらの制限はすべてのゲートウェイリージョンに共通して適用され、特定のユーザーとワークスペースに対して引き上げることができます。ファイル操作とジョブのステータス確認は分単位の利用枠を消費しますが、管理エンドポイントは消費しません。

ゲートウェイの利用枠を超えると、秒数を示す `Retry-After` とともに `429` が返されます。エラーの理由は `customer_requests_per_minute` または `free_requests_per_day` です。その時間を待ってから再試行してください。利用枠の確認が一時的に利用できない場合、ゲートウェイは再試行の案内とともに `503` を返します。

## プロバイダーの制限

BYOK リクエストには、ご自身のプロバイダーアカウントの制限が適用されます。管理対象のリクエストは共有のプロバイダー容量を使用します。この容量は、個々のワークスペースに割り当てられた利用枠ではありません。

ルーティング先のプロバイダーが `Retry-After` を返した場合、Phaseo は検証済みの値を転送します。BYOK のレスポンスには `X-Phaseo-Upstream-RateLimit-*` ヘッダーが含まれることもあります。これらのクォータヘッダーは共有のプロバイダー容量を示すため、管理対象のリクエストでは省略されます。その他の上流ヘッダーは転送されません。

## 制限されたリクエストへの対応

1. [エラーコード](./errors.mdx)を確認し、プロバイダーによる一時的な制限と、設定変更が必要なポリシーや予算の制約を区別してください。
2. `Retry-After` がある場合は従ってください。値は秒数による待機時間、または HTTP 日付です。再試行をスケジュールする前に値を検証してください。
3. それ以外の場合は、ランダムな揺らぎと最大待機時間を設定した指数バックオフを使用してください。
4. 再試行は、試行回数と全体の期限の両方で制限してください。不要になった処理をキャンセルし、再試行する前に失敗した各レスポンスのボディを解放してください。
5. 制限が続く場合は同時実行数を減らしてください。

結果が不明なジョブの送信を自動的に再試行したり、完了済みのツール操作を繰り返したりしないでください。クライアントがレスポンスを失っても、リクエストはプロバイダーに届いている可能性があります。再試行により処理や料金が重複するおそれがあります。受け付け済みの動画ジョブやバッチジョブは、再送信せずにステータスエンドポイントを使用してください。

## スロットリングの監視

エンドポイントとモデル別に `429` の発生率を追跡し、リクエストログでフォールバックの頻度を確認してください。アプリケーションのログを[ルーティング設定](../guides/routing-and-fallbacks.mdx)、および BYOK トラフィックに対するプロバイダーアカウントのクォータと照合してください。

ワークスペースの支出とアクセスの制御については、[予算](./endpoint/budgets-list.mdx)と[ガードレール](./endpoint/guardrails.mdx)を参照してください。
