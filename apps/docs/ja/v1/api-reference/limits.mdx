選択したプロバイダー、または適用されるワークスペースやキーのポリシーによって、リクエストが制限される場合があります。ルーティングとフォールバックによりプロバイダーの障害を減らせますが、リクエストが `429` を返す可能性は残ります。

## ゲートウェイの制限

各ワークスペースの各ユーザーには、直近1分間で計測される1分あたりのリクエスト利用枠があります。同じユーザーが作成した API キーはこの利用枠を共有します。OAuth リクエストは認証済みユーザーに基づいて計数されます。所有者のないキーはワークスペース単位の利用枠を共有します。

利用枠はワークスペースのアカウント状況によって決まり、ワークスペースの利用実績が積み重なるにつれて自動的に引き上げられます。

| ワークスペース | 1分あたりのリクエスト数 |
| --- | --- |
| 新しいワークスペース | 10 |
| 作成から7日以上、または有料チャージ済み | 25 |
| 作成から30日以上かつ返金を差し引いた有料チャージ額が50ドル以上 | 60 |
| 請求書払い | 120 |

ワークスペースには、条件を満たす中で最も高い利用枠が適用されます。変更は数分以内に反映されます。

無料モデルのルートには、同じユーザーとワークスペースのすべての無料モデルで共有する**UTC の1日あたり1500リクエスト**の利用枠もあります。有料モデルのリクエストはこの日次枠を消費しません。受け付けられた無料リクエストは、その後プロバイダーが失敗しても計数されます。同じリクエスト内のフォールバックは1回として数えます。

これらの制限はすべてのゲートウェイリージョンに共通して適用され、特定のユーザーとワークスペースに対して引き上げることができます。ファイル操作とジョブのステータス確認は分単位の利用枠を消費しますが、管理エンドポイントは消費しません。

ゲートウェイの利用枠を超えると、秒数を示す `Retry-After` とともに `429` が返されます。エラーの理由は `customer_requests_per_minute` または `free_requests_per_day` です。その時間を待ってから再試行してください。利用枠の確認が一時的に利用できない場合、ゲートウェイは再試行の案内とともに `503` を返します。

## キーの制限と予算

API キーの日次・週次・月次のリクエスト数や支出の上限、またはワークスペースの[予算](./endpoint/budgets-list.mdx)に達すると、エラーコード `key_limit_exceeded` とともに `429` が返されます。レスポンス本文の `reason`、`limit_window`、`reset_at` フィールドで、どの制限に達したか、その期間がいつリセットされるかを確認できます。`Retry-After` はリセットまでの秒数を示します。生涯予算や一時的にブロックされたキーなど、制限が自動的にリセットされない場合は省略されます。その場合は再試行せず、ワークスペースの予算を引き上げてください。キーの上限の場合は、キーの上限を引き上げるか別のキーを使用してください。

## レート制限ポリシー

ワークスペース管理者は `/v1/rate-limits` 管理 API で名前付きのレート制限ポリシーを作成し、API キー、ワークスペースメンバー、ガードレール、またはエンドユーザーごとの既定値として割り当てられます。ゲートウェイは、ポリシーの `requests_per_minute` を直近 1 分間のローリングウィンドウで適用します。

- **キー:** キー専用の割り当て。
- **メンバー:** メンバーのキーと OAuth リクエストで共有する 1 つの割り当て。
- **ガードレール:** ガードレールが対象とするキー（または OAuth ユーザー）ごとの個別の割り当て。
- **エンドユーザーごとの既定値:** リクエストの `user` フィールドまたは `X-Phaseo-User-Id` ヘッダーで識別されるエンドユーザーごとの個別の割り当て。エンドユーザー ID のないリクエストには適用されません。

複数のポリシーが適用される場合は、それぞれがカウントされ、最初に上限に達したポリシーがリクエストを拒否します。ポリシーの制限は、上記のゲートウェイ制限に加えて適用されます。`tokens_per_minute`、`concurrent_requests`、部門への割り当てはまだ適用されません。ポリシーの変更は約 1 分以内に反映されます。

拒否されたリクエストは `429` を返し、エラーコード `rate_limit_exceeded`、理由 `policy_requests_per_minute`、`policy_id`、`limit_scope`（`key`、`member`、`guardrail`、`end_user` のいずれか）、および秒単位の `Retry-After` を含みます。ポリシーが適用されたリクエストのレスポンスには、最も厳しいポリシーの `x-ratelimit-limit-requests`、`x-ratelimit-remaining-requests`、`x-ratelimit-reset-requests`（例: `60s`）が含まれます。カウントはバックグラウンドで行われるため、`remaining` は概算です。1 つのリクエスト内のプロバイダーフォールバックは 1 回としてカウントされ、レスポンスキャッシュのヒットはカウントされません。

## プロバイダーの制限

BYOK リクエストには、ご自身のプロバイダーアカウントの制限が適用されます。管理対象のリクエストは共有のプロバイダー容量を使用します。この容量は、個々のワークスペースに割り当てられた利用枠ではありません。

ルーティング先のプロバイダーが `Retry-After` を返した場合、Phaseo は検証済みの値を転送します。BYOK のレスポンスには `X-Phaseo-Upstream-RateLimit-*` ヘッダーが含まれることもあります。これらのクォータヘッダーは共有のプロバイダー容量を示すため、管理対象のリクエストでは省略されます。その他の上流ヘッダーは転送されません。

## 制限されたリクエストへの対応

1. [エラーコード](./errors.mdx)を確認し、プロバイダーによる一時的な制限と、設定変更が必要なポリシーや予算の制約を区別してください。
2. `Retry-After` がある場合は従ってください。値は秒数による待機時間、または HTTP 日付です。再試行をスケジュールする前に値を検証してください。
3. それ以外の場合は、ランダムな揺らぎと最大待機時間を設定した指数バックオフを使用してください。
4. 再試行は、試行回数と全体の期限の両方で制限してください。不要になった処理をキャンセルし、再試行する前に失敗した各レスポンスのボディを解放してください。
5. 制限が続く場合は同時実行数を減らしてください。

結果が不明なジョブの送信を自動的に再試行したり、完了済みのツール操作を繰り返したりしないでください。クライアントがレスポンスを失っても、リクエストはプロバイダーに届いている可能性があります。再試行により処理や料金が重複するおそれがあります。受け付け済みの動画ジョブやバッチジョブは、再送信せずにステータスエンドポイントを使用してください。

## スロットリングの監視

エンドポイントとモデル別に `429` の発生率を追跡し、リクエストログでフォールバックの頻度を確認してください。アプリケーションのログを[ルーティング設定](../guides/routing-and-fallbacks.mdx)、および BYOK トラフィックに対するプロバイダーアカウントのクォータと照合してください。

ワークスペースの支出とアクセスの制御については、[予算](./endpoint/budgets-list.mdx)と[ガードレール](./endpoint/guardrails.mdx)を参照してください。
