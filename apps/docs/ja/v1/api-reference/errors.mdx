このページでは、Phaseo のエラーの意味と、次に取るべき対応を確認できます。

すべてのエラーレスポンスは共通の JSON 形式です。モデルやプロバイダーにかかわらず、アプリケーションで一貫して失敗を処理できます。 `error` フィールドは `code`、`message`、`type` を持つオブジェクトで、OpenAI 互換の SDK が読み取る形式です。そのため SDK の例外にゲートウェイのメッセージが含まれます。

## エラーレスポンスの例

```json
{
  "error": {
    "code": "upstream_error",
    "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
    "type": "server_error",
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "attempt_count": 1,
  "failed_providers": ["google-ai-studio"],
  "failed_statuses": [403],
  "provider_failure_diagnostics": {
    "category": "provider_access_missing",
    "hint": "The provider account appears not to have access to this model or feature yet. Verify account entitlements and provider-side access.",
    "provider": "google-ai-studio"
  },
  "upstream_error": {
    "code": "PERMISSION_DENIED",
    "message": "The caller does not have permission.",
    "description": null,
    "param": null
  },
  "failure_sample": [
    {
      "provider": "google-ai-studio",
      "type": "upstream_non_2xx",
      "status": 403,
      "upstream_error_code": "PERMISSION_DENIED",
      "upstream_error_message": "The caller does not have permission.",
      "upstream_error_description": null,
      "upstream_error_param": null,
      "upstream_payload_preview": "{\"error\":{\"status\":\"PERMISSION_DENIED\"}}",
      "retryable": false
    }
  ]
}
```

## 常に含まれるフィールド

- `generation_id`: サポートに共有できる安定したリクエスト ID。
- `status_code`: HTTP ステータスコードと同じ値。
- `error`: 失敗内容を表すオブジェクト。
  - `error.code`: `validation_error` などの機械可読なエラーコード。
  - `error.message`: 何が起きたかのわかりやすい説明。
  - `error.type`: エラーの種類（下の「エラーの種類」を参照）。
  - `error.param`: エラーの原因となったリクエストパラメーター。ゲートウェイが特定できない場合は `null`。
  - `error.metadata`（任意）: 失敗したプロバイダー、詳細な理由、失敗したステータス、`retry_after_seconds` などの構造化された詳細。同じ値はトップレベルにも返されます。
- `code`: `error.code` と同じコード。以前のレスポンスはこのコードを文字列として `error` に返していました。クライアントがそこに文字列を想定していた場合は `code` を読んでください。
- `message`: `error.message` と同じテキスト。
- `error_type`: 通常 `user` または `system` の大分類。
- `error_origin`: 主な原因が呼び出し元、Phaseo、上流プロバイダーのいずれかを示します。
- `description`: 発生した内容を平易に説明します。
- `details`（任意）: リクエスト検証エラーの構造化された詳細。

## 追加で表示されるフィールド

問題を早く解決できるよう、エラーによっては次の情報も含まれます。

- `reason`: `all_candidates_failed` や `pricing_not_configured` など、より具体的な理由。
- `provider_candidate_diagnostics` と `provider_enablement`: 指定されたエンドポイントでモデルを使用できなかった理由。
- `routing_diagnostics`: ルーティングや可用性チェックで候補が絞り込まれた詳細。
- `provider_failure_diagnostics`: 認証情報やアクセスの不足、地域制限、レート制限など、プロバイダー側の失敗に関するヒント。
- `upstream_error` と `failure_sample`: リクエストがプロバイダーまで届いた場合に、最初のプロバイダーエラーを可能な範囲で要約します。
- `failed_providers`、`failed_statuses`、`attempt_count`: 再試行とフェイルオーバーに関する追加情報。

## エラーの種類

`error.type` は OpenAI の[文書化されたエラータイプ](https://platform.openai.com/docs/guides/error-codes)に従い、HTTP ステータスから決まります。

| ステータス | `error.type` |
| --- | --- |
| `400`, `409`, `410`, `413`, `422` およびその他の 4xx | `invalid_request_error` |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `500`, `502` およびその他の 5xx | `server_error` |

`/v1/messages` のエラーも同じボディを使うため、Anthropic の SDK も `error.type` と `error.message` を読み取れます。

## ステータスクラスの見方

| ステータス | 意味 | 推奨する対応 |
| --- | --- | --- |
| `400-499` | リクエスト、認証、権限の問題 | 再試行する前にリクエストまたは認証情報を修正します。 |
| `429` | プロバイダーまたはルート単位のスロットリング | バックオフして再試行し、`Retry-After` に従います。 |
| `500-599` | Phaseo または上流プロバイダーの障害 | ジッター付きバックオフで再試行し、リクエスト ID をログに記録します。 |

## よくあるエラーコード

| `error.code` | HTTP ステータス | `error.type` | 説明 |
| --- | --- | --- | --- |
| `unauthorised` | `401` | `authentication_error` | API キーがないか、無効です。 |
| `guardrail_blocked` | `403` | `permission_error` | ワークスペースのガードレールまたはアクセスポリシーがリクエストをブロックしました。 |
| `not_found` | `404` | `not_found_error` | エンドポイントまたはリソースが見つかりません。 |
| `model_retired` | `410` | `invalid_request_error` | モデルは提供終了しており、どのプロバイダーも提供していません。`replacement_model` に切り替えてください。 |
| `insufficient_funds` | `402` | `insufficient_quota` | ワークスペースのクレジットがリクエストに対して不足しています。 |
| `key_limit_exceeded` | `429` | `rate_limit_error` | API キーが上限のいずれかに達しました。 |
| `phaseo_free_model_limit_exceeded` | `429` | `rate_limit_error` | Phaseoの無料モデル共通の日次上限に達しました（既定で1,500リクエスト）。`Retry-After`に従い、00:00 UTCのリセットを待つか、有料モデルを選択してください。 |
| `rate_limit_exceeded` | `429` | `rate_limit_error` | ワークスペースの[レート制限ポリシー](./limits.mdx)の上限に達しました。`policy_id`と`limit_scope`で対象を特定できます。`Retry-After`に従うか、ワークスペース管理者にポリシーの変更を依頼してください。 |
| `validation_error` | `400` | `invalid_request_error` | パラメーターまたはリクエスト本文が無効です。 `error.param` は最初の無効なフィールドを示します。 |
| `upstream_error` | `429` | `rate_limit_error` | リクエストで試行したすべてのプロバイダーがレート制限を適用しました。`Retry-After` に従ってください。BYOK リクエストには `X-Phaseo-Upstream-RateLimit-*` ヘッダーも含まれます。 |
| `upstream_error` | `502` | `server_error` | 上流のモデルプロバイダーが正しく応答しませんでした。 |
| `upstream_stream_failure` | `502` | `server_error` | ストリーミングしないリクエストで、生成開始後にプロバイダーが失敗しました。部分的な出力は返されず、リクエストは課金されません。 |
| `gateway_error` | `500` | `server_error` | Phaseo 内部で予期しない問題が発生しました。 |

## プロバイダーのエラー

Phaseo がプロバイダーに到達したものの、リクエストが失敗した場合は、次の情報が表示されることがあります。

- `provider_failure_diagnostics.category`
- `provider_failure_diagnostics.hint`
- `provider_failure_diagnostics.provider`

現在のカテゴリは次のとおりです。

- `credentials_not_configured`
- `credentials_invalid_or_forbidden`
- `provider_access_missing`
- `region_or_project_restriction`
- `model_unavailable_for_endpoint`
- `rate_limited`
- `server_error`

これらのフィールドを使うと、完全なデバッグモードを有効にせずに問題を解決できます。

## モデルまたはエンドポイントが利用できない場合

`unsupported_model_or_endpoint` のレスポンスには、次の情報が含まれる場合があります。

- `provider_candidate_diagnostics`
- `provider_enablement`
- `missing_pricing_providers`
- `routing_diagnostics`

これらの情報を使って、次の状態を見分けます。

- 既知だが、まだ有効になっていないモデル
- 要求されたエンドポイントに対応していないモデル
- 料金データの不足
- ロールアウトまたは内部可用性の制限

よく使われるフィールド：

- `provider_candidate_diagnostics.totalProviders`: エンドポイントのフィルタリング前に、そのモデルで認識されていたプロバイダーの数。
- `provider_candidate_diagnostics.supportsEndpointCount`: 要求されたエンドポイントに対応するプロバイダーの数。
- `provider_candidate_diagnostics.candidateCount`: アダプターの確認後に残ったプロバイダーの数。
- `provider_candidate_diagnostics.droppedUnsupportedEndpoint`: そのエンドポイントに対応していないため除外されたプロバイダー。
- `provider_candidate_diagnostics.droppedMissingAdapter`: そのエンドポイント用の Gateway アダプターがまだ存在せず、除外されたプロバイダーとエンドポイントの組み合わせ。
- `provider_enablement.capability`: `video_generation` など、適用される機能ゲート。
- `provider_enablement.providersBefore` / `provider_enablement.providersAfter`: 機能または有効化フィルター適用前後のプロバイダー。
- `provider_enablement.dropped[].reason`: `pricing_missing` などの機械可読な理由。
- `routing_diagnostics.filterStages[].stage`: 機能、ロールアウト、ルーティング状態などのルーティング段階。
- `routing_diagnostics.filterStages[].beforeCount` / `routing_diagnostics.filterStages[].afterCount`: 各段階の前後に残ったプロバイダー数。
- `routing_diagnostics.filterStages[].droppedProviders[].reason`: ロールアウトやルーティングの制限などの機械可読な理由。

### 例

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
    "message": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
    "type": "invalid_request_error",
    "param": null
  },
  "code": "unsupported_model_or_endpoint",
  "generation_id": "G-unsupported123",
  "status_code": 400,
  "description": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
  "provider_candidate_diagnostics": {
    "totalProviders": 3,
    "supportsEndpointCount": 2,
    "candidateCount": 1,
    "droppedUnsupportedEndpoint": ["provider-a"],
    "droppedMissingAdapter": [
      {
        "providerId": "provider-b",
        "endpoint": "responses"
      }
    ]
  },
  "provider_enablement": {
    "capability": "responses",
    "providersBefore": ["provider-b", "provider-c"],
    "providersAfter": ["provider-c"],
    "dropped": [
      {
        "providerId": "provider-b",
        "reason": "pricing_missing"
      }
    ]
  },
  "routing_diagnostics": {
    "filterStages": [
      {
        "stage": "provider_routing_status",
        "beforeCount": 1,
        "afterCount": 0,
        "droppedProviders": [
          {
            "providerId": "provider-c",
            "reason": "provider_status_not_ready"
          }
        ]
      }
    ]
  }
}
```

## モデルが提供終了になった場合

提供終了したモデルも、いずれかのプロバイダーが提供している間は引き続き利用できます。どのプロバイダーも提供しなくなると、そのモデルへのリクエストは `410` と `model_retired` エラーで失敗します。

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

- `model`: リクエストしたモデル。
- `retired_at`: モデルが提供終了になった日時。日付が記録されていない場合は `null`。
- `replacement_model`: 推奨される代替モデル。ない場合は `null`。

再試行しても解決しません。リクエストのモデル ID を更新してください。移行中もこれらのリクエストを処理し続けるには、リクエストの `models` リストに代替モデルを追加するか、ワークスペースで提供終了モデルのルーティングを有効にしてください。[モデルの非推奨化と提供終了](../guides/model-retirement.mdx)を参照してください。

## 任意のデバッグモード

ほとんどのリクエストスキーマは、制御されたトラブルシューティング用の `debug` オブジェクトに対応しています。

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

利用可能なフィールド：

- `enabled`
- `return_upstream_request`
- `return_upstream_response`
- `trace`
- `trace_level`（`summary` または `full`）

デバッグモードは、開発時または厳格に管理された環境でのみ使用してください。

## 再試行の方針

- **429 以外の 400 番台のエラー：**再試行する前に、リクエスト、認証情報、またはアクセスポリシーを修正してください。
- **429:** 指数バックオフを実装し、`Retry-After` ヘッダーに従います。
- **500 番台のエラー：**操作を安全に繰り返せる場合に限り、上限を設けて再試行してください。結果が不明な送信でも、すでにジョブが作成されたり料金が発生したりしている可能性があります。受け付け済みのジョブは、再送信せずに取得してください。

試行回数の上限と全体の期限を設定し、バックオフの待機時間にランダムな揺らぎを加えてください。レスポンスヘッダーと再試行の処理については、[レート制限](./limits.mdx)を参照してください。

## ストリーミング固有の注意点

- ストリーミング開始前に失敗すると、通常の JSON エラーペイロードが返されます。
- ストリームの途中で失敗した場合、ストリームは通常の終了ではなくエンドポイントの失敗イベントで終わります。Chat Completions では `error` フレーム、Responses では `response.failed`（または `error`）、Messages では `error` イベントです。部分的なストリームを未完了として扱い、再試行を提案します。
- Chat Completions の `error` フレームにも同じエラーオブジェクトが含まれ、`error.type` はコードから決まります。

  ```json
  {
    "object": "error",
    "message": "The upstream stream ended before the response completed.",
    "code": "upstream_stream_failure",
    "error": {
      "code": "upstream_stream_failure",
      "message": "The upstream stream ended before the response completed.",
      "type": "server_error",
      "param": null
    }
  }
  ```
- ストリーミングしないリクエストでプロバイダーが途中で失敗すると、部分的な応答ではなく `upstream_stream_failure` を伴う `502` が返されます。
- 必ず `generation_id` とエンドポイント、モデルのメタデータをログに記録します。

## トラブルシューティングのヒント

- [Gateway のステータスページ](https://status.phaseo.app)で進行中のインシデントを確認します。
- リクエスト本文をエンドポイントのドキュメントと照合します。
- サポートに連絡する際は `generation_id` を共有してください。

エージェント向けのエラー処理ルール（このページの要約）:

- メッセージの文面ではなく、`error.code`（トップレベルの `code` にも返されます）、`error.type`、`status_code` で分岐します。失敗ごとに `generation_id` を記録します。
- `400`、`401`、`403`、`404`: まずリクエスト、キー、アクセス権を修正します。同じリクエストをそのまま再試行しないでください。
- `410` と `model_retired`: `replacement_model` が `null` でなければ切り替えます。`null` の場合は `GET /v1/models` で新しいモデルを選びます。
- `429`: `Retry-After`（秒数または HTTP 日付）がある場合は、その時間だけ待ってから再試行します。ない場合はジッター付き指数バックオフを使います。`Retry-After` のない `key_limit_exceeded` エラーは自動ではリセットされないため、再試行しないでください。
- `500`〜`599`: 呼び出しを繰り返しても安全な場合に限り、試行回数の上限、全体の期限、ジッター付き指数バックオフを設定して再試行します。非同期ジョブでは再送信せず、受け付け済みのジョブを取得します。
- デバッグペイロードは機密情報として扱い、永続ログに書き込む前にマスキングします。
- 実績のある再試行とエラー解析のパターンには、`phaseo-gateway` スキルをインストールします: `npx skills add https://phaseo.app/docs --skill phaseo-gateway`
</Visibility>
