---

複数のサービスを 1 つのプリセットに移行してプロンプト、モデル、プロバイダーのルールを共有させ、リクエストのログで各リクエストの行き先を説明できるようにします。完成すると、呼び出し元は `"model": "@release-summary"` と入力だけを送り、ポリシーの変更を呼び出し元ごとに 1 つずつ展開できるようになります。

このリクエストの形は本番環境で使えます。プリセットの設定がリクエストとどう統合されるかは[プリセット](../guides/presets)で説明しています。このレシピでは展開を扱います。

## 呼び出し元をプリセットに移行する

<Steps>
<Step title="プリセットを作成する">

**設定 → プリセット** で、システムプロンプト、承認済みのモデル、プロバイダーの優先設定、`temperature` などの既定のパラメーターを持つ `release-summary` を作成します。管理キーを使って作成することもできます。

```bash
curl https://api.phaseo.app/v1/presets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"@release-summary","config":{"model":"anthropic/claude-sonnet-5.5"}}'
```

</Step>
<Step title="名前で呼び出す">

プリセットを `model` として送ります。別の `preset` フィールドはありません。

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@release-summary",
    "input": "Generate a release summary for the last 24 hours.",
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "@release-summary",
  input: "Generate a release summary for the last 24 hours.",
  meta: true,
});

console.log(response.model, response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "@release-summary",
        "input": "Generate a release summary for the last 24 hours.",
        "meta": True,
    }
)

print(response.get("model"), response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

レスポンスの `model` は応答したモデル、`meta.routing.selected_provider` はプロバイダーです。

</Step>
<Step title="プリセットが適用した内容を確認する">

**設定 → 使用量 → ログ** でリクエストを開きます。どのプリセットの既定値が適用されたかが表示されます。プリセットで許可されていないモデルは、別のモデルに振り替えられるのではなく、`validation_error`（キーワード `preset_model_not_allowed`）で失敗します。

</Step>
</Steps>

## ルーティングの判断を説明する

リクエストが想定どおりにルーティングされなかった場合は、**設定 → 使用量 → ログ** でリクエストの **ルーティングの可観測性** を展開します。次の 3 つの疑問に答えられます。

| 疑問 | 確認する箇所 |
| --- | --- |
| プロバイダーがスキップされたのはなぜか | 順位付けの前に除外されたプロバイダーとその理由、およびロールアウトやルーティングのステータスによって順位を下げられたプロバイダー |
| リクエストがブロックされたのはなぜか | リクエストに対するワークスペースポリシーやガードレールによるブロック |
| このプロバイダーが選ばれたのはなぜか | 順位付けされた各プロバイダーの最終スコアと、その根拠となる要素 |

各フィールドの説明は[ルーティングの判断を説明する](../guides/routing-and-fallbacks#explain-a-routing-decision)を参照してください。

## ポリシーの変更を展開する

1. 変更をプリセットの新しいバージョンとして公開します。ポリシーが大きく異なる場合は、新しいスラッグを作成します。
2. リスクの低い呼び出し元を 1 つ移行します。たとえば、`@release-summary@v4` や `canary` ラベルを指すようにします。
3. そのリクエストの詳細と使用量の推移を、他の呼び出し元と比較します。
4. ルーティングが想定どおりになったら、残りの呼び出し元を移行します。ロールバックするには、ラベルを以前のバージョンに向けます。

バージョンとラベルについては[バージョン管理とロールバック](../guides/presets#version-and-roll-back)で説明しています。プリセットに含めるべきでないリクエスト単位の上書きについては、[プロバイダーを固定または除外する](./pin-or-ignore-providers-per-request)を参照してください。
