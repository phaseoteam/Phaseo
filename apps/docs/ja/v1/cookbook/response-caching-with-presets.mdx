<Warning>
レスポンスキャッシュはまだ利用できません。プリセットは `response_caching.enabled` と `response_caching.ttl_seconds` を受け付けますが、現在 Gateway はレスポンスを保存も再生もしないため、すべてのリクエストはプロバイダーに送られ、通常どおり課金されます。
</Warning>

今すぐ繰り返しのリクエストのコストとレイテンシを下げるには、[プロンプトキャッシュ](../guides/prompt-caching)を使います。プロバイダーは長く安定したプロンプトの先頭部分を再利用し、キャッシュされた部分を低い料金で課金します。Phaseo は、会話をそのキャッシュを持つプロバイダーに留めます。[プロバイダーアフィニティ](../guides/prompt-caching#provider-affinity)を参照してください。

## キャッシュに備えてプリセットを整える

次の習慣は現在のプロンプトキャッシュに役立ち、レスポンスキャッシュの提供開始後にも重要になります。どちらもリクエストが同一であり続けることに依存するためです。

| 安定させるもの | 理由 |
| --- | --- |
| システムプロンプトの文言 | 少しでも変更すると新しいキャッシュエントリが始まります |
| モデル、プロバイダーのオプション、推論の設定 | 2 つのリクエストを同一とみなす要素の一部です |
| `temperature` などのパラメーター | 同上 |
| レスポンスの形式、ツール、ツールの選択 | 同上 |

これらを 1 つの[プリセット](../guides/presets)にまとめて、すべての呼び出し元が同じリクエストを送るようにします。試行的な呼び出し元や temperature の高い呼び出し元には専用のプリセットを用意し、キャッシュ可能なトラフィックと混ざらないようにしてください。

## キャッシュすべきでない場合

外部のライブな状態に依存するプロンプト、文脈がすぐに変わるユーザー固有の回答、変動しやすいツール出力を含むリクエスト、毎回新しい回答が欲しい生成は、キャッシュする前提にしないでください。
