A request can be throttled by the selected provider or by an applicable workspace or key policy. Routing and fallbacks can reduce provider failures, but a request can still return `429`.

## Gateway limits

Each user in each workspace has a requests-per-minute allowance, measured over a rolling minute. API keys created by the same user share that allowance. OAuth requests use the authenticated user. Keys without an owner share a workspace allowance.

The allowance depends on the workspace's account standing and rises automatically as the workspace becomes established:

| Workspace | Requests per minute |
| --- | --- |
| New workspace | 10 |
| At least 7 days old, or has made a paid top-up | 25 |
| At least 30 days old with at least $50 of paid top-ups, net of refunds | 60 |
| Invoiced billing | 120 |

A workspace receives the highest allowance it qualifies for. Changes take effect within a few minutes.

Free-model routes also have a default allowance of **1500 requests per UTC day**, shared across free models for the same user and workspace. Paid-model requests do not consume this daily allowance. An admitted free request counts even if the provider subsequently fails; provider fallbacks within that request count once.

These limits apply across gateway regions. They can be increased for a specific user and workspace. File operations and job-status polling use the minute allowance; management endpoints do not.

A gateway quota rejection returns `429` with `Retry-After` in seconds. Its error reason is `customer_requests_per_minute` or `free_requests_per_day`. Wait for that delay before retrying. If quota enforcement is temporarily unavailable, the gateway returns `503` with retry guidance.

## Key limits and budgets

An API key's daily, weekly or monthly request and spend limits, and the workspace's [budgets](./endpoint/budgets-list.mdx), return `429` with the `key_limit_exceeded` error code once reached. The body's `reason`, `limit_window` and `reset_at` fields identify the limit and when its window resets. `Retry-After` gives the seconds until that reset. It is omitted when the limit does not reset by itself, such as a lifetime budget or a soft-blocked key; instead of retrying, raise the workspace budget, or for a key limit, raise the key's limit or use a different key.

## Rate limit policies

Workspace admins can create named rate limit policies through the `/v1/rate-limits` management API and assign them to API keys, workspace members, guardrails, or as the default for each end user. The gateway enforces a policy's `requests_per_minute`, measured over a rolling minute:

- **Key:** the key's own allowance.
- **Member:** one allowance shared by the member's keys and OAuth requests.
- **Guardrail:** a separate allowance for each key (or OAuth user) the guardrail covers.
- **End-user default:** a separate allowance for each end user, identified by the request's `user` field or `X-Phaseo-User-Id` header. Requests without an end-user ID are not limited by it.

When several policies apply, each is counted and the first one exhausted rejects the request. Policy limits apply in addition to the gateway limits above. `tokens_per_minute`, `concurrent_requests` and department assignments are not enforced yet. Policy changes take effect within about a minute.

A rejected request returns `429` with the `rate_limit_exceeded` error code, reason `policy_requests_per_minute`, the `policy_id` and the `limit_scope` (`key`, `member`, `guardrail` or `end_user`), plus `Retry-After` in seconds. Responses to requests a policy applies to include `x-ratelimit-limit-requests`, `x-ratelimit-remaining-requests` and `x-ratelimit-reset-requests` (for example `60s`) for the most restrictive policy. Counting happens in the background, so `remaining` is approximate. Provider fallbacks within one request count once, and response cache hits are not counted.

## Provider limits

BYOK requests use the limits of your provider account. Managed requests use shared provider capacity; that capacity is not an individual workspace allowance.

Phaseo forwards a validated `Retry-After` value when the routed provider supplies one. BYOK responses can also include `X-Phaseo-Upstream-RateLimit-*` headers. These quota headers are omitted for managed requests because they describe shared provider capacity. Other upstream headers are not forwarded.

## Handle a throttled request

1. Inspect the [error code](./errors.mdx) to distinguish temporary provider throttling from a policy or budget restriction that requires configuration changes.
2. Respect `Retry-After` when present. It can be a delay in seconds or an HTTP date; validate the value before scheduling a retry.
3. Otherwise, use exponential backoff with jitter and a maximum delay.
4. Bound retries by both attempt count and an overall deadline. Cancel abandoned work and release each failed response body before retrying.
5. Reduce concurrency if throttling persists.

Do not automatically retry an ambiguous job submission or replay completed tool actions. A request may have reached the provider even if the client lost its response; retries can duplicate work and charges. For an accepted video or batch job, use its status endpoint rather than submitting it again.

## Monitor throttling

Track `429` rates by endpoint and model, and inspect fallback frequency in request logs. Compare your application logs with [routing settings](../guides/routing-and-fallbacks.mdx) and provider account quotas for BYOK traffic.

See [budgets](./endpoint/budgets-list.mdx) and [guardrails](./endpoint/guardrails.mdx) for workspace spending and access controls.
