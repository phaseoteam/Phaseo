Text API errors use the envelope expected by the request protocol: OpenAI error objects for Responses and Chat Completions, and Anthropic's `type: "error"` envelope for Messages. Phaseo diagnostic fields remain alongside that envelope for retries, routing details, and support correlation.

## OpenAI Responses and Chat Completions

```json
{
  "request_id": "G-abc123",
  "generation_id": "G-abc123",
  "status_code": 503,
  "error_code": "provider_service_unavailable",
  "category": "provider_unavailable",
  "error": {
    "message": "The upstream provider is temporarily unavailable.",
    "type": "service_unavailable_error",
    "param": null,
    "code": "provider_service_unavailable"
  },
  "message": "The upstream provider is temporarily unavailable.",
  "description": "All configured provider candidates failed.",
  "error_type": "system",
  "error_origin": "upstream",
  "retryable": true,
  "action": "Retry after a short delay or choose another provider. Contact support with the request ID if it continues.",
  "help_url": "https://phaseo.app/docs/v1/api-reference/errors",
  "docs_url": "https://phaseo.app/docs/v1/api-reference/errors",
  "support_url": "https://phaseo.tawk.help/",
  "reason": "provider_service_unavailable",
  "attempt_count": 1,
  "failed_providers": ["novita"],
  "failed_statuses": [503],
  "upstream_error": {
    "code": "SERVICE_NOT_AVAILABLE",
    "message": "The provider service is temporarily unavailable."
  },
  "retry_after_seconds": 15
}
```

## Anthropic Messages

```json
{
  "type": "error",
  "error": {
    "type": "rate_limit_error",
    "message": "The upstream provider is rate limiting this request."
  },
  "request_id": "G-abc123",
  "error_code": "provider_capacity_exhausted",
  "category": "rate_limit",
  "status_code": 429,
  "error_type": "system",
  "error_origin": "upstream",
  "retryable": true,
  "retry_after_seconds": 10,
  "upstream_error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "You have exceeded the request rate limit.",
    "description": "current limit 30 requests per minute"
  }
}
```

Anthropic Messages responses also return the correlation ID in the `request-id` response header.

`generation_id` is retained as a backwards-compatible alias. Use `request_id` in new integrations, but accept either field when reading older responses.

## Fields to use in client code

| Field | Meaning |
| --- | --- |
| `error` | Protocol-standard error object. OpenAI responses include `message`, `type`, `param`, and `code`; Anthropic Messages include `type` and `message`. |
| `error_code` | Stable Phaseo machine-readable code, such as `provider_request_rejected` or `provider_capacity_exhausted`. |
| `category` | Broad failure category on inference gateway errors: authentication, model, unsupported feature, invalid request, rate limit, billing, provider availability, or internal failure. |
| `error.code` | On OpenAI endpoints, the same stable Phaseo code as `error_code`. |
| `error.type` | Protocol error category such as `invalid_request_error`, `rate_limit_error`, or `server_error`/`api_error`. |
| `message` | Short, user-safe summary suitable for a log or UI. |
| `description` | More detailed explanation of the failure. |
| `status_code` | The HTTP status returned by the Gateway. |
| `error_type` | `user` when the request or credentials need a change, or `system` when Phaseo or a provider needs attention. |
| `error_origin` | The main source of the failure: `user`, `gateway`, or `upstream`. |
| `retryable` | Whether retrying without changing the request may succeed. This is a hint, not permission to retry forever. |
| `action` | The recommended next step. Display this when you need to guide a user. |
| `help_url` | A relevant model, key, billing, or documentation page when one is available. |
| `request_id` | Stable correlation ID for logs, Request Logs, and support conversations. |
| `docs_url` | The current error contract and recovery guidance. |
| `support_url` | The Phaseo Help Center. |
| `retry_after_seconds` | Normalized delay when the response includes a usable `Retry-After` header. |

The response may also include `details`, `reason`, `routing_diagnostics`, `provider_failure_diagnostics`, `failed_providers`, `failed_statuses`, `attempt_count`, `upstream_error`, and `failure_sample`. Treat those fields as diagnostic context. Do not build application behavior around provider-specific text.

## Choose the right recovery path

| Status or code | What it usually means | What to do |
| --- | --- | --- |
| `400` `invalid_json` or `validation_error` | The body or one of its fields is invalid. | Read `details`, correct the request, and send it again. |
| `400` `provider_request_rejected` | A provider rejected request parameters or a feature for the selected route. | Read the bounded `failure_sample`; correct the request or select a compatible model/provider. Do not retry unchanged. |
| `400` `provider_feature_unsupported` | The provider reports that this model does not support a requested feature. | Review the model page in `help_url` and remove the feature or choose another model. |
| `400` `unsupported_model_or_endpoint` | The model is not available for the requested endpoint or capability. | Check the model page and endpoint reference, then choose a supported combination. |
| `400` `byok_credentials_required` | The selected BYOK route does not have the required provider credentials. | Check the workspace BYOK configuration or select a managed Phaseo route. |
| `401` `unauthorised` | The API key is missing, invalid, or not being sent as a bearer token. | Check the key and the `Authorization` header. Never put the key in browser code. |
| `402` `insufficient_funds` | Your workspace needs more credits. | Add credits using `help_url`. |
| `402` `pricing_not_configured` | The gateway cannot price the selected model route. | Choose another model or contact support with `request_id`. |
| `403` `guardrail_blocked` or `model_region_unavailable` | A policy, workspace, provider, or region restriction applies. | Read `action` and the diagnostic fields, then change the request or configuration. |
| `404` `not_found` | The endpoint or referenced resource was not found. | Check the URL, workspace, model ID, and resource identifier. |
| `409` `not_ready` | A resource or route is temporarily unavailable. | Wait briefly and retry if `retryable` is true. |
| `429` `key_limit_exceeded` or `provider_capacity_exhausted` | A key, route, or provider is temporarily at its limit. | Respect `Retry-After` and use bounded exponential backoff. |
| `500` `gateway_error` or `pipeline_execution_error` | Phaseo could not complete the request internally. | Retry when `retryable` is true. If it persists, contact support with `request_id`. |
| `502` `upstream_error` or `provider_payment_required` | A provider route failed or its billing/access needs attention. | Read provider diagnostics. Retry only when `retryable` is true. |
| `503` `provider_service_unavailable` | The selected provider reports that its service is unavailable. | Retry with bounded backoff or select another provider. |

Use `error_code` or OpenAI's `error.code` for the specific Phaseo failure, `category` for broad handling, and `error.type` for the protocol's standard category. The provider's original code and message remain under `upstream_error` when available. Always consider `status_code`, `retryable`, and `action` together.

## Provider error normalization

Provider code names vary. Every executor passes upstream HTTP failures through the shared normalizer, which maps common status codes and error-code aliases to stable gateway categories. Provider-specific mappings live beside that provider's executor; Novita mappings are listed below. The original provider code and message remain in `upstream_error` and `failure_sample` for diagnosis.

| Novita upstream error | Gateway response | OpenAI `error.type` | Anthropic `error.type` | Retryable |
| --- | --- | --- | --- | --- |
| `NOT_ENOUGH_BALANCE` (403) | `502` `provider_payment_required` | `server_error` | `api_error` | No |
| `INVALID_REQUEST_BODY` (400) | `400` `provider_request_rejected` | `invalid_request_error` | `invalid_request_error` | No |
| `INVALID_REQUEST_BODY` with a structured output support message (400) | `400` `provider_feature_unsupported` | `invalid_request_error` | `invalid_request_error` | No |
| `RATE_LIMIT_EXCEEDED` (429) | `429` `provider_capacity_exhausted` | `rate_limit_error` | `rate_limit_error` | Yes |
| `TOKEN_LIMIT_EXCEEDED` (429) | `429` `provider_capacity_exhausted` | `rate_limit_error` | `rate_limit_error` | Yes |
| `SERVICE_NOT_AVAILABLE` (503) | `503` `provider_service_unavailable` | `service_unavailable_error` | `overloaded_error` | Yes |

When a provider supplies `Retry-After`, the Gateway forwards it and exposes the parsed delay as `retry_after_seconds`.

For the Novita structured output rejection, the response says “Structured outputs are not supported by this model” and links to the model page in `action` and `help_url`. The original Novita `reason` and `message` remain in `upstream_error`.

## Retry safely

Use bounded exponential backoff with jitter. Honor the `Retry-After` header when it is present. Do not retry validation, authentication, permission, billing, or unsupported-model failures without changing the cause.

For `500`-series errors, repeat an operation only when doing so is safe. An ambiguous submission may already have created a job or incurred a charge; retrieve an accepted job instead of submitting it again.

```js
async function requestWithBackoff(makeRequest, maxAttempts = 3) {
  for (let attempt = 0; attempt < maxAttempts; attempt += 1) {
    const response = await makeRequest();
    if (response.ok) return response;

    const payload = await response.json().catch(() => ({}));
    const retryable = payload.retryable === true;
    if (!retryable || attempt === maxAttempts - 1) return { response, payload };

    const retryAfterSeconds = Number(payload.retry_after_seconds);
    const serverDelayMs = Number.isFinite(retryAfterSeconds) ? retryAfterSeconds * 1000 : 0;
    const backoffMs = Math.min(10_000, 500 * 2 ** attempt);
    const jitterMs = Math.floor(Math.random() * 250);
    await new Promise((resolve) =>
      setTimeout(resolve, Math.max(serverDelayMs, backoffMs) + jitterMs),
    );
  }
}
```

For a `429` response, `Retry-After` may be a number of seconds or an HTTP date. Use `retry_after_seconds` when you want to avoid parsing the header yourself.

## Provider and routing diagnostics

When routing reaches a provider, Phaseo may include safe summaries of the attempts:

- `provider_failure_diagnostics.category` and `provider_failure_diagnostics.hint` explain common credential, access, region, rate-limit, and provider-service failures.
- `failed_providers`, `failed_statuses`, and `attempt_count` show how failover progressed.
- `upstream_error` and `failure_sample` contain bounded, provider-safe summaries of the failure.
- `failure_sample[].normalized_error_code` records the shared category assigned to an individual provider attempt; `failure_sample[].upstream_error_code` retains the provider's original code.
- `provider_candidate_diagnostics`, `provider_enablement`, and `routing_diagnostics` explain why a model or endpoint was filtered out.

These fields are intended for troubleshooting. Phaseo redacts sensitive request content from diagnostics, but you should still avoid writing full error payloads to shared logs without reviewing them.

## Validation details

Validation errors can include a `details` array:

```json
{
  "error_code": "validation_error",
  "status_code": 400,
  "error": {
    "message": "temperature must be less than or equal to 1",
    "type": "invalid_request_error",
    "param": "temperature",
    "code": "validation_error"
  },
  "details": [
    {
      "message": "temperature must be less than or equal to 1",
      "path": ["temperature"],
      "keyword": "maximum"
    }
  ]
}
```

Show the detail message and field path to the developer or user. Do not retry the same payload unchanged.

## Streaming-specific behavior

- If the request fails before streaming begins, the Gateway returns the JSON contract described on this page.
- If a provider fails after streaming starts, the stream can contain an error event instead of a complete response. Treat the response as incomplete.
- Store `request_id` from the initial response or error event, along with the endpoint and model.
- Offer a bounded retry only when the error is retryable. Never append a partial streamed answer to a successful response.

## Debug mode

Some request schemas support a controlled `debug` object:

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

Use debug mode only in development or tightly controlled troubleshooting. Upstream requests and responses can contain sensitive data. Redact them before storing or sharing logs.

## Contact support with useful context

If the problem continues, open the [Phaseo Help Center](https://phaseo.tawk.help/) and include:


1. `request_id` or `generation_id`.
2. The UTC time of the request.
3. The endpoint and model ID.
4. The HTTP status, `error_code`, `message`, and `action`.
5. Relevant `details` or provider diagnostics.
6. A minimal reproduction with secrets, API keys, prompts, and personal data removed.

Do not send API keys, full authorization headers, raw prompts, provider credentials, or unredacted request logs in a support message.

Check the [Gateway status page](https://status.phaseo.app) for ongoing incidents.
