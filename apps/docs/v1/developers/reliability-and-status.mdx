Check the [status page](https://status.phaseo.app) and `GET /v1/health` to see whether Phaseo is healthy, `GET /v1/models` to see whether a model is routable now, and your own test run to see whether a route meets your reliability target.

## Check current service health

1. Open the [Phaseo status page](https://status.phaseo.app) for current incidents and incident history.
2. Call `GET /v1/health` for a minimal Gateway health check.
3. If a single request failed, keep its request ID and inspect its activity or generation record before assuming the whole service is down.

```bash
curl https://api.phaseo.app/v1/health
```

```json
{
  "status": "ok"
}
```

<Note>
The public status page reports service health. Phaseo does not currently claim a contractual public uptime SLA.
</Note>

## Confirm that a model is routable

The Phaseo catalog lists more models than the Gateway can route: a catalog entry means Phaseo tracks the model, not that a public route exists. `GET /v1/models` returns only currently routable models by default:

```bash
curl https://api.phaseo.app/v1/models \
  -H "Authorization: Bearer $PHASEO_API_KEY"
```

Add `availability=all` to also see coming-soon and inactive mappings. Send production traffic to a provider row only when its `availability_status` is `active` and `is_active_gateway` is `true`. See [Provider and Phaseo Statuses](../guides/provider-statuses.mdx) for what the status icons on model pages mean.

| State | What it means |
| --- | --- |
| `active` | At least one public Gateway route is available now. |
| `coming_soon` | Phaseo tracks a planned or preview route, but it is not publicly routable. |
| `inactive` | A known route is disabled, unavailable, expired, or otherwise not routable. |
| `not_listed` | No Gateway provider mapping is currently listed for the model. |

`active` doesn't guarantee uptime, access in every region, or the same commercial terms for every workspace.

## Interpret performance metrics

Phaseo's performance data summarizes real requests routed through the Gateway; it isn't a controlled lab benchmark.

| Metric | Definition |
| --- | --- |
| Gateway TTFT | Gateway request start to the first content-bearing generated output. |
| Provider TTFT | Provider dispatch to the first content-bearing generated output. |
| Provider duration | Provider dispatch to the terminal response. |
| Gateway E2E | Gateway request start to completion. |
| Phaseo overhead | The non-negative difference between Gateway E2E and provider duration. |
| Effective throughput | All output tokens divided by full provider duration. |
| Output speed | Output tokens after the first divided by provider time after TTFT. |

TTFT and output speed need a streaming response with a content-bearing first output. A non-streaming request still contributes duration and effective throughput, but no TTFT.

Read every metric with its time window, route, region, streaming mode and percentile. Provider load, prompt length, output length, retries and network conditions all change the result.

For the complete definitions, see [Pricing & Performance](../exploring/pricing-performance) and [How Phaseo measures latency and throughput](https://phaseo.app/how-phaseo-measures-latency-throughput).

## Validate with your workload

Public metrics show direction; they don't prove a route meets your production target. Run a small, reproducible test before a rollout:

1. Remove sensitive production data and keep a representative prompt mix.
2. Record the model ID, endpoint, provider constraints, region, streaming mode, and concurrency.
3. Run enough repetitions to compare distributions rather than one request.
4. Capture success rate, Gateway TTFT, provider duration, Gateway E2E, output tokens, and final cost.
5. Test invalid keys, invalid models, rate limits, and unavailable-provider failures.
6. Save request IDs and the exact time window so another engineer can reproduce the result.

Do not publish a customer name, quote, workload result, or reliability percentage without permission and a documented method.

## Triage a failed request

1. Check [service status](https://status.phaseo.app).
2. Confirm the model still appears in the default [`GET /v1/models`](../api-reference/endpoint/models) response, and check its [endpoints](../api-reference/endpoint/model-endpoints).
3. Look up the HTTP status and error code in [Errors and Debugging](../api-reference/errors).
4. Retry transient `429` and `5xx` responses with bounded exponential backoff; see [Rate Limits](../api-reference/limits.mdx).
5. Keep the request ID when you contact [support](https://phaseo.app/help).

To keep requests working when one provider fails, set up [routing and fallbacks](../guides/routing-and-fallbacks).
