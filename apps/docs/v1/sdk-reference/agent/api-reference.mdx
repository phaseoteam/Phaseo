## Create an agent

Creates an agent from a definition. The definition's step limit applies to each run or continue call.

| Language | Name | Default step limit |
| --- | --- | --- |
| TypeScript | `createAgent(definition)` | 12 |
| Python | `create_agent(definition)`, from a dict or an `AgentDefinition` | 12 |
| Go | `CreateAgent(AgentDefinition) *Agent` | 8 |
| C# | `AgentSdk.CreateAgent(AgentDefinition)` | 12 |
| PHP | `AgentSdk::createAgent(AgentDefinition)` | 12 |
| Ruby | `PhaseoAgentSdk.create_agent(definition)`, from an `AgentDefinition` or keyword fields | 12 |
| Java | `AgentSdk.createAgent(AgentDefinition)` | 12 (a `maxSteps` below 1 becomes 12) |
| Rust | `create_agent(AgentDefinition::new(id, model))` | 8 (values are clamped to at least 1) |

### Definition fields

Rust builds the definition with methods instead of fields: `AgentDefinition::new(id, model)`, then `.instructions(text)`, `.tool(tool)` (once per tool), `.max_steps(limit)`, `.model_retries(count, backoff)` and `.human_review(callback)`. Java's `AgentDefinition` is a record with 10-, 13- and 19-argument constructors.

| Field | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby) | PascalCase (Go, C#) | Not in |
| --- | --- | --- | --- | --- |
| Agent ID (required) | `id` | `id` | `ID` (Go), `Id` (C#) | |
| Model or preset | `model`, `preset` | `model`, `preset` | `Model`, `Preset` | Rust has no `preset` |
| Model list (only the first is used, when `model` isn't set; no fallback) | `models` | | | All but TypeScript |
| Instructions | `instructions` | `instructions` | `Instructions` | |
| Tools | `tools` | `tools` | `Tools` | |
| Tools offered on a step | `activeTools` | | | All but TypeScript |
| Rewrite history before each model request | `prepareMessages` | | | All but TypeScript |
| Step limit and stop conditions | `maxSteps`, `stopWhen` | `max_steps`, `stop_when` | `MaxSteps`, `StopWhen` | Rust has no `stop_when` |
| Model retry and tool concurrency | `modelRetry`, `toolExecution` | `model_retry`, `tool_execution` | `ModelRetry`, `ToolExecution` | Rust has no tool concurrency |
| Sampling and length | `temperature`, `maxOutputTokens`, `topP` | `temperature`, `max_output_tokens`, `top_p` | | Go, C#, Java, Rust |

In TypeScript, `model`, `instructions` and the sampling values can be fixed or dynamic.

## Run and continue

| Purpose | TypeScript | Python | Go | C# | PHP | Ruby | Java | Rust |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Run | `run(options)` | `run(...)` | `Run(ctx, RunOptions)` | `Run(RunOptions)` | `run(...)` | `run(...)` | `run(RunOptions)` | `run(&mut client, options)`, `run_with_events(&mut client, options, callback)` |
| Run and stream | `stream(options)` | `stream(...)` | `Stream(ctx, RunOptions)` | `Stream(RunOptions)` | `stream(...)` | `stream(...)` | `stream(RunOptions)` | None |
| Continue | `continueRun(options)` | `continue_run(...)` | `Continue(ctx, ContinueOptions)` | `ContinueRun(ContinueOptions)` | `continueRun(...)`, `continueRunById(...)` | `continue_run(...)` | `continueRun(ContinueOptions)` | `continue_run(&mut client, options)`, `continue_with_events(...)` |
| Continue and stream | `continueStream(options)` | `continue_stream(...)` | `ContinueStream(ctx, ContinueOptions)` | `ContinueStream(ContinueOptions)` | `continueStream(...)` | `continue_stream(...)` | `continueStream(ContinueOptions)` | None |

Run and continue return a run result: a `Promise<AgentRunResult>` in TypeScript, `(RunResult, error)` in Go, `Task<RunResult>` in C#, `Result<RunResult, AgentError>` in Rust, and the run result directly elsewhere. Stream methods return a stream result immediately.

### Run options

PHP and Ruby take these as named or keyword arguments; Java's `RunOptions` is a positional record in the order `input, client, context, model, preset, maxSteps, modelRetry, toolExecution, onEvent, devtools`, then an optional `state`.

| Option | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) | Not in |
| --- | --- | --- | --- | --- |
| Input | `input` | `input` | `Input` | |
| Whole conversation instead of input | `messages` | | | All but TypeScript |
| Model client | `client` | `client` | `Client` | Rust passes it as a separate argument |
| Application context | `context` | `context` | `Context` | |
| Model, preset and step limit overrides | `model`, `preset`, `maxSteps` | `model`, `preset`, `max_steps` | `Model`, `Preset`, `MaxSteps` | Rust has `model` and `max_steps` only |
| Retry and tool concurrency overrides | `modelRetry`, `toolExecution` | `model_retry`, `tool_execution` | `ModelRetry`, `ToolExecution` | Rust |
| Sampling overrides | `temperature`, `maxOutputTokens`, `topP` (TypeScript) | | | All but TypeScript |
| Cancellation | `signal` (TypeScript) | | `CancellationToken` (C#) | Go uses `ctx`; others cancel through the stream |
| Event handler | `onEvent` | `on_event` | `OnEvent` | Rust uses `run_with_events` |
| Local capture | `devtools` | `devtools` | `Devtools` | Rust |
| State accessor | `state` | `state` | `State` | Rust |
| Add messages before the next model request | `takeMessages` (TypeScript) | | | All but TypeScript |

Python's `run()` also accepts `stop_when` but ignores it; set stop conditions on the definition. PHP's `stream()` and Ruby's `stream` take only `input`, `client`, `context` and `state`. Rust creates defaults with `RunOptions::new(input)`.

### Continue options

Continue options take the run overrides above, plus:

| Option | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) | Not in |
| --- | --- | --- | --- | --- |
| The saved run | `run` | `run` (Rust: `result`) | `Run` | |
| Load the run by ID through `state` | `runId` | `run_id` | `RunID` (Go), `RunId` (C#) | Rust; PHP uses `continueRunById($runId, $state, $client, ...)` |
| Human input | `humanInput` | `human_input` | `HumanInput` | |
| Structured human messages | `humanMessages` (TypeScript) | | | All but TypeScript |
| Approvals | `approvals` (TypeScript alias `approveToolCalls`) | `approvals` | `Approvals` | |
| Rejections | `rejections` (TypeScript alias `rejectToolCalls`) | `rejections` | `Rejections` | Rust |
| Tool outputs | `toolOutputs` | `tool_outputs` | `ToolOutputs` | |

Java's `ContinueOptions` order is `run, client, context, model, preset, maxSteps, humanInput, modelRetry, toolExecution, onEvent, devtools`, then `approvals, rejections, toolOutputs`, then `runId, state`. Besides this 16-argument form, it has constructors that take only the first 11 or the first 14 arguments; the rest default to empty lists or `null`. Rust creates defaults with `ContinueOptions::new(result)`.

## Stream result

| Purpose | TypeScript | Python | Go | C# | PHP | Ruby | Java |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Completed result | `getResult()`, or `await` the stream | `result()` | `Result()` | `GetResult()` | `getResult()` | `result` | `getResult()` |
| Full final text | `getText()` | | | | | | |
| Text deltas | `getTextStream()` | `text_stream()` | `Text()` | `TextStream()` | `textStream()` | `text_stream` | `textStream()` |
| Reasoning deltas | `getReasoningStream()` | `reasoning_stream()` | | | `reasoningStream()` | `reasoning_stream` | |
| Items | `getItemsStream()` | `item_stream()` | | | `itemStream()` | `item_stream` | |
| Tool events | `getToolStream()` | `tool_stream()` | | | | | |
| Every event | `getFullStream()` | `full_stream()` | `Events()` | `FullStream()` | `fullStream()` | `full_stream` | `fullStream()` |
| Cancel | `cancel(reason?)` | `cancel()` | `Cancel()` | `Cancel()` | `cancel()` | `cancel` | `cancel()` |

Consumers replay from the start, so several can read the same run. How they behave differs:

| Language | Stream result type | Behaviour |
| --- | --- | --- |
| TypeScript | `AgentStreamResult` | `getFullStream()` ends with a `result` event |
| Python | `AgentStreamResult` | Runs in a background thread; `result()` blocks until done |
| Go | `*StreamResult` | `Text()` and `Events()` are channels; `Cancel()` cancels the run's context |
| C# | `AgentStreamResult` | `IAsyncEnumerable` consumers; `Cancel()` cancels the run's linked token |
| PHP | `AgentStreamResult` | Runs in a Fiber; `$result` holds the `RunResult` once the stream is drained, otherwise `null` |
| Ruby | `StreamResult` | Runs in a worker thread; `result` joins it and `cancel` kills it |
| Java | `StreamResult` | `textStream()` and `fullStream()` return a `List` after the run ends; `cancel()` interrupts the worker thread |
| Rust | None | No streaming in `0.2` |

## Run result

| Field | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) |
| --- | --- | --- | --- |
| Run record | `run` | `run` | `Run` |

| Full conversation | `messages` | `messages` | `Messages` |

The type is `AgentRunResult` in TypeScript and Python and `RunResult` elsewhere. ### Usage summary

`inputTokens`, `outputTokens`, `cachedTokens`, `totalTokens`, `cost` (TypeScript, Java); `input_tokens`, `output_tokens`, `cached_tokens`, `total_tokens`, `cost` (Python, PHP and Ruby keys, Rust); `InputTokens`, `OutputTokens`, `CachedTokens`, `TotalTokens`, `Cost` (Go, C#). The type is `AgentUsageSummary` in TypeScript and Python and `UsageSummary` in Go, C#, Java and Rust. PHP and Ruby use an array or Hash. See [Observability](./observability) for caveats about `cost`.

## Model clients

Implement a model client to send model turns through another transport, or to wrap the gateway client.

| Language | Interface | Methods |
| --- | --- | --- |
| Go | `ModelClient`, `StreamingModelClient` | `Generate(ctx, ModelRequest)`; `Stream(ctx, ModelRequest)` |
| C# | `IModelClient`, `IStreamingModelClient` | `Generate(ModelRequest)`; `Stream(ModelRequest)` |
| PHP | `ModelClient`, `StreamingModelClient` (interfaces) | `generate(ModelRequest)`; `stream(ModelRequest)` |
| Java | `ModelClient`, `StreamingModelClient` | `generate(ModelRequest)`; `stream(ModelRequest)` |
| Rust | `ModelClient` (trait) | `fn generate(&mut self, request: &ModelRequest) -> Result<ModelResponse, AgentError>` |

In Rust, `ModelRequest` holds the agent ID, effective model, instructions, current messages, tool specifications (`ToolSpec`: `id`, `description`, JSON Schema `parameters`) and application context. `ModelResponse` holds `message`, `usage`, `request_id`, `provider`, `model` and `finish_reason`. `Message` has `role`, `content`, `tool_calls`, `tool_call_id`, `name` and `is_error`, with `Message::user(content)` and `Message::assistant(content)` constructors; `ToolCall` has `id`, `name` and JSON `input`.
