Change the model to `mistral/mistral-small-4` and decide per route whether reasoning is on. Mistral Small 4 has two reasoning modes, off and high, and Phaseo maps every effort value onto one of them.

```json
{
  "model": "mistral/mistral-small-4",
  "messages": [
    { "role": "user", "content": "Why is fast inference important?" }
  ],
  "reasoning": { "effort": "high" }
}
```

## Turn reasoning on or off

Reasoning is off unless the request asks for it. On Mistral's own API, Phaseo sends `reasoning_effort` as follows:

| Request | Sent to Mistral |
| --- | --- |
| No reasoning setting | `reasoning_effort: "none"` |
| `reasoning.effort: "none"` or `reasoning.enabled: false` | `reasoning_effort: "none"` |
| Any other `reasoning.effort`, or `reasoning.enabled: true` | `reasoning_effort: "high"` |

A flat `reasoning_effort` in the request takes precedence over `reasoning.effort`. Use `none` for lightweight routes and `high` for deep reasoning; `low` and `medium` behave exactly like `high`.

## Read the answer and the reasoning

Mistral can return mixed content blocks, such as `thinking` followed by `text`. Phaseo splits them into OpenAI-style fields, so downstream code that reads Chat Completions keeps working:

- the answer is in `choices[0].message.content`;
- the reasoning text is in `choices[0].message.reasoning_content` and `reasoning_details`.

## Roll out

1. Change the model ID from Mistral Small 3.2 to `mistral/mistral-small-4`.
2. Test reasoning with only `none` and `high`.
3. Re-run output quality and schema tests on the routes that use `high`.
4. Compare latency and cost for `none` and `high` before full cutover.
