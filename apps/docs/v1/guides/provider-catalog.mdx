title: "Publish a provider catalog"
description: "Publish V1 or V1.1 model feeds with normalized service-tier offers and rate limits."
icon: "list"
---

Approved providers can update offers for existing public canonical models through their catalog feed or provider settings. New canonical models require approval. Each catalog is a complete snapshot: removing an offer retires that feed-managed offer and preserves its pricing history.

## Choose a format

Existing V1 feeds continue to work without changes. An unversioned `{"data": [...]}` document, or one declaring `"schema_version": "1.0"`, uses the existing standard-tier format.

V1.1 declares `"schema_version": "1.1"` and publishes `service_tiers` inside each model. The importer selects the format from the document. URL query parameters such as `?format=phaseo-v1.1` are optional conventions for your endpoint; Phaseo does not infer a version from the URL.

Download the [V1 schema](https://phaseo.app/api/internal/provider-catalog/schema) or [V1.1 schema](https://phaseo.app/api/internal/provider-catalog/schema?version=1.1). Unsupported versions are rejected explicitly.

## Publish normalized tiers

| Tier | Meaning |
| --- | --- |
| `standard` | Normal synchronous execution; required for every model. |
| `fast` | A faster or priority offer. Provider names such as HighSpeed stay in the upstream model ID. |
| `ultrafast` | A separate, higher-speed offer when supported. |
| `flex` | A flexible, lower-priority synchronous offer. |
| `batch` | Asynchronous execution through the Batch API. Requires a batch capability. |

Do not use provider-specific tier names as normalized IDs. `priority` remains a supported caller alias for Fast; catalogs publish `fast`.

Fast, Ultrafast and Flex selection is supported on text generation requests. Batch runs through the separate Batch API and still requires an installed provider Batch integration; publishing a tier does not install that integration. For uploaded provider-native files, use the declared Batch model ID or submit requests inline so Phaseo can translate it.

Use the same canonical model ID for its service tiers. Different models need separate canonical identities. Tiers inherit the model's capabilities, limits and release schedule. Each tier declares its own upstream model ID, availability and effective pricing.

```json
{
  "schema_version": "1.1",
  "data": [{
    "id": "your-provider/example-model",
    "name": "Example model",
    "capabilities": ["chat.completions"],
    "service_tiers": [{
      "service_tier": "standard",
      "provider_model_slug": "example-model",
      "availability": "ready",
      "pricing": [{
        "meter_key": "input_text_tokens",
        "modality": "text",
        "direction": "input",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 100000000,
        "display_label": "Input",
        "display_unit": "1M tokens"
      }, {
        "meter_key": "output_text_tokens",
        "modality": "text",
        "direction": "output",
        "unit": "token",
        "unit_quantity": 1000000,
        "price_nanos": 200000000,
        "display_label": "Output",
        "display_unit": "1M tokens"
      }]
    }]
  }]
}
```

To add Fast, add another tier object with `"service_tier": "fast"`, its effective prices, and a distinct upstream model ID for that offer. If the provider selects its lane using a native parameter instead, use the same upstream model ID and declare `"upstream_service_tier": "priority"` or `"fast"`. Omit that field when the model ID selects the lane. Standard accepts `default` or `standard`; Flex and Ultrafast accept their corresponding values. Phaseo rejects nonstandard synchronous tiers that have no distinct model ID or native selector.

Every tier needs explicit pricing, including output and any cache/media meters you bill. Zero prices are valid; negative prices, unknown meters, duplicate tiers and conditional rates are rejected. `price_nanos` remains the effective price after promotions. Publish a new snapshot when rates change; Phaseo keeps previous effective prices.

## Declare rate limits

Declare the request and token limits your platform applies to Phaseo's account in an optional top-level `rate_limits` array. It works the same way in V1 and V1.1 documents. Leave out `model` for a limit across all of your models, or set it to the upstream `provider_model_slug` of any model or tier in the same document.

```json
{
  "schema_version": "1.1",
  "data": [{ "id": "your-provider/example-model", "...": "..." }],
  "rate_limits": [
    { "requests_per_minute": 600, "tokens_per_minute": 2000000 },
    { "model": "example-model", "requests_per_day": 100000, "tokens_per_day": 500000000 }
  ]
}
```

Each entry accepts `requests_per_minute`, `requests_per_day`, `tokens_per_minute` and `tokens_per_day`. Each value is a positive integer or `null`, and each entry needs at least one value. Phaseo counts each limit globally across all of its traffic to you. A model limit applies in addition to the limit across all models.

Limits never block requests. When a limit is reached, Phaseo ranks that offer lower and sends traffic to other providers first, so a value that is too low only reduces your own share of traffic. For that reason, limits apply without review once your provider application is approved, usually within a minute.

When the array is present, it replaces your declared limits on every import of a changed feed. An empty array removes them. Omit `rate_limits` to keep the limits you manage in provider settings. Phaseo rejects the whole snapshot, and keeps your current catalog and limits, if an entry names a model that is not in the document, repeats a scope, or uses a value that is not a positive integer. The rejection appears as **Needs changes**.

You can also edit limits in **Provider settings → Your models → Rate limits**. Those edits save separately from catalog changes. The catalog editor does not accept `rate_limits`.

## Update and verify

Polling and signed catalog-change webhooks accept both versions through the same onboarding and refresh flow. In provider settings, select a tier before editing its upstream ID, availability or prices. Adding another tier changes the saved catalog to V1.1.

The catalog does not add an inference adapter or credentials. A provider and its advertised capabilities must be integrated before routing is enabled. Batch pricing does not make Batch available on synchronous chat endpoints.

An unavailable canonical model or unknown publisher mapping is shown as **Needs changes** without preventing valid models from importing. Check the provider dashboard for model-specific reasons.

For API-fed catalogs, dashboard edits are persistent overrides. Imports update fields without overrides. Select **Use feed value** to remove an override and resume following that field. The dashboard shows the latest feed value, effective value, editor and time; catalog activity records edits and reversions. Models added manually remain local offers. Removing a model from the feed retires that feed offer even if some of its fields were edited. Existing manual-only catalogs remain supported.
