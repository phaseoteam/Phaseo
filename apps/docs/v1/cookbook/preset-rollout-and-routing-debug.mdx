Move several services onto one preset so they share a prompt, model and provider rules, then use the request logs to explain where each request went. When you're done your callers send `"model": "@release-summary"` and their input, and you can roll a policy change out to one caller at a time.

The request shape is production-ready. [Presets](../guides/presets) explains how a preset's settings merge with the request; this recipe is the rollout.

## Move a caller onto a preset

<Steps>
<Step title="Create the preset">

In **Settings → Presets**, create `release-summary` with a system prompt, the approved models, provider preferences, and default parameters such as `temperature`. Or with a management key:

```bash
curl https://api.phaseo.app/v1/presets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"@release-summary","config":{"model":"anthropic/claude-sonnet-5.5"}}'
```

</Step>
<Step title="Call it by name">

Send the preset as the `model`. There is no separate `preset` field.

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@release-summary",
    "input": "Generate a release summary for the last 24 hours.",
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "@release-summary",
  input: "Generate a release summary for the last 24 hours.",
  meta: true,
});

console.log(response.model, response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "@release-summary",
        "input": "Generate a release summary for the last 24 hours.",
        "meta": True,
    }
)

print(response.get("model"), response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

`model` in the response is the model that answered, and `meta.routing.selected_provider` the provider.

</Step>
<Step title="Check what the preset applied">

Open the request in **Settings → Usage → Logs**. It shows which preset defaults were applied. A model outside the preset's allowed models fails with `validation_error` (keyword `preset_model_not_allowed`) instead of being rerouted.

</Step>
</Steps>

## Explain a routing decision

When a request didn't route the way you expected, expand **Routing observability** on the request in **Settings → Usage → Logs**. It answers three questions:

| Question | Look at |
| --- | --- |
| Why was a provider skipped? | Providers excluded before ranking, with the reason, and providers deranked by their rollout or routing status |
| Why was the request blocked? | Workspace-policy or guardrail blocks on the request |
| Why did this provider win? | Each ranked provider's final score and the factors behind it |

[Explain a routing decision](../guides/routing-and-fallbacks#explain-a-routing-decision) describes every field.

## Roll out a policy change

1. Publish the change as a new preset version, or create a new slug for a very different policy.
2. Move one low-risk caller to it, for example by pointing it at `@release-summary@v4` or a `canary` label.
3. Compare its request details and usage trends with the other callers.
4. Move the remaining callers once routing matches what you expect. To roll back, point the label at the earlier version.

[Version and roll back](../guides/presets#version-and-roll-back) covers versions and labels. For request-level overrides that shouldn't live in a preset, see [Pin or ignore providers](./pin-or-ignore-providers-per-request).
