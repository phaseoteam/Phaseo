Compare what a model costs on each provider with how fast it has served Gateway traffic, then confirm the finalists with your own prompts before moving production traffic.

## Pick the metric that matters for your workload

| Workload | Start with | Why |
| --- | --- | --- |
| Chat, copilots, and voice | Gateway TTFT | Users notice how quickly useful output begins. |
| Long answers and code generation | Output speed | Sustained generation speed dominates longer responses. |
| Tools and structured workflows | Gateway E2E | Routing, retries, and orchestration affect the complete result. |
| Batch or offline work | Cost and effective throughput | A slower start may be acceptable when total throughput and spend matter more. |

No single score proves that a model is the best choice for every workload.

## Compare pricing

Provider price sheets use different units: per token, per million tokens, per image, per second, per minute, or per request. Phaseo keeps each price in its own unit and converts comparable text prices to per 1 million tokens for catalog views and the pricing calculator.

For text models, compare input, cached input, cache write, reasoning, and output meters separately when they are present. Media models keep their own billing unit; compare a per-second video price only with other per-second prices.

<Note>
Catalog pricing estimates a request; it isn't a quote for every payload. Provider tiers, regional offers, batch pricing, cache behavior, and request-specific meters change the final amount.
</Note>

Use the [pricing calculator](https://phaseo.app/tools/pricing-calculator) for a representative payload, then confirm the charged amount in Gateway usage after a test request.

## Understand the performance metrics

Phaseo records operational timing for requests routed through the Gateway.

| Metric | Definition |
| --- | --- |
| **Gateway TTFT** | Gateway request start to the first content-bearing generated output. |
| **Provider TTFT** | Selected provider dispatch to the first content-bearing generated output. |
| **Provider duration** | Selected provider dispatch to the terminal response. |
| **Gateway E2E** | Gateway request start to completion. |
| **Phaseo overhead** | `max(0, Gateway E2E - provider duration)`. |
| **Effective throughput** | All output tokens divided by full provider duration. |
| **Output speed** | Output tokens after the first, leaving out hidden reasoning done before it, divided by provider time after TTFT. Not shown when the whole answer arrives in one network read. |
| **TPOT / ITL** | Request-level average time per token after the first output. |

TTFT, output speed, TPOT, and ITL require a streaming response with a content-bearing first output. Metadata-only stream frames do not count. Non-streaming responses can still contribute provider duration, Gateway E2E, and effective throughput without an invented TTFT.

Phaseo overhead is the time outside the selected provider call: Gateway processing, routing work, retries, and network effects. It varies by request, so read it as a distribution over a defined window, not a fixed number.

## Read operational data correctly

Performance pages summarize live Gateway traffic. They are observations, not controlled benchmark runs, and they describe a route over a window rather than the model itself. Past latency and uptime don't guarantee future results.

Results move because of:

- provider and route selection
- Cloudflare execution location and network path
- provider queueing or regional load
- prompt and output length
- streaming versus non-streaming behavior
- retries, cancellations, and tool calls
- model or provider updates during the selected window

Public charts can expose percentiles such as P50, P90, P95, and P99. For latency, lower is better. For throughput, higher is better, so a lower throughput percentile describes the slow tail.

Always record the selected time window, route, region, sample filters, and percentile beside a result. Do not compare two screenshots with different windows as though they were the same study.

## Run a reproducible workload study

Use public telemetry to narrow the candidates, then validate the finalists with your own prompt mix.

1. Choose two or three routable models from the default `GET /v1/models` response.
2. Create a sanitized prompt set that represents short, typical, and long requests.
3. Fix the endpoint, region, streaming mode, provider constraints, and concurrency.
4. Run repeated requests for each prompt instead of relying on one sample.
5. Capture request ID, selected provider, success or error, output tokens, Gateway TTFT, provider duration, Gateway E2E, Phaseo overhead, and cost.
6. Compare distributions and failure modes, then keep the raw results with the test configuration.

Example result schema:

```json
{
  "study_id": "support-summary-v1",
  "model": "<verified-model-id>",
  "endpoint": "responses",
  "stream": true,
  "region": "<execution-region>",
  "request_id": "req_...",
  "gateway_ttft_ms": 0,
  "provider_duration_ms": 0,
  "gateway_e2e_ms": 0,
  "phaseo_overhead_ms": 0,
  "output_tokens": 0,
  "cost_usd": 0,
  "status": "completed"
}
```

The zero values are placeholders. Publish measured values only with the workload definition, sample count, time window, and permission to disclose the data.

A catalog entry doesn't mean a model is routable, so start from the default `GET /v1/models` response. A benchmark score doesn't establish quality on your prompt mix; see [Benchmark methodology](../research/benchmark-methodology) for how scores are sourced, separately from Gateway telemetry.
