Faites passer plusieurs services sur un même préréglage pour qu’ils partagent un prompt, un modèle et des règles de fournisseur, puis utilisez les journaux de requêtes pour expliquer où chaque requête est allée. À la fin, vos appelants envoient `"model": "@release-summary"` et leur entrée, et vous pouvez déployer un changement de règle un appelant à la fois.

La forme de requête est prête pour la production. [Préréglages](../guides/presets) explique comment les réglages d’un préréglage se fusionnent avec la requête ; cette recette porte sur le déploiement.

## Faire passer un appelant sur un préréglage

<Steps>
<Step title="Créer le préréglage">

Dans **Paramètres → Préréglages**, créez `release-summary` avec un prompt système, les modèles approuvés, les préférences de fournisseur et des paramètres par défaut comme `temperature`. Ou avec une clé de gestion :

```bash
curl https://api.phaseo.app/v1/presets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"@release-summary","config":{"model":"anthropic/claude-sonnet-5.5"}}'
```

</Step>
<Step title="L’appeler par son nom">

Envoyez le préréglage comme `model`. Il n’existe pas de champ `preset` séparé.

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/responses \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@release-summary",
    "input": "Generate a release summary for the last 24 hours.",
    "meta": true
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const response = await client.generateResponse({
  model: "@release-summary",
  input: "Generate a release summary for the last 24 hours.",
  meta: true,
});

console.log(response.model, response.meta?.routing);
```

```python Python
import os

from phaseo import Phaseo

client = Phaseo(api_key=os.environ["PHASEO_API_KEY"])

response = client.generate_response(
    {
        "model": "@release-summary",
        "input": "Generate a release summary for the last 24 hours.",
        "meta": True,
    }
)

print(response.get("model"), response["meta"]["routing"]["selected_provider"])
```
</CodeGroup>

Dans la réponse, `model` est le modèle qui a répondu, et `meta.routing.selected_provider` le fournisseur.

</Step>
<Step title="Vérifier ce que le préréglage a appliqué">

Ouvrez la requête dans **Paramètres → Utilisation → Journaux**. Vous y voyez les valeurs par défaut du préréglage qui ont été appliquées. Un modèle hors des modèles autorisés du préréglage échoue avec `validation_error` (mot-clé `preset_model_not_allowed`) au lieu d’être rerouté.

</Step>
</Steps>

## Expliquer une décision de routage

Quand une requête n’a pas été routée comme prévu, dépliez **Observabilité du routage** sur la requête dans **Paramètres → Utilisation → Journaux**. Cette section répond à trois questions :

| Question | Où regarder |
| --- | --- |
| Pourquoi un fournisseur a-t-il été écarté ? | Les fournisseurs exclus avant le classement, avec la raison, et ceux rétrogradés en raison de leur état de déploiement ou de routage |
| Pourquoi la requête a-t-elle été bloquée ? | Les blocages par une règle de l’espace de travail ou par un garde-fou sur la requête |
| Pourquoi ce fournisseur l’a-t-il emporté ? | Le score final de chaque fournisseur classé et les facteurs qui l’expliquent |

[Expliquer une décision de routage](../guides/routing-and-fallbacks#explain-a-routing-decision) décrit chaque champ.

## Déployer un changement de règle

1. Publiez le changement comme nouvelle version du préréglage, ou créez un nouveau slug pour une règle très différente.
2. Faites passer un appelant à faible risque dessus, par exemple en le faisant pointer vers `@release-summary@v4` ou vers un libellé `canary`.
3. Comparez le détail de ses requêtes et ses tendances d’utilisation avec celles des autres appelants.
4. Faites passer les autres appelants une fois que le routage correspond à vos attentes. Pour revenir en arrière, faites pointer le libellé vers la version précédente.

[Versionner et revenir en arrière](../guides/presets#version-and-roll-back) présente les versions et les libellés. Pour les ajustements au niveau de la requête qui n’ont pas leur place dans un préréglage, voir [Épingler ou ignorer des fournisseurs](./pin-or-ignore-providers-per-request).
