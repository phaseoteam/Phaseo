Ajoutez une destination dans **Paramètres → Notifications** pour envoyer les alertes de votre espace de travail par e-mail, dans Slack, Discord, Microsoft Teams ou vers votre propre webhook HTTPS. Les destinations appartiennent à l’espace de travail, et vous pouvez envoyer un test avant de vous y fier.

| Destination | Ce que vous fournissez | Mentions |
| --- | --- | --- |
| E-mail | Des adresses ou des listes de diffusion | Aucune |
| Slack | Une URL de webhook entrant | ID utilisateur et ID de groupes d’utilisateurs |
| Discord | Un canal et un token de bot, ou une URL de webhook | ID utilisateur et ID de rôle |
| Microsoft Teams | Une URL de workflow | Adresses e-mail Microsoft 365 ou ID d’objet Entra |
| Webhook personnalisé | Une URL HTTPS | Aucune ; les envois sont [signés](#verify-webhook-signatures) |

Les identifiants et les URL de webhook sont chiffrés avant leur enregistrement. Limitez les identifiants de canal à l’envoi de notifications et renouvelez-les en cas d’exposition.

## Ajouter une destination

<Steps>
<Step title="Créez-la">
Ouvrez **Paramètres → Notifications**, sélectionnez **Ajouter une destination**, saisissez un nom et choisissez un ou plusieurs canaux. Ajoutez les informations de la destination et les éventuelles mentions.
</Step>
<Step title="Testez chaque canal">
Sélectionnez **Envoyer le test** pour chaque canal, puis créez les destinations une fois que tous les tests ont réussi.
</Step>
<Step title="Enregistrez le secret de signature">
Un webhook personnalisé reçoit un secret de signature à sa création. Copiez-le depuis la boîte de dialogue qui s’ouvre ; il n’est affiché qu’une seule fois.
</Step>
</Steps>

Depuis la CLI, lancez `phaseo notifications destinations create`, vérifiez la destination avec `phaseo notifications destinations test <id>`, puis choisissez les alertes qu’elle reçoit avec `phaseo notifications routes set <event-kind> --destination-ids <id>`.

Utilisez les mentions avec parcimonie : envoyez les alertes fréquentes à un canal surveillé plutôt que d’alerter un groupe étendu.

<span id="enable-product-alerts"></span>
## Activer les alertes produit

La page des notifications liste les types d’alertes disponibles pour votre espace de travail. Les destinations reçoivent une alerte en plus des destinataires intégrés affichés dans le tableau de bord.

Les **Alertes de dépréciation de modèle** préviennent avant le retrait d’un modèle utilisé par l’espace de travail.

Les **Avis de modèle remplaçant** sont envoyés lorsque le [routage des modèles retirés](./model-retirement.mdx#route-requests-to-a-replacement-automatically) est activé et qu’un modèle remplaçant répond aux requêtes de l’espace de travail pour un modèle que plus aucun fournisseur ne sert. Un avis est envoyé par modèle et par remplaçant, la première fois qu’un remplaçant répond avec succès. Le propriétaire de l’espace de travail reçoit toujours un e-mail ; choisissez des destinations pour envoyer aussi l’avis à votre équipe.

<span id="spend-reports"></span>
## Rapports de dépenses

Les propriétaires de l’espace de travail reçoivent chaque lundi à 09:00, dans le fuseau horaire de facturation de l’espace de travail, un e-mail de rapport de dépenses pour la semaine précédente, du lundi au dimanche. Modifiez-le dans **Alertes de dépenses → Réglages des dépenses de l'espace de travail** sur la page des notifications : quotidien (à 09:00, pour la veille), hebdomadaire, mensuel (le 1er, pour le mois précédent) ou désactivé, et si les administrateurs le reçoivent aussi. Les périodes sans dépense sont ignorées.

Chaque rapport présente les dépenses et l’évolution par rapport à la période précédente, les principales clés, modèles, membres et départements, la prévision du mois, l’autonomie du solde, ainsi que les alertes et blocages de dépenses de la période. Chaque destinataire peut se désabonner depuis le lien de l’e-mail ; cela n’arrête que sa copie du rapport de cet espace de travail. Les destinations associées à **Rapports de dépenses** reçoivent un résumé par rapport.

Les mêmes réglages sont `spend.report_cadence` et `spend.report_include_admins` dans l’[API des réglages de notification](../api-reference/endpoint/notifications-settings-update.mdx).

Pour être alerté sur les dépenses, les budgets, les prévisions, les pics et un solde bas, et pour bloquer les requêtes une fois les dépenses au-delà d’une limite, consultez [Alertes de dépenses](./spend-alerts.mdx).

<Note>Les e-mails de rapport de dépenses sont en cours de déploiement. Tant qu’ils ne sont pas activés, votre choix est enregistré mais aucun rapport n’est envoyé.</Note>

## Garder les destinations opérationnelles

Utilisez **Envoyer un test** à côté d’une destination existante après avoir renouvelé ses identifiants ou modifié son canal. Supprimez les destinations que personne ne surveille, pour que les alertes ne semblent pas livrées alors qu’elles arrivent dans un canal abandonné.

Un récepteur de webhook personnalisé doit vérifier chaque requête avant de la traiter, renvoyer rapidement une réponse de réussite et confier les tâches plus longues à un traitement en arrière-plan.

<span id="verify-webhook-signatures"></span>
## Vérifier les signatures de webhook

Phaseo signe chaque envoi de webhook personnalisé, y compris les tests envoyés depuis une destination enregistrée, avec le même schéma que les [webhooks vidéo et batch](./async-video-and-batch.mdx#receive-updates). Chaque requête contient ces en-têtes :

```http
POST /your/endpoint HTTP/1.1
content-type: application/json
user-agent: Phaseo-Notifications/1.0
x-phaseo-event-id: 6f1c0f5e-3f0b-4a39-9a51-2f4f2c1d9e10
x-phaseo-event-type: rate_limit_throttled
x-phaseo-timestamp: 1792569600
x-phaseo-signature: 5d2a…e41f
```

`x-phaseo-signature` est le HMAC-SHA256 hexadécimal de la valeur de `x-phaseo-timestamp`, d’un point littéral (`.`) et du **corps de requête non modifié**, calculé avec le secret de signature de la destination (`whsec_…`). `x-phaseo-timestamp` est exprimé en secondes Unix.

Pour vérifier un envoi :

1. Lisez le corps brut de la requête avant de l’analyser comme JSON.
2. Recalculez la signature et comparez-la en temps constant.
3. Rejetez les horodatages qui s’écartent de plus de cinq minutes de votre horloge.
4. Dédupliquez sur `x-phaseo-event-id`. Les envois en échec sont retentés, et chaque tentative est signée de nouveau avec un nouvel horodatage.

<CodeGroup>
```js Node.js
import crypto from "node:crypto";

// rawBody est le corps de la requête tel que reçu, sous forme de chaîne.
export function verifyPhaseoSignature(rawBody, headers, secret, toleranceSeconds = 300) {
  const timestamp = headers["x-phaseo-timestamp"];
  const signature = headers["x-phaseo-signature"];
  if (!timestamp || !signature) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > toleranceSeconds) return false;
  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");
  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

```python Python
import hashlib
import hmac
import time

# raw_body est le corps de la requête tel que reçu, en octets.
def verify_phaseo_signature(raw_body: bytes, headers, secret: str, tolerance_seconds: int = 300) -> bool:
    timestamp = headers.get("x-phaseo-timestamp", "")
    signature = headers.get("x-phaseo-signature", "")
    if not timestamp.isdigit() or not signature:
        return False
    if abs(time.time() - int(timestamp)) > tolerance_seconds:
        return False
    expected = hmac.new(secret.encode(), timestamp.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```
</CodeGroup>

### Générer ou renouveler un secret

Le secret n’est affiché qu’une fois, à la création de la destination. Pour le remplacer, sélectionnez **Renouveler le secret** à côté de la destination dans **Paramètres → Notifications**, ou appelez [`POST /v1/notifications/destinations/{id}/rotate-secret`](/fr/v1/api-reference/endpoint/notifications-destination-rotate-secret). L’envoi suivant est signé avec le nouveau secret et l’ancien cesse de fonctionner : mettez à jour votre récepteur immédiatement.

Les webhooks personnalisés créés avant l’arrivée de la signature n’ont pas de secret et sont toujours envoyés sans signature. Ils apparaissent comme **Non signé** dans les paramètres. Sélectionnez **Générer un secret**, ajoutez le secret à votre récepteur, puis envoyez un test pour vérifier la validation. Les tests envoyés depuis le panneau **Ajouter une destination**, avant l’enregistrement de la destination, ne sont pas signés car aucun secret n’existe encore.

Les destinations e-mail, Slack, Discord et Microsoft Teams ne sont pas signées : ces services authentifient eux-mêmes l’URL du webhook ou le token du bot.
