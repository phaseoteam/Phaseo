Enregistrez vos messages avec des `{{variables}}` dans un [préréglage](/fr/v1/guides/presets) : votre application n’envoie plus que la référence du préréglage et les valeurs des variables. Phaseo vérifie les valeurs, remplit les messages et envoie la requête au modèle du préréglage. Modifier le prompt dans le tableau de bord ne nécessite aucun déploiement, et tous les appelants obtiennent la même formulation, les mêmes outils et le même format de réponse.

Les modèles de prompt fonctionnent sur `POST /v1/chat/completions`, `POST /v1/responses` et `POST /v1/messages`.

## Créer et appeler un modèle de prompt

<Steps>
<Step title="Écrire le modèle">

Ouvrez **Paramètres -> Préréglages**, créez ou ouvrez un préréglage, choisissez son modèle et ouvrez l’onglet **Modèle de prompt**. Ajoutez des messages et écrivez les variables entre doubles accolades :

```text
System: You triage support tickets for {{company}}. Reply in a {{tone}} tone.
User:   Ticket: {{ticket}}
```

L’éditeur liste chaque variable qu’il trouve. Définissez son type, si elle est obligatoire, une valeur par défaut et une description. Remplissez le panneau **Essayer** pour voir les messages exacts que le Gateway enverra, puis enregistrez.

Une fois le préréglage enregistré, **Exécuter le préréglage enregistré** envoie une vraie requête avec vos valeurs de test et affiche la réponse, le modèle et le nombre de tokens. Cela utilise les crédits de votre espace de travail. Le même panneau fournit le code cURL, TypeScript et Python de la requête, rempli avec vos valeurs de test.

</Step>

<Step title="Envoyer les variables">

Référencez le préréglage dans `prompt.id` et placez les valeurs dans `prompt.variables`. Omettez `model`, ou définissez-le sur la même référence.

<CodeGroup>
```bash cURL
curl https://api.phaseo.app/v1/chat/completions \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": {
      "id": "@support-triage",
      "variables": {
        "company": "Acme",
        "tone": "friendly",
        "ticket": "I was charged twice this month."
      }
    }
  }'
```

```typescript TypeScript
import Phaseo from "@phaseo/sdk";

const client = new Phaseo({ apiKey: process.env.PHASEO_API_KEY! });

const completion = await client.generateText({
	model: "@support-triage",
	messages: [],
	prompt: {
		id: "@support-triage",
		variables: {
			company: "Acme",
			tone: "friendly",
			ticket: "I was charged twice this month.",
		},
	},
});
```

```python Python
from phaseo import Phaseo

client = Phaseo(api_key="YOUR_API_KEY")

completion = client.generate_text({
    "prompt": {
        "id": "@support-triage",
        "variables": {
            "company": "Acme",
            "tone": "friendly",
            "ticket": "I was charged twice this month.",
        },
    },
})
```
</CodeGroup>

</Step>

<Step title="Vérifier la requête">

Ouvrez **Gateway -> Journaux** pour voir la requête, le modèle qui l’a servie et son coût. Les métadonnées de la requête enregistrent le préréglage, les noms des variables et le nombre de messages générés, mais pas les valeurs des variables.

</Step>
</Steps>

## Utiliser les modèles de prompt depuis chaque endpoint

Le même objet `prompt` fonctionne sur les trois endpoints. Les messages system et developer du modèle deviennent les instructions système de l’endpoint, et ses autres messages sont placés avant toute conversation envoyée par votre requête.

| Endpoint | Les messages système du modèle vont dans | La conversation du modèle est placée avant |
| --- | --- | --- |
| `/v1/chat/completions` | `messages` (conservés comme messages système) | vos `messages` |
| `/v1/responses` | `instructions` | votre `input` |
| `/v1/messages` | `system` | vos `messages` |

Vous pouvez envoyer une conversation avec le modèle. Par exemple, une requête de chat peut ajouter les tours de suivi de l’utilisateur après les messages du modèle :

```json
{
  "prompt": { "id": "@support-triage", "variables": { "company": "Acme", "ticket": "Refund request" } },
  "messages": [
    { "role": "assistant", "content": "Can you share the order number?" },
    { "role": "user", "content": "It is 10482." }
  ]
}
```

## Syntaxe des modèles

Les modèles de prompt utilisent un petit sous-ensemble de Mustache, sans logique. Rien dans un modèle n’est jamais exécuté comme du code.

| Syntaxe | Effet |
| --- | --- |
| `{{name}}` | Insère une valeur. Le texte est inséré tel quel, les nombres et booléens sous forme de texte, et les listes et objets en JSON. Une valeur facultative absente n’insère rien. |
| `{{customer.name}}` | Insère un champ d’une variable objet. |
| `{{#name}}...{{/name}}` | Affiche le bloc une fois lorsque la valeur est définie et différente de `false`, ou une fois pour chaque élément d’une liste. À l’intérieur, `{{.}}` est l’élément courant et ses champs peuvent être utilisés par leur nom. |
| `{{^name}}...{{/name}}` | Affiche le bloc lorsque la valeur est absente, `false`, un texte vide ou une liste vide. |
| `{{! note }}` | Un commentaire. Il est supprimé. |
| `\{{` | Un `{{` littéral. |

Les valeurs sont insérées en texte brut, sans échappement HTML. Une valeur peut modifier le texte d’un message, mais jamais la structure de la requête.

Si un message ne produit que des espaces, il est supprimé. Utilisez cela pour rendre un message entier facultatif :

```text
{{#notes}}Notes from the account manager: {{notes}}{{/notes}}
```

Pour répéter du texte pour chaque élément d’une liste, ouvrez une section sur la liste et utilisez `{{.}}` pour l’élément courant :

```text
Examples of good replies:
{{#examples}}- {{.}}
{{/examples}}
```

Les partiels (`{{> name}}`), les balises non échappées (`{{{name}}}` et `{{& name}}`), les changements de délimiteurs et les lambdas ne sont pas pris en charge, et l’éditeur comme l’API refusent les modèles qui les utilisent.

## Variables

Chaque variable a un type. Vous n’avez besoin de déclarer une variable que pour modifier ses valeurs par défaut ; les variables utilisées dans les messages mais non déclarées sont du texte obligatoire.

| Type | Accepte |
| --- | --- |
| `string` | Du texte. Définissez `max_length` pour limiter sa longueur. |
| `number` | Un nombre. |
| `boolean` | `true` ou `false`. |
| `enum` | L’une des chaînes listées dans `enum`. |
| `array` | Une liste. |
| `object` | Un objet JSON. |
| `any` | N’importe quelle valeur JSON. |
| `image` | Une image pour un message utilisateur. Consultez [Variables d’image](#image-variables). |

Chaque variable peut aussi avoir :

- `required` : la requête échoue lorsque la valeur est absente. Une variable obligatoire ne peut pas avoir de valeur par défaut.
- `default` : utilisée lorsque la requête omet la valeur. Elle doit correspondre au type.
- `description` : affichée dans l’éditeur et dans les messages d’erreur, jusqu’à 500 caractères.

Un nom utilisé uniquement pour ouvrir des sections, comme `notes` et `examples` ci-dessus, est facultatif et accepte n’importe quelle valeur.

Les requêtes sont vérifiées strictement. Une valeur obligatoire absente, une valeur du mauvais type ou un nom que le modèle ne contient pas renvoie un `400` qui liste tous les problèmes à la fois : une faute de frappe ne peut donc pas supprimer discrètement une partie d’un prompt.

<span id="image-variables"></span>
## Variables d’image

Une variable d’image remplit une partie de contenu entière d’un message utilisateur : c’est donc le modèle qui décide où va l’image. Dans l’éditeur, choisissez **Ajouter une image** dans un message utilisateur. Dans l’API, utilisez une partie `variable` :

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "Before:" },
    { "type": "variable", "name": "before" },
    { "type": "text", "text": "After:" },
    { "type": "variable", "name": "after" },
    { "type": "text", "text": "What changed?" }
  ]
}
```

La requête peut envoyer chaque image sous forme d’URL `https`, d’URL `data:image/...` ou de partie image au format Chat Completions, Responses ou Messages. Phaseo la convertit au format de l’endpoint appelé. Le modèle sélectionné doit accepter les images en entrée.

## Outils et format de réponse

Un modèle peut inclure `tools`, `tool_choice` et `response_format`, écrits au format Chat Completions (consultez [Appel d’outils](./tool-calling.mdx) et [Sorties structurées](./structured-outputs.mdx)). Phaseo les convertit pour les endpoints Responses et Messages.

La requête l’emporte toujours lorsque les deux définissent la même chose :

- Les outils sont fusionnés par nom de fonction. Si la requête définit un outil portant le même nom, la définition de la requête est utilisée.
- Le `tool_choice` et le format de réponse de la requête (`response_format`, `text.format` ou `output_config.format`) remplacent ceux du modèle.

Les paramètres de requête tels que `temperature` et `max_tokens` fonctionnent normalement. Les valeurs par défaut du préréglage ne remplissent que les champs que la requête omet.

## Créer un modèle de prompt avec l’API

Les modèles de prompt sont stockés dans le `config.prompt` du préréglage. Créez ou mettez à jour le préréglage avec une [clé API de gestion](/fr/v1/developers/management-api-keys) dotée de `presets:write` :

```bash
curl https://api.phaseo.app/v1/presets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "@support-triage",
    "visibility": "team",
    "config": {
      "models": ["anthropic/claude-haiku-5.5"],
      "prompt": {
        "messages": [
          { "role": "system", "content": "You triage support tickets for {{company}}. Reply in a {{tone}} tone." },
          { "role": "user", "content": "Ticket: {{ticket}}" }
        ],
        "variables": {
          "company": { "type": "string", "required": true },
          "tone": { "type": "enum", "enum": ["formal", "friendly"], "default": "formal" },
          "ticket": { "type": "string", "required": true, "max_length": 4000 }
        }
      }
    }
  }'
```

Phaseo vérifie le modèle lors de l’enregistrement. Un modèle comportant une erreur de syntaxe, un type inconnu ou une valeur par défaut qui ne correspond pas à son type est refusé avec `400 invalid_prompt_template` et l’emplacement de chaque problème, ici comme dans l’éditeur.

Les modifications enregistrées atteignent les requêtes en deux minutes environ.

<span id="versions-and-labels"></span>
## Versions et libellés

Chaque fois que vous publiez un préréglage, Phaseo enregistre une version immuable (consultez [Préréglages](/fr/v1/guides/presets#version-and-roll-back)). Les requêtes exécutent la dernière version publiée, sauf si elles en épinglent une. Une requête épinglée utilise à la fois les modèles, les paramètres et le modèle de prompt de cette version.

Épinglez une version avec `prompt.version` :

```json
{
  "prompt": {
    "id": "@support-triage",
    "version": "production",
    "variables": { "company": "Acme", "ticket": "My invoice is wrong" }
  }
}
```

`prompt.version` accepte un libellé de version tel que `v3`, `1.2.0` ou `2026.10.27`, ou un libellé tel que `production`. Vous pouvez aussi placer la version dans l’identifiant du modèle, avec ou sans modèle de prompt :

```json
{
  "model": "@support-triage@production",
  "messages": [{ "role": "user", "content": "My invoice is wrong" }]
}
```

Les préréglages publics utilisent `@publisher/support-triage@production`. Si `model` et `prompt.version` épinglent tous deux une version, ils doivent nommer la même.

### Libellés

Un libellé est un nom, tel que `production` ou `staging`, qui pointe vers une version publiée. Les libellés comptent de 1 à 32 lettres minuscules, chiffres, traits d’union ou tirets bas, commencent par une lettre et ne peuvent pas ressembler à un libellé de version (`v1`, `v2`).

Dans **Paramètres -> Préréglages**, ouvrez le préréglage. **Publier**, à côté de **Enregistrer le brouillon**, enregistre vos modifications et les publie comme version suivante. Ouvrez **Versions et libellés** pour gérer les libellés : chaque libellé a un sélecteur de version ; choisir une autre version déplace le libellé, et choisir une version antérieure revient en arrière. Utilisez **Ajouter un libellé** pour en créer un. Ouvrez une version pour voir ses modèles et les messages de son modèle de prompt, ainsi que leurs différences avec la version par défaut (celle qu’exécutent les requêtes qui n’épinglent pas de version), et utilisez **Exécuter** pour essayer cette version avec les valeurs de test de **Modèle de prompt**. Le créateur du préréglage peut modifier ses libellés, de même que les propriétaires et administrateurs de l’espace de travail lorsque le préréglage est partagé. Avec une [clé API de gestion](/fr/v1/developers/management-api-keys) dotée de `presets:write` :

```bash
curl -X PUT https://api.phaseo.app/v1/presets/support-triage/labels/production \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "version": "v3" }'
```

Le corps accepte `version` (un libellé de version, ou un autre libellé dont on copie la cible) ou `version_id`. `GET /v1/presets/{id}/labels` liste les libellés, et `DELETE /v1/presets/{id}/labels/{label}` en supprime un. Les requêtes qui épinglent un libellé supprimé échouent jusqu’à ce qu’il soit ajouté de nouveau.

### Revenir en arrière

Pour revenir en arrière, déplacez le libellé vers la version antérieure : choisissez cette version dans le sélecteur de version du libellé dans **Versions et libellés**, ou envoyez la même requête avec `"version": "v2"`. Les requêtes qui épinglent `production` exécutent de nouveau la v2 sans aucune modification de votre application.

Les déplacements de libellés atteignent les requêtes en deux minutes environ, comme les autres modifications de préréglage.

## Erreurs

Les problèmes de modèle dans une requête renvoient `400` avec le code `validation_error`. `reason` contient le code du premier problème et `details` les liste tous avec leur chemin :

```json
{
  "error": {
    "code": "validation_error",
    "message": "Template \"@support-triage\" needs variable \"ticket\" (string)",
    "type": "invalid_request_error"
  },
  "code": "validation_error",
  "reason": "template_variable_required",
  "description": "Template \"@support-triage\" needs variable \"ticket\" (string)",
  "details": [
    {
      "message": "Template \"@support-triage\" needs variable \"ticket\" (string)",
      "path": ["prompt", "variables", "ticket"],
      "keyword": "template_variable_required"
    }
  ]
}
```

| Motif | Cause |
| --- | --- |
| `template_variable_required` | Une variable obligatoire est absente. |
| `template_variable_type` | Une valeur ne correspond pas à son type, à sa liste enum ou à `max_length`. |
| `template_variable_unknown` | La requête a envoyé une variable que le modèle ne contient pas, ou le préréglage n’a pas de modèle de prompt. |
| `template_variables_invalid` | `prompt.variables` n’est pas un objet. |
| `template_limit_exceeded` | Les variables ou le texte généré dépassent les limites ci-dessous. |
| `template_rendered_empty` | Le modèle n’a produit aucun message user ou assistant et la requête n’en a envoyé aucun. |
| `template_endpoint_unsupported` | Le préréglage a un modèle de prompt et a été appelé depuis un endpoint autre que les trois ci-dessus. |
| `prompt_model_conflict` | `model` nomme un préréglage ou un modèle différent de `prompt.id`, ou épingle une version différente de `prompt.version`. |
| `prompt_version_invalid` | `prompt.version` est vide, dépasse 64 caractères ou contient des caractères autres que des lettres, des chiffres, `.`, `_`, `+` et `-`. |
| `prompt_model_fallbacks_unsupported` | La requête a défini des modèles de repli `models`. Listez plutôt les modèles de repli dans le préréglage. |

Un `prompt.id` qui ne correspond à aucun préréglage de votre espace de travail renvoie `404`.

Une version ou un libellé épinglé qui n’existe pas, ou que la clé ne peut pas utiliser, renvoie `404` avec le motif `preset_version_not_found`.

## Limites

| Limite | Valeur |
| --- | --- |
| Messages par modèle | 64 |
| Variables par modèle | 64 |
| Longueur d’un nom de variable | 64 caractères |
| Texte du modèle sur l’ensemble des messages | 48 000 caractères |
| Profondeur d’imbrication des sections | 8 |
| Répétitions de sections par requête | 1 000 |
| Texte généré par requête | 1 000 000 caractères |
| Taille de `prompt.variables` | 256 Ko |
| Valeurs par `enum` | 100 |

## Garde-fous et journaux

Les [garde-fous](/fr/v1/cookbook/guardrails-for-api-keys) vérifient les valeurs des variables comme du contenu utilisateur, même lorsque le modèle les place dans un message système. Un garde-fou qui masque une valeur la masque partout où le modèle l’a insérée, et un garde-fou qui bloque une valeur bloque la requête.

Les métadonnées de la requête enregistrent le préréglage, les noms des variables et le nombre de messages générés. Les valeurs elles-mêmes ne sont conservées que là où le corps de la requête est conservé, selon les paramètres de journalisation habituels de votre espace de travail.
