Basez votre logique sur `error.code` et le statut HTTP, pas sur le texte du message. Toutes les erreurs Phaseo ont le même corps JSON sur tous les endpoints, et leur objet `error` (`code`, `message`, `type`, `param`) a la forme que lisent les SDK compatibles OpenAI : leurs exceptions contiennent donc le message de Phaseo.

```json
{
  "error": {
    "code": "upstream_error",
    "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
    "type": "server_error",
    "param": null,
    "metadata": {
      "reason": "all_candidates_failed",
      "attempt_count": 1,
      "failed_providers": ["google-ai-studio"],
      "failed_statuses": [403],
      "upstream_error": {
        "code": "PERMISSION_DENIED",
        "message": "The caller does not have permission.",
        "description": null,
        "param": null
      }
    }
  },
  "code": "upstream_error",
  "message": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "generation_id": "G-abc123",
  "status_code": 502,
  "error_type": "system",
  "error_origin": "upstream",
  "reason": "all_candidates_failed",
  "description": "Provider \"google-ai-studio\" failed with HTTP 403 for endpoint \"responses\" on model \"google/gemini-2.5-pro\".",
  "attempt_count": 1,
  "failed_providers": ["google-ai-studio"],
  "failed_statuses": [403],
  "provider_failure_diagnostics": {
    "category": "provider_access_missing",
    "hint": "The provider account appears not to have access to this model or feature yet. Verify account entitlements and provider-side access.",
    "provider": "google-ai-studio"
  },
  "upstream_error": {
    "code": "PERMISSION_DENIED",
    "message": "The caller does not have permission.",
    "description": null,
    "param": null
  },
  "failure_sample": [
    {
      "provider": "google-ai-studio",
      "type": "upstream_non_2xx",
      "status": 403,
      "upstream_error_code": "PERMISSION_DENIED",
      "upstream_error_message": "The caller does not have permission.",
      "upstream_error_description": null,
      "upstream_error_param": null,
      "upstream_payload_preview": "{\"error\":{\"status\":\"PERMISSION_DENIED\"}}",
      "retryable": false
    }
  ]
}
```

## Champs présents dans chaque erreur

| Champ | Contenu |
| --- | --- |
| `error.code` | Code lisible par une machine, comme `validation_error`. Consultez [Codes d’erreur](#error-codes). |
| `error.message` | Explication en langage courant. |
| `error.type` | Classe d’erreur, définie à partir du statut HTTP. Consultez [Types d’erreur](#error-types). |
| `error.param` | Le champ de la requête à l’origine de l’erreur, lorsque Phaseo le connaît ; sinon `null`. |
| `error.metadata` | Facultatif. Détails structurés comme `reason`, `failed_providers`, `failed_statuses` ou `retry_after_seconds`. Les mêmes valeurs figurent aussi au niveau supérieur. |
| `code` | Identique à `error.code`. Les anciennes réponses renvoyaient cette chaîne dans `error` ; lisez `code` si votre client y attend une chaîne. |
| `message`, `description` | Même texte que `error.message`. |
| `generation_id` | ID de requête à journaliser et à communiquer au support. |
| `status_code` | Le statut HTTP. |
| `error_type` | `user` ou `system`. |
| `error_origin` | L’origine du problème : l’appelant (`user`), Phaseo (`gateway`) ou un fournisseur (`upstream`). |
| `details` | Facultatif. Détails de validation lorsque le corps de la requête n’est pas valide. |

Certaines erreurs ajoutent du contexte :

| Champ | Quand il apparaît |
| --- | --- |
| `reason` | Un motif précis, comme `all_candidates_failed` ou `no_provider_pricing`. |
| `provider_failure_diagnostics` | Un fournisseur a été atteint et a échoué. Consultez [En cas d’échec d’un fournisseur](#when-a-provider-fails). |
| `upstream_error`, `failure_sample` | Un résumé, au mieux, du premier échec d’un fournisseur. |
| `failed_providers`, `failed_statuses`, `attempt_count` | Les fournisseurs essayés et ce qu’ils ont renvoyé. |
| `provider_candidate_diagnostics`, `provider_enablement`, `routing_diagnostics` | Aucun fournisseur ne peut servir le modèle sur cet endpoint. Consultez [Lorsqu’un modèle ou un endpoint n’est pas disponible](#when-a-model-or-endpoint-is-not-available). |

<span id="error-types"></span>
## Types d’erreur

`error.type` suit les [types d’erreur documentés](https://platform.openai.com/docs/guides/error-codes) d’OpenAI et est défini à partir du statut HTTP :

| Statut | `error.type` |
| --- | --- |
| `401` | `authentication_error` |
| `402` | `insufficient_quota` |
| `403` | `permission_error` |
| `404` | `not_found_error` |
| `429` | `rate_limit_error` |
| `408`, `500`, `502` et les autres 5xx | `server_error` |
| `503` | `service_unavailable` |
| `529` | `overloaded` |
| `400`, `409`, `410`, `413`, `422` et les autres 4xx | `invalid_request_error` |

Les erreurs sur `/v1/messages` utilisent le même corps : les SDK Anthropic y trouvent donc aussi `error.type` et `error.message`.

<span id="error-codes"></span>
## Codes d’erreur

| `error.code` | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `validation_error` | `400` | Un paramètre ou le corps de la requête n’est pas valide. `error.param` indique le premier champ non valide. | Corrigez la requête. |
| `invalid_json` | `400` | Le corps n’est pas un JSON valide. | Corrigez la requête. |
| `model_required` | `400` | La requête n’a pas de `model`. | Ajoutez `model`. |
| `unsupported_model_or_endpoint` | `400` | Aucun fournisseur ne peut servir ce modèle sur cet endpoint. | Consultez la [section ci-dessous](#when-a-model-or-endpoint-is-not-available). |
| `unsupported_modalities` | `400` | Aucune route n’accepte les types d’entrée ou de sortie de la requête. | Changez de modèle ou d’entrées. |
| `byok_credentials_required` | `400` | La route ne fonctionne qu’avec votre propre clé de fournisseur. | Ajoutez une [clé de fournisseur](./endpoint/provider-credentials-create.mdx) éligible. |
| `upstream_error` | `400`, `413` ou `422` | Tous les fournisseurs ont rejeté la requête avec le même statut (motif `upstream_rejected_request`). | Corrigez la requête ; réessayer ne servira à rien. |
| `unauthorised` | `401` | La clé est absente ou non valide. `reason` indique pourquoi. | Vérifiez l’en-tête `Authorization`. |
| `insufficient_funds` | `402` | L’espace de travail n’a pas assez de crédits. | Ajoutez des crédits. |
| `pricing_not_configured` | `402` | Aucun fournisseur de ce modèle n’a de tarification (motif `no_provider_pricing`). | Choisissez un autre modèle. |
| `guardrail_blocked` | `403` | Un garde-fou ou une politique d’accès a bloqué la requête. | Modifiez la requête ou le garde-fou. |
| `model_region_unavailable` | `403` | Aucun fournisseur ne sert le modèle dans la région requise, ou depuis l’emplacement de l’appelant. | Assouplissez l’exigence de région ou choisissez un autre modèle. |
| `not_found` | `404` | L’endpoint ou la ressource n’existe pas. | Vérifiez le chemin et l’ID. |
| `not_ready` | `409` | Les résultats d’une tâche ne sont pas encore prêts. | Interrogez l’état de la tâche. |
| `model_retired` | `410` | Le modèle est retiré et aucun fournisseur ne le sert. | Passez à `replacement_model`. Consultez la [section ci-dessous](#when-a-model-is-retired). |
| `payload_too_large` | `413` | Le corps dépasse la taille acceptée par l’endpoint. `max_bytes` indique la limite. | Envoyez un corps plus petit ou téléversez un fichier. |
| `key_limit_exceeded` | `429` | Une limite de clé, un budget ou la limite par minute de la passerelle a été atteint. | Consultez [Limites de débit](./limits.mdx#key-limits-and-budgets). |
| `phaseo_free_model_limit_exceeded` | `429` | Le quota quotidien des modèles gratuits (1 500 requêtes par défaut) est épuisé. | Respectez `Retry-After`, attendez la réinitialisation à 00:00 UTC ou utilisez un modèle payant. |
| `rate_limit_exceeded` | `429` | Une [politique de limite de débit](./limits.mdx#rate-limit-policies) de l’espace de travail est épuisée. `policy_id` et `limit_scope` l’identifient. | Respectez `Retry-After`, ou demandez à un administrateur de modifier la politique. |
| `spend_rule_blocked` | `429` | Une [règle de dépenses](../guides/spend-alerts.mdx) réglée sur le blocage est active. | Respectez `Retry-After`, ou demandez à un propriétaire ou à un administrateur de lever le blocage. |
| `upstream_error` | `429` | Tous les fournisseurs essayés ont limité la requête. | Respectez `Retry-After`. Les requêtes BYOK portent aussi des en-têtes `X-Phaseo-Upstream-RateLimit-*`. |
| `provider_capacity_exhausted` | `429` | Tous les fournisseurs éligibles sont à pleine capacité (motif `all_candidates_rate_limited`). | Respectez `Retry-After` s’il est présent, sinon espacez les tentatives. |
| `gateway_error` | `500` | Une erreur s’est produite dans Phaseo. | Réessayez avec un backoff. |
| `not_implemented_yet` | `501` | L’opération n’est pas encore disponible. | Ne réessayez pas. |
| `upstream_error` | `502` | Le fournisseur n’a pas répondu correctement. | Réessayez avec un backoff. |
| `upstream_stream_failure` | `502` | Une requête sans streaming dont le fournisseur a échoué après avoir commencé à générer. Aucune sortie partielle n’est renvoyée et la requête n’est pas facturée. | Réessayez. |
| `provider_payment_required` | `502` | Le compte de Phaseo chez le fournisseur nécessite une intervention. | Réessayez plus tard ou signalez-le. |

## Réessayer les bonnes erreurs

| Statut | Réessayer ? |
| --- | --- |
| `400`–`499` sauf `429` | Non. Corrigez d’abord la requête, la clé ou l’accès. |
| `429` | Oui. Attendez `Retry-After` (secondes ou date HTTP), sinon utilisez un backoff exponentiel avec gigue. Une erreur `key_limit_exceeded` sans `Retry-After` ne se réinitialise pas seule : ne la réessayez pas. |
| `500`–`599` | Seulement lorsque répéter l’opération est sans risque. Une soumission ambiguë peut déjà avoir créé une tâche ou un débit ; recherchez la tâche acceptée au lieu de la soumettre à nouveau. |

Fixez un nombre maximal de tentatives et une échéance globale. Consultez [Limites de débit](./limits.mdx) pour les en-têtes de limite de débit.

<span id="when-a-provider-fails"></span>
## En cas d’échec d’un fournisseur

Lorsque Phaseo a atteint un fournisseur et que la requête a tout de même échoué, `provider_failure_diagnostics` contient une `category`, un `hint` et le `provider`. Catégories :

| `category` | Signification |
| --- | --- |
| `credentials_not_configured` | Aucun identifiant n’est configuré pour cette route. |
| `credentials_invalid_or_forbidden` | L’identifiant a été refusé. |
| `provider_access_missing` | Le compte chez le fournisseur n’a pas accès au modèle ou à la fonctionnalité. |
| `region_or_project_restriction` | Le fournisseur a refusé en raison de la région ou du projet. |
| `model_unavailable_for_endpoint` | Le fournisseur n’expose pas le modèle sur cet endpoint. |
| `rate_limited` | Le fournisseur a limité la requête. |
| `server_error` | Le fournisseur a échoué ou a dépassé le délai. |

<span id="when-a-model-or-endpoint-is-not-available"></span>
## Lorsqu’un modèle ou un endpoint n’est pas disponible

Les erreurs `unsupported_model_or_endpoint` peuvent contenir `provider_candidate_diagnostics`, `provider_enablement`, `missing_pricing_providers` et `routing_diagnostics`. Ensemble, ils permettent de distinguer un modèle pas encore actif, un modèle qui ne prend pas en charge l’endpoint, une tarification manquante et des restrictions de déploiement.

| Champ | Signification |
| --- | --- |
| `provider_candidate_diagnostics.totalProviders` | Fournisseurs connus pour le modèle avant le filtrage par endpoint. |
| `provider_candidate_diagnostics.supportsEndpointCount` | Fournisseurs qui prennent en charge l’endpoint demandé. |
| `provider_candidate_diagnostics.candidateCount` | Fournisseurs restants après les vérifications d’adaptateur. |
| `provider_candidate_diagnostics.droppedUnsupportedEndpoint` | Fournisseurs écartés parce qu’ils ne prennent pas en charge l’endpoint. |
| `provider_candidate_diagnostics.droppedMissingAdapter` | Paires fournisseur–endpoint écartées parce que Phaseo n’a pas encore d’adaptateur pour cet endpoint. |
| `provider_enablement.capability` | La capacité appliquée, comme `video_generation`. |
| `provider_enablement.providersBefore`, `providersAfter` | Fournisseurs avant et après le filtrage par capacité. |
| `provider_enablement.dropped[].reason` | Raison pour laquelle un fournisseur a été écarté, comme `pricing_missing`. |
| `routing_diagnostics.filterStages[].stage` | Une étape de routage, comme le filtrage par capacité, par déploiement ou par état de routage. |
| `routing_diagnostics.filterStages[].beforeCount`, `afterCount` | Fournisseurs avant et après cette étape. |
| `routing_diagnostics.filterStages[].droppedProviders[].reason` | Raison pour laquelle un fournisseur a été écarté à cette étape. |

```json
{
  "error": {
    "code": "unsupported_model_or_endpoint",
    "message": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
    "type": "invalid_request_error",
    "param": null
  },
  "code": "unsupported_model_or_endpoint",
  "generation_id": "G-unsupported123",
  "status_code": 400,
  "description": "No provider is currently routable for endpoint \"responses\" on model \"example/model\".",
  "provider_candidate_diagnostics": {
    "totalProviders": 3,
    "supportsEndpointCount": 2,
    "candidateCount": 1,
    "droppedUnsupportedEndpoint": ["provider-a"],
    "droppedMissingAdapter": [
      {
        "providerId": "provider-b",
        "endpoint": "responses"
      }
    ]
  },
  "provider_enablement": {
    "capability": "responses",
    "providersBefore": ["provider-b", "provider-c"],
    "providersAfter": ["provider-c"],
    "dropped": [
      {
        "providerId": "provider-b",
        "reason": "pricing_missing"
      }
    ]
  },
  "routing_diagnostics": {
    "filterStages": [
      {
        "stage": "provider_routing_status",
        "beforeCount": 1,
        "afterCount": 0,
        "droppedProviders": [
          {
            "providerId": "provider-c",
            "reason": "provider_status_not_ready"
          }
        ]
      }
    ]
  }
}
```

<span id="when-a-model-is-retired"></span>
## Lorsqu’un modèle est retiré

Un modèle retiré reste servi tant qu’un fournisseur le sert. Dès qu’aucun ne le sert plus, les requêtes échouent avec `410` et `model_retired` :

```json
{
  "error": {
    "code": "model_retired",
    "message": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
    "type": "invalid_request_error",
    "param": null,
    "metadata": {
      "retired_at": "2026-09-30T00:00:00Z",
      "replacement_model": "lab/new-model"
    }
  },
  "code": "model_retired",
  "generation_id": "G-retired123",
  "status_code": 410,
  "reason": "model_retired_without_providers",
  "description": "Model \"lab/old-model\" was retired on 2026-09-30 and no provider serves it any more. Use \"lab/new-model\" instead.",
  "model": "lab/old-model",
  "retired_at": "2026-09-30T00:00:00Z",
  "replacement_model": "lab/new-model"
}
```

`model` est le modèle demandé, `retired_at` la date de son retrait (ou `null`), et `replacement_model` le remplaçant suggéré (ou `null`).

Réessayer ne sert à rien ; changez l’ID du modèle. Pour que ces requêtes continuent de fonctionner pendant la migration, ajoutez le remplaçant à la liste `models` de la requête ou activez le routage des modèles retirés pour l’espace de travail. Consultez [Dépréciation et retrait des modèles](../guides/model-retirement.mdx).

## Erreurs pendant un flux

Si une requête échoue avant le début du streaming, vous recevez le corps d’erreur JSON ci-dessus. Si elle échoue en cours de flux, le flux se termine par l’événement d’échec de l’endpoint au lieu d’une fin normale :

| Endpoint | Événement d’échec |
| --- | --- |
| Chat Completions | Une trame `error` |
| Responses | `response.failed` (ou `error`) |
| Messages | Un événement `error` |

Considérez la sortie partielle comme incomplète et proposez de réessayer. La trame `error` de Chat Completions contient le même objet d’erreur, avec `error.type` défini à partir du code :

```json
{
  "object": "error",
  "message": "The upstream stream ended before the response completed.",
  "code": "upstream_stream_failure",
  "error": {
    "code": "upstream_stream_failure",
    "message": "The upstream stream ended before the response completed.",
    "type": "server_error",
    "param": null
  }
}
```

Une requête sans streaming dont le fournisseur échoue en cours de route renvoie `502` avec `upstream_stream_failure`, et non une réponse partielle. Consultez [Streaming](../guides/streaming.mdx).

<span id="debug-a-request"></span>
## Déboguer une requête

Envoyez un objet `debug` pour obtenir les traces de routage et les charges utiles échangées avec le fournisseur :

```json
{
  "debug": {
    "enabled": true,
    "return_upstream_request": true,
    "return_upstream_response": false,
    "trace": true,
    "trace_level": "summary"
  }
}
```

`trace_level` vaut `summary` ou `full`. Les charges utiles de débogage peuvent contenir le contenu de votre requête : ne les utilisez qu’en développement ou dans des environnements étroitement contrôlés. Consultez [`debug`](./parameters.mdx#parameter-debug).

Lorsqu’une requête échoue, consultez la [page d’état](https://status.phaseo.app) pour les incidents, comparez votre charge utile à la page de référence de l’endpoint, et journalisez `generation_id` avec l’endpoint et le modèle. Indiquez `generation_id` lorsque vous contactez le [support](https://phaseo.app/help).

<Visibility for="agents">
Règles de gestion des erreurs pour les agents, résumant cette page :

- Basez la logique sur `error.code` (aussi renvoyé au niveau supérieur dans `code`), `error.type` et `status_code`, pas sur le texte du message. Journalisez `generation_id` à chaque échec.
- `400`, `401`, `403` et `404` : corrigez d’abord la requête, la clé ou l’accès. Ne réessayez pas la même requête sans modification.
- `410` avec `model_retired` : passez à `replacement_model` s’il n’est pas `null` ; sinon, choisissez un nouveau modèle depuis `GET /v1/models`.
- `429` : lorsque `Retry-After` est présent (secondes ou date HTTP), attendez ce délai avant de réessayer ; sinon, utilisez un backoff exponentiel avec gigue. Une erreur `key_limit_exceeded` sans `Retry-After` ne se réinitialise pas seule : ne la réessayez pas.
- `500` à `599` : ne réessayez que lorsque répéter l’appel est sans risque, avec un nombre maximal de tentatives, une échéance globale et un backoff exponentiel avec gigue. Pour les tâches asynchrones, recherchez la tâche acceptée au lieu de la soumettre à nouveau.
- Traitez les charges utiles de débogage comme sensibles et masquez-les avant de les écrire dans des journaux persistants.
- Pour des modèles éprouvés de nouvelles tentatives et d’analyse des erreurs, installez la skill `phaseo-gateway` : `npx skills add https://phaseo.app/docs --skill phaseo-gateway`.
</Visibility>
