Consultez la [page d’état](https://status.phaseo.app) et `GET /v1/health` pour savoir si Phaseo fonctionne correctement, `GET /v1/models` pour savoir si un modèle peut être routé maintenant, et votre propre série de tests pour savoir si une route atteint votre objectif de fiabilité.

## Vérifier l’état actuel du service

1. Ouvrez la [page d’état de Phaseo](https://status.phaseo.app) pour consulter les incidents en cours et leur historique.
2. Appelez `GET /v1/health` pour une vérification minimale de l’état du Gateway.
3. Si une seule requête a échoué, conservez son ID de requête et examinez son activité ou son enregistrement de génération avant de conclure que tout le service est indisponible.

```bash
curl https://api.phaseo.app/v1/health
```

```json
{
  "status": "ok"
}
```

<Note>
La page d’état publique indique la santé du service. Phaseo ne revendique actuellement aucun SLA contractuel public de disponibilité.
</Note>

## Vérifier qu’un modèle peut être routé

Le catalogue Phaseo répertorie plus de modèles que le Gateway ne peut en router : une entrée du catalogue signifie que Phaseo suit le modèle, pas qu’une route publique existe. Par défaut, `GET /v1/models` ne renvoie que les modèles routables actuellement :

```bash
curl https://api.phaseo.app/v1/models \
  -H "Authorization: Bearer $PHASEO_API_KEY"
```

Ajoutez `availability=all` pour voir aussi les correspondances à venir et inactives. N’envoyez du trafic de production vers une ligne de fournisseur que si son `availability_status` vaut `active` et son `is_active_gateway` vaut `true`. Consultez [États du fournisseur et de Phaseo](../guides/provider-statuses.mdx) pour comprendre les icônes d’état des pages de modèle.

| État | Signification |
| --- | --- |
| `active` | Au moins une route publique du Gateway est disponible maintenant. |
| `coming_soon` | Phaseo suit une route prévue ou en aperçu, mais elle n’est pas routable publiquement. |
| `inactive` | Une route connue est désactivée, indisponible, expirée ou non routable pour une autre raison. |
| `not_listed` | Aucune correspondance de fournisseur Gateway n’est actuellement répertoriée pour le modèle. |

`active` ne garantit ni la disponibilité, ni l’accès dans toutes les régions, ni les mêmes conditions commerciales pour tous les espaces de travail.

## Interpréter les métriques de performance

Les données de performance de Phaseo résument des requêtes réelles routées par le Gateway ; il ne s’agit pas d’un benchmark contrôlé en laboratoire.

| Métrique | Définition |
| --- | --- |
| TTFT du Gateway | Du début de la requête au Gateway jusqu’à la première sortie générée porteuse de contenu. |
| TTFT du fournisseur | De l’envoi au fournisseur jusqu’à la première sortie générée porteuse de contenu. |
| Durée chez le fournisseur | De l’envoi au fournisseur jusqu’à la réponse finale. |
| E2E du Gateway | Du début de la requête au Gateway jusqu’à la fin. |
| Surcoût Phaseo | La différence positive ou nulle entre l’E2E du Gateway et la durée chez le fournisseur. |
| Débit effectif | Tous les tokens de sortie divisés par la durée totale chez le fournisseur. |
| Vitesse de sortie | Les tokens de sortie après le premier, divisés par le temps passé chez le fournisseur après le TTFT. |

Le TTFT et la vitesse de sortie nécessitent une réponse en streaming dont la première sortie porte du contenu. Une requête sans streaming contribue tout de même à la durée et au débit effectif, mais pas au TTFT.

Lisez chaque métrique avec sa fenêtre temporelle, sa route, sa région, son mode de streaming et son percentile. La charge du fournisseur, la longueur du prompt, la longueur de la sortie, les nouvelles tentatives et les conditions réseau modifient toutes le résultat.

Pour les définitions complètes, consultez [Prix et performances](../exploring/pricing-performance) et [Comment Phaseo mesure la latence et le débit](https://phaseo.app/how-phaseo-measures-latency-throughput).

## Valider avec votre charge de travail

Les métriques publiques donnent une tendance ; elles ne prouvent pas qu’une route atteint votre objectif de production. Effectuez un petit test reproductible avant un déploiement :

1. Retirez les données de production sensibles et conservez un ensemble de prompts représentatif.
2. Notez l’ID du modèle, l’endpoint, les contraintes de fournisseur, la région, le mode de streaming et la concurrence.
3. Répétez suffisamment le test pour comparer des distributions plutôt qu’une seule requête.
4. Relevez le taux de réussite, le TTFT du Gateway, la durée chez le fournisseur, l’E2E du Gateway, les tokens de sortie et le coût final.
5. Testez les clés invalides, les modèles invalides, les limites de débit et les échecs liés à un fournisseur indisponible.
6. Conservez les ID de requête et la fenêtre temporelle exacte pour qu’un autre ingénieur puisse reproduire le résultat.

Ne publiez pas de nom de client, de citation, de résultat de charge de travail ou de pourcentage de fiabilité sans autorisation et sans méthode documentée.

## Diagnostiquer une requête en échec

1. Consultez l’[état du service](https://status.phaseo.app).
2. Vérifiez que le modèle figure toujours dans la réponse par défaut de [`GET /v1/models`](../api-reference/endpoint/models), et consultez ses [endpoints](../api-reference/endpoint/model-endpoints).
3. Recherchez le code d’état HTTP et le code d’erreur dans [Erreurs et débogage](../api-reference/errors).
4. Relancez les réponses `429` et `5xx` transitoires avec un backoff exponentiel borné ; consultez [Limites de débit](../api-reference/limits.mdx).
5. Conservez l’ID de requête lorsque vous contactez le [support](https://phaseo.app/help).

Pour que les requêtes continuent de fonctionner quand un fournisseur échoue, configurez le [routage et les solutions de repli](../guides/routing-and-fallbacks).
