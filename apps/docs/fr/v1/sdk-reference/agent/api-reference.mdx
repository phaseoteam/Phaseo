## Créer un agent

Crée un agent à partir d’une définition. La limite d’étapes de la définition s’applique à chaque appel run ou continue.

| Langage | Nom | Limite d’étapes par défaut |
| --- | --- | --- |
| TypeScript | `createAgent(definition)` | 12 |
| Python | `create_agent(definition)`, à partir d’un dict ou d’une `AgentDefinition` | 12 |
| Go | `CreateAgent(AgentDefinition) *Agent` | 8 |
| C# | `AgentSdk.CreateAgent(AgentDefinition)` | 12 |
| PHP | `AgentSdk::createAgent(AgentDefinition)` | 12 |
| Ruby | `PhaseoAgentSdk.create_agent(definition)`, à partir d’une `AgentDefinition` ou de champs en arguments nommés | 12 |
| Java | `AgentSdk.createAgent(AgentDefinition)` | 12 (un `maxSteps` inférieur à 1 devient 12) |
| Rust | `create_agent(AgentDefinition::new(id, model))` | 8 (les valeurs sont ramenées à au moins 1) |

### Champs de la définition

Rust construit la définition avec des méthodes plutôt qu’avec des champs : `AgentDefinition::new(id, model)`, puis `.instructions(text)`, `.tool(tool)` (une fois par outil), `.max_steps(limit)`, `.model_retries(count, backoff)` et `.human_review(callback)`. L’`AgentDefinition` de Java est un record avec des constructeurs à 10, 13 et 19 arguments.

| --- | --- | --- | --- | --- |

## Conditions d’arrêt

| Condition | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby) | PascalCase (Go, C#) |
| --- | --- | --- | --- |
| Nombre d’étapes | `stepCountIs` | `step_count_is` | `StepCountIs` |
| Tokens utilisés | `maxTokensUsed` | `max_tokens_used` | `MaxTokensUsed` |
| Coût | `maxCost` | `max_cost` | `MaxCost` |
| Temps écoulé | `maxDuration` (millisecondes en TypeScript et PHP ; une `Duration` en Java) | `max_duration` (millisecondes) | `MaxDuration` (une `time.Duration` en Go ; un `TimeSpan` en C#) |

Go et Java renvoient une `StopCondition` ; C# renvoie une `Func<StopState, (bool Stop, string Reason)>` ; PHP renvoie un `callable` ; Ruby renvoie une lambda. Rust n’a pas de conditions d’arrêt, seulement la limite d’étapes. Voir [Conditions d’arrêt](./stop-conditions).

## Exécuter et reprendre

| Rôle | TypeScript | Python | Go | C# | PHP | Ruby | Java | Rust |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Exécuter | `run(options)` | `run(...)` | `Run(ctx, RunOptions)` | `Run(RunOptions)` | `run(...)` | `run(...)` | `run(RunOptions)` | `run(&mut client, options)`, `run_with_events(&mut client, options, callback)` |
| Exécuter en streaming | `stream(options)` | `stream(...)` | `Stream(ctx, RunOptions)` | `Stream(RunOptions)` | `stream(...)` | `stream(...)` | `stream(RunOptions)` | Aucun |
| Reprendre | `continueRun(options)` | `continue_run(...)` | `Continue(ctx, ContinueOptions)` | `ContinueRun(ContinueOptions)` | `continueRun(...)`, `continueRunById(...)` | `continue_run(...)` | `continueRun(ContinueOptions)` | `continue_run(&mut client, options)`, `continue_with_events(...)` |

Run et continue renvoient un résultat d’exécution : une `Promise<AgentRunResult>` en TypeScript, `(RunResult, error)` en Go, `Task<RunResult>` en C#, `Result<RunResult, AgentError>` en Rust, et directement le résultat d’exécution ailleurs. Les méthodes de streaming renvoient immédiatement un résultat de flux.

### Options d’exécution

PHP et Ruby les prennent en arguments nommés ; le `RunOptions` de Java est un record positionnel dans l’ordre `input, client, context, model, preset, maxSteps, modelRetry, toolExecution, onEvent, devtools`, puis un `state` facultatif.

| Option | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) | Absent de |
| --- | --- | --- | --- | --- |
| Entrée | `input` | `input` | `Input` | |
| Conversation complète au lieu de l’entrée | `messages` | | | Tous sauf TypeScript |
| Client de modèle | `client` | `client` | `Client` | Rust le passe comme argument séparé |
| Contexte applicatif | `context` | `context` | `Context` | |
| Surcharges du modèle, du préréglage et de la limite d’étapes | `model`, `preset`, `maxSteps` | `model`, `preset`, `max_steps` | `Model`, `Preset`, `MaxSteps` | Rust n’a que `model` et `max_steps` |
| Surcharges des nouvelles tentatives et de la concurrence des outils | `modelRetry`, `toolExecution` | `model_retry`, `tool_execution` | `ModelRetry`, `ToolExecution` | Rust |
| Surcharges d’échantillonnage | `temperature`, `maxOutputTokens`, `topP` (TypeScript) | | | Tous sauf TypeScript |
| Annulation | `signal` (TypeScript) | | `CancellationToken` (C#) | Go utilise `ctx` ; les autres annulent via le flux |
| Gestionnaire d’événements | `onEvent` | `on_event` | `OnEvent` | Rust utilise `run_with_events` |
| Capture locale | `devtools` | `devtools` | `Devtools` | Rust |
| Accesseur d’état | `state` | `state` | `State` | Rust |
| Ajouter des messages avant la prochaine requête au modèle | `takeMessages` (TypeScript) | | | Tous sauf TypeScript |

Le `run()` de Python accepte aussi `stop_when` mais l’ignore ; définissez les conditions d’arrêt sur la définition. Le `stream()` de PHP et le `stream` de Ruby ne prennent que `input`, `client`, `context` et `state`. Rust crée les valeurs par défaut avec `RunOptions::new(input)`.

### Options de reprise

Les options de reprise acceptent les surcharges d’exécution ci-dessus, plus :

| Option | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) | Absent de |
| --- | --- | --- | --- | --- |
| L’exécution enregistrée | `run` | `run` (Rust : `result`) | `Run` | |
| Charger l’exécution par ID via `state` | `runId` | `run_id` | `RunID` (Go), `RunId` (C#) | Rust ; PHP utilise `continueRunById($runId, $state, $client, ...)` |
| Saisie humaine | `humanInput` | `human_input` | `HumanInput` | |
| Messages humains structurés | `humanMessages` (TypeScript) | | | Tous sauf TypeScript |
| Approbations | `approvals` (alias TypeScript `approveToolCalls`) | `approvals` | `Approvals` | |
| Rejets | `rejections` (alias TypeScript `rejectToolCalls`) | `rejections` | `Rejections` | Rust |
| Sorties d’outils | `toolOutputs` | `tool_outputs` | `ToolOutputs` | |

L’ordre du `ContinueOptions` de Java est `run, client, context, model, preset, maxSteps, humanInput, modelRetry, toolExecution, onEvent, devtools`, puis `approvals, rejections, toolOutputs`, puis `runId, state`. En plus de cette forme à 16 arguments, il existe des constructeurs qui ne prennent que les 11 ou les 14 premiers arguments ; les autres valent par défaut des listes vides ou `null`. Rust crée les valeurs par défaut avec `ContinueOptions::new(result)`.

Les consommateurs rejouent depuis le début ; plusieurs peuvent donc lire la même exécution. Leur comportement diffère :

| Langage | Type de résultat de flux | Comportement |
| --- | --- | --- |
| TypeScript | `AgentStreamResult` | `getFullStream()` se termine par un événement `result` |
| Python | `AgentStreamResult` | S’exécute dans un thread en arrière-plan ; `result()` bloque jusqu’à la fin |
| Go | `*StreamResult` | `Text()` et `Events()` sont des channels ; `Cancel()` annule le contexte de l’exécution |
| C# | `AgentStreamResult` | Consommateurs `IAsyncEnumerable` ; `Cancel()` annule le jeton lié de l’exécution |
| PHP | `AgentStreamResult` | S’exécute dans une Fiber ; `$result` contient le `RunResult` une fois le flux consommé, sinon `null` |
| Ruby | `StreamResult` | S’exécute dans un thread de travail ; `result` attend sa fin et `cancel` le tue |
| Java | `StreamResult` | `textStream()` et `fullStream()` renvoient une `List` après la fin de l’exécution ; `cancel()` interrompt le thread de travail |
| Rust | Aucun | Pas de streaming en `0.2` |

## Résultat d’exécution

| Champ | camelCase (TypeScript, PHP, Java) | snake_case (Python, Ruby, Rust) | PascalCase (Go, C#) |
| --- | --- | --- | --- |
| Enregistrement de l’exécution | `run` | `run` | `Run` |
| Enregistrements des étapes | `steps` | `steps` | `Steps` |
| Sortie finale | `output` | `output` | `Output` |
| Conversation complète | `messages` | `messages` | `Messages` |
| Utilisation cumulée | `usage` | `usage` | `Usage` |

Le type est `AgentRunResult` en TypeScript et Python et `RunResult` ailleurs. TypeScript ajoute `stepResults` (résultats d’étapes normalisés) et `items` (messages, raisonnement, activité des outils, erreurs et sortie finale, dans l’ordre ; voir [Éléments](./items)). En Rust, `output` est une `serde_json::Value`, et `RunResult`, `RunRecord`, `RunStep`, `Message`, `ToolCall`, `HumanPause`, `PendingToolCall`, `ToolDecision`, `ToolOutput` et `UsageSummary` se sérialisent avec Serde.

| Java | `ModelClient`, `StreamingModelClient` | `generate(ModelRequest)` ; `stream(ModelRequest)` |
| Rust | `ModelClient` (trait) | `fn generate(&mut self, request: &ModelRequest) -> Result<ModelResponse, AgentError>` |

En Rust, `ModelRequest` contient l’ID de l’agent, le modèle effectif, les instructions, les messages courants, les spécifications des outils (`ToolSpec` : `id`, `description`, `parameters` en JSON Schema) et le contexte applicatif. `ModelResponse` contient `message`, `usage`, `request_id`, `provider`, `model` et `finish_reason`. `Message` a `role`, `content`, `tool_calls`, `tool_call_id`, `name` et `is_error`, avec les constructeurs `Message::user(content)` et `Message::assistant(content)` ; `ToolCall` a `id`, `name` et `input` en JSON.
