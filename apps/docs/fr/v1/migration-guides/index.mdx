Choisissez le guide selon ce que vous changez : la plateforme qu’appelle votre application (ci-dessous) ou le modèle qu’elle utilise ([migrations de modèles](../model-migrations)). Si vous changez les deux, migrez d’abord la plateforme et gardez le même modèle jusqu’à ce que le nouveau chemin soit vérifié.

Pour une liste de contrôle personnalisée, utilisez l’[Assistant de migration](https://phaseo.app/migrate).

<span id="platform-migrations"></span>
## Migrations de plateformes

Chaque guide de plateforme suit le même ordre : changer l’URL de base et la clé, faire correspondre les identifiants de modèle, faire correspondre les fonctionnalités de la plateforme, puis tester et déployer en gardant un retour arrière limité à un changement d’URL de base et de clé.

| Vous appelez | Indices dans le code | Guide |
| --- | --- | --- |
| OpenAI directement | `api.openai.com`, `OPENAI_API_KEY`, `AzureOpenAI` | [SDK OpenAI](./from-openai) |
| Anthropic directement | `api.anthropic.com`, `ANTHROPIC_API_KEY`, `@anthropic-ai/sdk` | [SDK Anthropic](./from-anthropic) |
| OpenRouter | `openrouter.ai`, `OPENROUTER_API_KEY`, clés `sk-or-v1` | [OpenRouter](./from-openrouter) |
| Vercel AI Gateway | `ai-gateway.vercel.sh`, `@ai-sdk/gateway`, modèles sous forme de simple chaîne dans les appels AI SDK | [Vercel AI Gateway](./from-vercel) |
| LLM Gateway | `api.llmgateway.io`, `LLM_GATEWAY_API_KEY` | [LLM Gateway](./from-llmgateway) |
| Un proxy LiteLLM | `config.yaml` avec `model_list`, variables `LITELLM_*`, port 4000 | [LiteLLM](./from-litellm) |
| Cloudflare AI Gateway | `gateway.ai.cloudflare.com`, en-têtes `cf-aig-*` | [Cloudflare AI Gateway](./from-cloudflare) |
| Helicone | `*.helicone.ai`, `Helicone-Auth` | [Helicone](./from-helicone) |

Pour planifier et vérifier le déploiement, utilisez la [Liste de contrôle des fonctionnalités pour la migration](./feature-parity-matrix).

## Migrations de modèles

Utilisez un [guide de migration de modèle](../model-migrations) lorsque l’intégration reste la même mais que le modèle change. Chacun couvre les changements de paramètres de requête, l’évolution du comportement des prompts et du raisonnement, les différences de sorties structurées et d’appels d’outils, et la manière de déployer avec un modèle de secours.

Pour les deux types de migration, vérifiez les paramètres de requête et le comportement des endpoints avant de comparer la qualité des sorties, et exécutez des évaluations proches de la production avant de déplacer le trafic réel.
