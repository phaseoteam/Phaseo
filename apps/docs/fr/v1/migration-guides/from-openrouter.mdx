Remplacez l’URL de base par `https://api.phaseo.app/v1` et la clé par `PHASEO_API_KEY`. Les charges utiles des requêtes, l’en-tête `Authorization: Bearer`, l’objet `provider` et le tableau de secours `models` continuent de fonctionner ; vérifiez les identifiants de modèle et les quelques champs du tableau ci-dessous.

| Paramètre | OpenRouter | Phaseo |
| --- | --- | --- |
| URL de base | `https://openrouter.ai/api/v1` | `https://api.phaseo.app/v1` |
| Clé API | `OPENROUTER_API_KEY` (`sk-or-v1-…`) | `PHASEO_API_KEY` |
| Authentification | `Authorization: Bearer <key>` | Inchangée |
| Charge utile de la requête | Compatible OpenAI | Inchangée |
| Identifiants de modèle | `<org>/<model>` | `<org>/<model>` ; la plupart correspondent, certaines organisations diffèrent |
| En-têtes d’attribution | `HTTP-Referer`, `X-Title` | Inchangés ; ajoutez `X-App-Id` pour un regroupement stable |

## Changer de client

<CodeGroup>
```typescript Avant
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENROUTER_API_KEY,
  baseURL: "https://openrouter.ai/api/v1",
});

const response = await client.chat.completions.create({
  model: "openai/gpt-4.1-mini",
  messages: [{ role: "user", content: "Summarize our migration plan." }],
});
```

```typescript Après
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.PHASEO_API_KEY,
  baseURL: "https://api.phaseo.app/v1",
});

const response = await client.chat.completions.create({
  model: "openai/gpt-4.1-mini",
  messages: [{ role: "user", content: "Summarize our migration plan." }],
});
```

```bash cURL
curl -s "https://api.phaseo.app/v1/chat/completions" \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-6-astra",
    "messages": [{"role":"user","content":"Say hello"}]
  }'
```
</CodeGroup>

Gardez la charge utile inchangée lors du premier passage et obtenez la parité avant d’optimiser. Supprimez `OPENROUTER_BASE_URL` et l’ancienne clé du code, de la CI et des paramètres d’hébergement. `@openrouter/ai-sdk-provider` devient `@phaseo/ai-sdk-provider` (voir [Migrer depuis Vercel AI Gateway](./from-vercel)) ; les SDK propres à OpenRouter (`@openrouter/sdk`, `openrouter` sur PyPI) nécessitent un changement de client, pas seulement une nouvelle URL de base.

## Vérifier les identifiants de modèle

La plupart des identifiants correspondent, mais certaines organisations diffèrent : `x-ai/` devient `spacex-ai/`, `meta-llama/` devient `meta/` et `mistralai/` devient `mistral/`. Listez les identifiants Phaseo et vérifiez chaque modèle de production par rapport à cette liste :

```bash
curl -s "https://api.phaseo.app/v1/models?format=openai" \
  -H "Authorization: Bearer $PHASEO_API_KEY" | jq -r '.data[].id'
```

La liste par défaut ne contient que les modèles que vous pouvez appeler maintenant ; ajoutez `availability=all` pour voir les modèles inactifs ou à venir. Sans `format=openai`, la réponse est la liste paginée `models` de Phaseo, qui ne contient pas de tableau `data`.

## Faire correspondre les champs de requête

| OpenRouter | Sur Phaseo |
| --- | --- |
| `provider.order`, `only`, `ignore`, `allow_fallbacks`, `require_parameters`, `max_price` | Mêmes champs. Utilisez les identifiants de fournisseur de base, pas les slugs d’endpoint. |
| `provider.sort` | Même champ : `price`, `latency` ou `throughput`. |
| `provider.zdr` | Accepté comme alias de `provider.require_zero_data_retention`. |
| `provider.data_collection: "deny"` | Renvoie `400`. Utilisez plutôt `zdr: true`. |
| Tableau de secours `models` | Identique, de 1 à 25 entrées. `model` est obligatoire ; déplacez donc `models[0]` dans ce champ. |
| Suffixe `:nitro` | Identique (débit). Phaseo propose aussi `:cheap` et `:fast` ; `:floor` devient `:cheap`. Supprimez `:online` et `:thinking` et utilisez plutôt la recherche Web et `reasoning`. |
| `openrouter/auto`, `openrouter/free` | `phaseo/auto` ([Routage automatique](../guides/auto-routing), alpha, ne peut pas être combiné avec `models`) et `phaseo/free`. |
| `plugins` `web`, `web-fetch`, `response-healing` | Mêmes identifiants de plugin. Les autres plugins, comme `file-parser`, renvoient `400`. |
| `transforms`, `usage: { include: true }` | Non acceptés. Supprimez-les ; l’utilisation et le coût sont toujours renvoyés. |
| `X-OpenRouter-Title` | Renommez-le en `X-Title`. Consultez [Attribution des applications](../guides/app-attribution). |
| Préréglages `@preset/<slug>` | Recréez-les en tant que [Préréglages](../guides/presets) et appelez-les avec `"model": "@slug"`. |
| `usage.cost`, `reasoning_details`, `provider` dans les réponses | Renvoyés. `native_finish_reason` et `is_byok` ne le sont pas ; normalisez-les dans une seule couche si les appelants les lisent. |

Phaseo propose aussi `provider.required_execution_region` et `provider.required_data_region`, qui n’ont pas d’équivalent OpenRouter. Consultez [Épingler ou ignorer des fournisseurs](../cookbook/pin-or-ignore-providers-per-request) et [Router uniquement vers des fournisseurs UE ou compatibles ZDR](../cookbook/route-only-to-eu-or-zdr-providers) pour des requêtes complètes.

Regroupez les champs propres à OpenRouter qui restent dans un seul adaptateur plutôt qu’à chaque point d’appel, pour que le retour arrière reste un changement d’URL de base et de clé.

## Valider avant la bascule

Exécutez ces commandes sur Phaseo, puis les mêmes vérifications via le chemin client de votre application :

```bash
curl -s "https://api.phaseo.app/v1/health"

curl -s "https://api.phaseo.app/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -d '{"model":"openai/gpt-6-astra","messages":[{"role":"user","content":"Say hello"}]}'

# Streaming
curl -N "https://api.phaseo.app/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -d '{"model":"openai/gpt-6-astra","stream":true,"messages":[{"role":"user","content":"Reply with: stream works"}]}'

# Modèle invalide : l’application doit gérer l’erreur sans exposer d’identifiants
curl -s "https://api.phaseo.app/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $PHASEO_API_KEY" \
  -d '{"model":"invalid/migration-test","messages":[{"role":"user","content":"test"}]}'
```

Avant de déplacer une part importante du trafic, vérifiez que :

- `OPENROUTER_API_KEY` est remplacée par `PHASEO_API_KEY` dans chaque environnement ;
- chaque identifiant de modèle de production figure dans `GET /v1/models?format=openai` ;
- une requête sans streaming et une requête en streaming passent par `/v1/chat/completions` ou `/v1/responses`, avec le même chemin client qu’en production ;
- les flux d’appels d’outils et de sorties structurées passent avec de vrais prompts ;
- les échecs de clé invalide et de modèle invalide sont gérés ;
- une requête en échec peut être consultée avec `GET /v1/generations?id=<request_id>` et, lorsque `replay_supported` vaut `true`, relancée à partir de `replay_request` ;
- les en-têtes et champs de réponse propres à OpenRouter sont supprimés ou normalisés, et les valeurs par défaut partagées se trouvent dans des préréglages.

## Déployer

1. Commencez par le trafic interne.
2. Déplacez 5 à 10 % du trafic de production et comparez la qualité, la latence et le coût.
3. Passez à 100 % une fois la parité confirmée.
4. Gardez le retour arrière sous la forme d’un changement d’URL de base et de clé jusqu’à ce que la bascule soit stable.

## Confier la migration à un agent de code

Donnez à l’agent cette séquence délimitée, ou installez la [compétence de migration d’OpenRouter vers Phaseo](https://github.com/phaseoteam/Phaseo/tree/main/.agents/skills/openrouter-to-phaseo-migration), qui regroupe les mêmes étapes d’inventaire, de correspondance, de validation et de retour arrière :

1. Recherchez dans le code d’exécution et la configuration de déploiement `openrouter.ai`, `OPENROUTER_API_KEY`, `sk-or-v1`, `HTTP-Referer` et `X-Title`.
2. Changez la frontière du client pour `https://api.phaseo.app/v1` et `PHASEO_API_KEY` sans ajouter de valeur secrète au contrôle de version.
3. Interrogez `GET /v1/models?format=openai` et notez chaque correspondance entre ancien et nouveau modèle.
4. Adaptez les options de routage ou les champs de réponse propres à OpenRouter dans un seul module de compatibilité.
5. Exécutez les vérifications de santé, sans streaming, en streaming et de chemin d’échec ci-dessus.
6. Indiquez les fichiers modifiés, les changements de noms de secrets, les correspondances de modèles, les preuves de test, les écarts de parité et le mécanisme de retour arrière.

Pour une version guidée, ouvrez le [guide interactif de migration depuis OpenRouter](https://phaseo.app/migrate/openrouter), voyez comment les deux [se comparent](https://phaseo.app/compare/openrouter) ou [obtenez une aide gratuite pour la migration](https://phaseo.app/contact).
