حدّد لكل نوع من الطلبات هدفًا للإدخال وحدًّا للإخراج، ثم قارن الاستخدام الفعلي بهما. كل رمز ترسله أو تتلقاه يضيف زمن استجابة وتكلفة، وحدّ الإخراج الصغير جدًا يقطع الإجابات.

## ما يُحتسب ضمن الطلب

| الجزء | يُحتسب كـ | انتبه إلى |
| --- | --- | --- |
| تعليمات النظام والمطوّر | إدخال | التعليمات الطويلة المكررة في كل طلب. خزّنها مؤقتًا باستخدام [تخزين المطالبات مؤقتًا](./prompt-caching.mdx). |
| إدخال المستخدم | إدخال | اللصق والرفع غير المحدودين. |
| السياق المسترجَع (المستندات، نتائج البحث، مخرجات الأدوات) | إدخال | المقاطع قليلة الصلة التي تضيف رموزًا وتُضعف الإجابة. |
| مخططات الأدوات وتعريفات الدوال | إدخال | تُحتسب الأدوات المعلنة كإدخال سواء استدعاها النموذج أم لا. |
| الاستدلال | إخراج | تستهلك نماذج الاستدلال جزءًا من حد الإخراج قبل أن تجيب. |
| الإجابة | إخراج | الحدود التي تقطع الإجابات أو المخرجات المنظَّمة. |

## عندما يستهلك الاستدلال حد الإخراج

قد يستهلك نموذج الاستدلال حد الإخراج كاملًا قبل أن ينتج إجابة. تظل الاستجابة HTTP `200` وتحتوي على الاستدلال الذي أُنتج، دون أي إجابة مختلَقة:

| نقطة النهاية | ما تحصل عليه |
| --- | --- |
| Chat Completions | `reasoning_content`، مع `finish_reason: "length"` |
| Responses | عنصر مخرجات الاستدلال، مع `status: "incomplete"` |

يظل الإيقاف العادي `stop` (في Chat Completions) أو `completed` (في Responses). ارفع حد الإخراج أو خفّض مستوى جهد الاستدلال إذا رأيت هذه الحالات كثيرًا.

## حدّد ميزانية لكل مسار

1. حدّد حجمًا أقصى للإدخال لكل نوع من الطلبات، مثل إجابة بحث أو مسودة طويلة. لا تنسخ حدًا واحدًا عبر كل نقاط النهاية.
2. اترك مساحة إخراج تكفي لأطول إجابة ينبغي أن ينتجها ذلك النوع من الطلبات.
3. اقتطع السياق الكبير أو لخّصه قبل إرساله، بدءًا بالمقاطع الأقل احتمالًا لأن تكون مهمة.
4. افحص المخرجات بحثًا عن الاقتطاع، مثل `finish_reason: "length"` أو JSON جزئي، وأعد المحاولة بمساحة أكبر عند حدوثه.
5. تتبّع أعداد الرموز في `usage` لكل استجابة بمرور الوقت، وعدّل الحدود كلما تغيّرت موجّهاتك.

لمعرفة كيف تتفاعل حدود الإخراج مع أخذ العينات، راجع [معاملات الاستدلال](./inference-parameters.mdx).
