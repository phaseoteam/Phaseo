اقرأ رمز الخطأ و`reason` في استجابة `429` لتعرف أي حد أوقف الطلب، ثم انتظر `Retry-After` أو غيّر الحد. يقلّل التوجيه والبدائل الاحتياطية إخفاقات المزوّدين، لكن قد يظل الطلب مقيّدًا من جانب مزوّد أو بسياسة لمساحة العمل أو المفتاح.

| الحد | رمز الخطأ | `reason` | يُعاد ضبطه تلقائيًا |
| --- | --- | --- | --- |
| [الطلبات في الدقيقة](#gateway-limits) | `key_limit_exceeded` | `customer_requests_per_minute` | نعم، `Retry-After` بالثواني |
| [طلبات النماذج المجانية في اليوم](#gateway-limits) | `phaseo_free_model_limit_exceeded` | `free_requests_per_day` | نعم، عند 00:00 UTC |
| [حد المفتاح أو ميزانية مساحة العمل](#key-limits-and-budgets) | `key_limit_exceeded` | الحد الذي بُلغ؛ مع `limit_window` و`reset_at` | فقط عند وجود `Retry-After` |
| [ميزانية القسم](#department-budgets) | `key_limit_exceeded` | `department_daily_cost_budget_reached` (أو `weekly` أو `monthly`) | نعم، عند `reset_at` |
| [قاعدة إنفاق مضبوطة على الحظر](#key-limits-and-budgets) | `spend_rule_blocked` | | عند `reset_at` إن كان للحظر موعد، أو عندما يرفعه مالك أو مسؤول |
| [سياسة حد المعدل](#rate-limit-policies) | `rate_limit_exceeded` | `policy_requests_per_minute` أو `policy_tokens_per_minute` أو `policy_concurrent_requests` أو `policy_unavailable` | نعم، `Retry-After` بالثواني |
| [واجهة API للإدارة](#management-api-limits) | `rate_limit_exceeded` | `management_api_rate_limit` | نعم، `Retry-After` بالثواني |
| [المزوّد](#provider-limits) | `upstream_error` أو `provider_capacity_exhausted` | | اتبع `Retry-After` الخاص بالمزوّد |

تُرجع كل هذه الحدود `429`. إذا تعذّر فرض حصص الـ Gateway لفترة وجيزة، يُرجع الـ Gateway بدلًا من ذلك `503` مع إرشادات لإعادة المحاولة.

<span id="gateway-limits"></span>
## حدود الـ Gateway

لكل مستخدم في كل مساحة عمل حصة من الطلبات في الدقيقة، تُقاس على مدى دقيقة متحركة. تتشارك مفاتيح API التي أنشأها المستخدم نفسه هذه الحصة. وتُحتسب طلبات OAuth على المستخدم المسجّل دخوله، وتتشارك المفاتيح التي ليس لها مالك حصة واحدة لمساحة العمل.

ترتفع الحصة تلقائيًا كلما ترسّخت مساحة العمل. تحصل مساحة العمل على أعلى صف تستوفي شروطه، وتسري التغييرات خلال بضع دقائق:

| مساحة العمل | الطلبات في الدقيقة |
| --- | --- |
| مساحة عمل جديدة | 10 |
| عمرها 7 أيام على الأقل، أو أجرت شحنًا مدفوعًا للرصيد | 25 |
| عمرها 30 يومًا على الأقل مع شحن مدفوع للرصيد لا يقل عن $50 بعد خصم المبالغ المستردة | 60 |
| الفوترة عبر الفواتير | 120 |

للنماذج المجانية أيضًا حصة افتراضية قدرها **1,500 طلب لكل يوم بتوقيت UTC**. وهي مشتركة بين جميع النماذج المجانية وبين كل مساحات العمل التي يرسل فيها المستخدم نفسه طلبات. لا تستهلكها طلبات النماذج المدفوعة. يُحتسب الطلب المجاني المقبول حتى إذا فشل المزوّد بعد ذلك، وتُحتسب البدائل الاحتياطية بين المزوّدين ضمن الطلب الواحد مرة واحدة.

ينطبق الحدّان عبر كل مناطق الـ Gateway، ويمكن رفعهما لمستخدم ومساحة عمل محددين. تستهلك عمليات الملفات واستطلاع حالة المهام حصة الدقيقة؛ أما نقاط نهاية الإدارة فلا تستهلكها.

يُرجع الطلب المرفوض `429` مع `Retry-After` بالثواني. انتظر هذه المدة قبل إعادة المحاولة.

<span id="management-api-limits"></span>
## حدود واجهة API للإدارة

تتشارك نقاط نهاية الإدارة، مثل `/v1/keys` و`/v1/logs` و`/v1/analytics`، حصة قدرها **200 وحدة في الدقيقة** لكل بيانات اعتماد. لكل مفتاح إدارة ورمز OAuth وجلسة لوحة تحكم حصته الخاصة، وتتشارك الطلبات التي لا تحمل بيانات اعتماد حصة واحدة لكل عنوان IP. لا تستهلكها نقاط نهاية النماذج والملفات والدُفعات والمهام.

يستهلك كل طلب وحدات بحسب مقدار العمل الذي يتطلبه:

| الوحدات | الطلبات |
| --- | --- |
| 1 | قراءات الكتالوج (`/v1/models`, `/v1/pricing`, `/v1/providers`, `/v1/organisations`)، و`/v1/key` و`/v1/me` و`/v1/settings` |
| 2 | القراءات الأخرى، مثل `/v1/keys` و`/v1/workspaces` |
| 3 | إنشاء أي شيء أو تحديثه أو حذفه |
| 5 | البحث في السجلات والتوليدات وأحداث التدقيق والنشاط والملاحظات والأحداث |
| 10 | `/v1/analytics`، والاختبارات التي تستدعي خدمة خارجية: اختبارات وجهات المراقبة وعيّناتها، واختبارات المصنّفات، وتشغيلات اختبار الإعدادات المسبقة |

إن `/v1/health` وطلبات CORS التمهيدية مجانية. يُرجع الطلب الذي يتجاوز الحصة `429` مع `rate_limit_exceeded`، والسبب `management_api_rate_limit`، و`Retry-After: 60`. العدّ تقريبي ولا تحمل هذه الاستجابات ترويسات `x-ratelimit-*`، لذا وزّع السكربتات الجماعية على فترات بدلًا من تشغيلها حتى الحد.

<span id="key-limits-and-budgets"></span>
## حدود المفاتيح والميزانيات

عند بلوغ حدود الطلبات أو الإنفاق اليومية أو الأسبوعية أو الشهرية لمفتاح API، أو [ميزانيات](./endpoint/budgets-list.mdx) مساحة العمل، يُرجع الطلب `429` مع `key_limit_exceeded`. توضح الحقول `reason` و`limit_window` و`reset_at` في الجسم أي حد بُلغ ومتى تُعاد فترته، ويعطي `Retry-After` عدد الثواني حتى ذلك الحين.

يغيب `Retry-After` عندما لا يُعاد ضبط الحد تلقائيًا، مثل ميزانية مدى الحياة أو مفتاح محظور حظرًا مرنًا. لا تُعد المحاولة: ارفع ميزانية مساحة العمل، أو ارفع حد المفتاح، أو استخدم مفتاحًا آخر.

يدير مالكو مساحة العمل ومسؤولوها الميزانيات باستخدام مفتاح إدارة عبر `/v1/budgets` أو من [الإعدادات ← الميزانيات](https://phaseo.app/settings/budgets)، التي تعرض لكل ميزانية الإنفاق حتى الآن، والنسبة المستخدمة، وتوقعًا للفترة، وموعد إعادة الضبط. تُعاد الميزانيات اليومية والأسبوعية والشهرية عند حدود UTC: منتصف الليل، ويوم الاثنين 00:00، واليوم الأول من الشهر.

يمكن أن تنبّه [تنبيهات الإنفاق](../guides/spend-alerts.mdx) قبل بلوغ هذه الحدود. تُرجع قاعدة الإنفاق المضبوطة على الحظر `429` مع `spend_rule_blocked`. وهي تعمل بأفضل جهد وتبدأ بعد بضع دقائق من تجاوز الإنفاق حدها، لذا استخدم حدود المفاتيح والميزانيات للحصول على سقوف دقيقة. تعني الترويسة `x-phaseo-spend-warning` أن حظرًا قد يتبع.

<span id="department-budgets"></span>
### ميزانيات الأقسام

يدير المالكون والمسؤولون ميزانيات الأقسام باستخدام `phaseo department-budgets`، أو واجهة `/v1/department-budgets`، أو من [الإعدادات ← الميزانيات](https://phaseo.app/settings/budgets)، أو بالمورد `phaseo_department_budget` في موفّر Terraform. يحتسب إنفاق القسم المفاتيح وطلبات OAuth نفسها التي تحتسبها [حدود معدل الأقسام](#rate-limit-policies).

بعد أن يستنفد القسم ميزانيته اليومية أو الأسبوعية أو الشهرية، تُرجع طلبات مفاتيح API التي تُحتسب عليه `429` مع `key_limit_exceeded` والسبب `department_daily_cost_budget_reached` أو `department_weekly_cost_budget_reached` أو `department_monthly_cost_budget_reached`. يحدد الحقلان `department_id` و`department_name` في الجسم القسم، ويوضح `reset_at` و`Retry-After` موعد إعادة ضبط ميزانيته.

- إذا تعذّر التحقق من الميزانية لفترة وجيزة، يُسمح بالطلبات، لذا قد يتجاوز القسم ميزانيته لوقت قصير.
- يتلقى المالكون والمسؤولون إشعارًا فوريًا على الهاتف عند نحو 80% من الميزانية ثم عند 100%. تُفحص الميزانيات لهذه التنبيهات كل 15 دقيقة، لذا قد تُرفض الطلبات قبل وصول تنبيه 100%.

<span id="rate-limit-policies"></span>
## سياسات حدود المعدل

يمكن لمسؤولي مساحة العمل إنشاء سياسات مسمّاة تضبط `requests_per_minute` و`tokens_per_minute` و`concurrent_requests`، وتعيينها للمفاتيح أو الأعضاء أو الأقسام أو المستخدمين النهائيين. أدِرها باستخدام `phaseo rate-limits policies` و`phaseo rate-limits assignments`، أو واجهة `/v1/rate-limits`، أو من [الإعدادات ← حدود المعدل](https://phaseo.app/settings/rate-limits)، أو بالمورديْن `phaseo_rate_limit_policy` و`phaseo_rate_limit_assignment` في موفّر Terraform.

| مُعيَّنة إلى | ما الذي يتشارك حصة واحدة |
| --- | --- |
| المفتاح (`key`) | طلبات ذلك المفتاح. |
| العضو (`member`) | مفاتيح العضو وطلبات OAuth الخاصة به. |
| القسم (`department`) | كل ما يُحتسب على القسم (انظر أدناه). |
| القيمة الافتراضية للمستخدم النهائي (`end_user`) | يحصل كل مستخدم نهائي على حصته الخاصة، ويُعرَّف بحقل `user` في الطلب أو بالترويسة `X-Phaseo-User-Id`. لا تُقيَّد الطلبات التي لا تحمل معرّف مستخدم نهائي. |

**ما الذي يُحتسب على القسم.** يُحتسب المفتاح المرتبط بقسم على ذلك القسم وحده. ويُحتسب أي مفتاح آخر على كل قسم ينتمي إليه منشئه، وتُحتسب طلبات OAuth على كل أقسام مستخدمها. ويُحتسب العضو الذي لديه تجاوز للقسم على قسم التجاوز وحده. لاحتساب هذه المفاتيح وطلبات OAuth على القسم الأساسي للشخص وحده، اضبط إسناد الأقسام على primary من [الإعدادات ← الإشعارات](https://phaseo.app/settings/notifications)، أو عبر `spend.department_attribution` في `PATCH /v1/notifications/settings` باستخدام مفتاح إدارة. تستخدم ميزانيات الأقسام وقواعد الإنفاق الإعداد نفسه.

عند انطباق عدة سياسات، تُحتسب كل منها، وأول سياسة تُستنفد ترفض الطلب. تنطبق السياسات إضافةً إلى [حدود الـ Gateway](#gateway-limits). تسري تغييرات السياسات خلال دقيقة تقريبًا؛ وقد تستغرق تغييرات عضوية الأقسام التي تُجرى في لوحة التحكم أو عبر SCIM ما يصل إلى خمس دقائق تقريبًا.

### الطلبات والـ tokens في الدقيقة

يُقاس كلاهما على دقيقة متحركة. تحتسب `tokens_per_minute` الـ tokens الداخلة والخارجة لكل طلب عند اكتماله، بما في ذلك الطلبات المتدفقة والفاشلة التي استهلكت tokens. يُرفض الطلب بمجرد أن يبلغ الاستهلاك خلال الدقيقة الأخيرة الحد، لذا قد تتجاوزه الطلبات الجارية بالفعل. تُحتسب البدائل الاحتياطية بين المزوّدين ضمن الطلب الواحد مرة واحدة.

يُرجع الطلب المرفوض `429` مع `rate_limit_exceeded`، والسبب `policy_requests_per_minute` أو `policy_tokens_per_minute`، و`policy_id`، و`limit_scope` (`key` أو `member` أو `department` أو `workspace` أو `end_user`)، و`Retry-After` بالثواني.

تحمل الاستجابات للطلبات التي تشملها سياسة ترويسات الحد الأكثر تقييدًا:

| الترويسة | مثال |
| --- | --- |
| `x-ratelimit-limit-requests` و`x-ratelimit-remaining-requests` | `60` و`42` |
| `x-ratelimit-reset-requests` | `60s` |
| `x-ratelimit-limit-tokens` و`x-ratelimit-remaining-tokens` و`x-ratelimit-reset-tokens` | مثلها، لحد الـ tokens |

لا يحمل الطلب المرفوض إلا ترويسات الحد الذي رفضه. يجري العدّ في الخلفية، لذا فإن `remaining` تقريبية، ولا تتضمن ترويسات الـ tokens بعدُ استهلاك الطلب الحالي نفسه.

### الطلبات المتزامنة

يحدّ `concurrent_requests` من عدد الطلبات التي يمكن أن تكون قيد التنفيذ في الوقت نفسه. يشغل الطلب خانة منذ قبوله حتى تُرسل استجابته كاملة، بما في ذلك الاستجابة المتدفقة كلها؛ وتتشارك البدائل الاحتياطية بين المزوّدين والنماذج ضمن الطلب تلك الخانة. عندما تكون كل الخانات مشغولة، يُرفض الطلب بالسبب `policy_concurrent_requests` مع `Retry-After: 1`.

يتطلب التحقق من حد التزامن انتظار عدّاد السياسة، ما يضيف زمن انتقال بسيطًا. تتحرر الخانة التي فُقد إطلاقها تلقائيًا بعد 15 دقيقة. لا تُقيَّد الدفعات وجلسات الوقت الفعلي، ولا يشغل إنشاء الفيديو خانة إلا أثناء الطلب الذي يبدؤه.

### السياسات الصارمة

افتراضيًا، تسمح السياسة بالطلب عند الإخفاق: إذا تعذّر التحقق من حدودها، يُسمح بالطلب. اضبط `fail_closed` لجعلها صارمة. تتحقق السياسة الصارمة من حدود الطلبات والـ tokens قبل إرسال الطلب لا في الخلفية، ما يجعلها دقيقة لكنه يضيف زمن انتقال. إذا تعذّر التحقق منها خلال ثانيتين، يُرفض الطلب بالسبب `policy_unavailable`.

لا تحمل حالات الرفض بسبب التزامن أو `policy_unavailable` ترويسات `x-ratelimit-*`.

<span id="provider-limits"></span>
## حدود المزوّد

تستخدم طلبات BYOK حدود حسابك لدى المزوّد. وتستخدم الطلبات المُدارة سعة مشتركة لدى المزوّد، وهي ليست حصة مخصصة لمساحة عملك.

يمرّر Phaseo قيمة `Retry-After` بعد التحقق منها عندما يرسلها المزوّد. قد تتضمن استجابات BYOK أيضًا ترويسات `X-Phaseo-Upstream-RateLimit-*`؛ وتُحذف من الطلبات المُدارة لأنها تصف سعة مشتركة. لا تُمرَّر ترويسات المزوّد الأخرى. راجع [رموز الأخطاء](./errors.mdx#error-codes) لرموز `429` الخاصة بالمزوّد.

## التعامل مع طلب مقيّد

1. اقرأ [رمز الخطأ](./errors.mdx) للتمييز بين التقييد المؤقت وحدّ أو ميزانية أو سياسة تحتاج إلى تغيير في الإعدادات.
2. التزم بـ `Retry-After` عند وجوده. قد يكون ثواني أو تاريخ HTTP؛ تحقّق منه قبل جدولة إعادة المحاولة.
3. وإلا، فاستخدم تراجعًا أُسّيًا مع تذبذب عشوائي وحد أقصى للتأخير.
4. قيّد إعادة المحاولة بعدد المحاولات وبمهلة إجمالية. ألغِ العمل المتروك وحرّر جسم كل استجابة فاشلة قبل إعادة المحاولة.
5. قلّل التزامن إذا استمر التقييد.

لا تُعد تلقائيًا إرسال مهمة غير مؤكدة النتيجة، ولا تكرّر إجراءات أدوات اكتملت. ربما وصل الطلب إلى المزوّد حتى لو فقد العميل الاستجابة، لذا قد تكرّر إعادة المحاولة العمل والرسوم. بالنسبة إلى مهمة فيديو أو دفعة مقبولة، استخدم نقطة نهاية حالتها بدلًا من إرسالها مجددًا.

لمراقبة التقييد، تتبّع معدلات `429` حسب نقطة النهاية والنموذج، وافحص تكرار البدائل الاحتياطية في سجلات الطلبات. قارنها مع [إعدادات التوجيه](../guides/routing-and-fallbacks.mdx)، ومع حصص حسابك لدى المزوّد بالنسبة إلى حركة BYOK. تتحكم [ضوابط الحماية](./endpoint/guardrails.mdx) في المفاتيح التي يمكنها استخدام كل نموذج ومزوّد.

<Visibility for="agents">
قواعد حدود المعدل للوكلاء، تلخّص هذه الصفحة:

- تُرجع حصص الـ Gateway الرمز `429` مع السبب `customer_requests_per_minute` (الرمز `key_limit_exceeded`) أو `free_requests_per_day` (الرمز `phaseo_free_model_limit_exceeded`)؛ انتظر عدد الثواني في `Retry-After`. إذا لم يكن فرض الحصص متاحًا، يُرجع الـ Gateway الرمز `503` مع إرشادات لإعادة المحاولة.
- تُرجع حدود المفاتيح والميزانيات `429` مع `key_limit_exceeded` وقيمة `reset_at`. بدون `Retry-After` لا يُعاد ضبط الحد تلقائيًا: ارفع الحد أو استخدم مفتاحًا آخر بدلًا من إعادة المحاولة.
- تُرجع ميزانية القسم المستنفدة `429` مع `key_limit_exceeded` والسبب `department_<interval>_cost_budget_reached` و`department_id` و`department_name` و`reset_at`؛ انتظر عدد الثواني في `Retry-After` أو ارفع الميزانية. إذا تعذّر التحقق من الميزانية، يُسمح بالطلب.
- تُرجع قواعد الإنفاق الحاظرة `429` مع `spend_rule_blocked`؛ انتظر `Retry-After`، أو اطلب من مالك أو مسؤول رفع الحظر. تعني `x-phaseo-spend-warning` أن حظرًا قد يتبع.
- تُرجع سياسات حدود المعدل في مساحة العمل `429` مع `rate_limit_exceeded` و`policy_id` و`limit_scope`. قيمة `x-ratelimit-remaining-requests` تقريبية.
- تُرجع نقاط نهاية الإدارة (المفاتيح والسجلات والتحليلات وغيرها) `429` مع `rate_limit_exceeded` والسبب `management_api_rate_limit` عندما تستهلك بيانات الاعتماد وحداتها الـ 200 لتلك الدقيقة؛ وتستهلك الطلبات الأثقل وحدات أكثر. انتظر `Retry-After` (60) ثانية.
