Most teams find out they needed a limit right after something used up the shared capacity. An agent loops overnight, a batch script retries every failure at once, or one heavy user of your app slows things down for everyone else.

Phaseo now has **rate limit policies** and **department budgets**. You decide how many requests, tokens and parallel calls each API key, team member, department or end user gets, and how much each department can spend before its requests stop. It works across the models and providers you call through Phaseo, with no code changes. Nothing is limited until you set it up.

Rate limits for keys, members, guardrails and end users are available on every workspace. Department limits and budgets come with [Self Serve Enterprise](https://phaseo.app/docs/v1/pricing/tiers), alongside SSO, SCIM and directory management.

## How rate limiting works on Phaseo

Every request passes through the same checks before it reaches a model. If any check says no, the request gets a `429` straight away and never reaches the provider, so it costs nothing.

<Flow title="Each request is checked against your limits before it reaches a provider.">
  <FlowStep title="Request arrives" ok="For any model or provider">From your app, an agent or a teammate's key.</FlowStep>
  <FlowStep title="Rate limit policies" stop="429 rate_limit_exceeded">Requests, tokens and concurrency for the key, member, department, guardrail and end user.</FlowStep>
  <FlowStep title="Department budget" stop="429 key_limit_exceeded">Daily, weekly or monthly spend for the departments the request counts toward.</FlowStep>
  <FlowStep title="Model provider" ok="Response, with rate limit headers">Routing and fallbacks as usual.</FlowStep>
</Flow>

## Rate limit policies: requests, tokens and concurrency

A policy is a named set of limits that you can reuse anywhere:

| Limit | What it counts | Good for |
| --- | --- | --- |
| Requests per minute | Calls over a rolling minute | Fair access and abuse protection |
| Tokens per minute | Input and output tokens over a rolling minute | Matching real model load and cost |
| Concurrent requests | Requests in progress at the same time | Long streams, agents and batch scripts |

### Rate limit per API key, user, team or end user

You assign a policy to whatever it should limit. A department can share a pool of 600 requests a minute while each person in it is held to 60. When several policies apply, each is counted, and the first one used up refuses the request.

<FeatureGrid columns="3">
  <Feature title="API key" meta="key">That key on its own.</Feature>
  <Feature title="Team member" meta="member">One allowance across everything a person sends: all their keys and OAuth requests.</Feature>
  <Feature title="Department" meta="department">One shared pool for everyone in the department.</Feature>
  <Feature title="Guardrail" meta="guardrail">A separate allowance for each key the guardrail covers.</Feature>
  <Feature title="End user" meta="end_user_default">A separate allowance for each of your own users, from the `user` field or `X-Phaseo-User-Id` header.</Feature>
</FeatureGrid>

Fallbacks to another provider within one request count once, and responses served from cache don't count at all.

### Exact limits when you need them

Request and token limits are counted in the background by default, so they add no latency. The trade-off is that a sudden burst can briefly go over the limit before the count catches up.

When a limit must hold exactly, mark the policy **strict**. Strict limits are checked before the request is sent, which adds a little latency. If the check can't complete within two seconds, the request is refused rather than let through. Concurrency limits are always exact: a request holds its slot until its response has been sent in full, including the whole of a streamed response.

## AI budgets per department that actually stop spending

On Self Serve Enterprise workspaces, give a department a daily, weekly or monthly budget, and Phaseo tracks its spend as requests complete. Owners and admins get a push notification at about 80% and again at 100%. Once a budget is used up, that department's API-key requests are refused until the period resets, at midnight UTC, on Mondays or on the 1st of the month.

A department's spend includes the keys linked to it. Keys that aren't linked to a department count toward the departments of the person who created them, and OAuth requests count toward the departments of the signed-in person.

### Count each person once with primary department attribution

People often belong to more than one department, especially when departments are synced from your identity provider through SCIM. By default their unlinked keys count toward every department they're in, so each of those departments sees the spend.

To count each person once, switch the workspace to **primary department only** under [Settings → Notifications](https://phaseo.app/settings/notifications). Their spend then goes to their primary department alone. Department budgets and department rate limits follow the same setting, so the numbers agree everywhere. A key linked to a department, or a member's department override, still wins.

## What your application sees: 429 responses and rate limit headers

Responses to requests that a policy covers include the standard rate limit headers, so OpenAI-compatible clients and retry logic work unchanged:

```http
x-ratelimit-limit-requests: 60
x-ratelimit-remaining-requests: 41
x-ratelimit-reset-requests: 60s
```

A refused request returns `429` with a `Retry-After` header and a body that says exactly which limit was hit:

```json
{
  "error": {
    "code": "rate_limit_exceeded",
    "reason": "policy_requests_per_minute",
    "limit_scope": "department",
    "policy_id": "…"
  }
}
```

A department budget refusal uses `key_limit_exceeded` with the reason `department_monthly_cost_budget_reached` (or daily or weekly), the department's name and `reset_at`, so you can tell people exactly when they can try again.

## Set up rate limits and budgets in minutes

Everything is in the dashboard under [Settings → Rate limits](https://phaseo.app/settings/rate-limits) and [Settings → Budgets](https://phaseo.app/settings/budgets). To manage limits from code, use the management API. For example, a shared pool for a department with a monthly budget on top:

```bash
curl https://api.phaseo.app/v1/rate-limits/policies \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "Support team", "requests_per_minute": 600, "concurrent_requests": 20}'

curl https://api.phaseo.app/v1/rate-limits/assignments \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"policy_id": "<policy-id>", "target_type": "department", "target_id": "<department-id>"}'

curl https://api.phaseo.app/v1/department-budgets \
  -H "Authorization: Bearer $PHASEO_MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"department_id": "<department-id>", "interval": "monthly", "limit": 500}'
```

Phaseo CLI commands and Terraform resources, so limits can be reviewed and versioned with the rest of your infrastructure, arrive with their next releases.

## Good to know

- These limits come on top of each workspace's built-in allowance, which still applies.
- By default, a policy lets requests through if its limits briefly can't be checked. A department budget does the same if its check is unavailable, so a department can briefly spend past its budget. Use a strict policy when a rate limit must never be exceeded.
- Batch jobs, realtime sessions and OAuth requests aren't blocked by department budgets yet. Their spend still counts toward the department.
- Budget notifications are based on usage that can lag by up to an hour, so a request can be refused before the 100% notification arrives.
- Policy changes apply within about a minute. Department membership changes, including those from SCIM, can take up to about five minutes.
